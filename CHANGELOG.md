# Changelog

## Unreleased

Changes since [v0.1.7157](https://github.com/aufkrawall/capture-engine/releases/tag/v0.1.7157).

### Improved

- **Application profiles with many injection targets:** the complete selector policy is published atomically, so long path lists cannot drop a target or a more-specific injection restriction.

- **Application-audio profiles with many path selectors:** the audio worker now receives its complete selection policy through shared memory, so long profile lists are not limited by the Windows process command line, and parent/child launcher trees matched by a more-specific path profile are excluded as a whole from generic fallback profiles.

- **Application profiles can distinguish installations of the same executable:** `process` now accepts a Windows image-path suffix as well as an executable name. For example, `process=Modded\game.exe` matches that folder at any drive/root, while `process=D:\Games\Modded\game.exe` matches that full installation; a matching path-specific profile takes precedence over the generic `process=game.exe` fallback. Paths use either slash direction, complete folder boundaries and case-insensitive comparison. Selector matching is UTF-8/UTF-16 end to end, so Cyrillic, CJK and other Unicode executable names and folders work regardless of the Windows active code page, with a kernel per-PID path fallback when direct process-handle access is denied. The same identity is used for injection, WGC/DXGI selection, per-profile overrides, desktop overlay settings, window heartbeat and application audio.

- **Stable release verification:** oversized hook and build-tool files were split, and graphics, audio and test warnings that blocked the release checks were corrected. The accepted-warning baseline is now tighter.

- **A recorded microphone that keeps losing data is now named in the log:** a webcam's built-in USB microphone set as the Windows default input reported a data discontinuity every 40 ms for whole recordings, and the game's frames stalled 2-5 ms on that same clock while it was recorded (Heroes of the Storm micro-stutter during inject recordings). The log only showed the first eight discontinuities and never said which device "default" was. Recording audio sources now log the device they resolved to (`[AudioCapture] Endpoint resolved: 'Mikrofon (USB Microphone)' (capture)`), the face camera logs which camera it opened, and a source that keeps losing data gets a warning naming the device and its glitch interval (`[AudioCapture] WARNING: input device '...' keeps losing capture data: 125 WASAPI data discontinuities in 5.0s, typically one every 40.0 ms ...`), a reminder every 30 seconds while it lasts, a line when it stops and a per-recording total.
- **The hook log lists the graphics environment variables the game received:** variables such as `VKD3D_SWAPCHAIN_PRESENT_MODE`, `VKD3D_DISABLE_EXTENSIONS`, `DXVK_*` or `VK_LOADER_*` only take effect when they reach the game process itself, which a launcher started before they were set never passes on. The hook log now names every `VKD3D_*`, `DXVK_*`, `PROTON_*`, `VK_*`, `__GL_*`, `DXGI_*` and `D3D12_*` variable the game process sees (`Environment: 2 graphics variable(s) reached this process: ...`), or says that none did.
- **NGX parameter diagnostics:** their format arguments are now checked by the compiler, catching mismatched placeholders before they can produce incorrect logs in an injected hook.

- **DLSS frame generation flip-metering bridge for vkd3d-proton (experimental / in progress, proper driver metering does not work properly yet):** with vkd3d-proton and dxvk-nvapi in `custom_dll_paths` (GTA V Enhanced), DLSS frame generation's generated and real frames reached the screen whenever the GPU finished them, so a 2x batch alternated between short and long frames even though the game presented them evenly. On native D3D12 the NVIDIA driver spaces each batch itself through flip metering, which the translation layers do not provide. CaptureEngine now carries the bridge plumbing: it answers the frame generator's flip-metering request (`NvAPI_D3D12_SetFlipConfig`) when the loaded NVAPI has none, and passes each batch size to NVIDIA's Vulkan present metering on the batch's first present, matched through the frame id both sides already carry. Proper driver-level flip metering in vkd3d-proton does not work properly yet: while the bridge passes the driver's response back so frame generation falls back to CPU pacing (`feedback=0x1` / `numFramesPerBatch=0`) rather than leaving batches unpaced, the driver does not yet meter the translated swapchain flatly like native D3D12. The plumbing, engine-name aliasing (`vkd3d` -> `vkd3d-proton`), and diagnostics are in place to continue investigating why the driver declines metering on translated swapchains. The logs show the status: `NVAPI flip metering: SetFlipConfig numFramesPerBatch=2 presented=2 ... feedback=0x0` in the hook log and `the driver meters the batch` in `vulkan_layer.log` when accepted; `feedback=0x1` and `the driver did NOT meter the batch` mean the driver declined and frame generation falls back to pacing itself.

- **Slow D3D12 Present calls during a recording say what they waited on:** the hook log now has `[PRESENT STALL]` lines. Every 10 seconds in which a frame was recorded or a Present call took 2 ms or more, a summary compares the Present time of recorded and other frames. For each slow call it says whether the GPU still owed earlier recording copies when the call began, and whether copies finished while it blocked. The first slow calls are also logged one by one (`[PRESENT STALL] slow down-call #1 3.48ms captured=1 copies(... inFlightAtEntry=2 retiredDuringCall=1) capture=live`). The GPU also timestamps each frame's recording copy inside the copy's own command list, so the summary says how often and by how much the GPU was still behind the frame when the game called Present, and each logged slow call gets a follow-up saying whether the call returned when the GPU finished the frame or blocked on something else (`[PRESENT STALL] slow down-call #1 copy on GPU: start=+2900us end=+3100us returned=+3200us (from call entry) -> returned-at-copy-end`). The timing adds no work outside that command list. When the display timing stream runs (the overlay's default frame time source, and every inject recording), each frame is also followed through the graphics kernel: when its Present reached the kernel, when the GPU finished it, when the flip was programmed and when it reached the screen. A second summary line compares these steps for recorded and other frames, and counts which step each slow call returned right after, including the previous frame reaching the screen. Each logged slow call gets a third line once its frame is on screen (`[PRESENT STALL] slow down-call #1 captured=1 flip: start=+40us submit=+100us ready=+150us programmed=+2900us screen=+3150us returned=+3200us previousScreen=-3990us (from call entry) -> returned after its flip on screen`). The `[DisplayTiming]` health line counts the milestones it received (`milestones(ready= programmed=)`). While an inject recording runs in a 64-bit game, a Present call that is still blocked 1.5 ms after it started also gets the presenting thread's call stack logged as module offsets (`[PRESENT STALL] stack #1 down-call blocked 1.62ms ...: ntdll.dll+0x... dxgi.dll+0x...`), for the first eight such calls and then at most once every 10 seconds. The game's thread is paused only for the time it takes to copy its registers and stack. When a 10-second window holds at least 12 slow calls, a period line also says whether they follow a clock from outside the game, such as a device or driver that disturbs the system at a fixed rate, and at which period, or whether they follow the game's own every-Nth-frame cadence (`[PRESENT STALL] period window=10046ms calls=1413 slow=127 lock=OUTSIDE CLOCK 40.00ms (25.00 Hz) R=0.53 ...`).

- **Application-audio logs stay compact during normal backlog correction:** routine active/slack changes now produce at most one summary every five seconds per source, with exact observed transition counts, state durations, backlog ranges and peak compensation. First activation and exceptional states still report immediately; epoch resets and recording stop flush pending summaries so short activity is retained. Audio correction and capture timing are unchanged.

- **Log bursts wake the logger immediately:** committed hook and Vulkan log records now signal the logging service instead of waiting for its next 100-250 ms poll. This removes idle polling delays that could fill the shared ring and force file writes onto the application threads; shutdown still takes priority over pending logs.

- **Application-audio teardown diagnostics expose failed workers:** the optional probe now tests capture reuse, cancellation and the worker entry without an unrelated COM apartment keeping them alive, requires actual audio in stable-source runs, and fails on child crashes or timeouts.

- **Scaled recordings leave more CPU time for capture and encoding:** unchanged frame sizes and scaling settings now reuse the Lanczos weight tables instead of rebuilding them for every video frame. Image quality and scaling settings are unchanged.

- **The face camera reads NV12 and YUY2 frames directly and converts them in its overlay draw instead of through Media Foundation's VideoProcessor:** webcams that output NV12 or YUY2 natively—and MJPEG or H.264 cameras whose decoder outputs NV12 or YUY2—no longer run Media Foundation's D3D11 Video Processor MFT on the recording device to convert every camera frame to RGB32 first. CaptureEngine now requests NV12 or YUY2 output with advanced video processing off, keeps the smaller YUV frames in its camera history (1.5 B/px for NV12 and 2 B/px for YUY2 instead of 4 B/px for RGB32), and converts to RGB inside the single composite draw using the camera's colour matrix (`BT.709`, `BT.601` or `BT.2020`, defaulting by resolution when omitted) and range (`limited` or `full`). Cameras whose native mode is already `RGB32`/`ARGB32` continue to pass through unchanged (`[FaceCamera] Native YUV path: subtype=... matrix=... range=... gpu=0|1` in the media log).

- **Scaled, FP16 SDR and non-sampleable recordings convert on CaptureEngine's own shaders instead of the D3D11 VideoProcessor:** scaled recordings (`[VideoScaling] enabled=true`), linear FP16 SDR games (`scRGB` swapchains) and non-sampleable or multisampled capture surfaces no longer fall back to the driver's `ID3D11VideoProcessorBlt`, whose GPU work on NVIDIA queued behind NVENC and could starve high-frame-rate recordings. CaptureEngine now scales both SDR and HDR frames with a separable anti-ringing Lanczos shader (`quality=normal` uses 2 lobes, `quality=best` uses 3; `sharpness=0..100` scales the sharpening side lobes while clamping each pass to the main lobe's sample range so edges sharpen without halos, and downscaling widens the filter over the ratio so fine detail cannot alias), normalizes linear FP16 SDR inputs to sRGB in the shader, and copies or resolves non-sampleable inputs before conversion. Because `[VideoScaling] sharpness` and `quality` now drive this uniform shader scaler rather than each GPU driver's proprietary VideoProcessor edge enhancement, scaled SDR recordings have consistent sharpness and left chroma siting across NVIDIA, AMD and Intel (`[Scaler] Plan: ...` and `[SDR YUV] Direct shader conversion active: ... scaler=lanczos2|lanczos3` in the media log).

- **Profile settings written without their section name are reported when they change several settings:** in a `[Profile.*]` section, a setting written without its section (`fps=60` instead of `Video.fps=60`) changes every section that has a setting of that name: `fps` also sets the face camera's frame rate, and `enabled=true` switches on streaming, the face camera, the microphone and every numbered audio source. Older config files keep working exactly as before, but CaptureEngine now logs which sections such a key changed (`Config: [Profile.My Game] 1 bare key(s) change several sections: fps -> [FaceCamera], [Video]`), so the profile can name the one that was meant. A setting that exists in only one section (`dlss_fg_factor=3x`) still works without its section, and the profile notes in the default config.ini now say so.

- **The default config.ini is shorter and says what settings do:** a new installation's config.ini drops about 120 lines. Comments that explained how CaptureEngine implements a setting (frame generation V-Sync handling, sharpening, Streamline substitution and upgrade, NGX updates, the third-party tool loader) now say what the setting does, what it needs and what it risks; the five near-duplicate anti-cheat example profiles became one safe/unsafe summary and one example; and developer-only overlay test switches are no longer listed (they still work when present). Existing config.ini files are not changed.

- **Vulkan `vsync_mode=fifo` reaches NVIDIA's DXGI presentation without waiting for another DXGI caller:** with frame generation's present metering, NVIDIA presents Vulkan through an internal DXGI swapchain, which only gets its vertical blank once CaptureEngine has seen a Windows DXGI factory. That used to wait for some other component's factory call to pass through CaptureEngine. Once the policy arms, CaptureEngine now creates a factory itself, so the forced vertical blank no longer depends on what else the game loads (`Vulkan DXGI FIFO: system factory method-body capture #1 from CE's own system factory active`).

### Fixed

- **Performance CSV logging after shutdown and reopen:** every new log file now starts its frame sequence and timing summary afresh, including when a resident hook resumes logging after the previous file was already closed.

- **Regression-test reliability:** performance-log rebind and NGX module-copy tests now own separate temporary directories for every fixture lifetime, avoiding access-denied and cleanup failures when Windows is still retiring a previous test's files.

- **Application audio when a child process starts playing:** active process-tree captures now recheck profile exclusions on audio-session changes and before activation. A child owned by a more-specific profile triggers clean process selection again, preventing duplicate or excluded audio from continuing through its parent's capture; unrelated process trees leave healthy captures running.

- **Background-window recovery after profile changes:** newly added executable-path rules now apply to games already being watched. Disabling recovery, removing a profile, or shutting down CaptureEngine queues restoration of any pending move or resize without overwriting geometry changed by the user or game.

- **Vulkan profiles with injection disabled:** an explicitly excluded child process can no longer inherit Vulkan layer eligibility from its parent. The current host's denial also takes precedence over an older persisted admission.

- **Lint and line-length ratchets:** tightened clang-tidy baseline and wrapped long declarations in media headers to satisfy the line-length limit.

- **Verification reliability:** isolated temporary log-sink test directories and updated audio route checks for complete selector policies.

- **Application-audio worker integration:** fixed the shared policy transport boundary so capture and media components can build together.

- **Present-stall diagnostics:** if the stack sampler cannot start, its temporary buffer and timer are now released instead of remaining allocated for the rest of the game.

- **Estimated PC latency in games that check swapchain status:** `DXGI_PRESENT_TEST` calls no longer enter the display-timing queue as rendered frames. Those status probes never submit an image; counting one before every real Present could make a displayed frame match a call several frames old and inflate the estimate by about 50 ms at 140 fps. The timing log now counts ignored probes explicitly.

- **Returning to a game after Alt+Tab no longer triggers a false freeze dump:** the watchdog excludes an ordinary background pause from its freeze deadline and starts monitoring the resumed presentation interval. Genuine stuck Present calls, removed devices and frame-generation presenters remain monitored in the background. Diagnostics distinguish the real heartbeat age from time spent expecting presentation to progress.

- **DLSS Neural Rendering no longer appears as frame generation:** NGX feature 18, used alongside DLSS Super Resolution in Metro 2033 Redux, no longer activates a fictitious DLSS FG 2x status or halves the base frame rate used to estimate PC latency. Actual DLSS frame generation still reads its 2x/3x/4x factor from the FG feature's parameters.

- **Heroes of the Storm on DXUP no longer loses its DirectX 12 device at startup:** DXUP briefly creates a test swapchain for a hidden window, releases it, and the game's real swapchain can come back at the same memory address on another command queue. CaptureEngine still held the test swapchain's queue for that address, drew its overlay and sharpening from that queue on the first frame, and the GPU device was removed (`deviceRemoved=0x887A002B`). The game then recovered on plain DirectX 11 for the rest of the session. A new swapchain now replaces any queue CaptureEngine held for its address, and a held queue is dropped when the swapchain shows another window than the one it was held for (`... — discard-stale-identity its parked create (... presentedWindow=different ...)` in the hook log). This applies to every DirectX 12 game, not just Heroes of the Storm.

- **A game that recovers from a lost GPU device is no longer reported frozen, and CaptureEngine resumes its work there:** after a device loss CaptureEngine stops its per-frame work and its freeze detection's heartbeat, so a game stuck on the dead device gets a freeze dump. Only a new DirectX 12 device lifted that state. Heroes of the Storm went on presenting a new DirectX 11 swapchain at 60 fps, yet 30 seconds later the freeze detection wrote `Render thread frozen for 30 seconds`, a 65 MB dump that froze the game for about 3 seconds. A DirectX 11 game recovering through the same Present path would also have kept its overlay off for good. The first Present that succeeds after a device loss now proves its device alive and lifts that state, whichever API presents (`DXGI: ... succeeded (hr=0x00000000) after a device loss - its device is alive ...` in the hook log); a game still presenting on the dead device keeps it.

- **Crash and freeze dumps no longer stall games that redirect their DLL search, such as Heroes of the Storm:** CaptureEngine writes these dumps from a separate `captureengine.exe` helper, so the game keeps running while it is recorded. Windows passes a game's DLL search folder on to the programs it starts. Heroes of the Storm points it at its `Support64` folder, so the helper loaded DXUP's `d3d11.dll` from there instead of Windows' own, failed to start (`External pre-termination dump helper failed (... exit=3221225785)`, Windows' "entry point not found" for `CreateDirect3D11DeviceFromDXGIDevice`), and the dump fell back to being written inside the game, which froze it for about 3 seconds. `captureengine.exe` now loads the DLLs it links against only from its own folder and the Windows system folder.

- **Recording again in the same game works after an inject recording was stopped:** stopping a recording could leave the game's shared frame ring in a state every later recording start rejected as corrupt, so the second and every further recording in that game failed at once until the game was restarted (Heroes of the Storm; the media log said `Inject recording rejected corrupt shared frame ring (write=14343 ingest=14342 read=14343 ...)`). The stopping recording switches to a private copy of the session state so its finalization cannot disturb a newer recording, but its frame intake kept running across that switch: it read the copy's empty ring, spent four seconds of the stop in a catch-up over four billion positions (`Lag detected! Dropping 4294952952 frames`), and its last cursor update never reached the game. A stopping recording now ends its frame intake and hands the ring back fully read before it switches (`[RecordingLifecycle] Detached from the shared live state (...) ring(ingest=N read=N write=N)` with ingest equal to write).

- **A recording process that ends abruptly can no longer leave the game unrecordable:** the recording process could release a captured frame back to the game an instant before it marked the frame as taken, so a recording process that crashed or was killed in that instant left the game's frame ring in the state later recordings reject as corrupt until the game restarted. Frames are now marked as taken first. An inconsistent ring position is also logged as an error (`[Inject Thread] Frame ring cursor fault #N ...`) and resolved within the ring's 32 slots, instead of a catch-up that could hold up a recording stop for seconds.

- **Streamline frame generation in Vulkan-presented games no longer retries a DX12 overlay route at every frame:** in a D3D12 game translated to Vulkan (GTA V Enhanced on vkd3d-proton), turning DLSS frame generation on armed CaptureEngine's DX12 overlay route, which draws into Streamline's DX12 swapchain. Vulkan presented the game, so that swapchain never appeared: the route's startup stayed pending, was retried at every presented frame for as long as it lasted (28 seconds and 2,448 retries in one session, each logging two lines), and the game's own requests to turn frame generation off were held back meanwhile. Where the Vulkan layer presents, which also draws the overlay there, the DX12 route now stays off (`DX12: Streamline FG ON while the Vulkan layer owns presentation`). The repeated startup message is also rate-limited for any game.

- **Face-camera shutdown diagnostics:** samples cancelled because recording is stopping are counted separately from extraction failures. Genuine buffer failures remain visible even when shutdown starts during extraction.

- **Recording timing analysis reports measured discrepancies accurately:** a raw timing residual crossing its threshold no longer establishes a clock-domain mismatch or a visual-timeline fault by itself. Reports retain the warning and show raw/selection measurements and thresholds; independently unsafe timing still produces a fault verdict.

- **Application-audio crashes at recording stop and worker restart:** capture now keeps COM's multithreaded apartment alive until the audio client and any pending activations have been released. This prevents Windows from unloading the audio engine while its loopback mixer still needs it, avoiding worker crashes and the resulting shutdown or restart delays.

- **Bottom-up webcam frames no longer read beyond their image:** RGB32 cameras that provide a negative row stride through Media Foundation now keep the top-row pointer Windows supplies, avoiding corrupted face-camera images and recording-process crashes.

- **Custom graphics runtimes work when their DLLs are already loaded:** configured `custom_dll_paths` images now participate in replacement adoption even when the game or an earlier dependency loaded them first, so application imports and module queries use the configured runtime.

- **DXGI factory creation stays consistent during runtime replacement:** concurrent lookups keep each runtime paired with its own factory function, and proxy DLLs with forwarded factory exports resolve to executable code instead of a forwarding string. This avoids mixed native/replacement factories and crashes with forwarding proxies.

- **`cengine.dll` always reports a media helper that crashes while a recording starts:** the engine checks its helpers on every pass and announces a lost one with a `CE_EVENT_HELPER` event. A recording, however, judged the media helper by a second, later check. When the helper died between the two, the recording failed and the dead helper was set aside, so the next check no longer counted it as needed and the loss was never announced: a program saw the failed recording but no lost helper. The recording now acts on the same check the engine announces, so the lost helper is always reported, before the failed recording (`[Runtime] helper media lost` in the log).

- **GTA V Enhanced no longer crashes at startup with DXVK and vkd3d-proton:** with DXVK's `dxgi.dll` in `custom_dll_paths`, the game crashed inside Windows' own D3D11 once Vulkan presentation began. Both crashes had the same cause: a DXVK adapter reached Windows' D3D11, which can only work with Windows' own adapters. First, CaptureEngine's Vulkan capture layer received DXVK's DXGI factory for its capture interop; it now keeps the Windows exports it asks for and refuses any adapter Windows' DXGI did not create. Second, the Epic Online Services overlay that GTA V Enhanced loads passed DXVK's adapter to Windows' D3D11 when it set up its Vulkan overlay. While `dxgi.dll` is replaced and D3D10/D3D11 are not, Windows' D3D10/D3D11 device creation now receives Windows' adapter for the same GPU, whoever calls it. The hook log names each exchange (`ModuleReplacement: d3d11.dll!D3D11CreateDevice from <module> received an adapter of the replaced dxgi.dll`). Covered by flow regressions with a translation-layer adapter and adapter-ownership unit tests.

- **Crash dumps show the real fault when a game's thread dies of it:** when an unhandled crash ends a thread through Windows' thread-start handler, which unwinds the stack before it terminates the process, CaptureEngine's pre-termination dump recorded only its own exit hook. It now carries the faulting instruction, registers and call stack that CaptureEngine recorded when the fault happened, as long as the exit code names that fault.

- **Custom graphics DLLs receive calls through addresses saved before injection:** graphics entry points cached from Windows' DXGI or D3D10/11/12 runtime now reach the DLL listed in `custom_dll_paths`, including calls that bypass import-table and `GetProcAddress` hooks. Proxies can still forward to Windows' runtime, including through compiler tail calls, and CaptureEngine's own native calls stay native. This closes a path that could leave a game on native D3D12 after loading a translation runtime.

- **DX12 overlay stays active when a DLL only enumerates Vulkan adapters:** connecting the Vulkan layer no longer makes CaptureEngine hand presentation to an adapter probe. Ownership protects actual Vulkan swapchain creation, stays continuous across successful swapchain replacements, and ends when the last swapchain is destroyed; failed creation releases its temporary claim. Live Vulkan swapchains regain ownership when CaptureEngine reconnects.

- **Custom DLLs named like a Windows graphics DLL take effect in games that load Windows' copy first:** with `[ThirdParty] custom_dll_paths` listing DXVK's `dxgi.dll` and vkd3d-proton's `d3d12.dll` and `d3d12core.dll`, GTA V Enhanced still ran on Windows' own D3D12. The game loads Windows' `dxgi.dll` and `d3d12.dll` before CaptureEngine, and loading a second DLL of the same name changed nothing, because Windows answers every request for that name with the first one. A listed DLL named like one already loaded now replaces it for the game, as if it had been copied next to the game's executable: the game's imports, its `LoadLibrary`, `GetModuleHandle` and `GetProcAddress` lookups (Streamline's too, which loads Windows' copy by its full path) and CaptureEngine's own DXGI and D3D12 wrappers reach the listed DLL, while Windows' own components and CaptureEngine's capture keep Windows' copy. The hook log names each replacement (`ModuleReplacement: d3d12.dll now resolves to ... instead of ...`).

- **Starting CaptureEngine after Heroes of the Storm is already running hooks it fully again:** to hook a running game safely, CaptureEngine briefly pauses the game's other threads. Heroes of the Storm keeps one of its own threads paused all the time, at the 127-pause limit Windows allows, so Windows refused CaptureEngine's pause and CaptureEngine gave up every hook for the rest of the game. Whether the overlay still appeared depended on which graphics route CaptureEngine found first; with RTSS running it often did not, and some crash-dump hooks, swapchain-resize handling and the DX12 overlay route were missing either way. A thread its owner keeps paused cannot run, so CaptureEngine now checks where it stopped, leaves it paused and finishes hooking (`ThreadQuiescence: 1 peer(s) already held suspended by another owner`). Threads that are just exiting are left out the same way. If a running thread ever refuses, the hook log names it (`ThreadQuiescence: live peer tid=... refused suspension`).

- **DXUP games started before CaptureEngine get the same DX12 route as games started after it:** with DXUP (D3D11 games running on D3D12), CaptureEngine draws the overlay, sharpens, captures and limits frames once, on DXUP's D3D12 output, but it only knew that DXUP's D3D11 swapchain presents through that output if it had seen the output being created. Starting CaptureEngine after the game, it now learns this from the output's first frame instead (`DXGI translation: native output ... published its output marker from its first processed Present`), so frames are not processed a second time on DXUP's D3D11 side. The hook log also names what first proved the game uses D3D12 (`D3D12 use: first evidence from ...`), which decides whether CaptureEngine installs its DX11 hooks.

- **Loading Special K, ReShade or OptiScaler through CaptureEngine pauses the earlier tools' threads again:** to avoid startup deadlocks between these tools, CaptureEngine pauses the threads of the tools it already loaded while it loads the next one. Since August that protection paused nothing: CaptureEngine opened the threads without the access right needed to see which module started them, so no thread was ever recognized as a tool's. A retry after a tool thread was caught inside the Windows loader also paused nothing, and giving up could undo a pause another program held. All three are fixed; the load line now says how many tool threads were paused (`ThirdParty preload: ... toolThreadsSuspended=N`).

- **Restarting CaptureEngine while a game runs keeps the game's logs in the new session:** a game keeps CaptureEngine's hook loaded when CaptureEngine closes, and the next CaptureEngine reconnects to it. Until now most of the hook's log lines (everything about presents and the overlay) and the Vulkan layer's `vulkan_layer.log` kept going into the folder of the first session, so the new session's `hook_debug.log` was nearly empty (2708 of 2725 lines missing in one Heroes of the Storm report). They now move to the new session's folder, starting with `[InjectLifecycle] Direct log files follow the replacement host's session now`.

- **Overlay hardware readings and freeze detection return after restarting CaptureEngine while a game runs:** the hook's hardware-metrics thread and its freeze watchdog stopped when CaptureEngine closed and never started again for that game, so the new session never learned the game's graphics adapter (`adapterLuid=0x0` in sensors.log) and game freezes were no longer detected. Both now restart when CaptureEngine reconnects (the logs show `SystemMetricsCollector: resumed ...` and `FreezeWatchdog: Resumed after host reconnect`). This also fixes a crash that could happen when the game recreated its graphics device after such a restart.

### Changed

- **`WindowHeartbeat.enabled` tries to recover background games whose picture froze, instead of pinging them (experimental, untested on a real occurrence):** a game running in the background (borderless, often limited to 30 fps there) can stop updating until its window is resized, possibly caused by multi-plane overlays, and a crash reporter may then take the stalled game for a hang and close it. The cause is not confirmed and the freeze could not be reproduced on demand. The old setting sent a `WM_NULL` message every 250 ms, which only wakes a message loop; that most likely could not help, since a window that a resize unsticks is still processing its messages. The new behavior rests on the assumption that the freeze leaves the game's Present call blocked until the window's geometry changes. While a profiled game has a visible background window, CaptureEngine watches its Present calls in the elevation service's display trace. When one has not returned for longer than the GPU timeout (`TdrDelay`, 2 s by default), it moves the window by 1 pixel and back, and if the Present call still does not return, makes the window 1 pixel narrower and back, as a manual resize would. If the freeze turns out to have another cause, nothing is detected and nothing happens. One attempt per stall, never on the foreground window, and nothing inside the game: no injection, no access to its memory, focus or input. The log names the stall and each step's outcome (`[WindowHeartbeat] Present stall pid=... openMs=... mpo=1 ...`, `move nudge queued`, `Present resumed pid=... after the move nudge`, or `Present still blocked ... after move and resize nudges`), so the next occurrence shows whether the assumption holds. It needs the elevation service; without it the log says that stall recovery is inactive. Vulkan and Direct3D 9 games are not covered. Captioned (windowed) game windows qualify too now, not only borderless ones.

- **AMD (AMF) recordings use the fastest encoder preset by default:** new config files use `[AMF] preset=speed` instead of `balanced`, like NVENC's `p1` and Quick Sync's `veryfast`. The fastest preset leaves the most encoder headroom for high-frame-rate recordings, and at recording bitrates the quality difference is small. `[AMF] async_depth` now defaults to `auto`: 16 frames in flight as before up to 160 fps and more above that (24 at 240 fps, at most 42), so the encoder does not stall behind CaptureEngine's queued frames at high frame rates. Existing config.ini files keep the `preset` and `async_depth` values written in them; change them to `speed` and `auto` to switch. The media log shows the depth used (`[VideoEncoder]   async_depth=`).

## v0.1.7157

Changes since [v0.1.7156](https://github.com/aufkrawall/capture-engine/releases/tag/v0.1.7156).

### Improved

- **NVIDIA LOD-spread fix documentation:** clarified that `nv_lod_spread_fix` forces the High Quality (HQ) texture filtering setting in Vulkan and OpenGL because the driver erroneously keeps the lower-quality Quality (Q) setting for `FERMI_UNOPT_LOD_SPREAD` even when HQ is selected (unlike D3D10–12). Documented the real visual effects: excessive temporal shimmering with negative mip bias and excessive blur with positive mip bias.

- **AAC audio encoding:** updated FFmpeg to a pinned revision of the 9.1 release branch with newer NMR quality and bitrate-control refinements. Recordings continue to use NMR's best-quality mode.

- **10-bit desktop and WGC recordings use a third less video memory for the smoothness buffer:** the buffered frames (300 ms of delay, 64 frames at 4K120) used to keep each 10-bit value in 16 bits. They are now stored packed at 16 bits per pixel instead of 24, and the encoder rebuilds exactly the same 10-bit picture from them: at 4K the buffer shrinks from about 1519 to 1013 MB, for DXGI duplication and WGC, SDR and HDR alike. The delay, the frame count, frame selection and audio sync are unchanged, and the extra GPU work per frame is about what the old copy cost. The media log names the route (`[WGC] Retained reservoir route: ... -> P010_PACKED16 (yuv (packed P010))`) and counts the rebuilt frames (`packedUnpacks=`). `wgc_retained_packed_p010=false` in `[WGC]` keeps the unpacked frames, for comparison.

- **The first recording after starting CaptureEngine no longer spends about a second compiling shaders:** the color conversion, buffered-frame, cursor, face camera and overlay shaders of the recording path are now compiled when CaptureEngine is built, not at the first recording start of every session; that was about 0.65 s for the cursor and camera overlay alone, on a CPU core next to the game. All capture methods, codecs, bit depths and SDR/HDR use them. The media log shows `Shader bytecode: precompiled=N runtimeCompiled=0`.

- **Faster build gate (development):** the unit tests and the Python tool self-tests now run while the frame-generation flow scenarios run, instead of before them; they used one processor core while the scenarios keep all the others busy, and added about 95 seconds to every gate. An unfiltered gate skips the flow scenarios entirely when nothing they are built from or run with changed since their last passing run (their sources and headers, the version resources and export lists of the stand-in runtimes, the libraries and linker they are linked with, the build scripts, the compiler, their config and Windows' WARP and Direct3D 12 modules), which is the case for changes to the app, the media engine, settings and the other parts the scenarios never load; `--rerun-flow-tests` and `--verify` (also `--verify-runtime` and a resumed verification) always run them. Any failed flow run, forced or filtered ones included, makes the next gate run them again, and a flow-test program that cannot list its scenarios fails the gate instead of passing with nothing run. The slowest scenarios now start first, and the log lists them with their times.


### Fixed

- **PC latency no longer drops out when frame generation changes its factor:** the overlay's PC latency row started its measurement over whenever the frame-generation factor changed, and showed `PC Latency --` for about a second until it had new samples. DLSS dynamic multi frame generation switches between 2x, 3x and 4x by itself during normal gameplay, so the reading kept dropping out there. The measurement now carries across factor changes while the same frame generation keeps running; switching frame generation on or off, or to another kind, still starts it over. The overlay log's `[Overlay] PC latency chain` line counts these changes (`factorChanges=`).

- **The frametime graph stays stable while a game is minimized or composed by the desktop:** occasional game-owned flips could alternate the graph between presentation and display-change timing, repeatedly changing its history even though the game stayed in the same presentation mode (seen in The Talos Principle Reawakened's minimized menu). The sensor now keeps every sample in its established composed mode until it confirms that the game's own flips have resumed without compositor frames. Latency keeps all timestamps, and the sensor's bounded health log counts these mixed completions as `ownWhileComposed=`.

- **WGC and desktop recordings keep their video timing aligned when the game's frame rate changes:** smoothing capture timestamps could leave a permanent offset of several milliseconds after the source slowed down or sped up. The smoother now fits recent source timestamps to keep its phase aligned while preserving smooth frame selection, real stalls, and the existing synchronization limits. The media log identifies the new timing model once per recording as `model=source_phase_fit`.

- **WGC and desktop recordings avoid a frozen picture at the start when the game runs at or below the recording frame rate:** the startup buffer now waits for the number of frames the source can deliver, rather than always expecting the recording frame rate. This avoids an unnecessary full-second wait and the roughly 0.3-second frozen opening seen with an 84 fps game recorded at 120 fps. At matching frame rates, startup selects a frame that leaves the full required reserve. Old buffered frames make room before the capture pool starts rejecting new ones. Startup frames lost to pool pressure are reported in the media log and count against the smoothness verdict.

- **The media log reports the buffered-frame converter once per recording:** `[RetainedYuv] Ingress converter released` could appear up to three times with the same counts when a recording stopped; the counts now cover one recording.

- **WGC and desktop recordings avoid a freeze when the cursor or camera first appears:** cursor and retained NV12/P010 overlay shaders are prepared before video frames are encoded, including when an overlay starts out hidden. The first cursor frame previously paused encoding for roughly three quarters of a second.

- **Recording summaries report real repeat counts:** source-limited and timer repeats remain accurate when shared recording status resets at shutdown; summaries could previously claim over four billion repeats and give a misleading smoothness verdict.

- **DXGI duplication recordings no longer fall back to the larger RGB frame buffer at random:** the first desktop frame proves the capture format, and CaptureEngine set up its frame buffer for that format from two threads at once. Now and then the buffer came out in one format while its NV12/P010 views were made for another; the capture then kept its frames in full RGB for the whole recording (about 1.3 GB more video memory at 4K in 8-bit for the same delay, 2025 instead of 759 MB) and logged `Retained-YUV plane RTV creation failed ... 0x80070057`. The capture thread now waits with the first frame until the format is adopted, then delivers it; the log shows `Duplication delivered format adopted ... frame delivery opened`.

- **Desktop recordings show the mouse cursor and the face camera again:** since v0.1.7155, WGC and DXGI duplication recordings keep their buffered frames in the encoder's own NV12/P010 format and draw the cursor and the face camera into each frame from a small separate layer. Neither could be drawn into that layer, so those recordings had no hardware cursor and no face camera at all; only a software cursor Windows paints into the desktop image itself (while dragging a window, for example) showed up. Both are drawn again, on every frame including repeated ones. Should an overlay fail to draw on a frame, the media log now says so (`[RetainedYuv] Cursor layer draw failed`, `[CursorRenderer] No render target view`) and the encoder summary counts it (`layerFailures=`).

- **A desktop screenshot on an HDR desktop no longer freezes CaptureEngine:** on an HDR desktop, a screenshot without a game captures the desktop through Windows Graphics Capture. Before the first one, CaptureEngine asked Windows whether it may hide the yellow capture border and waited for the answer on the thread that also runs the hotkeys. When Windows did not answer at once, as on the affected system, it handed the answer back to that same thread, which was blocked waiting for it: the screenshot never finished, no hotkey worked afterwards and Exit in the tray menu no longer closed CaptureEngine. SDR desktop screenshots and recordings never waited there. The question is now asked once in the background and nothing waits for it. The log names the answer (`[WGC] Borderless access answered: ...`) and when CaptureEngine is asked to close (`[Runtime] Shutdown requested`).

- **A deleted config.ini comes back when CaptureEngine starts, with the elevation service on:** CaptureEngine runs without administrator rights and cannot create files in its Program Files folder, so a deleted `config.ini` stayed missing until setup ran again. When the elevation service is on (the default after setup), CaptureEngine now asks it to recreate the file from the default settings at startup; it never replaces an existing file, writes only into its own installation folder and gives the file the usual rights so you can edit it without administrator rights. The log names the outcome (`[Settings] config.ini was missing; the elevation service restored it`, or the service's answer in the `could not be created` warning). Needs the elevation service from this version; an older one is left alone.

- **Hotkeys, recording and screenshots work without a config.ini:** when `config.ini` was missing from an installation under Program Files, CaptureEngine (running without administrator rights) cannot create a new one there, and it then ran on bare internal defaults instead of the default settings: no hotkey at all, so Ctrl+9 and Ctrl+0 did nothing, and no output folder or frame rate. The recording and capture processes read different fallbacks again (F9 to record, no screenshot key, recordings beside the program). Every part of CaptureEngine now runs on the settings a fresh `config.ini` would hold, taken from the copy built into the program, until the file exists again; running setup again restores the file itself. The log says so once (`[Settings] config.ini is missing and could not be created ... the built-in first-run template applies`, and `[Config] ...` in the other processes).


### Security

- **Creating config.ini never follows a link:** a symbolic link planted at the name `config.ini` in a folder ordinary users can write (a custom or portable installation) could make CaptureEngine running as administrator create the link's target and open it to all users. The first-run file and the elevation service's restore now never follow a link at that name, and the service refuses a folder that is itself a link.

## v0.1.7156

Changes since [v0.1.7155](https://github.com/aufkrawall/capture-engine/releases/tag/v0.1.7155).

### New

- **The inject overlay works with Intel XeSS frame generation (XeFG), in games that ship it and through OptiScaler:** XeSS frame generation presents every displayed frame itself, the generated ones from a thread of its own, on a swapchain and a GPU queue of its own, so CaptureEngine used to draw on none or only some of them. CaptureEngine now recognizes the swapchain XeSS frame generation creates, also when it takes over the game's own swapchain, and draws the overlay once on every frame it presents, generated or not, on XeSS frame generation's own queue, without copies and without waiting for the GPU. The overlay shows "XeFG 2x" to "XeFG 4x" while generation is on, from the frames actually presented, and the frame rates show what reaches the screen and what the game renders. Inject-capture recordings contain every frame XeSS frame generation presents, each with its own presentation time, with or without the overlay. Turning generation on and off, changing the factor, resizing the window and leaving XeSS frame generation for the game's own swapchain and back keep the overlay on screen throughout. The hook log names the swapchain and queue XeSS frame generation presents with (`[FG PRESENTER]`, `[RUNTIME OUTPUT]`) and every call that changes its state (`XeFG: ...`).

- **The FPS limiter paces the game's frames under XeSS frame generation, not the generated output:** CaptureEngine's frame cap now holds the game's own frame on its thread, right before it goes to XeSS frame generation, and lets every frame XeSS frame generation presents pass, the way it already handles FSR frame generation: a 120 fps cap with XeFG 2x renders 60 frames and shows 120, spaced by XeSS frame generation itself instead of a second limiter behind it. A frame cap the game sets in Intel's latency reduction (XeLL) runs alongside: whichever cap is lower holds the frames, and the hook log names both and the one that holds (`XeLL: frame caps in series`). XeLL's per-frame markers also give the PC latency estimate the moment each frame started, as NVIDIA's markers do in DLSS games.


### Improved

- **Crash logs say whether a stack overflow runs through CaptureEngine:** when a game dies of a stack overflow, `crash.log` now carries one line that walks the crashed thread's stack: how many frames it holds, the function calls that repeat at the crash, how many of the frames belong to CaptureEngine, and where the thread started (`StackOverflow attribution: ... CE frames=...`). A startup crash of The Talos Principle Reawakened with OptiScaler and ReShade could previously be told apart from a CaptureEngine fault only with a debugger: 75,000 nested calls of OptiScaler's own hook, none of them CaptureEngine's.

- **DirectX 12 hooks coexist with native API input wrappers:** body interception can preserve the two-argument FidelityFX API across a foreign entry detour, including its scratch-register prologue, while keeping live argument registers intact. Unloaded body-hook registrations can be retired without touching an address that another image may already have reused.


### Fixed

- **The Steam overlay works again in DLSS frame generation games when ReShade or OptiScaler is loaded too (The Talos Principle Reawakened):** with two or more overlay-type tools loaded, CaptureEngine handed Streamline's frame generation swapchain back wrapped in an object of its own, even though its hook below the Steam overlay already saw every frame of that swapchain. The Steam overlay hooks the swapchain it is given, found CaptureEngine's code instead of Windows' and could not hook it, so it never drew anything. CaptureEngine now returns the swapchain as created whenever its hook below the other overlays covers it, and keeps its own wrapper only where it is CaptureEngine's sole view of the frames. The hook log names the choice for every Streamline swapchain (`Streamline runtime swapchain ... returned as created (view=real-below-foreign-chain ...)`).

- **The Steam overlay keeps its HDR color-space hook when the game starts many threads at once:** CaptureEngine watches the game's HDR color-space changes from inside Windows' function so that the Steam overlay can hook its start. That hook was tried only once and, when it met a thread being created at that moment, CaptureEngine took the function's start instead, where the Steam overlay cannot follow it. It is now retried like CaptureEngine's other hooks below the Steam overlay (`DXGI: SetColorSpace1 body hook ... installed on attempt N`). The back-buffer reference diagnostics retry their hook the same way.

- **Ending FSR frame generation behind OptiScaler's FFX inputs no longer reads a wrong security cookie:** when CaptureEngine observes AMD's `ffxDestroyContext` below another program's detour, it replays the start of AMD's function from a copy of its own. That start loads a security cookie relative to the code's address, and the copy loaded it from the wrong place, which could crash the game or fail AMD's stack check when frame generation was turned off or the game exited. The copy now addresses the real cookie; the hook log shows the correction (`DeepHook: Fixed prolog RIP-relative`).

- **Switching from DLSS frame generation to FSR frame generation through OptiScaler keeps FSR FG and its overlay:** when OptiScaler first passed the game's DLSS frame generation requests on to a running DLSS FG and the game then switched to OptiScaler's FSR frame generation, the game's continuing DLSS requests in the first seconds still counted as DLSS FG, because Streamline had presented the frames shortly before. CaptureEngine took down its FSR overlay route and never showed FSR FG again. The swapchain FSR frame generation creates now ends that evidence at once (`[FG PRESENTER] ... Streamline proves itself again with its next present`).

- **DLSS frame generation switched on before a game's first frame shows as DLSS FG through OptiScaler's wrapper:** a game that turns DLSS frame generation on at startup, before it renders anything, had its request held because Streamline had not presented a frame yet to prove it real, and CaptureEngine never applied it afterwards: DLSS FG ran while the overlay said FG off. The request is now applied as soon as Streamline presents, and CaptureEngine's DLSS FG state follows whenever Streamline starts or stops presenting (`Streamline Hook: Streamline FG signal is no longer a front`).

- **XeSS frame generation stays observed when the game unloads and reloads Intel's DLLs, and a second copy cannot break it:** Windows maps a reloaded `libxess_fg.dll` or `libxell.dll` at its old address without CaptureEngine's hooks, and CaptureEngine's record of the unloaded copy refused to hook it again, so XeSS frame generation went unseen: no overlay status, no frame pacing at the game's frame. The records of an unloaded copy are now forgotten before the next one is hooked (`XeFG: ... mapped after an unload`). A second copy loaded from another folder while the first is still loaded is left alone (`second image ... left unobserved`): hooking it had pointed the first copy's hooked functions at the second copy's code.

- **FSR frame generation without a game UI layer shows the overlay on every displayed frame, smooth and sharp (OptiScaler's DLSS-to-FSR frame generation, The Talos Principle Reawakened):** when a game hands AMD's frame generation no separate UI layer, as OptiScaler does with `EnableFfxInputs=true`, CaptureEngine drew its overlay into the rendered image before frame generation, so AMD interpolated it like part of the scene: the overlay changed only with each rendered frame (45 times a second on a 90 fps screen), the frame time graph scrolled in visible steps, and generated frames showed it warped by the scene's motion, which can make the whole picture look less smooth. CaptureEngine now hands the overlay to its final-output route as soon as that route has proven itself on AMD's presenter thread, and draws it on every displayed frame after AMD composed it, generated ones included; until then, and if that proof is lost, the rendered image keeps the overlay so it never disappears. The handover waits until AMD presents from its own thread: at frame generation start AMD presents a few frames from the game's thread first, and handing over earlier cost the overlay on the next frame (7 frames without it in the first seconds of a test run). The game's own render thread no longer submits overlay GPU work in that mode either. The hook log shows the handover (`FFX proxy overlay route transition no-ui-resource-backbuffer -> no-ui-resource-topmost`, `final-batch overlay ownership GRANTED (no UI resource: ...)`).

- **OptiScaler DLSS-G input calls keep the active FSR overlay visible:** repeated DLSS-G options and Reflex activation no longer trigger FSR overlay teardown or repeatedly start DLSS UI rendering when another runtime is actually generating the frames.

- **OptiScaler DLSS-to-FSR frame generation works with default FFX inputs:** fixed the missing inject overlay with `EnableFfxInputs=true`, as reported in The Talos Principle Reawakened. CaptureEngine now observes native FidelityFX output calls below existing input detours, including calls through saved originals, while preserving those detours and their ability to detach. The existing FSR composition and GPU queue paths stay in use.

- **FSR frame generation can resize with the final-output overlay active:** the resizing swapchain's completed overlay command lists release their old backbuffers before `ResizeBuffers`, preventing DXGI from rejecting the resize because those buffers remain referenced.

- **Frame generation that another tool ships in its own folder is recognized as frame generation (OptiScaler):** OptiScaler keeps Intel's XeSS frame generation (`libxess_fg.dll`, `libxell.dll`) and AMD's FSR frame generation in its `OptiScaler` folder, and CaptureEngine took everything in that folder for part of an overlay. It then misjudged which component presented a frame: with OptiScaler's XeSS frame generation in The Talos Principle Reawakened, the frames XeSS presented looked like Streamline's or the game's own. A frame-generation runtime is now recognized by its file name wherever it is installed, and a copy of `dxgi.dll` or another Windows graphics DLL outside the Windows folder is treated as code of its own instead of as Windows. The hook log names who presents on every swapchain and thread (`[PRESENT ORIGIN]`, with a 10-second summary), and the overlay coverage check no longer counts a frame CaptureEngine did not draw on as covered merely because frame generation is on: only frames the generating runtime itself presents can carry an overlay CaptureEngine drew earlier (`uncoveredByOriginator=` in `[OVERLAY COVERAGE]`).

- **The overlay no longer vanishes for 30 frames when a game switches from FSR frame generation to another one:** CaptureEngine hides the overlay briefly after a long pause with frame generation on, such as a loading screen. Switching from FSR frame generation to a frame generation with a swapchain of its own (such as XeSS frame generation) looked like such a pause, because FSR frame generation's frames are drawn through a different path that the pause detection does not see, and the overlay disappeared for the first 30 frames. A pause is no longer measured across a change of swapchain; the hook log notes each such change (`Scene transition gap rebased on a new swapchain`).

- **With the Steam overlay and RTSS both running, RTSS's Present hook is no longer taken for Steam's when Streamline or XeSS frame generation loads after them:** when CaptureEngine cannot tell from the code address which overlay hooked the game's Present, the overlay that loaded last owns it. Streamline's `sl.interposer.dll` and `libxess_fg.dll` are watched only to know they are loaded, but each load still counted as the latest overlay, so in a game that loaded Steam, then RTSS, then Streamline, CaptureEngine applied its Steam-overlay handling to RTSS's hook. Only real overlays count as the latest one now, and the hook log no longer calls those two DLLs overlays.

- **OptiScaler's frame generation in place of DLSS frame generation no longer shows or runs as DLSS FG:** with OptiScaler set to take the game's DLSS frame generation requests (`FGInput=DLSSG`) and generate with XeSS or FSR frame generation instead, the game still turns DLSS frame generation on, but OptiScaler answers those calls, not NVIDIA's Streamline. CaptureEngine took them for DLSS frame generation: the overlay said "DLSS FG 2x" and CaptureEngine treated frames as Streamline's that Streamline never presented. A DLSS frame generation request answered by another program while Streamline presents no frames, or made while another frame generation presents the frames itself, now leaves CaptureEngine's DLSS FG state off, and NVIDIA frame-generation features created beside it are ignored. When OptiScaler only passes the requests on to a DLSS frame generation that really runs, Streamline presents the frames and it is DLSS FG as before. The hook log says so once per change (`Streamline Hook: FG signal ON (2x) via ... is a front`).

- **OptiScaler's FSR frame generation output shows the overlay and no longer crashes the game when DLSS frame generation is switched on (The Talos Principle Reawakened):** OptiScaler generates with its own copy of AMD's `amd_fidelityfx_framegeneration_dx12.dll` from its folder, next to the game's copy of the same name, and calls it in a way CaptureEngine's usual routes do not see. CaptureEngine watched only the game's copy, never noticed OptiScaler's frame generation start, and kept the overlay off. When the game then asked for DLSS frame generation (which OptiScaler answers itself), CaptureEngine took that for a switch from FSR to DLSS, drew on FSR's swapchain from the game's GPU queue, and the GPU device was removed (`0x887A002B`): the game closed without a crash dump. CaptureEngine now watches every loaded copy of AMD's frame generation runtime and follows the one that creates the frame generation swapchain (`FFX Hook: the frame-generation swapchain was created by ...`). A DLSS request that another program answers no longer ends an FSR frame generation start. CaptureEngine also never draws on a frame generation swapchain from a GPU queue it only guessed (`No swapchain queue captured ... SKIPPING the overlay`).

- **Games with OptiScaler installed as `dxgi.dll` no longer crash when Streamline starts (The Talos Principle Reawakened):** OptiScaler and CaptureEngine both hook Streamline's functions, and OptiScaler checks that its hook on `sl.common.dll` is still in place. CaptureEngine placed its own hook in front of OptiScaler's by rewriting the bytes OptiScaler had written; OptiScaler took that for a freshly loaded `sl.common.dll` and hooked it again in front of CaptureEngine, so each called the other until the game ran out of stack (`0xC00000FD`). CaptureEngine now leaves a Streamline function alone when another program has already hooked it and sees the game's calls through its own `GetProcAddress` and import hooks instead, which still run before the other program's hook. Functions nobody else hooked, and every other kind of hook CaptureEngine places, are unchanged. The hook log names each function it left and the program that owns it (`InlineHook: Left ... owner=...`, `Streamline Hook: Left ...`).

- **`cengine.dll` status always matches the recording event a program just received:** the engine announced a recording that started, went live or began stopping before its status showed it, so a program reading `ce_runtime_get_status` right after the event could still see the previous state. The status now changes first and the event follows, as it already did for settings and the runtime state.


### Changed

- **Under FSR frame generation without a game present callback, overlays hooked into Present draw above the CaptureEngine overlay while they show something, and the CaptureEngine overlay no longer skips frames when they stop (GTA V Enhanced, OptiScaler's FSR output):** CaptureEngine drew its overlay into the last graphics submission before each displayed frame so it stayed on top. When that last submission was another overlay's, such as a Steam notification or OptiScaler's start-up message, the frame right after it stopped drawing had no CaptureEngine overlay at all. CaptureEngine now draws into AMD's own last submission for each frame, which every displayed frame has. Overlays that draw after AMD's frame generation (Steam notifications and the Steam overlay, OptiScaler's own messages, effects applied at Present) now cover the CaptureEngine overlay while they are visible, and are not part of inject-capture recordings under FSR frame generation. The hook log notes each change (`[OVERLAY LAYER] No-callback FSR: N submission(s) now follow the runtime's last batch`).

## v0.1.7155

Changes since [v0.1.7154](https://github.com/aufkrawall/capture-engine/releases/tag/v0.1.7154).

### New

- **Recordings interrupted by a crash are repaired automatically:** when capture or encoding crashed, or CaptureEngine (or another program running its engine) ended unexpectedly, the half-written recording used to stay behind as an unplayable or unseekable `capture_stage_*` file, and an audio-only recording looked finished but had no duration. CaptureEngine now repairs it right after a helper crash, or at its next start, into `capture_recovered_*.mkv` (or `.mka`) with an index and duration, every audio track and the video ending at the same instant, and shows a tray notification. MKV recordings now close their blocks every second, so a crash loses at most about one second instead of up to five. Files that cannot be read are kept as `capture_incomplete_*` instead of being deleted.

- **Crash-safe MP4/MOV recordings on request (`[Output] fragmented_mp4=true`):** mp4 and mov recordings are written in fragments of about a second, so an interrupted recording stays playable and is repaired like an MKV. Off by default: a fragmented file cannot state its exact end, so its audio may end up to one audio frame (about 20 ms) after the video; MKV stays the container with exact track lengths.

- **Other programs can drive CaptureEngine (`cengine.dll` and an SDK folder):** CaptureEngine's engine (the helper processes, recording, hotkeys, the desktop overlay, screenshots, game launching, settings and the sensor driver, elevation service and autostart setup) now runs inside `cengine.dll` behind a documented C API, and the CaptureEngine app is one program that uses it. The installation contains an `sdk` folder with the header files, import libraries for clang/MinGW and MSVC, the export list, a CMake package (`find_package(cengine)`), an example program and a developer guide with recipes for every task. A program placed in the CaptureEngine folder can start the engine, record, take screenshots, change settings and receive events such as a finished recording with its file path. Only one engine runs per Windows session: while the CaptureEngine app runs, another program is told the engine is busy.

- **Programs that use `cengine.dll` can host CaptureEngine's helper processes in their own executable (`CE_FEATURE_SELF_ROLE_HOST`):** a program that wants game injection, capture and encoding in separate processes (so a crash there does not end the program) used to get `captureengine.exe` processes for them. With the new feature bit, those helpers, the per-application audio worker, the hardware sensors and administrator setup steps run as further instances of the program's own executable, which hands them to the engine by calling `ce_role_host_main()` first thing in `main`; the engine then starts even without `captureengine.exe`. The SDK's example program shows it (`--self-role-host`), and each helper's log names the executable it ran from (`[RoleHost] helper executable=...`).

- **Recording picks the best video encoder of your GPU automatically (`[Video] encoder=auto`, the new default):** recordings used `av1_nvenc` unless you changed it, so on AMD or Intel graphics, and on NVIDIA GPUs without an AV1 encoder, recording failed until the right encoder was configured by hand. CaptureEngine now finds the GPU that will encode (the game's GPU with inject capture, the captured monitor's GPU for screen capture, or the first GPU that can encode when that one cannot) and test-opens its encoders there once, best first: AV1, then HEVC, then H.264, through the vendor's own encoder (NVENC, AMF, Quick Sync) and then Windows Media Foundation. With `bit_depth=auto` or `10` it prefers an encoder that also records 10-bit and HDR, the configured container must support the codec, and if the chosen encoder still fails to open at the recording's real size or settings, the next one is used for that same recording. The result is remembered for the GPU, so later recordings start without testing again (about 0.2 s once, measured on an RTX 5070, which picks AV1). `av1_auto`, `hevc_auto` and `h264_auto` choose only within that codec, and live streaming with `auto` uses the GPU's best H.264 encoder. A named encoder such as `hevc_amf` is used exactly as before and never switched. The media log shows each test (`[EncoderAuto] Probe ...`) and one line per decision with the GPU, the choice and every candidate tried (`[EncoderAuto] request=auto ...`). Existing `config.ini` files keep the encoder they name.


### Improved

- **The injected DLLs are 5.6 MB smaller and leave 32-bit games more address space:** `capture_hook_x86.dll` and `capture_hook_x64.dll` each carried 5.6 MB of room for the pacing diagnostics trace inside the file, so every game CaptureEngine injected into had to map it, although only a debug-logging session ever fills that trace. The trace now takes its memory only when debug logging starts it, and the hook log says so (`[PacingTrace] armed: ... (5632 KiB, allocated)`). In a 32-bit game, where the game and everything loaded into it share at most 4 GB, the hook now occupies about 6 MB less.

- **Less memory for every thread of an injected game:** CaptureEngine's frame statistics kept a 32 KB work buffer that Windows sets up for every thread of the game, not only the one that renders, in DirectX games through the hook DLLs and in Vulkan games through the overlay layer; a game with 200 threads paid more than 6 MB for it. The overlay's 1% and 0.1% lows are now worked out with about 330 bytes on the rendering thread and give the same values. The per-thread data drops from about 40 KB to 7-9 KB in the hook DLLs and to under 1 KB in the Vulkan layer.

- **Every CaptureEngine program and DLL is 0.25 to 0.6 MB smaller:** each one carried debug information for the parts of the C runtime it contains, which the debuggers CaptureEngine's crash analysis uses never read (CaptureEngine's own debug information is in the `.pdb` files next to them) but which every process loading the file had to map, games included. It is left out now, 4.3 MB less across the ten files; the small Vulkan gate layer and the elevation service are less than half their previous size, and crash dumps resolve exactly as before. The build now also rejects a CaptureEngine file that carries such data again, holds more than 256 KB of preset writable data, or sets aside more than 16 KB for every thread of the process that loads it.

- **The hook DLLs store each overlay and sharpening shader once:** the Direct3D 11 and Direct3D 12 code each had their own copy of the same compiled shaders; one copy is shared now, 55 KB less per hook DLL.

- **Forced anisotropic filtering in Direct3D 11 games no longer forgets shaders it has room for:** CaptureEngine remembers, per game thread, which shaders it has already examined, so switching back to one costs nothing. Depending on where the graphics driver happened to place them in memory, a few shaders could push each other out even with the memory a quarter full, and every switch to them repeated the slower lookup. Each shader now has two possible places, and one is only given up when both are full.

- **CPU clocks in the overlay without the sensor driver, and NVIDIA GPU values without LibreHardwareMonitor (`[HardwareSensors] backend`):** the CPU clock row stayed empty unless the PawnIO driver was installed and CaptureEngine ran with administrator rights through the elevation service, and every GPU temperature, power or clock needed LibreHardwareMonitor. CaptureEngine now reads the CPU's average clock (the performance cores on hybrid CPUs) and its fastest core from Windows itself, and the temperature, power and clocks of an NVIDIA GPU straight from the driver when it is the PC's only graphics card; LibreHardwareMonitor is started only for what is left (CPU temperature and power, fan, voltage, other GPUs) and not at all when nothing is. `backend=native` never starts it, `backend=lhm` keeps the previous behavior, and the sensor log names the source of every value (`[Sensors] sources (backend=auto): ...`).

- **Per-application audio capture shuts Windows' audio client down properly:** the short-lived worker that records one application's audio used to leave Windows' capture client running until the worker exited, a precaution against a crash in Windows' audio mixer seen in June. A new test that tears thousands of captures down in every way CaptureEngine ever did found no crash on current Windows, so the worker now stops and releases each client (`[ProcessLoopback] client stopped and released` in the log). The worker stays a separate process, so a crash on another system would still not affect the recording of anything else.

- **Programs that use `cengine.dll` can keep their own FFmpeg:** CaptureEngine's FFmpeg libraries now have names of their own (`avcodec-ce-63.dll` and so on) and carry their helper libraries inside (Opus, AV1 encoders, Intel's video runtime, the C++ runtime) instead of shipping them as separate DLLs. A program that runs the engine in its own process and already loaded its own FFmpeg, libc++ or libopus could otherwise make Windows hand CaptureEngine that program's copy, with crashes or broken recordings as the result. The `ffmpeg` folder now holds just the five FFmpeg DLLs.

- **Crash reports and dumps say which part of CaptureEngine crashed:** every thread CaptureEngine starts now carries a name (for example `CE media r0003 encoder`, `CE app audio capture`, `CE runtime engine`), which debuggers, Process Explorer and performance traces show, and `crash.log` names the faulting thread (`Faulting thread tid=... name='...'`). That matters most when recording runs inside another program or with `isolated_helpers=off`, where every part shares one process. When the last in-process recording is gone, the log reports what it left behind (`[MediaTeardown] residue handles=+0 threads=+0 ...`), and so does every destroyed runtime (`[RuntimeTeardown] residue ...`), so a leak shows up as growing numbers across recordings.

- **`backbuffer_count` now also limits how far Vulkan games queue frames ahead:** in Vulkan, CaptureEngine can only raise a swapchain's image count, never lower it below what the game asks for, because a game sizes its rendering to that count and fails when images are taken away. So in a game that asks for 3 images, such as Strange Brigade, `backbuffer_count=2` did nothing. Now, on GPUs and drivers that support the Vulkan present-wait extensions, CaptureEngine keeps the image count and before each present waits until the present `backbuffer_count - 1` frames earlier has reached the screen, the same way the setting already limits the queue in DirectX games. That wait never takes longer than 1 second. When a present does not complete within that time (a minimized window, for example), CaptureEngine stops waiting and only checks until the game's presents complete again, so the game is never held up. CaptureEngine stays out of the way where waiting would be wrong: in games that use these extensions themselves, with frame generation that places its own frames (DLSS frame generation, for example), when one present covers several swapchains, and when the image count already limits the queue. If the driver refuses the device with the extensions added, the device is created without them. The Vulkan layer log says once per device whether pacing is on and why not (`queue-depth pacing on this device: ...`), says once per swapchain whether it paces (`queue-depth pacing for swapchain ...`), reports the waits every 10 seconds, and logs each missed 1 s limit and each recovery. The 10-second report continues across swapchain re-creations (`generations=`), because games such as Strange Brigade rebuild their swapchain every few seconds and on every minimize, which used to suppress the report entirely.

- **Fewer repeat-then-skip stutters in inject recordings when the game runs close to the recording frame rate:** with an uncapped game hovering around 120 fps on a 120 fps recording, small frame-time jitter made the recorder show one frame twice and then skip the next, a visible 0-step/2-step hitch. In The Talos Principle with DLSS 3x about 0.8 of these per second were avoidable. The recorder now plans the next four output frames together from the frames it already holds. It only changes a choice when that avoids a repeat or a skip, and never shows a frame more than one output frame (8.3 ms at 120 fps) away from its place relative to the audio. In replays of that session and of jittered 110-121 fps test sources this removes about two thirds to nearly all of these stutters, at about 0.3 ms more typical timing error and a lower worst case (8 instead of 11 ms). Games running steadily at 60, 144 or 240 fps record exactly as before. This applies to inject capture with and without frame generation; screen capture (WGC, DXGI duplication) is unchanged, since its repeats in tested sessions were all slots where Windows delivered no new frame. The media log reports the changed choices (`Horizon playout avoided-repeat/avoided-skip`, `[Inject CFR] Horizon playout over ...`, `Horizon*` totals in `[Inject CFR QUALITY SUMMARY]`).

- **Capture-sync recordings in Direct3D 10, 11 and 12 games follow the FPS limiter's exact frame grid:** with capture sync, the limiter holds every frame to an exact grid at the recording rate, but CaptureEngine timestamped each recorded frame when it copied it, before the limiter's wait. So the timestamps carried how long the game took to build each frame and jumped by several milliseconds whenever the game's load changed, and the recorder had to keep realigning to them. In BioShock Infinite at a 120 fps capture sync the frames reached the screen within 0.2 ms of the grid, yet their timestamps landed 1.2 to 6.1 ms early and shifted by about 4.5 ms with load; the recorder realigned 8 times in 36 seconds and showed 14 frames twice and skipped 12. Each frame now carries the moment the limiter actually presents it, so a 120 fps recording of a 120 fps capture-synced game gets an evenly spaced source; a general FPS cap above the recording rate is now converted in an even pattern too. Relative to the sound, each frame now sits where it appeared on screen; before, it sat up to one limiter wait (at most one frame interval) too early. Frames that miss their slot keep their own time, and frame generation, Vulkan, Direct3D 9 and 8, OpenGL and DirectDraw are unchanged (the last four already capture at their present). The hook log names the timestamp source when it changes (`pre-limiter captures stamped by ...`) and the limiter statistics count it (`stamp(...)`); the media log counts frames stamped ahead of their arrival (`StampAhead=` in `[Inject Contention]`). The limiter trace log no longer cuts its statistics line short.

- **FPS limiter latency recovers instantly after a stutter spike:** frame pacing never needed to recover, but the limiter's low-latency placement did. After one spike it released the game earlier than necessary for the next 64 frames, and a spike that made one frame late kept a safety margin that took up to about ten seconds to shrink (roughly 4 ms of extra input latency after a 4 ms spike at 120 fps). Now the two largest frame times of the last 64 frames are ignored when sizing the budget, and the safety margin only grows when late frames repeat within those 64 frames, so an isolated spike costs nothing once it is over while a game whose frames are really getting slower is still protected. The trace log notes each ignored spike (`front-load isolated overrun ignored`).

- **FPS limiter with FSR frame generation limits the game, not AMD's output frames (DirectX 12, capture sync and general limiter):** CaptureEngine used to wait on AMD's presenter thread for every displayed frame, on top of AMD's own frame pacing, while the game itself was only held back by AMD's queue filling up. It now limits the game's own frame rate right where the game hands each frame to FSR (half the configured rate at 2x, a third at 3x, on an exact grid) and lets AMD space the displayed frames, as AMD recommends; the configured value is still the displayed frame rate. It applies with FSR frame generation on and off, with and without the game's present callback. If a game stops handing frames through FSR's swapchain, CaptureEngine notices within a few presents and limits the displayed frames again. The hook log says which side owns pacing (`FPS Limiter: the game's Present into the frame-generation runtime owns pacing`, `... paces again`).

- **The frame-time graph no longer makes the overlay rebuild all of its text every frame:** with the graph shown, the overlay redid its text on every frame just to move the graph, although the text only changes at its update interval (half a second by default). Now only the graph is redrawn between text updates, and drawing it is about four times faster with exactly the same result, so the overlay's own drawing work per frame drops from about 13 to 3 microseconds, which shows at high frame rates. The hook log reports every 10 seconds how many frames were fully rebuilt, graph-only or reused, and what each kind cost.

- **Fewer graphics calls per frame for the Direct3D 11 overlay:** this matters most through translation layers like DXUP, where every call goes through the translator. The overlay no longer re-uploads unchanged drawing data, no longer saves and restores the game's render targets twice, identifies the swapchain's API once instead of every frame, and reads the graphics DLLs' version information only when a DLL is loaded or unloaded instead of on every frame.

- **The FPS limiter releases frames on time instead of up to 0.7 ms late:** the limiter sleeps on a Windows high-resolution timer until shortly before a frame's slot and spends the last moment in a precise wait. That last stretch was capped at 0.25 ms, but when a game keeps Windows' timer at 1 ms resolution, as BioShock Infinite does, the timer often woke 0.5 to 0.6 ms late: 30 to 45% of the limiter's waits ended after the slot, by up to 0.68 ms, which showed as uneven frame times. The limiter now measures how late the timer wakes and starts the precise wait early enough for 99% of wakes (up to 1 ms before the slot). That precise wait takes CPU time, about as long as the margin per frame; the hook log's limiter statistics show both (`marginUs`, `fineMeanUs`). CaptureEngine also no longer raises Windows' timer resolution to 1 ms for its Reflex-based frame pacing, because on the test system that made the high-resolution timer itself less precise (it is still raised when that timer is unavailable).

- **Smoother frame times with CaptureEngine's FPS limiter in Direct3D 10 and 11 games:** the limiter waits in the game's present call until the frame's slot comes, and in Direct3D 10/11 the game's frame stays with the driver until that present call hands it to the GPU. So the GPU sat idle while CaptureEngine waited and only started on the frame afterwards, and when the frame reached the screen depended on how long the GPU needed for it rather than on the limiter. In BioShock Infinite at a 140 fps cap this made displayed frame times vary more than twice as much as the limiter's own timing (frame-time standard deviation about 350 µs against 138 µs; uncapped the game reaches 50-80 µs), showed frames about 3 ms later than necessary, and made the render-ahead limit (`cpu_prerender_limit`) wait on every other frame. CaptureEngine now hands the recorded frame to the GPU right before the limiter waits, so the GPU renders it during the wait and the frame is ready when its slot comes. The cap, its timing and Direct3D 12, Vulkan, OpenGL and Direct3D 9 games are unchanged. The limiter's statistics line in the hook log now counts these hand-overs (`preWaitSubmits`) and shows how precisely the limiter's waits ended (`wake(...)`), including whether the system timer or the final wait phase was late.

- **Direct3D 12 rows of the perf CSV show CaptureEngine's present work:** each Direct3D 12 frame's row in `perf_metrics_*.csv` lacked the overlay time and the split around the game's present call, so the CSV could not show how long the present itself took (Heroes of the Storm through a Direct3D 11-to-12 translation layer, for example), and its FPS-limiter wait was the previous frame's. The row now carries `overlay_us`, `pre_present_us`, `present_call_us`, `post_present_us` and this frame's `fps_limit_wait_us`, like Direct3D 11 rows. `total_us` keeps its meaning (CaptureEngine's frame processing), and every present still writes exactly one row.

- **The render-ahead limit (`cpu_prerender_limit`) in Direct3D 11 games no longer keeps a CPU core busy while it waits:** when a game's swapchain has no frame-latency wait object (BioShock Infinite, for example), CaptureEngine held the game's render thread back by asking the GPU, in a tight loop, whether an earlier frame had finished. Whenever the GPU was the bottleneck the thread spun through the whole wait, 0.05 to 2 ms per frame in BioShock Infinite, up to about half a CPU core at 240 fps. CaptureEngine now marks the end of each presented frame with a GPU fence and sleeps until the frame the limit allows has finished, and before it sleeps it hands the GPU the work the game already recorded for the next frame, so the GPU does not wait for the CPU. The limit itself is unchanged; devices without fence support keep the previous method. The wait now shows where it belongs: in the perf CSV's `prerender_wait_us` column (always 0 for Direct3D 11 before), in the limiter stage of the hook log's `[PRESENT STAGE COST]` line instead of `startup_routing`, and every 10 seconds in a new `[D3D11 PRERENDER]` line.

- **Repeated frames no longer cost an encode in AV1 recordings and streams with NVIDIA (`av1_nvenc`):** when a recording slot repeats the previous picture (the game renders fewer frames than the recording rate, a static screen, or encoder overload), CaptureEngine encoded the same picture again, which takes NVENC as long as a new frame. At 4K 120 fps with preset p6 that left no headroom, so short overloads trimmed frames (12-14 in one session). AV1 can tell the player to show the frame it already has again with a 5-byte header, and CaptureEngine now writes that instead. Frame count, timestamps, audio sync and the repeated pictures stay exactly as before; under overload the existing frame pacing can now trade repeats for time instead of trimming. NVENC budgets its bitrate per encoded frame, so CaptureEngine raises the encoder's bitrate by the share of skipped frames and the recording keeps the configured bitrate: in CaptureEngine's hardware test (RTX 5070) the unique frames came out 0.2 to 3.7 dB PSNR better at about the same size, and identical without repeats. Live streams stay within 10% of the configured bitrate in any second and add no latency beyond the encoder's own. Keyframes follow the encoder's frame count, so with many repeats they can be up to twice the keyframe interval apart. Repeats are still encoded with B-frames or lookahead, right after a keyframe, while the cursor or face camera moves, and for HEVC and H.264. If the encoder returns a frame that cannot be shown again (an unexpected keyframe), the repeats already promised behind it keep their time, also as the last frame of a recording. The media log reports it (`[AV1 ShowExisting]`). This needs the bundled FFmpeg's new option to change the bitrate without a new keyframe.

- **Forced AF in Direct3D 11 decides once per draw instead of at every sampler change:** in games whose device CaptureEngine wraps (BioShock Infinite, for example), each sampler change ran CaptureEngine's AF decision right away, against a shader and textures the game often changed again before drawing; the draw then decided once more. In BioShock Infinite that redone work was a quarter to a third of forced AF's cost (about 40 ms of CPU time per second at peak). Sampler changes now wait for the draw that uses them, and the game reads back exactly what it set in the meantime. Saving or switching the device context's state (`SwapDeviceContextState`), clearing it and command lists keep the pending changes correct. The same now applies where CaptureEngine reaches a game's Direct3D 11 rendering through hooks on the real device context and routes its calls through a function table of its own (after a late injection, for example; see the fix below), because there it sees every draw. Rendering CaptureEngine can only hook in place, such as that of Direct3D 11-to-12 translation layers like DXUP in Heroes of the Storm, decides at the sampler change as before. Which textures get AF is unchanged. The cost line counts the deferred changes (`deferral(deferred/s ...)`).

- **Less CPU time for forced AF in 32-bit Direct3D 11 games:** CaptureEngine counts its forced-AF work for the hook log's cost lines, several times per texture bind, sampler update and sampler creation. In a 32-bit game each of those counts was a 64-bit operation that the processor carries out slowly there, about 40 cycles each, more than much of the work being counted (BioShock Infinite: millions per second). 32-bit games now count with 32 bits, which costs under one cycle. The cost lines report the same numbers.

- **Less CPU time per texture and sampler bind with forced AF in Direct3D 11 games:** each texture or sampler bind and each sampler update made CaptureEngine rescan all 16 pixel-sampler slots, twice, to find which ones the game had bound and which held CaptureEngine's AF version (BioShock Infinite: well over a million binds per second). CaptureEngine now keeps both as the slots change. A sampler update that changes adjacent slots now reaches Direct3D as one call instead of one call per slot, and the updates are counted per device context instead of in one process-wide counter shared by all render threads. Which textures get AF is unchanged. The cost line reports the slots per call (`rebinds(slotsPerCall)`).

- **Less CPU time for forced AF when a Direct3D 11 game switches pixel shaders:** every pixel-shader switch made CaptureEngine read the shader's forced-AF data back from Direct3D, even when the game bound the shader that was already set (BioShock Infinite switches up to 180,000 times per second). The shader already set now costs nothing, and each render thread remembers up to 1024 shaders it switched to, so a game alternating between its shaders reads that data once per shader. A first version kept only 64 per device context, too few for BioShock Infinite: half of its switches still read the data. The memory keeps no shader alive; a shader the game releases is forgotten as Direct3D destroys it, so a new shader at the same address is always read afresh. Which textures get AF is unchanged. The cost line counts these switches (`shaderSwitches(repeat memo lookup evicted)`).

- **Forced-AF cost report for Direct3D 11 games covers all of its work:** the hook log's forced-AF cost line (`[D3D11 AF COST]`, `[D3D11 AF COST wrapper]`) left out the shader lookup each pixel-shader switch makes, and nothing timed the work CaptureEngine adds to each sampler the game creates (BioShock Infinite creates about 157,000 per second). Shader switches are now timed on their own, lookup included (`shaderUs`, `shaders=` in `estMsPerS`), and `[D3D11 SAMPLER CREATES]` reports CaptureEngine's time per creation next to Direct3D's own (`ceUs`, `runtimeUs`, `estMsPerS`). This shows how much of a game's CPU time forced AF really takes. The cost line also measures how often a sampler update's AF work is redone before the game's next draw, and what deciding only at the draw would save (`deferral(...)`), as evidence for a possible further reduction.

- **Less CPU time per sampler a Direct3D 11 game creates while sampler overrides are on:** for every sampler a game created, CaptureEngine took a process-wide lock and copied its whole configuration (dozens of text settings) just to read the sampler settings, and it rewrote the sampler's tag even when Direct3D had handed back an existing, already tagged object. BioShock Infinite creates a sampler on almost every draw for each texture that is still streaming in, so this ran on its render thread thousands of times per second right after loading a save. Together with the replacement scans fixed above, this is the likely cause of textures streaming in slowly there (not yet measured in the game). Sampler creation now reads the thread's cached settings and leaves an unchanged tag alone. Each creating thread also remembers the sampler descriptions it has seen and the objects it has already checked, so a repeated creation skips both the settings work and reading the tag back, and counts itself without any process-wide atomic operation. In BioShock Infinite that still cost CaptureEngine about as much time as Direct3D's own creation; a repeated creation now also skips a settings check that only matters when the game binds a sampler, finds its entry with a hash that 32-bit games compute twice as fast, counts itself once instead of four times, and no longer reads the system clock. This memory holds no sampler alive (Direct3D allows a device 4096 of them); a sampler the game releases is forgotten as Direct3D destroys it, so a new sampler at the same address is always tagged afresh. Every 10 seconds the hook log counts the game's sampler creations, how many of them returned an already tagged object, and how many the per-thread memory answered (`[D3D11 SAMPLER CREATES]`, `memo(desc tag raced threads)`).

- **Less CPU time per sampler a Direct3D 12 game creates while sampler overrides are on:** with forced AF, mip mapping or mip bias configured, every Direct3D 12 sampler a game or a Direct3D 11-to-12 translation layer created made CaptureEngine take a process-wide lock and copy its whole configuration twice, hash the sampler settings again and take one more lock for a log that had stopped logging after 16 samplers. Engines and translators that create sampler descriptors every frame paid this on their render thread. Sampler creation now reads the thread's cached settings and their hash, which are computed once per configuration change, and skips the finished log without a lock. The same cached settings now also serve Direct3D 11 sampler creation. Which samplers get changed, and how, is unchanged.

- **Less CPU time per frame in every game CaptureEngine hooks:** each frame, CaptureEngine still took a process-wide lock and copied its whole configuration (dozens of text settings) several times to read single values: for the render-ahead limit and vsync setting at every Direct3D 9, 11 and 12 present, for the frame-latency pacing of DXGI games, for the Direct3D 7 overlay route, and in DLSS, DLSS Frame Generation and Streamline calls that games make every frame, such as each DLSS parameter they set. Direct3D 9 additionally kept a full copy per frame that nothing read. These paths now read the thread's cached settings, which are refreshed on every configuration change, so overrides still take effect at the next frame and behave exactly as before.

- **Less locking for forced AF in Direct3D 11 games CaptureEngine reaches through hooks on the real device:** every texture, sampler or shader change on such a game's Direct3D 11 rendering (for example Heroes of the Storm through a Direct3D 11-to-12 translation layer) took one process-wide lock and a table lookup, so a game that records on several threads at once also waited for its own other threads there. Each rendering context now keeps its forced-AF state to itself and reaches it without any shared lock.

- **One forced-anisotropic-filtering implementation for all Direct3D 11 games:** CaptureEngine reaches a game's Direct3D 11 rendering in one of two ways, through its own stand-in for the game's device (when it intercepted the device's creation, as in BioShock Infinite) or through hooks on the real one (for example after a late injection, or with a Direct3D 11-to-12 translation layer such as DXUP in Heroes of the Storm). Each way used to decide forced AF with its own code, and only one of them got the recent speed-ups: in BioShock Infinite forced AF still cost about 0.8 ms of the game's CPU time per frame. Both ways now share one implementation, so every Direct3D 11 game gets the cached per-sampler decisions, a configuration change takes effect at the next draw everywhere, and both write the same cost line to the hook log (`[D3D11 AF COST]` and `[D3D11 AF COST wrapper]`). Sampler creation with mip bias or AF disabled is shared too.

- **Video memory of a recording broken down in the log:** the media log now has a `[GpuMemory]` line that splits the recording's GPU memory into the WGC/DXGI smoothness buffer, the encoder's input frames, repeat caches, conversion copies and overlays, plus the remainder the encoder and drivers use internally. It is logged while the total changes and once when the recording stops, with the peak. The video memory added by opening the encoder is logged too (`[GpuMemory] Codec open`). Windows' per-process video memory counters, including the per-process value in Task Manager, count a texture shared between two GPU devices once per device although it uses the memory once; the line shows that part separately (`countedTwice`) and the real usage (`physical`). The total dedicated usage of the GPU is not affected. This shows where memory goes when a recording uses more VRAM than expected.

- **Up to 62% less video memory for WGC and DXGI duplication recording:** the smoothness buffer that keeps these recordings smooth (300 ms by default) now holds its frames already converted to the video encoder's format (NV12/P010) instead of full RGB frames. Delay, frame count, smoothness and audio sync stay the same. At 4K 120 fps a 10-bit recording needs about 1.5 GB instead of 2 GB and an 8-bit recording about 0.75 GB. HDR recordings, which did not fit the full 300 ms into the 3000 MB budget before, now get it with about 2 GB. Cursor and face camera are still drawn into every output frame. This includes DXGI duplication, which captures on its own GPU device and now converts into frames it shares with the encoder. Recordings with output scaling or HDR recorded as SDR keep RGB frames, as does DXGI duplication on GPUs that cannot share NV12/P010 frames between devices; `[WGC] wgc_retained_yuv=false` restores the previous behavior. The log shows the chosen format per recording (`[WGC] Retained reservoir route`).

- **Less background CPU work during game loading:** repeated requests for an already loaded DLL no longer wake a full hook scan or repeat Unreal console-variable discovery when Windows load/unload notifications are available. New modules and reloads still trigger discovery immediately, and loader-return discovery remains available if notification registration fails. Hook-thread summaries now distinguish coalesced loader returns from fallback requests.

- **Less CPU work when forcing anisotropic filtering in Direct3D 11 games and API translators:** forced AF is decided per texture on the game's render thread, at every texture, sampler or shader change (for example Heroes of the Storm through a Direct3D 11-to-12 translation layer). Each sampler's decision is now worked out once and reused for all later draws, also when the game switches between samplers from draw to draw, so a texture or sampler change costs one cached lookup instead of several Direct3D queries, replacement-cache scans and lock round trips. Up to 128 sampler states per device context stay referenced for this; they hold no texture memory. Vertex, geometry, tessellation and compute shader texture and sampler bindings are no longer intercepted at all, because forced AF only ever changes pixel-shader samplers. Shader sample dependencies use compact records, and shader or texture changes recheck only affected samplers while still restoring ordinary filtering for protected resources (single-mip render targets, depth and non-color formats, explicit-LOD sampling). Presentation and DLSS overrides no longer trigger sampler replacement checks when all sampler settings are at their defaults. A configuration change still takes effect at the next texture or sampler change. The hook log now reports this work every 10 seconds while it happens (`[D3D11 AF COST]`: binds per second, reused and recomputed decisions, sampled CPU time of the bind hooks and of the sampler updates, and the total per second). Games whose Direct3D 11 device goes through CaptureEngine's own device wrapper (for example BioShock Infinite) get the same report as `[D3D11 AF COST wrapper]`.

- **Quick Sync pipeline depth follows the frame rate:** `[QuickSync] async_depth` now defaults to `auto`, which keeps about 100 ms of frames in flight (12 at 120 fps) like NVENC does. The previous fixed default of 4 stalled every frame once CaptureEngine's conversion had to wait more than about three frame intervals behind the game's GPU work, which is the cause of the NVIDIA encoder overloads fixed earlier. Explicit values from 1 to 64 still apply, and the live-streaming preset keeps its low-latency value. Existing configuration files that still contain `async_depth=4` keep 4; set it to `auto` to use the new behavior.

- **Less video memory for SDR recordings:** CaptureEngine no longer sets up the Windows video processor and its full-size staging copy (about 33 MB at 4K) for recordings it converts with its own shaders. Both are now created only when a frame actually needs the video processor, which today means scaled recordings and 16-bit floating-point SDR sources.

- **Encoder overload easier to diagnose:** when handing a frame to the hardware encoder takes most of a frame interval, the media log now shows whether the encoder was waiting on CaptureEngine's own GPU copy and color conversion, and whether that work ran slowly or sat queued behind the game's rendering. This works for inject capture, Windows Graphics Capture and DXGI desktop duplication, for both new and repeated frames. One frame per second is measured without blocking, and the results are summarized in one line every few seconds while recording, with a final line when the recording stops. The per-second encoder timing line now covers every capture method and also shows how many frames are inside the encoder against its pipeline depth, and the log records the pipeline depth the encoder actually opened with. A second line per window follows one frame through each of CaptureEngine's GPU steps (conversion, releasing the game's frame buffer, the encoder hand-off, the start of the next frame) and shows, for each step, how long the GPU took next to how long CaptureEngine took to submit it, so a step at which the GPU waits for the encoder stands out.

- **The Vulkan layer log says why a game may be composed instead of flipping on its own:** a Vulkan game that the desktop compositor draws shows no tearing and at most one new picture per refresh, even with vsync off. For each swapchain the log now records whether the window covers its monitor, whether the swapchain matches the window's size, whether Windows stretches the window for display scaling, whether it is a layered (transparent) window, and which NVIDIA presentation modules were loaded when the swapchain was created (`presentation path at ... blockers=`). The window is checked again every 512 frames and logged again only when something changed.

- **Video encoder workload visible in the log:** while a recording or stream is encoding, the sensors log now reports every 10 seconds, and once more for the last stretch when encoding stops, how busy each part of the GPU was while it encoded: 3D rendering, split into the game's share and everything else (including CaptureEngine's own conversion), compute, copy, video encode, video decode and any other engine. A video-encode engine near 100% means the encoder itself is at its limit and only a faster preset helps. A video-encode engine well below that while frames are still repeated means the encoder is waiting on other GPU work. The values come from the same Windows GPU counters CaptureEngine already reads for the overlay, so this adds no measurement cost.


### Fixed

- **Release lint and sanitizer verification gates pass cleanly:** resolved pre-release static analysis, file-size ratchets, and clang-tidy findings across media encoding headers, packaging tests, and platform thread labeling; added default member initializers to the overlay configuration to eliminate undefined bool evaluations under UBSan; and accommodated AddressSanitizer thread provenance in process residue regression tests.

- **Builds kept outdated 32-bit copies of the frame-generation test apps:** the DLSS and FSR frame-generation test apps are built for 64-bit only, because their runtimes are, but copies from older builds stayed in `installed/testapp/x86` with their old build settings, and every build's checks kept examining them. The build now removes them (`Removed ... stale x86 output(s) of x64-only test apps` in the build log); they were never part of the packages.

- **Programs that record through `cengine.dll` no longer lose graphics memory with every recording:** each recording made inside a program's own process (the default for programs using `cengine.dll`, or `isolated_helpers=off`) left its NVIDIA video encoder device behind, with about 22 driver threads and roughly 250 MB of video memory, so a program that recorded often slowly ran out of both. Every encoded frame also kept a small allocation alive until the recording's process ended, also in the CaptureEngine app. Recording now gives the encoder's frames back, so the device is released when the recording ends. The log shows it at the end of each recording (`[EncoderBridge] Encoder D3D11 device released (references left=0)`) and names the owners of any threads a recording left behind (`[MediaTeardown] residue threads: ...`).

- **A recording started while the previous one is still being saved now records:** when a new recording started before the last one had finished saving (stopping and starting again right away, by hotkey or from a program using `cengine.dll`), the new recording never went live and ended up canceled with no file. The finishing recording reset the shared recording state when its file was done, wiping out the new recording's start; with game capture it could also withdraw the new recording's encoder textures and discard its first frames. A recording that is told to stop now keeps its own copy of that state for the rest of its saving, so nothing it does afterwards reaches the next recording; the media log says so (`[RecordingLifecycle] Detached from the shared live state`).

- **A program using `cengine.dll` gets a `config.ini` when the folder has none:** the engine creates a missing `config.ini` from the built-in template, but it looked for that template in the running program, which only the CaptureEngine app carries, so for any other program no file was created and the engine ran on built-in defaults. `cengine.dll` now carries the template itself. The engine inside such a program also registers the Vulkan overlay layer and starts game injection from the CaptureEngine folder, never from the program's own folder.

- **Editing `config.ini` in the installation folder no longer asks for administrator rights after an update:** setup lets ordinary users edit `config.ini` in the installation folder (under Program Files by default), but gave that permission only to a `config.ini` it created itself. A `config.ini` from an older installation, from a folder you copied in, or one saved over by an editor running as administrator kept the folder's read-only permissions, so every save needed administrator rights. Setup now gives the permission on every install and update, to `config.ini` and `config.ini.new`. It never changes permissions through a link: if `config.ini` or one of CaptureEngine's data folders (`logs`, `captures`, `screenshots`, `benchmarks`) is a junction or symbolic link, the link is left as it is and the folder or file it points to is not touched. The setup log reports the result (`config: ... opened_to_users=`) and each link it left alone.

- **A missing `config.ini` is recreated editable, and CaptureEngine says when it cannot recreate it:** when `config.ini` is missing, CaptureEngine writes a new one with its built-in defaults. Running as administrator, it created that file with the installation folder's permissions, so under Program Files only administrators could edit it. It now gives the file the same permission setup gives `config.ini`. Running normally, CaptureEngine cannot create files in Program Files at all, and it then ran on its built-in defaults without saying why. The log now says so once at startup (`[Settings] config.ini is missing and could not be created ...`); running setup again restores the file.

- **"Open config" no longer starts your editor as administrator:** when CaptureEngine runs as administrator, the editor started from the tray menu ran as administrator too. Editors that save through a temporary file and a rename then replaced `config.ini` with a copy only administrators can change, so editing it normally asked for administrator rights from then on. CaptureEngine now hands the file to the Windows desktop (Explorer), which starts your editor as you. If Explorer is not running, the file opens as before. The log says which way it was opened (`[Controller] Open config: ...`).

- **Direct3D 9, Direct3D 8 and DirectDraw games no longer risk a crash when CaptureEngine closes while they run:** when CaptureEngine stopped (closing the app, or a program using `cengine.dll` ending its engine), the game's CaptureEngine module released its capture textures from its own background thread while the game kept drawing. Direct3D 9 and 8 devices must only be used from one thread at a time, so that could crash the graphics driver inside the game; it did reproducibly in CaptureEngine's Direct3D 9 test app on an NVIDIA GPU, right after an automatic recording stopped and CaptureEngine exited. DirectDraw games had the same problem with the Direct3D 7 overlay CaptureEngine draws with on the game's device. The capture now only stops on that thread, and the textures are released on the game's own thread: in Direct3D 9 and 8 at its next device reset or on its first frame when CaptureEngine starts again, in DirectDraw at its next frame, surface creation or device release. The hook log shows both steps (`[InjectLifecycle] DX9: host generation retired on HookThread`, `... released on the game's thread`; likewise `DX8:` and `DDraw:`).

- **The sensor notes no longer say CPU sensors need CaptureEngine itself to run as administrator:** the generated `config.ini` and the LibreHardwareMonitor plugin's `README.txt` said CPU temperature, package power and core clock stay blank unless CaptureEngine runs elevated. With the PawnIO driver installed, the optional elevation service (offered by the setup and in the tray menu) reads them while CaptureEngine runs without administrator rights; both notes now say so. Existing `config.ini` files are not changed.

- **The default `config.ini` no longer calls `streamline_upgrade` non-functioning:** the note still said no Streamline 1.x game had been upgraded end to end, although the bridge runs The Witcher 3 with DLSS super resolution and 4x multi-frame generation. It now says so and that other 1.x titles are untested; where one differs, CaptureEngine refuses and logs why. Existing `config.ini` files are not changed.

- **A stopped audio-only recording is no longer reported as canceled:** the file was saved, but right after saving it CaptureEngine also treated the stop as one that came before the recording started and recorded a second, canceled result over the saved one. The overlay could then show the recording as canceled, the recording manifest ended with a canceled entry, and a program using `cengine.dll` was told the recording was canceled and got no file path. Video recordings were not affected. The media log showed it as `[RecordingLifecycle] Stop accepted before the recording ever started` right after `[STOP SUMMARY] Audio-only recording finalized`.

- **CaptureEngine installed in a folder Windows cannot name in its code page now says so instead of running half-configured:** when the installation path contains characters the Windows code page cannot express and the drive has no 8.3 short names, CaptureEngine ran with default settings and wrote no logs, without telling you. It now shows a message that explains the cause and how to fix it (a folder with Latin characters, or 8.3 names on that drive) and does not start. A second CaptureEngine started while one is running also no longer creates an empty log session folder before it reports that CaptureEngine is already running.

- **Closing CaptureEngine right after stopping a recording no longer cuts the recording short:** when CaptureEngine was closed while a recording was still being written (after a long recording or to a slow drive or network share), it waited at most 10 seconds for its helper processes and then ended them, although the recording process allows itself 60 seconds for the video encoder alone and keeps writing for as long as the file still advances. The recording then lost its end or could not be played. CaptureEngine now never ends its helper processes when it closes; it waits until each has finished, while the tray icon keeps showing that it is shutting down. While it waits, the log says every 10 seconds which helpers are still running (`[HostChildren] shutdown still waiting`).

- **Release memory-safety check of the overlay's teardown:** the overlay's shutdown assumed that every renderer registered as Direct3D 11 was CaptureEngine's own Direct3D 11 renderer and wrote one of that renderer's settings at a fixed position into memory the actual renderer did not own. The sanitizer stage of release verification stopped on it. In released builds only CaptureEngine's own renderer is ever registered as Direct3D 11, so games were not affected; the setting now reaches whichever renderer is registered through that renderer's own interface, as Direct3D 12 renderers already did.

- **Release verification passes its sanitizer stage again:** a Direct3D 11 dispatch test called generated code in a way the sanitizer's function-type check cannot follow, which stopped the sanitizer stage, and two recently changed test files exceeded the accepted static-analysis findings. Only tests changed; CaptureEngine itself is unaffected.

- **FPS limiter with DLSS frame generation paces whole game frames, not single images (DirectX 12):** in games where DLSS presents every image itself, such as The Talos Principle and GTA V Enhanced, CaptureEngine's FPS limiter treated each of DLSS's images as one of the game's own frames whenever it paced them itself (the basic limiter, or while the game's Reflex frames are missing). It waited for a frame slot on DLSS's presenting thread up to twice per frame, so at 4x under a 140 fps cap the game could drop to about 22 fps instead of 35. These images are now paced the way the limiter already paces them after an FSR phase and in Vulkan: one wait per group of generated images, which pass straight through. Where the game's own present also reaches CaptureEngine, nothing changes, so the game is never limited twice.

- **Short stutter after pauses when the limiter hands pacing back to Reflex (DirectX 12):** many games, Unreal Engine titles like The Talos Principle among them, run Reflex on one thread and present on another, so a Reflex frame can arrive just after the image it belongs to. The limiter counted that as missing Reflex and held two or three frames itself after every pause or frame generation switch. It now allows for that one-image delay and still takes over again within the first frame whose Reflex frame is really missing.

- **Latency and stutter for a second or two after a stall with DLSS multi frame generation (DirectX 12, Reflex):** after a short stall, CaptureEngine's FPS limiter waits for three steady Reflex frames before it hands pacing back to the NVIDIA driver, and it expected a new Reflex frame at every image it checked. In The Talos Principle with DLSS 4x, every generated image reaches CaptureEngine on its own, so the last image of each frame never had a new Reflex frame and counted as a stall: CaptureEngine held DLSS's presenting thread for about 25 ms on every frame and restarted the hand-over, for about 1.6 seconds until timing happened to line up. The limiter now judges the hand-over per game frame: one Reflex frame covers all images of its frame, so pacing returns to the driver within three frames. If the game really stops its Reflex frames, the limiter still takes over again within the first frame that is missing one.

- **High input latency with DLSS 3x and 4x multi frame generation after switching from FSR frame generation (DirectX 12):** after switching from FSR to DLSS frame generation in The Talos Principle, DLSS presents every image from its own thread, and CaptureEngine's FPS limiter treated each of those images as one of the game's own frames. After the short stall of each switch, the limiter waits for three steady Reflex frames before it hands pacing back to the NVIDIA driver, but at 4x it looked at two images per game frame and the second never had a new Reflex frame, so the hand-over never happened. CaptureEngine then held every frame for about 30 ms itself, and PC latency at 4x with a 120 fps capture sync was 115 to 145 ms (3x: 57 ms). The limiter now counts one evaluation per group of generated images there, as it already does for Vulkan, so pacing returns to the driver within a few frames after each switch. A 30 fps base frame rate (120 fps at 4x) still costs its own latency.

- **Repeat-and-skip bursts in recordings at menu transitions with DLSS frame generation after switching from FSR (inject capture, DirectX 12):** to time recorded frames to the screen, CaptureEngine matches each captured image to Windows' report of when an image reached the screen, in order. When an image had no report of its own (more images than reports, or a dropped report), it was given the next image's report instead, every later image was matched one report too late, and the learned delay kept growing: in The Talos Principle it went from 16 ms to over half a second across three menu transitions, and each correction showed about 12 repeated and 12 skipped frames in the recording. An image whose nearest report already belongs to the image before it now keeps its own timing, and a correction starts the matching afresh. The media log counts these images (`claimed=` in `[Inject DLSS FG] final-output timing`).

- **False sharpening gap in the hook log after switching DLSS frame generation off:** after DLSS frame generation was switched off following an FSR phase, CaptureEngine keeps drawing through the DLSS presentation route for a moment, and that route applies sharpening itself. The hook log still reported those frames as not sharpened (`PostProcess: DX12 still not correcting reason=left-before-decision`, 4800 frames in one session) although the picture was sharpened. Frames sharpened by another route in the same present now count as sharpened.

- **FPS limiter halved the frame rate while DLSS frame generation was enabled but generating nothing (DirectX 12):** in menus and loading screens a game can keep DLSS frame generation switched on while it presents only its own frames. The limiter still paced the game at the rate frame generation would multiply, so in The Talos Principle with a 120 fps capture sync the menu ran, and was recorded, at 60 fps for 7 seconds. CaptureEngine now treats DLSS frame generation as idle only when two independent proofs agree: for 12 frames the DLSS runtime reports no interpolated frames, and over the last 16 game frames about one image reaches the screen per game frame, so entering a menu raises the cap within a few tenths of a second. Both are needed, because with hardware flip metering DLSS reports one presented frame while it does generate. The game frames are counted from the game's own Reflex present markers, so this also works after switching from FSR to DLSS frame generation, where DLSS presents every image from its own thread and the game's present never reaches CaptureEngine's present hook. While idle, the limiter paces the game at the full target, and the driver's Reflex frame interval asks for the frame-generation factor on top, so a driver that divides its interval by that factor lands on the target too. When generation resumes, the halved pace returns within a few frames. The hook log reports each change of the runtime's report (`[DLSSG HEALTH] ON but idle for pacing` / `interpolating or off for pacing`) and of the measured image rate (`FG: DLSS-G output ratio ...`), and the limiter names the proof when both agree (`fgProof=dlss-g-idle`).

- **Inject recordings froze for about a second when FSR frame generation was switched on in AV1 recordings (DirectX 12):** switching frame generation on replaces the game's swapchain, and CaptureEngine can only start capturing the new one once the recorder has let go of the old swapchain's last frame. The recorder lets go of a frame when the GPU has finished reading it, and it checked that only when it encoded a frame. While the game's picture paused for the switch, the recorder repeated the last frame, and AV1 repeats with NVIDIA are written without an encode. So the check did not run until the next real encode: in The Talos Principle the recording showed one frame for 0.96 s while the game was already presenting with FSR frame generation. The recorder now also checks after every repeat, so the old frame is released within one output frame. The hook log reports each such wait as one episode, with how long it took (`SharedCapture deferring resource reset ... (deferrals=... waitedMs=...)`, `resource reset proceeds after ...`), instead of 12 lines for the whole session.

- **Inject recordings froze for almost two seconds when switching from FSR to DLSS frame generation (DirectX 12):** after FSR frame generation is switched off, The Talos Principle renders on a different graphics queue than the one it presents from. CaptureEngine recognizes a game's own frames by the rendering work it submits on the presenting queue, so each frame looked like one inserted by a frame-generation runtime, and none was recorded. Under FSR, FSR itself identified every frame, but once its swapchain was gone nothing did: the game ran at a steady 120 fps without frame generation for 1.4 s while the recording showed one frame for 1.87 s, against a 219 ms pause in the game's own presents. Recording only resumed when DLSS frame generation started. Now, while no frame-generation runtime is active, every frame the game presents is recorded as its own, since nothing else can present. With frame generation active nothing changes. The hook log reports this case (`Present without counted command lists is capturable as an application frame`).

- **Inject recordings no longer open on an old frame followed by a jump:** the game starts handing frames to CaptureEngine as soon as recording is requested, while the recorder is still preparing, and the recorder started the video with the oldest of those waiting frames. In BioShock Infinite at 120 fps, the first frame of every recording showed the game as it was about 270 ms earlier. It also stayed on screen while the encoder prepared itself on that first frame (about 120 ms at 4K: opening the output file and compiling the color-conversion shaders). The video then skipped 12 frames to catch up and repeated 3 while its buffer refilled. Now the recorder starts with the frame that belongs at the recording's start time, drops the older waiting frames, and if only old frames are available it waits up to a quarter second for a current one, so a stalled game still starts recording. The encoder prepares the output file and conversion shaders during the hidden warm-up, so the first frame encodes as fast as any other. The recording's frame clock now starts at the moment that first frame was picked, not a few milliseconds later when it had been encoded, so the second frame follows it directly instead of skipping one. Screen capture (WGC, DXGI duplication) also compiles the conversion shaders during its warm-up now, so its first frame no longer pays for them either. The media log reports the start frame's age and how many old frames were dropped (`Inject CFR start frame: ageUs=...`), any wait (`Inject CFR start waiting ...`), where the frame clock started (`Inject CFR live grid anchored at ...`), and the warm-up preparation (`Inject transactional video prewarm ...`, `[VideoPrewarm] inject ...`).

- **FPS limiter could skip one frame's pacing with FSR frame generation while another overlay is hooked (DirectX 12):** while the game's own Present into FSR frame generation owns the pacing, the frame-generation outputs pass the limiter, and a pass leaves a marker so the post-present step that follows belongs to that output. A present CaptureEngine forwards around a third-party overlay (such as the Steam overlay) passed without any post-present step, so the marker stayed set, and the thread's next real release - the game's own release after a nested present, or the first paced frame after frame generation was switched off - was taken for an output's and skipped. Only a pass with a matching post-present step sets the marker now, every limiter call clears it first, and the hook log's ownership lines count such unpaired passes (`unpaired=`).

- **Small memory leak at every recording start:** when a recording's first frame arrives, CaptureEngine sets the video encoder up again and replaced the previous, still unused encoder and container setup without freeing it, so every recording left a few kilobytes behind for the rest of the session. The previous setup is now released first.

- **Cursor and face camera ahead of the game picture in inject recordings:** when CaptureEngine delays the game picture to line it up with audio that arrives late (the measured audio capture latency), inject recordings still drew the cursor and the face camera for the undelayed moment. Both ran ahead of the game picture by that delay, and the face camera also ahead of the microphone. Each output frame now draws both for the same moment as its game picture, as WGC and DXGI duplication recordings already did. Recordings without that delay are unchanged.

- **Automatic encoder choice (`[Video] encoder=auto`) stopped working once the first frame arrived:** CaptureEngine sets the encoder up again for a recording's first frame and when the game's picture switches between 8-bit, 10-bit and HDR, and that forgot that the encoder was chosen automatically. An encoder that then failed to open at the recording's real size or settings was no longer replaced by the next one, so the recording failed, and a GPU first known at that point no longer decided the encoder. The automatic choice now survives these restarts; the media log shows `[EncoderAuto] reinit: request=auto kept ...`.

- **`backbuffer_count` did nothing in 64-bit DirectX 10/11/12 games while the Steam overlay or another overlay was loaded:** CaptureEngine limits the flip queue by adding a frame-latency waitable object to the game's swapchain. That is only safe while it can also correct the game's later resize calls, which Windows would otherwise reject. With an overlay loaded it has to hook the resize functions below the overlay's own patch, and that hook never installed: the resize functions in current Windows (10.0.26100) begin with a stack setup CaptureEngine's hook installer did not recognize (`Prolog at ... is not a recognized stack shape`). So the setting was silently withheld in every such game (Talos, Strange Brigade and the test apps in all recent logs), while games without an overlay worked. The installer now recognizes that setup, accepting it only where it provably leaves the stack and every argument untouched. A second cause hit games that ship their own `dxgi.dll` in the game folder, such as a ReShade proxy (The Witcher 3): the check that the resize function belongs to Windows' DXGI asked for "dxgi.dll" by name, got the proxy, and rejected the real function. It now checks against the system DXGI image. 32-bit games, Direct3D 8/9, DirectDraw and Vulkan apply the setting their own way and were not affected. The hook log shows the result in `resize flag reconciliation ready ... site=body-below-entry`.

- **Misleading render-ahead and queue-depth messages in the hook log (DirectX 10/11/12):** when a game's swapchain had no frame-latency waitable object (Strange Brigade DX12 with the Steam overlay, for example), CaptureEngine still tried to set the swapchain's maximum frame latency, which Windows always rejects there (`SetMaximumFrameLatency(1) failed hr=0x887A0001`), and reported every skipped `backbuffer_count` pacing wait as "requested by the application", the opposite of what had happened. `cpu_prerender_limit` itself was enforced all along by CaptureEngine's own render-ahead limiter (in that session on every frame). CaptureEngine now reads the swapchain's real flags first: it skips the call that cannot succeed and says which mechanism enforces the limit instead, and the pacing message names the actual reason: an older bitblt-model chain (BioShock Infinite DX11, for example) carries `backbuffer_count` as its buffer count and needs no pacing, a flip chain with more buffers than configured and no waitable cannot be limited, and otherwise the waitable is the application's own.

- **Judder in recordings with DLSS multi frame generation (inject capture, DirectX 12 and Vulkan):** with 3x and 4x MFG in The Talos Principle, recordings had stretches with up to 40 repeated and 40 skipped frames per second, although the encoder was nearly idle and no overload was reported. CaptureEngine spreads the generated frames NVIDIA hands over in a burst onto evenly spaced timestamps, and that clock could fall up to eight frames behind the moment a frame was actually handed over. Frames then reached the recorder after their own timestamp, too late for the slot they belonged to, so it repeated the previous frame and skipped one on the next slot. A frame's timestamp can no longer be earlier than its hand-over, so every frame arrives with the intended head start, and in those stretches video no longer runs up to about 27 ms ahead of the audio. The hook log's `Final Streamline output ... planned` line counts these corrections (`causalAnchors`, `maxCausalAnchorUs`); the Vulkan layer's line counts them too.

- **Repeated and skipped frames in inject recordings while the GPU was still copying the newest frames:** the recorder skips frames whose GPU copy is not finished yet, but it only ever held back the single newest one, because it sized that from a check that never waits. Under DLSS multi frame generation the newest two or three copies were often still running. Picking one of them made the recorder repeat the previous frame and then skip that frame on the next slot. It now holds back exactly the frames whose copy is provably still running and records the newest finished one instead. This applies to every inject capture, including FSR frame generation. The media log reports it (`Fence tail extended over in-flight inject copies`, `pendingCopyTail=` in `[Inject CFR] Repeat pressure`, `PendingCopyTailTicks`/`PendingCopyTailPeak` in `[Inject CFR QUALITY SUMMARY]`).

- **Hook log overstated CaptureEngine's cost with FSR frame generation:** the `[OVERLAY COST] FFX proxy Present` diagnostic counted the FPS limiter's intentional waits as CaptureEngine and AMD processing time (about 1.9 ms and 3.7 ms per frame in GTA V Enhanced). It now measures only the work around the wait, so the numbers show the real cost.

- **Frozen "ghost" overlay above the live one when FSR frame generation pauses (GTA V Enhanced quit dialog, DirectX 12):** pressing Alt+F4 in GTA opens a quit dialog that pauses FSR frame generation, and an old copy of the overlay appeared on top of the live one, which kept updating underneath. The old copy came from the very start of the FSR session: CaptureEngine had drawn it into its own stand-in UI texture, the game later used its own, and when the dialog switched back AMD blended the stand-in with its 55-second-old content over the picture. CaptureEngine now clears its stand-in texture whenever it moves the overlay onto the game's frame for paused or starting frame generation.

- **FSR frame generation pacing fix did not engage in GTA V Enhanced (and any game that could not reach the cap before):** with a 120 fps limit and FSR frame generation off, GTA only reached about 62 fps, and the limiter read every frame as a slightly missed deadline. It built up a safety reserve of almost a whole frame, kept it when FSR frame generation was switched on, and as a result never started the game's next frame after FSR's generated frame. Frames that are simply too slow for the cap no longer count as missed deadlines, and the limiter starts fresh whenever the cap, the frame-generation factor or the frame-generation state changes.

- **Uneven frame times with FSR frame generation and the FPS limiter (DirectX 12):** at a 120 fps cap the generated frames reached the screen about 1.4 ms later than the real ones, so frames alternated roughly 6.5 and 10 ms apart instead of 8.3 ms, with or without V-Sync. CaptureEngine let the game start its next frame the moment FSR took the previous one, and AMD's presentation of the generated frame then waited on the GPU behind the game's new work. The game now starts its next frame right after FSR has presented the generated frame(s) of the previous one, which also shortens how long a finished frame waits; it is never released so late that its frame could miss its slot. The hook log summarizes it every 600 frames (`FPS Limiter: frame-generation release ... byOutputs= byBound=`).

- **Overlay showed too few displayed frames with frame generation ("Base/Display" and the latency estimate):** with FSR frame generation at a 120 fps cap the overlay read "60 / 101 FPS" while 120 frames per second reached the screen, because the displayed rate came from the middle value of recent frame intervals, and with frames shown alternately 6.5 and 10.1 ms apart that middle value is one side of the pattern. The displayed rate is now the average interval (long hitches still left out), so it reads 120, and the latency estimate's frame-generation hold uses the same correct interval.

- **The render-ahead limit (`cpu_prerender_limit`) did nothing in Strange Brigade (Vulkan) and similar Vulkan games:** CaptureEngine applies the limit by adding a small marker to the game's graphics queue at each present and waiting until the GPU has finished an earlier frame. It skipped that whenever another thread of the game also submitted work, a check meant for the frame limiter that had nothing to do with whether the marker is safe. Strange Brigade presents from its graphics queue while a second thread submits too, so the limit never took effect and latency stayed at about 55 ms with or without it. Vulkan already guarantees CaptureEngine exclusive use of that queue during the present call, so the marker is now added there regardless of other threads. Games that present from a separate compute queue keep the previous rules, and CaptureEngine now also notices when their rendering moves to another thread after startup. This works the same whether the NVIDIA driver presents Vulkan natively or through a DXGI swapchain. For Vulkan, the `prerender_wait_us` column of `perf_metrics_*.csv` now shows how long the limit held the game back (it was always 0), and the Vulkan layer log adds a summary every 10 seconds (`Vulkan Prerender: summary`).

- **The overlay showed the refresh rate instead of the game's frame rate when Windows composes a game:** with the frame-time source set to screen changes, a game the desktop compositor draws (no tearing, at most one new picture per refresh) has no screen changes of its own; the compositor's are its refresh rate. Mirror's Edge on DXVK ran at about 925 fps with vsync off, but the overlay showed 144 fps and a flat graph, which looked like vsync. While a game is composed, all frame-rate figures now follow the game's own presents again: FPS, 1% and 0.1% lows, frame-time variation and graph, the benchmark's display frame times and the frame-rate columns of `perf_metrics_*.csv`. Latency still uses the compositor's screen times. As soon as the game's frames reach the screen as flips of their own, the overlay returns to screen changes. The hook log's frame-timing-source line says when this applies (`composed=1`).

- **FPS and frame-time graph jumped between the real screen rate and the game's present rate when Windows composes a game:** when the desktop compositor draws a game's frames instead of showing them directly (no tearing, at most one new picture per refresh), the overlay takes its screen times from the compositor. A single stray flip of the game's own ended that, although the compositor was still showing the game, and for the next 10 seconds the overlay received no screen times at all and showed the game's present rate instead. In Mirror's Edge on DXVK the overlay switched between 144 fps (the actual screen updates on a 144 Hz display) and about 460 fps (presents that never reached the screen) with a 9-second hole in its timing. The composed state now ends only when the game's own flips complete and the compositor no longer shows its frames, and it resumes immediately when the game is composed again. The sensors log notes once per composed stretch when the game's own flips were ignored this way, and the line that ends the state counts how often that happened (`refusedStops`).

- **DXUP's Direct3D 9 was reported as DXVK:** CaptureEngine called every Direct3D 9 DLL from outside the Windows system folder "DXVK", so the hook log of a game running DXUP's Direct3D 9 (Mirror's Edge, for example) said `dxvkD3D9=1`. CaptureEngine's handling of such a DLL is unchanged and correct for any translation layer: it never probes it with a test device. The log now names the actual runtime (DXVK, DXUP or another replacement, read from the DLL's version information), and only a real DXVK DLL gets the "(DXVK)" overlay label. The check is also remembered per loaded DLL instead of reading the DLL's path on every frame in Direct3D 9 games.

- **The Direct3D 11 overlay could unbind a game's extra render targets:** before drawing, it saved and restored only the first of the render targets the game had bound at Present and unbound the others. A game that relies on its multiple render targets staying bound across Present lost them. All of them, the depth buffer and every viewport are now put back.

- **Flickering overlay and wasted CPU time with DXUP's Direct3D 11:** DXUP's Direct3D 11 reports the back-buffer number of the Direct3D 12 swapchain beneath it (0, 1, 0, 1, ...), but like Windows' own Direct3D 11 it lets the game draw only into buffer 0. CaptureEngine drew the overlay on the reported buffer: with DXUP 1.1 every second frame's buffer was refused, so the overlay was missing from every second frame and each miss cost a failed lookup and two log lines (3,388 of 6,788 frames in Mirror's Edge with all DXUP files installed); with older DXUP versions it drew into a buffer DXUP then overwrote, and rebuilt its drawing target on every frame (16,000 times in a 40-second menu session at 450 to 750 FPS). Inject recordings and screenshots read the same refused buffer. The overlay, sharpening, recording and screenshots of Direct3D 10 and 11 games now always use buffer 0, the one the game draws into, and keep one drawing target per swapchain. Windows' own Direct3D 11 and DXVK always report buffer 0, so games without DXUP behave as before. A target that cannot be built is logged once per change with a repeat count instead of on every frame. Heroes of the Storm on DXUP was affected too; Direct3D 12, 9, 8 and DirectDraw were not.

- **Washed-out screenshots with ghost text in some games:** screenshots of 8-bit SDR games kept the alpha channel of the game's image, which is not part of the picture: the display ignores it and games leave anything there. BioShock Infinite, for example, keeps stale loading-screen text in it, so its screenshots looked partly transparent, bright and washed out, with faint "Loading..." and location text over the scene. Screenshots are now always saved fully opaque, exactly as the image appeared on screen. When a source had non-opaque alpha, the log notes it (`[Screenshot] Source alpha ignored`).

- **Tray and hotkeys froze for a quarter second on every configuration change:** after `config.ini` changed, CaptureEngine's main thread waited for the injection helper to confirm the reload, and that helper only looked for new commands every 250 ms (100 ms while a game ran), so tray menu and global hotkeys stopped responding for 250-313 ms each time. The same wait delayed every hotkey the helper confirms, such as the overlay toggle. The main process now wakes the helper the moment it sends a command, so only the reload itself remains (about 75 ms).

- **The render-ahead limit (`cpu_prerender_limit`) did nothing in Direct3D 10 games:** when the game's swapchain had no frame-latency wait object, CaptureEngine applied its own limit to Direct3D 11 swapchains only, and on Windows 10 and later it also mistook a Direct3D 10 swapchain for a Direct3D 11 one. Limits of 1-6 now set the Direct3D 10 device's own frame latency, which the graphics runtime enforces, and a limit of 0 waits for the GPU before each frame is presented. The hook log names the path once per swapchain and limit (`Prerender limit N on the d3d10 path`).

- **Direct3D 11 games running on DXVK were treated as Direct3D 10:** DXVK's Direct3D 11 devices also answer as Direct3D 10 devices, and since a fix for Direct3D 10 games in May CaptureEngine took every device that answers as both for Direct3D 10. Where CaptureEngine's Direct3D hooks rather than its Vulkan layer handled such a game, the overlay said "DX10 (DXVK)" and the Direct3D 10 overlay, capture and screenshot paths ran. A device that answers as both is now Direct3D 10 only when a Direct3D 10 runtime is loaded and the device runs at a Direct3D 10 feature level, which holds for real Direct3D 10 games on Windows and on DXVK. The hook log notes the decision once per swapchain (`[GraphicsAPI] swapchain=... answers ID3D10Device and ID3D11Device`).

- **The overlay named a newer Direct3D 11 version than the game uses:** CaptureEngine raised a game's label to "DX11.1" up to "DX11.4" whenever anything asked its device for a newer interface: CaptureEngine itself (with a render-ahead limit of 1-6, every Direct3D 11 game showed "DX11.4"), the graphics runtime, Windows components or another overlay. Only the game's own requests count now; the hook log names the module behind every request it ignores (`D3D11.N use ignored`) and behind every one it counts.

- **vkd3d-proton games showed "DX12" instead of "DX12 (VKD3D-Proton)":** the Direct3D 12 overlay recognized only Wine's vkd3d, and one of its drawing paths always said "DX12". All Direct3D 12 overlay paths now name vkd3d-proton the way the Vulkan overlay already did.

- **Games running on DXUP showed "DX12" instead of their own API:** DXUP translates DirectDraw (with Direct3D 6 and 7), Direct3D 8, 9 and 11 to Direct3D 12, and CaptureEngine's overlay sits on its Direct3D 12 output, so every DXUP game said "DX12". The overlay now names the game's API with the translator, at the detail CaptureEngine recorded for it: "DX7 (DXUP)", "DX8 (DXUP)", "DX9Ex (DXUP)" or "DX11.1 (DXUP)", for example. This includes games whose overlay CaptureEngine draws on DXUP's Direct3D 11 output: a 32-bit Direct3D 9 game such as Mirror's Edge showed "DX11.1 (DXUP)" and now shows "DX9 (DXUP)". The same holds with only DXUP's `d3d9.dll` next to the game, where DXUP draws through Windows' own Direct3D 11: Mirror's Edge showed "DX11" that way. DXUP's own requests to its Direct3D 11 no longer count as the game's. DXUP is recognized by the product name in its DLLs' version information, so other DLLs with the same file names (ReShade's `d3d9.dll` or `dxgi.dll`, for example) keep the game's own label.

- **Direct3D 10.1 games could fail to start with CaptureEngine running:** when a game loaded the Direct3D 10.1 runtime, or any other module that brings Direct3D 11 in with it, after CaptureEngine had started, CaptureEngine redirected that module's Direct3D 11 device creation to its own wrapper before it knew where the real function was, so every device creation failed (`E_FAIL`). CaptureEngine now looks the real function up first and leaves the module alone when it cannot; the hook log notes it (`D3D11 originals resolved on the load of module`).

- **Forced AF stopped following texture and shader changes in Direct3D 11 games CaptureEngine joins after they started:** when CaptureEngine reaches a game's Direct3D 11 rendering through hooks on the real device context (after a late injection, for example), those hooks sat in the context's function table, which Direct3D 11 itself rewrites while the game runs. From the first flush of each frame on, the game's draws bypassed CaptureEngine, so forced AF stayed as decided at the last sampler change: a texture or pixel shader the game switched to without changing samplers kept the previous decision, and textures that must keep their own filtering (single-mip textures, explicit-LOD sampling) could get AF. A game that turned on Direct3D 11's multithread protection or swapped device context state also bypassed CaptureEngine's sampler, shader and texture hooks, so its samplers reached Direct3D without AF and reading them back returned CaptureEngine's version. CaptureEngine now gives each such context a function table of its own that hands every call on to whatever Direct3D 11 currently uses, so Direct3D's own rewrites can no longer remove CaptureEngine's hooks. Tables are returned when the game destroys the context. The hook log names each context it switches over (`[D3D11 DISPATCH] adopted`) and any it cannot (`kept, slot hooks instead`).

- **The performance log of Direct3D 11 games showed only Direct3D's own present time:** with debug logging, CaptureEngine writes a per-frame performance table (`perf_metrics_*.csv`). For a Direct3D 11 game presenting through CaptureEngine's stand-in for its swapchain (BioShock Infinite, for example), the table's one row per frame came from an inner hook that saw only the real present: `total_us` was Direct3D's own time, and every column for CaptureEngine's work stayed zero. The row now comes from the outer hook and splits the frame into CaptureEngine's overlay drawing (`overlay_us`) and its GPU time (`overlay_gpu_us`), the recording's frame copy (`capture_us`), CaptureEngine's work before and after the present (`pre_present_us`, `post_present_us`) and the present itself (`present_call_us`). The GPU time is measured only while the table is written and never makes the game wait.

- **The performance log stayed empty for Direct3D 11 games that present with `Present1`, and showed only the frame time for those CaptureEngine hooks on the real swapchain:** a Direct3D 11 game that shows its frames through the newer `Present1` call (instead of `Present`) got no row at all in `perf_metrics_*.csv`, whether it presented through CaptureEngine's stand-in for its swapchain or through CaptureEngine's hook on the real swapchain. A `Present` that CaptureEngine reached through that hook got a row with only `total_us`, every column for CaptureEngine's work at zero. Each such frame now gets its row with the same columns as a stand-in's `Present` (overlay, its GPU time, the recording's frame copy, CaptureEngine's work before and after the present, the present itself), Direct3D 10 games alike. The hook log names the hook that writes these rows (`[PERF CSV]`).

- **The Direct3D 12 timing summary in the hook log showed meaningless present phases:** with debug logging, CaptureEngine logs a `[PERF] DX12 Present summary` line for every 32 sampled presents (one in 64), averaging how long each step of its swapchain stand-in's present took. Since 2026-10-12 the clocks of `metrics_update`, `process_frame_external`, `fps_limiter` and `present_call` never started in a Direct3D 12 game, so those averages (and the `present_call` maximum) were the machine's absolute clock cut to 32 bits, arbitrary figures that were often negative or thousands of seconds, and `swapchain_acquire` was always 0. Each step is now timed from its own start, and only on the presents that feed a summary sample.

- **Direct3D 11.1 to 11.4 device functions failed in games whose device CaptureEngine wraps:** when CaptureEngine intercepts a game's Direct3D 11 device creation (for example in BioShock Infinite), the game talks to CaptureEngine's stand-in for the device. That stand-in told the game it supported the newer device versions 11.1 to 11.4, but then failed every function those versions add (such as `CreateBlendState1`, `CreateDeferredContext1` or `CreateDeviceContextState`) with "interface not supported", because it had kept only the newest version the real device offered. A game using them could lose rendering features or fail to start. Each version is now forwarded on its own.

- **Steam overlay still missing in BioShock Infinite on some launches:** Steam only hooks a DXGI factory's swapchain creation while the factory's function table still points into Windows' own DXGI, so with the Steam overlay loaded CaptureEngine intercepts swapchain creation further inside those functions and leaves the table alone. When the game was still starting threads at that moment, CaptureEngine's hook was refused once and it took the factory's function table instead for the rest of the session. Steam then skipped every factory, as its own log shows (`points to another module, skipping hooks`), and never drew. These two hooks now retry the way the Present hook already did; the last attempt still proves that no thread is executing the code being changed. The hook log states when a refusal still leaves the table to CaptureEngine.

- **BioShock Infinite crashed with forced anisotropic filtering ("Rendering thread exception: Fatal error!"):** shortly after loading a save the game stopped with its own error dialog. BioShock creates a new Direct3D 11 sampler on almost every draw for each texture that is still streaming in (with that texture's detail-level limit and fade bias) and releases it right after. CaptureEngine kept the anisotropic replacement it made for each of these samplers until the AF setting changed, so within a minute the replacements used up Direct3D 11's limit of 4096 sampler objects per device. The game's own sampler creation then failed, its retry after freeing its own unused samplers failed too, and it crashed. A replacement now lives exactly as long as the game sampler it stands in for, plus a small per-context cache, so CaptureEngine's share follows the game's own samplers instead of growing. Each texture still gets anisotropic filtering with its own detail limit and bias, the same textures as before stay protected, and finding an existing replacement no longer means scanning every replacement made so far, which got slower with every new sampler. Every 10 seconds the hook log reports how many replacements were created and reused and how many game samplers hold one (`[D3D11 AF REPLACEMENTS]`), and it now logs every failed sampler creation of the game (`Game CreateSamplerState failed`), not only those CaptureEngine had changed.

- **Changing Direct3D 11 forced AF altered texture mip bias:** an AF-level change could apply the configured mip-bias offset or SGSSAA adjustment a second time. Samplers now retain the application's requested descriptor so changed settings are applied once, including when changing or removing an offset while AF remains active. Both the device-wrapper and raw-hook paths use the same correction.

- **WGC/DXGI recording stopped after a resize:** switching the smoothness buffer between YUV and RGB storage could be mistaken for a changed recording bit depth. Size changes now keep the configured output depth and continue through the existing geometry-fitting path; actual HDR or automatic output-depth changes still end the recording safely.

- **Face-camera crash while delayed recording starts:** growing the camera-frame history to cover the screen-capture delay could read a freed history entry. The selected frame and its timestamp now remain valid while the history grows.

- **Forced AF forgot its replacements at every resize in Direct3D 11 games CaptureEngine reaches through hooks:** before a swapchain resize CaptureEngine dropped everything it knew about each rendering context, also on other threads. A sampler the game was binding at that moment on another thread could be lost, and afterwards a texture that must not get anisotropic filtering (for example one with a single detail level) could keep CaptureEngine's replacement until the game bound that sampler again. A resize now only makes CaptureEngine let go of its references to the game's textures, which is what the resize needs, and keeps the rest; a context that has not been used since the previous resize is still forgotten entirely, so a destroyed one cannot keep its device in memory.

- **Texture sampling settings lost after a rendering-state reset with forced AF:** in Direct3D 11 games that CaptureEngine reaches through hooks on the real device (for example after a late injection or through a translation layer), a game that reset its rendering state and then bound the same sampler again could have that bind dropped while forced anisotropic filtering was on, so the texture was drawn with Direct3D's default sampler (other filtering and wrapping) until the game changed samplers. CaptureEngine now also follows the state resets it previously did not see (clearing the state, finishing or executing a command list, swapping the context state), and a new deferred context no longer inherits what CaptureEngine knew about an earlier one at the same address. The game also reads back its own sampler instead of CaptureEngine's anisotropic replacement on this path, as it already did otherwise.

- **Steam overlay missing in 32-bit and Direct3D 11 games:** in BioShock Infinite (32-bit, Direct3D 11) the Steam overlay never appeared while CaptureEngine was injected, for two reasons. On 32-bit games CaptureEngine hooked the start of DXGI's Present function, because it could only intercept that function further inside on 64-bit, and Steam leaves a function alone whose start already jumps somewhere else. CaptureEngine now intercepts Present on 32-bit games below the function start as well, after the instructions an overlay overwrites, and leaves the start to Steam and other overlays as it already did on 64-bit. Where a function's start does not have the expected form, it keeps hooking the start as before, and the hook log says so (`DeepHook(x86)`). Second, when a Direct3D 10 or 11 game created its swapchain while Steam was loaded, CaptureEngine handed Steam its own stand-in object instead of the real swapchain. Steam then expected the game's frames on the stand-in while they arrived on the real swapchain, so it never drew. Direct3D 12 games already got the real swapchain once CaptureEngine saw every Present below the other overlays. Direct3D 10 and 11 games now get it under the same condition, provided CaptureEngine also intercepts the swapchain's resizes there, which is where it lets go of the back buffer its own overlay draws on. The hook log states the decision for each swapchain and which part was missing. In addition, CaptureEngine's hooks for Present1 and for swapchain resizes below the other overlays could be refused for the whole session when the game happened to be starting threads while they were installed. They are now retried like the Present hook already was. CaptureEngine's overlay is then drawn last, on top of Steam's.

- **Two hook-log lines per frame in Direct3D 11 games with the overlay:** the overlay wrote a line before every draw (BioShock Infinite: 34,000 lines and 3 MB, 92% of its hook log, in 85 seconds). It now logs the first frames, then only when the device, context or render target changes, and otherwise every 10,000 frames with a count of the skipped lines.

- **Per-frame work and a fast-growing log with Direct3D 11-to-12 translation layers:** when a game created its first Direct3D 11 device and swapchain through a translation layer's own export (seen with Heroes of the Storm and DXUP installed in the game folder), a diagnostic that tracks who holds swapchain references patched the translator's swapchain class for the whole session. CaptureEngine could then no longer remember that the game's swapchain only forwards to the translator's real one, so on every frame it re-checked this on the game's render thread, retried a refused hook and wrote one log line (27 MB in 20 minutes). The diagnostic now applies only to DXGI's own swapchains, a refused hook is retried only after its slot changes, and the warning is logged once per change with a count.

- **Smoothness buffer back to full RGB after a capture recovery:** when WGC or DXGI duplication capture recovered (for example after a display change), the buffer dropped the NV12/P010 setting and the video memory reservation mode, so the rest of the recording used more video memory. Both settings now survive the recovery.

- **Face camera ahead of the microphone in WGC and DXGI duplication recordings:** the camera picture always showed the newest camera frame, while the screen and the microphone audio of each output frame are delayed by the smoothness buffer (up to 300 ms), so lips moved before the voice. Each output frame now shows the camera frame taken at its own content time, from a short history of recent camera frames on the GPU. The face-camera log line reports the remaining offset (`slotLagUs`).

- **Possible corrupted frames in WGC and DXGI duplication recordings:** the capture thread and the video encoder issued GPU commands on the same Direct3D 11 context without coordinating, so one thread's render target or shader setup could in rare cases land in the middle of the other's draw. Both now take the same lock around these commands. Found in code review, not in a recording log.

- **Late-loaded Unreal modules missed during discovery:** a full console-variable scan now preserves module notifications that arrive after its snapshot, so modules loaded while the scan is running still receive their configured overrides. Failed module enumeration remains eligible for retry, with repeated failures summarized in the log.

- **Sampler overrides applied twice through Direct3D 11 to Direct3D 12 translation:** when a translator creates a native sampler inside a Direct3D 11 sampler call, CaptureEngine now keeps the Direct3D 11 policy in charge. The native descriptor preserves shader/resource safety decisions and does not add the configured mip bias again. Direct3D 11 bind-time AF replacements also preserve mip settings already applied at creation under the same configuration; samplers created before interception keep the existing fallback.

- **DirectX 12 inject recording across swapchain replacements:** when a game replaced its swapchain, for example while switching between DLSS frame generation and FSR frame generation, and Windows happened to place the new swapchain at the old one's memory address with the same size and format, inject capture kept treating it as the old swapchain. The recording then kept the previous swapchain's capture setup instead of starting a fresh one, so capture that depends on the new swapchain's own command queue (such as FSR frame generation's final-output capture) could stop delivering frames. Whether it happened depended on memory allocation luck. CaptureEngine now marks each swapchain it captures from without holding on to it, so every new swapchain reliably gets its own capture setup. The hook log reports when a new swapchain reuses the captured one's address.

- **Encoder overload while the GPU is busy (NVIDIA):** recordings could fall below their frame rate and repeat frames whenever the game kept the GPU busy, even with the fastest encoder preset, although the encoder itself had capacity to spare. CaptureEngine's small per-frame GPU conversion has to wait its turn behind the game's rendering, and the encoder only allowed about two frame intervals for that wait before every new frame stalled. The encoder now keeps enough frames in flight to absorb about 100 ms of waiting at any frame rate (13 frames at 120 fps instead of 3). This costs extra video memory for the queued frames (about 25 MB per frame at 4K 10-bit) and adds the same small delay before packets reach the file or stream; recorded timing, frame order and audio sync are unaffected. Setting `surfaces` in the custom encoder options overrides the depth. Screen-capture audio no longer counts frames that are merely waiting inside the encoder as lost video.

- **Inject capture overloaded the encoder at presets DXGI desktop duplication handles (NVIDIA):** with inject capture, a heavier encoder preset could make the recording repeat frames although the encoder was not fully busy, while DXGI desktop duplication sustained even heavier presets at the same resolution and frame rate. On NVIDIA, the Windows video processor that converted each frame to the encoder's YUV format only finished once the hardware encoder had worked off its earlier frames, so CaptureEngine's conversion and the encoder kept waiting for each other. CaptureEngine now converts SDR frames to NV12/P010 with its own GPU shaders, as it already did for HDR, keeping the same color matrix (BT.709, or BT.2020 when configured), the configured full or limited range and left-sited chroma; game frames in RGBA order no longer need an extra full-frame channel-swap pass. Scaled recordings and 16-bit floating-point sources still use the video processor. The copy of each frame kept for repeating it under overload is now taken before the frame goes to the encoder instead of after, because reading a frame the encoder already owns also made CaptureEngine's GPU work wait for the encoder; this applies to every capture method. In addition, to know when it may hand each game frame buffer back, CaptureEngine signaled a GPU fence after reading the frame and pushed that work to the GPU on its own, ahead of handing the frame to the encoder. On NVIDIA, each such extra GPU submission held CaptureEngine's following GPU work until the encoder had finished up to two earlier frames, so every conversion waited for the encoder and the encoder for the conversion, and the encoder sat partly idle while frames queued up. CaptureEngine now marks the end of its reads with a GPU query that travels with the encoder hand-off instead of a submission of its own, and that only the encoder's own thread checks, between frames, so it never interferes with the hardware encoder's use of the GPU device; it marks it before handing the frame to the encoder (which also returns the game's frame buffer sooner), and no longer queues a redundant GPU wait for a game frame it has already confirmed finished on the CPU. The sensors log's encoder-workload lines no longer include stray single-poll windows with near-zero activity.

- **Encoder idle time between frames while the game keeps the GPU busy (NVIDIA):** with NVENC, any GPU work CaptureEngine queued right after handing a frame to the encoder waited until the encoder had finished that frame. Between frames the encoder therefore sat idle for CaptureEngine's next conversion, plus however long that conversion waited behind the game's rendering. Without a heavy game this cost about 2% of the encoder's capacity; with a game saturating the GPU it could make recordings repeat frames again. NVENC now runs on its own Direct3D 11 device. CaptureEngine converts each frame on its own device, the encoder reads the result through shared textures, and a frame goes to the encoder only after CaptureEngine has seen its conversion finish on the GPU, which normally requires no waiting. Nothing on CaptureEngine's GPU queue waits for the encoder any more; this also covers scaled recordings and 16-bit floating-point sources, which still use the Windows video processor. Each frame now reaches the encoder about one frame interval later than before, or at most about 33 ms later when the GPU is very busy. Recorded timing, frame order and audio sync are unaffected. If the shared textures cannot be set up, the encoder keeps sharing CaptureEngine's device as before, and the media log says why. The per-second encoder timing line shows how many frames are waiting for their conversion and how long CaptureEngine had to wait, if at all.

- **Screen capture on PCs with two GPUs:** for Windows Graphics Capture and DXGI desktop duplication, CaptureEngine created its GPU device on whichever graphics adapter Windows lists first. On laptops with integrated and NVIDIA or AMD graphics, that is usually the integrated GPU, where NVENC or AMF cannot run, so such recordings could fail to start. On desktops with two graphics cards, the recorded monitor could be attached to the other card, which forced a copy of every frame between the cards and made DXGI desktop duplication unavailable. CaptureEngine now picks a GPU that can run the configured encoder and, among those, prefers the one driving the recorded monitor. The media log names the chosen GPU and says whether frames still have to cross between GPUs. PCs with a single GPU are unchanged.

- **Media Foundation recordings could show a later frame's content:** FFmpeg's Media Foundation encoder hands each frame to the hardware encoder and immediately returns the frame's GPU texture to the shared pool. The hardware encoder works asynchronously, so CaptureEngine could write its next conversion into a texture that had not been encoded yet. CaptureEngine now keeps every Media Foundation input frame until the encoder has returned that frame's packet. Media Foundation also gets the separate encoder device described above, because on NVIDIA it runs on the same hardware encoder.

- **Builds fetched FFmpeg's full history although the source was already at its pinned version:** before reusing the FFmpeg source checkout, `python build.py --skip-updates` checks that it sits on the pinned commit. The MSYS2 git the build runs strips braces from its command-line arguments, so that check never matched, and every build that reached it (for example the first build in a fresh checkout) ran a full `git fetch --unshallow` of FFmpeg's history, which is slow and fails without network access. The check now passes git an argument it receives unchanged, so a checkout already at the pin is recognized locally without any network access, and moving to a pin whose commit is already present no longer fetches either. The build log says when a pinned commit is genuinely missing and history has to be fetched.


### Changed

- **Programs that use `cengine.dll` run the engine inside their own process (`[Runtime] isolated_helpers`):** game injection, recording and encoding, and log collection run as threads of the program that loads the engine, so it needs no CaptureEngine process for them. The CaptureEngine app itself keeps its separate `captureengine.exe` helper processes, so a crash in capture or encoding ends only that helper and every recording starts in a fresh process; `isolated_helpers=off` runs the app in-process as well (for testing), `on` forces separate processes for any program (programs can ask for them with `CE_FEATURE_ISOLATED_HELPERS`). Two things still start their own processes: recording a single application's audio (one short-lived worker per captured application, because tearing down Windows' per-application audio capture can crash the process that owns it) and the hardware sensors. An in-process program keeps its own process and GPU scheduling priority unless it opts in (`CE_FEATURE_PROCESS_TUNING`). Log files keep their names (`inject.log`, `media_<id>_<pid>.log`, `logger.log`); the runtime log names each helper's transport at startup (`[Runtime] helper transports: ...`). A relative or empty recording or screenshot folder is resolved against the CaptureEngine folder, also when another program loads the engine.

- **The app now talks to its engine like any other program:** a few details changed with it. `--auto-record` no longer starts the recording process at launch; it starts with the first recording, like every other recording. The tray's "Start with Windows" checkmark shows whether the autostart entry is actually registered rather than the stored preference. If the sensor process cannot be stopped before the PawnIO driver is uninstalled, the tray now says that the uninstallation did not complete (before, only the log did). The app's own lines in `captureengine.log` start with `[Client:CaptureEngine]`.

- **Both FPS limiters default to `auto` (`[FpsLimiter] capture_sync_limiter_mode=auto`, `general_limiter_mode=auto`):** new installs used `basic`, so a game with its own NVIDIA Reflex was still paced by CaptureEngine's timer next to the game's Reflex. `auto` hands the cap to the game's Reflex while the game has it turned on (always the case with DLSS frame generation) and uses `basic` otherwise, including with FSR frame generation and on AMD and Intel graphics. With frame generation the configured value stays the displayed frame rate in every mode. Existing `config.ini` files keep the mode they name.

- **The `fg_fallback` FPS limiter mode is retired (`[FpsLimiter] capture_sync_limiter_mode` / `general_limiter_mode`):** it never paced differently from `basic` - every mode already treats the configured rate as the displayed rate and divides it by the active frame-generation factor - so it only made the choice look harder than it is. A `config.ini` that still says `fg_fallback` keeps exactly the same pacing as `basic` and logs one line per key saying the mode is retired. `auto` now chooses between the game's own Reflex pacing (when the game has turned Reflex on) and `basic`, and its log line names which limiter (capture sync, general, display ceiling) it decided for.

## v0.1.7154

Changes since [v0.1.7153](https://github.com/aufkrawall/capture-engine/releases/tag/v0.1.7153).

### Improved

- **Direct3D 9 capture bottlenecks easier to diagnose:** the media log now reports captures skipped because every shared texture was still in use, distinguishing textures held by the encoder from capture work still pending on the game's GPU. These counters were previously missing for GPU-only Direct3D 9 capture.

- **Less background work while no game runs:** with the elevation service, watching for game starts no longer switches on system-wide display timing tracing. Presents, GPU submissions and input reads of every application on the PC are traced only while the display-timing overlay actually needs them; game-start detection stays just as fast. Older installed services keep working with the previous behavior.

- **Faster inject capture for classic Direct3D 9 games:** games that use plain Direct3D 9 (not Direct3D 9Ex) could previously only be captured through a slow copy into system memory and back, which cost a lot of performance at high resolutions and frame rates. CaptureEngine can now hand their frames to the encoder entirely on the GPU, as it already did for Direct3D 9Ex games. It first checks that this works on the installed Windows version and for that game, and otherwise keeps the previous capture path. Games that create their Direct3D 9 device for multithreaded use are included too: while switching sharing on for a single texture, CaptureEngine holds Direct3D 9's own device lock so the game's other threads wait, and it keeps the previous capture path whenever it cannot verify that lock on the installed Windows version.

- **Capture cost visible for GPU-only Direct3D 9 capture:** the performance log now records how much time capturing takes per frame when a Direct3D 9 game is captured entirely on the GPU, including games whose overlay drawing moves capture into a later drawing step. Previously these frames showed no capture time at all. The hook log also summarizes the average cost every ten seconds while recording.

- **Faster Vulkan startup for other applications:** while CaptureEngine runs, Vulkan programs that are not CaptureEngine targets (browsers, chat clients, other games) no longer take a snapshot of every process on the machine when they initialize Vulkan. CaptureEngine's Vulkan layer now reads only the program's own parent and makes the same decision as before.

- **Stable release verification:** pre-release static analysis, exception safety and explicit pointer conversions now satisfy the required release lint ratchet.


### Fixed

- **Inject recording restart after a GPU stall:** restarting after a recording's final GPU reads timed out could let a shared texture be reused while the previous recording was still reading it, corrupting frame contents. Restart now preserves those reservations and continues from the metadata ingest cursor, discarding only unread old frames without adding a wait to recording startup.

- **Recorded video jumped between older and newer frames in very high frame rate games:** with inject capture, the encoder's GPU had not always finished reading a frame when CaptureEngine handed that frame's shared texture back to the game for the next capture. - **Recording and screenshot feedback:** controller intent, health and notification updates now reject incompatible or replaced inject mappings and release mappings on every failure. Regression tests cover reconnects and publication across Windows processes.

- **Recording start, stop and failure feedback:** controller actions now share one recording session, with regression coverage for pending cancellation, uncertain acknowledgements, late observations and audio-only fallback. A stop during child readiness cannot resume a cancelled start.

- **Recording and frame-generation regression contracts:** documented the state, resource lifetime and timing guarantees used to verify recording cancellation, overlay handover and encode recovery during the core refactor.

- **Screenshot controls use the controller API:** screenshot hotkeys now use a controller-owned engine handle and share screenshot notifications with API callers.

- **Streamline code comments and archive dated incident logs to wiki:** stripped historical session timestamps and diagnostic narratives across hook thread initialization, swapchain wrapper present tracking, DLSS frame multiplier defaults, and queue reinitialization while archiving durable architectural knowledge in `llm-wiki/log/recent.md`.

- **Modular encoder session summary structures:** decoupled capture session summary and starved episode telemetry structures into dedicated header `media_encoder_session_summary.h`, maintaining strict line ceiling limits across media encoder session state.

- **Typed descriptors for DirectX 12 focus-loss and swapchain policies:** replaced multi-boolean positional parameters across focus-loss overlay fence synchronization and non-presentable backbuffer hold checks with structured parameter descriptors `D3D12FocusLossImmediateFenceDesc` and `D3D12NonPresentableSwapchainHoldDesc`, isolating focus-loss synchronization logic into `focus_loss_policy.h`.

- **Structured D3D11 frame submission descriptor:** replaced the multi-parameter Direct3D 11 / WGC frame processing signature with structured parameter descriptor `D3D11FrameSubmissionDesc`, clarifying frame parameter passing across capture and encoding loops while retaining inline compatibility forwarders.

- **Type-safe video frame submission descriptor:** replaced the 14-parameter inject video frame processing call with structured parameter descriptor `VideoFrameSubmissionDesc`, improving readability and maintainability across encoder loops while preserving backward-compatible forwarders.

- **Encapsulate Streamline hook runtime globals:** grouped loose global interception targets, failure retry counters, viewport runtime states, and module teardown trackers into a unified `StreamlineHookState` structure.

- **Encapsulate DirectX 12 command queue interception state:** grouped loose global command queue dispatch tables, real function pointers, and command list execution tracking into a unified `DX12ECLState` structure.

- **Encapsulate DirectX 12 Post-Streamline runtime state:** grouped loose global PostSL flags, epoch tracking, cooldown counters, and synchronization mutexes into a cohesive `DX12PostSLRuntimeState` structure.

- **Encapsulate DirectX 12 overlay coverage state:** grouped loose global overlay coverage tracking variables into a cohesive, domain-owned `DX12OverlayCoverageState` structure.

- **Streamline diagnostic log metering resilience:** multi-stream change gates now resolve hash collisions across their fixed slot pool, keeping alternating call shapes independently metered.

- **Session logs are much smaller and easier to read:** lines that repeated unchanged every frame or every second (overlay submits, queue choices, frame-generation decisions, Streamline UI-tag records, controller loop timing, config re-reads for every whitelisted game) are now written when something changes, with a "(+N unchanged)" count instead of the copies. Each hook installation is one line instead of about twenty, the Steam overlay is reported once instead of on every hook pass, and FPS-limiter stats and Vulkan layer lines are no longer written to two files. Nothing that marks a change, a failure or a recovery was removed.

- **Shorter hook log lines:** `hook_debug.log` lines read `time T<thread> #<line> p<pid> message`. The line number counts per file, so a gap now always means a lost line, and each process's first line names its executable and pid.

- **UE5 Ray Reconstruction preset no longer causes foliage shimmer:** `high` and `full` now use the smooth (bilinear) Lumen screen-probe interpolation that UE's own Epic and Cinematic quality use. Before, every level forced the cheaper stochastic one, which shows as boiling on foliage in shade and on thin detail further away. `medium` and up also undo UE 5.7's noisy half-resolution GI integration (`r.Lumen.ScreenProbeGather.IntegrateDownsampleFactor=1`).

- **UE5 RR preset levels match what each setting really costs:** the expensive steps (four times the screen-probe traces, full-resolution MegaLights) moved to `full`, faster surface-cache lighting updates moved to `high`, and the free probe-direction cycle moved to `medium`. `full` now also reaches full-resolution MegaLights on UE 5.6 (`r.MegaLights.DownsampleFactor`). Two temporal switches that only overrode deliberate game tuning are no longer written by any level; they stay available in `custom_cvar_overrides`.


### Fixed

- **Streamline detection after resident-runtime fallback:** selecting the game's initialized runtime no longer installs hooks inside a DLL loader notification, avoiding a startup lock deadlock. Calls return to the resident runtime immediately, while the hook worker restores imports and installs its detection hooks; late load requests also keep reusing the resident interposer during that cleanup.

- **Streamline runtime overrides during game startup:** concurrent Streamline calls now keep the runtime selected by the intercepted initialization call, preventing takeover rollback from splitting detection and feature calls between resident and override interposers. Games whose resident runtime initializes first still retain that runtime.

- **Streamline override startup freezes:** removed the takeover-lock dependency from runtime loading and module queries. Concurrent startup calls share one prepared runtime, while early dynamic export lookups retain their deferred takeover gate.

- **Streamline overrides after initialization:** cached NVIDIA Streamline cores with hashed DLL names now prevent replacement of an already initialized interposer, avoiding a split runtime. Incomplete module scans also preserve the resident runtime.

- **DirectX 12 post-process crashes:** fixed premature resource destruction when a frame-generation command list records correction for multiple output targets before submission. Every recording now retains its resources through GPU completion or explicit cancellation.

- **DirectX 12 FSR post-process routing, wrapped device identity, and overlay format retargeting:** the shared FSR owner-queue renderer no longer applies display gamma or sharpening to alpha-blended FFX UI textures or marker-only route-activation probes, and reclaims runtime post-process slots if command-list close or submission fails. D3D12 post-process passes now compare underlying COM `IUnknown` device identity so proxy `ID3D12Device` wrappers do not rebuild fences, descriptor heaps, or PSOs every frame. In addition, backbuffer format switches without a visible `ResizeBuffers` call now retarget the x86 Texture2D and fallback DX12 overlay backends and drain in-flight GPU work before replacing offscreen render targets.

- **Elevation service survives unexpected client errors:** an exception escaping a client worker thread (e.g. a failed string allocation while handing the client over) previously terminated the whole elevation service process, taking elevated CaptureEngine features down with it. Client workers now confine failures to the affected client and always release their slot.

- **Software outside the inject whitelist is created untouched:** while CaptureEngine runs, launchers and the desktop shell still carry the creation-only hook (that is the mechanism that reaches a target's static Streamline import). What changed is what those creators make: everything they start that is neither a capture/overlay target nor a launcher (e.g. an anti-cheat game launched from Steam) is now classified before its creation and takes its creator's exact creation path, with no forced suspension and no interception work. This removes the observable creation anomaly for everything the whitelist does not name; removing the creator-side hook itself from parent processes remains future work (see llm-wiki/startup-runtime-overrides.md).

- **Game launchers can no longer fail to start because of CaptureEngine:** a launcher that misses its readiness handshake with a running CaptureEngine now starts unintercepted (its game falls back to the ordinary injection discovery) instead of being terminated with a loader-init error. Likewise, a briefly unavailable creation gate now creates the process normally instead of failing the start.

- **Static Streamline interposer overrides:** same-generation games can now resolve their imported interposer directly from the override path during normal desktop and Steam launches. Creator hooks run before Windows binds the imports, and new launchers wait for interception before starting games. The opt-in legacy generation bridge and caller-requested suspension retain their existing contracts; actual Steam-overlay/game retesting remains pending.

- **Streamline overrides during game startup:** native core loads are now intercepted at the start of the hook worker, before configuration I/O and runtime/tool preloads, so the configured override can reach loads missed by the initial import hooks. Existing protection against mixed generations and duplicate runtimes remains active; a native-loader flow regression verifies the configured image is used before full hook installation.

- **Application-audio backlog warnings:** intentional video-buffer delay above 250 ms no longer produces false latency warnings. Warnings now measure backlog at least 50 ms above the current target, report suppressed repeats, and reset on recovery and recording boundaries. Audio processing and integrity checks retain their existing behavior.

- **Recording-log analysis across midnight:** fixed live/stop attribution and recording windows by retaining the calendar date, and stopped counting the same ingress-drop counter twice when both log fields are present. Overnight recordings and older single-field logs are covered by regression tests.

- **Second crackle 150 ms into the application-audio track when the first packet led the recording start:** the mirror case of the entry below. A source's first packet may start up to 5 ms before the recording start, and such a packet bypassed placement entirely and was written whole, so the source ran up to 5 ms late for the first 150 ms and the lead was then deleted in one piece. The decoded Track 1 of a quick test recording showed it: a 238-sample step in the alignment to the system track at exactly sample 7200 and the strongest click of the first 1.5 s there. The part of that first packet before the recording start is now dropped up front and the rest is placed at the start (or if the entire packet precedes the recording start, it is dropped before latching `hasAlignedStart` and `timelineValid` so the next packet starts the timeline), so nothing is cut later. This also stops a microphone with a latency-equalization delay from getting its delay as 29 ms of silence right after its first 10 ms packet instead of as leading silence. Marked by the new log line `[AudioLoop] Startup pre-start head trimmed`.

- **Crackle 150 ms into the application-audio track:** when an audio source's first packet started 1-4 ms after the recording start (a QPC phase offset that varies per recording), the gap was left unplaced for the first 150 ms, so the content ran early, and then inserted all at once as 2-3 ms of hard silence in the middle of the signal. The decoded Track 1 of a 41-minute recording showed exactly that: a cut from +0.0197 to zero at 150.000 ms, 141 samples of silence, and a 3.7 ms jump in alignment to the system track. The gap is now placed as leading silence before the signal starts, so the first 150 ms are aligned and nothing is inserted later. Present since the startup placement logic was added in April; the new log line `[AudioLoop] Startup first-packet gap placed at the start` marks each affected source.

- **Tiny audio cut-outs every 40-60 s on system-audio and microphone tracks:** a sound device whose clock runs a few tens of ppm apart from the video clock (measured -28 ppm loopback, -25 ppm microphone in a 5-minute WGC recording) used to be re-synchronised by deleting 1-1.7 ms of audio behind a 1.3 ms fade-in each time the offset reached 1 ms. The drift is now removed by bending the capture resampler's rate by the same few tens of ppm (about 0.05 cent, capped at 0.05%), so the tracks keep their exact length and sync without any cut. Real discontinuities (device stalls, jumps over 5 ms) and per-application audio keep the previous handling. The stop summary line `[STOP AUDIO PLACEMENT]` shows `laneEngaged`, `lanePpm` and `laneHardSeams`; real-game confirmation is pending.

- **Audio early by up to 30 ms in WGC and desktop-duplication recordings of a hooked game:** the audio-latency correction delayed video by the full measured audio latency, but a screen-grab video timestamp already trails the game's Present by the frames queued before they are shown (about 20 ms for an uncapped game on a 144 Hz display, 7 ms windowed, none when frame-capped). The measured present-to-screen latency is now taken off that correction for both the audio anchor and the video delay. Uncapped test scene: audio early by 30.2 ms -> 10.7 ms; windowed 22.0 -> 14.6 ms; frame-capped and recordings without the in-game overlay unchanged. `[AudioSync] screen_grab_queue_compensation=false` restores the previous behavior.

- **Opus audio running up to 30 ms longer than the video:** when a recording ended in the first two thirds of an Opus frame (about two thirds of all recordings), the encoder's final padded packet lay entirely after the end and the end trim signalled for it was larger than the packet, so players ignored it and every Opus track ended up to a frame late. Packets wholly past the end are now dropped and the trim is sized from the last kept packet. Decoding through Matroska and MP4 now returns the exact length for six end positions across the frame; WGC, inject and desktop-duplication recordings were re-checked live.

- **False "audio duration mismatch" warning for Opus recordings:** the post-recording check subtracted the encoder's own tail trim twice and reported a 13.5 ms shortfall on files that decode to the exact length.

- **WGC recording of a high-refresh window at a lower frame rate:** a 60 fps recording of a 144 Hz or faster window repeated about 40% of its frames (runs of up to 8 identical frames) because the smoothing buffer was filled with every source frame, overflowed its pool and then threw away the newest frames. Ingestion is now metered to the rate the buffer is sized for, and the frame-time estimator is told how many source frames each kept frame stands for, so selection stays on the source grid. A live 60 fps scene went from 40.6% to 0% repeated frames with no discarded frames; 120 fps recording is unchanged.

- **False "startup smoothing underfilled" fault on clean WGC recordings:** when only a small jitter buffer (about 22 ms) was requested, the end-of-recording summary compared it with the full 300 ms reservoir, reported a 279 ms deficit and flagged a visual timeline fault. The deficit is now judged against the delay that was actually requested.

- **Recording validation no longer depends on fixed capture-timing constants:** the audio/video test matrix measures each capture method's raw audio-to-video offset with a short shot instead of assuming one tuned for an earlier OS, driver or product state, and warns when that offset moves between runs. `--audio-latency-autodetect` runs the matrix with the product's own latency detection to show the offset a real capture gets.

- **Audio/video validation after source relayout:** the recording test matrix finds the built Capture Engine and stimulus app from the repository root again, including when launched from another working directory. The per-recording triage step now uses the same FFmpeg/FFprobe as the content analysis instead of looking for them on `PATH`, so a run no longer fails after a clean capture. A dry-run regression checks the installed layout and the forwarded tool paths before recordings are started.

- **Recording-audit regression coverage:** restored five disabled analyzer test groups covering missing audio, frame pacing, synchronization delay, finalization and track correlation. A dispatch regression prevents a partial self-test from silently reporting success again.

- **Audio sync checks on short recordings:** the completed-file analyzer now compares two independent content windows when a clip is long enough for both, so a repeatable track offset can be detected in short recordings. Delayed and aligned 16-second clips protect the check without lowering its confidence thresholds.

- **Overlay after DLSS FG off with ReShade:** fixed auxiliary command submissions replacing the live queue/device binding and clearing the confirmed overlay route. Queue discovery now preserves that binding; completed swapchain creation still supports queue and device replacement.

- **Missing automatic dumps for CE faults caught by a game:** hardware faults inside Capture Engine are now captured with their original thread and registers before the game's exception handler can consume them and leave a hang or clean exit. This closes the missing-dump path seen during The Witcher 3 Remastered's ReShade startup failure.

- **The Witcher 3 Remastered (DX12) startup with ReShade:** fixed an invalid renderer cast during overlay replacement that could crash inside CE and leave the game hung. Custom DX12 renderers now keep their own resource handling through startup and device changes.

- **Pre-release lint and test reliability:** resolved Python lint and type annotations in test generators, fixed implicit pointer conversions and enum initialization warnings in hook and test sources, rebalanced `tests/test_config.cpp` across `test_config_part3.cpp` and `test_config_gamma.cpp` to stay within the 800-line file-size ceiling, forced tracked-file reconciliation during persistent release-runner workspace sync when shared `external/` files change, and decoupled the window heartbeat test from the host foreground window state so headless release verification and background test runs succeed reliably.

- **Log flood from Streamline UI-tag diagnostics (The Witcher 3 Remastered):** the game tags one buffer per call and cycles the buffer type, so every call was logged as a change and about 85% of `hook_debug.log` (21k of 25k lines per minute of play) was tag lines. Each buffer type, and whether the call sets or clears the tag, is now its own metered stream with a per-stream heartbeat: one line per kind, plus a line when that buffer's tag really changes.

- **Dynamic frame generation factor ignored in The Witcher 3 Remastered (DirectX 12):** `dlss_fg_mode`, `dlss_fg_fixed_count`, `dlss_fg_dynamic_max`, `dlss_fg_target_fps` and the driver VSync answer never reached the game's own Streamline core, so the game always ran the fixed factor from its options menu. The game starts Streamline before CE finishes attaching; that core was mapped before CE could patch its driver-settings lookup. CE now patches already-loaded Streamline and frame-generation modules at startup too, including the driver entry points such a core had already cached in its own data, and logs each routed module (`NGX DRS: GetProcAddress import patch on ... via=startup sweep`, `NGX DRS: ... had already cached the driver's NvAPI entry points; retargeted ...`, `NGX DRS: nvapi_QueryInterface resolved by DLSS driver-settings consumer ...`).

- **Orphan Streamline copies beside the game's own (The Witcher 3 Remastered, DirectX 12, ReShade):** when the game's `sl.interposer.dll` was already loaded, CE could still load its configured `sl.common`/`sl.dlss*` copies by name. The game's interposer then loaded its own core from the game folder, leaving CE's copies as unused duplicates that held CE's Streamline hook slot (about 10 refused retargets and 66 repeated re-hook attempts in the first two seconds). CE now places no Streamline copies by name next to a game-owned interposer; the loader redirect remains the only substitution (`Runtime preload: sl.* plugin set not placed - sl.interposer.dll is already resident ...`).

- **Game window never appearing on some launches (The Witcher 3 Remastered, DirectX 12, manual Reflex limiter configured):** when the game had already loaded the NVIDIA API library before CE armed its low-latency hook, a later reload of that library on the game thread replaced CE's saved original entry point with the already-patched one. The hook then forwarded every NvAPI lookup to itself forever, so the game's main thread spun inside Streamline initialization (no window, no frames) and CE's own hook thread spun with it. CE now keeps the saved original once its hook is installed and updates it atomically otherwise; if the export ever has to be ignored, `ReflexLimiter: Init kept the published nvapi_QueryInterface trampoline` is logged.

- **Dynamic frame generation factor still ignored on some launches (The Witcher 3 Remastered, DirectX 12, ReShade):** whether the game's own Streamline core was routed through CE depended on a startup race. If it was mapped after the startup sweeps but before CE's loader hook existed, nothing ever patched its driver-settings lookup, so the in-game factor won on that launch (`NGX DRS: answered ... dynamic maximum` was missing) while other launches of the same setup worked. CE now also patches every driver-settings consumer from the loader's own load notification, on the loading thread before the module can use it, and reconciles cached driver entry points on the hook thread afterwards (`NGX DRS: GetProcAddress import patch on ... via=loader notification`).

- **False post-process failures on HDR games with display gamma on (DirectX 12):** HDR10 and scRGB frames, where gamma is deliberately left alone, were logged as `pass-failed` and counted as uncorrected frames. They are now treated as not requested, so the frame ledger and the per-route failure counts only show real failures.

- **Device removal after a DirectX 12 swapchain switch with display gamma or sharpen on:** the post-process pass cached its render-target view by the back buffer's address, so when a replaced swapchain's new buffer landed on the address of the destroyed one, the pass recorded against a view of a released resource and the graphics device was removed (intermittent when switching DLSS frame generation off to native and back on). The view is now written for every frame.

- **Overlay colors for a moment after start (The Witcher 3 DX12):** when the game switched its swapchain from `R8G8B8A8` to `R10G10B10A2` with HDR10 output and back during start-up, the overlay kept drawing through pipelines built for the old format, so its text showed garbled, oversaturated colors until the game switched back. The overlay now follows the format of the back buffer it writes, keeping one pipeline pair per format instead of rebuilding, and the HDR10 contract of those frames is applied to it.

- **One-frame 200 ms hitch when DLSS frame generation turns off (The Witcher 3 DX12):** opening the game menu rebuilt the overlay behind a wait on the whole game queue, which can only finish once the Streamline present thread returns, so it ran its full 200 ms timeout and held the previous frame on screen that long. It now waits only for the overlay's own submissions.

- **Shader rebuilds after source relayout:** shader generation now updates the headers actually consumed by the post-processing pipeline instead of writing into the retired source directory.

- **Worker configuration paths:** helper processes now honor the selected `--config` INI, including paths containing spaces and active-code-page characters. Launch paths are owned explicitly so a host can select the packaged worker instead of accidentally relaunching its own executable; delegated game launch options keep their own `--config` arguments.

- **Config edits during startup:** changes made after startup loading but before the first reload check are now applied instead of being mistaken for the already loaded version. One runtime settings owner retains the previous settings on an unreadable or changing file, schedules retries and publishes complete replacements before frontend/helper updates.

- **Clean verification after a failed build:** `--verify-clean` now takes precedence over resume and incremental flags, so a requested clean verification recompiles product objects while keeping the failed build identity. A regression covers all resume/incremental combinations; hook and test-harness diagnostics keep strict checks passing without raising warning baselines.

- **Recording restart and helper shutdown:** helper ownership now retains earlier media processes while they finish a recording, so shutdown waits for those finalizers too. Child startup, recovery and retirement use one private owner with generation checks; failed teardown retains ownership for retry, and console shutdown uses an atomic stop flag.

- **Recording to a slow disk or network share froze the video:** when the output target could not keep up (e.g. an SMB share slowed down by background CPU load), the full mux queue blocked the encoder. CFR timeline debt then grew to minutes, the video stayed frozen in "Recording recovering..." until the end, and buffered audio was dropped out of sync. CE now measures the writer's real throughput and caps fresh frames using the measured writer capacity and spreads cached repeats across CFR slots to reduce sustained queue pressure, without changing encoder settings or the audio timeline. `[CFR MUX BUDGET]` lines log entry, progress and exit.

- **Audio running ahead of the video after a long capture stall:** when CFR video fell further behind than the 30 s audio buffer could hold, the oldest buffered audio was discarded and every later sound moved earlier in the file, up to minutes ahead of the picture. The discarded span now becomes silence at its own position, so all audio that survives stays in sync with the video.

- **DirectX overlay coexistence:** fixed Present and Present1 forwarding that could skip an overlay already installed in the swapchain vtable. Vtable interception now retains its own next links independently of inline hooks, with regressions for both methods and nested status probes.

- **Frame generation Base/Display rates:** the overlay's Base/Display row under DLSS frame generation no longer freezes at the last rate seen before FG started (e.g. "67 / 133 FPS" while the screen ran at 52 fps). Both rates are now measured from the displayed frames and the game's own frame cadence, and show equal values while DLSS FG is enabled but not generating frames, as in menus.

- **Input-based latency estimate with the elevation service:** when CaptureEngine used the elevated service's display trace, the Windows input events behind the new "Latency est." anchor were never enabled, so no game received them. The service and CaptureEngine now enable one shared provider set.

- **PC latency estimate in multithreaded engines:** games whose game thread runs ahead of the presenting thread (e.g. Unreal Engine titles such as Talos) now anchor the estimate on their own frame-matched simulation markers, including under FSR FG, instead of a later frame's low-latency sleep that read whole frames too low. Sleeps on another thread are no longer paired, and frames without a boundary reuse their neighbours' recently measured span.

- **PC latency with the FPS limiter:** without frame generation, the time CE's limiter or flip-queue pacing waited inside the game's Present was counted twice in "Latency est." (about 9 ms too high at a 90 fps cap).

- **Frame-generation regression verification:** presenter address reuse no longer causes false frame-attribution failures during FG mode switching; wrong-frame outputs within a presenter lifetime still fail coverage checks.

- **Recording stop feedback:** explicit child rejection now remains distinct from an uncertain acknowledgement. The recording session owns media-first/inject-fallback ordering and endpoint release; API and hotkey toggles use that same lifecycle policy.

- **DX12 frame synchronization:** normal drawing and capture now retain the frame overlay lock, releasing it only around PostSL retirement and route rechecks. This prevents unowned unlocks and concurrent resource mutation after preparation.

- **FG route confirmation** activation and rendering proof now commit through the PostSL lifecycle owner; cancelled proof cannot be restored by a callback already publishing confirmation, while temporary suspension preserves validated handover ownership.

- **FG queue retirement** selected and pinned PostSL queues now retain GPU completion evidence across delayed callbacks and replacement fences; incomplete drains cannot release those references early.

- **FG callback queue lifetime** PostSL retains selected and wrapper queues through submission and rejects delayed callbacks from retired generations before acquiring resources.

- **FG handover lifecycle** PostSL render admission now covers recording and submission together; retired epochs cannot restore current rendering confirmation.

- **Privacy-blackout repeat recovery:** a successful cached-black repeat no longer promotes the unencoded fresh candidate as the last successful source or counts it as fresh catch-up output. Candidate ownership regressions exercise real ring leases.

- **Recording retry feedback:** an inactive inject or repeat encoder attempt now clears a previous deferred-fence result, preventing rejected attempts from being reported as still waiting for that earlier frame.

- **Recording controls could report success without working:** the controller API now rejects invalid handles, wrong-thread calls and invalid recording modes, returns command failures, and reports unsupported configuration and statistics explicitly. Stopping clears the recording flag, pending start and tray state so the next toggle starts correctly; event polling handles hotkeys and quit messages without millisecond polling sleeps. The reported version follows the actual application build.

- **Recording could crash with mismatched media DLLs:** typed frame submissions now use distinct DLL exports while the original exports retain their calling contract. A rejected DLL also clears its function pointers.

- **Concurrent diagnostic streams could lose changes:** log suppression slots now keep their owners; excess streams are logged instead of resetting a gate another thread is using. Colliding streams use all free slots before overflowing, keeping their separate suppression counts.

- **Elevation service installed in the wrong folder:** the service now runs from a protected runtime inside the actual Capture Engine install folder, including custom locations. Updating migrates an existing service out of the separate `C:\Program Files\CaptureEngine` folder; uninstall also handles older registrations.

- **Overlay kept showing "DLSS 2x" after DLSS frame generation was turned off right after turning it on:** an off request that arrives during DLSS-G's startup is held until the startup is over. Depending on timing it then reached DLSS-G without Capture Engine noticing, so the overlay status stayed on. It now always goes through Capture Engine's own handling.

- **Overlay on FSR frame generation when the game switches its present callback while frame generation stays on:** Capture Engine keeps its own callback in AMD's runtime across such a switch but still ran its callback-less overlay routes next to it, and the last frame before a switch to a callback could lose its overlay. The overlay now follows the route AMD actually uses, frame by frame.

- **Overlay hand-over with FSR UI textures that AMD reads directly:** games that keep their own HUD texture per frame (instead of letting AMD copy it) now get the same exact overlay hand-over at FSR on/off as the others. For a 1x1 placeholder without AMD's copy, Capture Engine alternates two textures instead of redrawing the one AMD is reading. A game that reuses one texture every frame keeps the overlay in that texture without a hand-over.

- **Overlay drawn twice or briefly missing when turning FSR frame generation on or off (games without a present callback):** AMD still shows the previous frame while the game already prepares the next one, and Capture Engine switched its overlay route by the next frame. At every FSR enable the previous frame's outputs got the overlay twice, at every disable or swapchain switch the last frame's final output got none. The route now switches with the frame AMD actually shows.

- **Overlay vanished for seconds after turning DLSS frame generation back on:** after an FSR frame generation phase, switching DLSS-G off and on again could hide the overlay for 6.5 s, and while it was off the overlay still showed "DLSS 2x". DLSS-G's last generated frame after the switch-off no longer counts as frame generation, and the overlay's transition pause always ends completely.

- **Overlay hidden for about half a second after leaving FSR frame generation:** switching from FSR frame generation (already off) to a DLSS or native swapchain no longer pauses the overlay; it is redrawn on the new swapchain at once.

- **Possible GPU device loss when DLSS frame generation starts after FSR:** a temporary resource Capture Engine used to test the game's queue was freed before the GPU had used it.

- **Possible freeze on the first FSR frame generation frame in games with a placeholder UI texture (GTA V Enhanced style):** re-registering Capture Engine's UI texture could re-enter Capture Engine's own hook and deadlock.

- **No overlay on FSR frame generation frames in games without a UI texture:** games that let FSR frame generation interpolate their HUD (no UI resource, no present callback) now show the overlay the same way.

- **Overlay could be submitted on AMD's internal queue:** a game that creates its FSR frame generation swapchain before presenting anything else made Capture Engine mistake AMD's present queue for the game's own, the case known to crash AMD's runtime.

- **Overlay coverage diagnostics missed FSR frame generation frames:** frames presented by FSR frame generation without a present callback were never counted in the session log's overlay coverage summaries, so gaps there went unreported.

- **DirectX 12 games crashed with the D3D12 debug layer or a capture tool wrapping their queues:** Capture Engine handed its first overlay submit to a D3D12 function that only understands D3D12's own queue objects, so a game running with the debug layer (or under a tool that wraps queues the same way) crashed at once. Such queues are now submitted through their own interface; the log names each decision (`Resolved ExecuteCommandLists ... REFUSED - calling through the queue's own vtable`).

- **Overlay drawn on DLSS frame generation frames without the required resource transition:** the overlay drew onto Streamline's output while D3D12 still had it marked ready for display, an invalid use the debug layer reported on every frame. When the overlay runs on the queue that presents the frame it now switches the image to drawing and back; the log line `PostSL barrier mode` shows the choice.

- **UE5 RR preset left reflections noisy without Ray Reconstruction:** under TSR, plain DLSS SR, an RR fallback, or after RR was turned off in a game's menu, the preset still switched off Lumen's reflection denoising. Those settings now follow whether RR is actually rendering and hand the game its own values back the moment it stops. The log says `UE5 overrides: Ray Reconstruction is rendering` / `stopped rendering`.

The injected game DLL no longer copies symbols at all.

- **Freeze dumps no longer extend the freeze:** when a game stops presenting for the watchdog timeout, the diagnostic dump is now written by the external helper whenever it is available, so the game's threads are not suspended while it is written.

- **External crash dumps name the faulting instruction:** dumps written by the external helper now carry the crashing thread's exception context, so the debugger opens at the fault instead of at the helper launch.

- **CaptureEngine keeps the game's own error-reporting settings:** the injected crash handler used to replace the game's Windows error mode and error-reporting flags; it now only adds its own.

- **Slow log writes now explain themselves:** a single log call that blocks longer than 50 ms writes a rate-limited warning into the log it slowed, so a stall episode is recorded in the very output it affected.

- **Settings-state mixups between different CaptureEngine builds can no longer hide in struct padding:** the shared-memory compatibility fingerprint now also covers the nested graphics/overlay struct sizes and the sharpen/DLSS frame generation fields, so a layout change that consumes padding fails closed between builds instead of silently misreading state.

- **Forced AF / sampler override visibility on DX9:** "CaptureEngine reached no sampler at all" is now logged at a settled render loop (2000 presents) instead of only at process shutdown, and another overlay re-patching the sampler hooks is detected per Present and reported as "sampler hook drift" instead of silently disabling forced AF and the sampler state shadow.

- **Bridged DLSS-G cadence writes are now attributable in logs:** when a forced frame-generation cadence is written on a Streamline 1.x bridged title, a rate-limited warning names the write and the unconfirmed 1.x field mapping behind it, so a wrongly-written cadence can be traced in session logs.

- **A `config.ini` change saved right after it was read is no longer missed (UTF-8 config files):** CaptureEngine keeps the parsed config and reused it while the file's write time and size matched, so a rewrite that kept both inside one file-time tick (a setting flipped `1` to `0`) kept its old value. A file written within the last 2.5 seconds is now confirmed byte for byte before the cached parse is used.

- **No wrong frame right after a DirectX 12 game rebuilds its display (injected capture):** a frame from the old display could still pass the recorder's handle check against a texture handle the new display reused, because the new generation began only after the old textures were closed. It now begins before, so such a frame is dropped instead.

- **A hidden helper window no longer keeps the game's graphics queue alive (DirectX 12 games that create a swapchain on a hidden window):** CaptureEngine held a reference on the queue of every hidden-window swapchain until that swapchain showed a frame, which a helper never does. References for windows that were destroyed are now released.

- **Caller identification cannot touch a DLL that is unloading:** the first lookup of a DLL's address range read its image headers without holding the DLL loaded, so a game unloading that exact DLL in that instant could crash it. The DLL is now held for the read.

- **A refused swapchain resize can no longer hold a game for minutes:** when a DirectX 12 game's resize is refused because something still holds its back buffers, CaptureEngine scans the process's memory once to name the holder. That scan now stops after 3 seconds and says so in the log, instead of running as long as the process has memory.

- **Another component's crash-time release is no longer removed when the keyboard hook stops:** CaptureEngine releases its low-level keyboard hook before writing a crash dump so that keyboard input on the whole desktop does not freeze during the dump; stopping the hook now removes only its own release.


### Fixed

- **Release log privacy:** fixed automatic cleanup and its verification for GitHub's empty log-deletion response, so self-hosted build logs are removed and checked unavailable after each release attempt.

- **Stable release builds:** isolated unused FPS-limiter test helpers and made the GPU pacing regression independent of host scheduling, so analyzer warnings and a busy PC no longer block verified releases containing the FSR pacing fixes.

- **FSR frame generation could exceed the FPS limit with uneven frame pacing:** when FSR presented distinct frames close together, CaptureEngine mistook them for duplicates and let them skip the general FPS limit, including when a lower general limit took precedence over capture sync. Every confirmed FSR output now takes its own pacing slot while the presenter keeps its nonblocking lock.

- **FPS limits cut the frame rate in half with FSR frame generation (DirectX 12 games where FSR presents the frames itself, seen in The Talos Principle Reawakened):** the general FPS limit (`FpsLimiter.general_fps`) held every frame FSR showed to half the configured rate, so a 120 fps limit showed 60 fps. With capture sync the same happened for about the first second of every recording, and the game then took a few seconds to become smooth again. In Reflex limiter mode, capture sync let the game render twice the recording rate. Capture sync was also compared against the general limit at double its real rate, so a higher general limit (for example 144) replaced it. CaptureEngine now knows that each of these frames is one shown frame and paces it at the configured rate. The limiter log shows `captureSource=final site=3` for this case.

- **Recordings with FSR frame generation moved at half the on-screen frame rate (injected DirectX 12 capture, seen in The Talos Principle Reawakened):** the game showed a smooth 120 fps, but the recording only took the frames the game rendered itself (60 per second) and skipped every frame FSR generated in between. Each missing frame was filled by repeating the previous one, so the 120 fps video looked like 60 fps. When FSR's own presentation step reports a frame just before showing it, CaptureEngine now records it whether FSR generated it or the game rendered it, so the recording matches what is on screen. The hook log now counts both kinds (`generatedOutputs=` / `applicationOutputs=`).

- **Recording stop could still hang on a stalled disk or network share:** a full packet queue stopped checking the write timeout, leaving the encoder blocked and shutdown waiting forever. The queue wait now keeps cancelling overdue writes so recording finalization can continue.

- **Game crash when FSR runtime unload overlaps CaptureEngine shutdown or runtime replacement:** restoring the FFX create-entry breakpoint now holds the exact DLL loaded through the byte restoration. A disappearing runtime is rejected without reading its old address, and DLL references are acquired and released outside the breakpoint mutex.

- **Recording never started after switching from DLSS to FSR frame generation in-game (DirectX 12 injected capture, seen in The Talos Principle Reawakened):** the recording stayed in its preparation phase and was discarded when stopped. With FSR's own presentation step, FSR draws CaptureEngine's overlay, so CaptureEngine's regular overlay stays switched off, and the switch from DLSS had just torn it down. CaptureEngine's frame processing stopped at "overlay not ready" on every frame, before it reached the capture step, so no frame was ever recorded. Now only the overlay setup waits and every frame still reaches the capture step. Recordings set to leave the overlay out now also record frames the overlay step never reached, instead of dropping them (`Overlay-free capture published after the overlay draw chain did not reach it` in the log).

- **Game closed when switching from DLSS to FSR frame generation after a recording (DirectX 12 injected capture, seen in The Talos Principle Reawakened):** once a recording had run, CaptureEngine's capture kept a hold on the game's display even after the recording stopped. When the game later switched frame generation, it released its old display, but CaptureEngine's hold kept it alive. Windows then refused FSR's new display for the same window, and the game quit. The capture now only remembers which display it copies from and takes no hold on it, so a released display really goes away. The "access denied" diagnostics in the log now also name the display the capture is bound to (`captureKey=`).

- **Capture sync FPS cap stopped working after switching from FSR to DLSS frame generation in-game (DirectX 12 games with the Steam overlay, seen in The Talos Principle Reawakened):** with `capture_sync_enabled=true` the game kept running above the capture rate (about 140 fps instead of 120) in every recording until the game was restarted. After the switch, DLSS frame generation's final frames take a separate route past the Steam overlay's outdated hook, and that route never ran CaptureEngine's FPS limiter, so neither capture sync nor the general FPS cap engaged. The route now paces frames exactly like the normal one, and the log records when the limiter starts or stops pacing there.

- **Profile DLSS/Streamline overrides were ignored in Portal RTX and other RTX Remix games:** `dlss_sr_dll_path`, `dlss_rr_dll_path`, `dlss_fg_dll_path`, `streamline_dll_path`, `dlss_sr_preset`, `dlss_rr_preset`, `dlss_fg_preset` and `dlss_debug_overlay` never took effect. These games draw with DLSS in a separate helper process (`NvRemixBridge.exe`), so CaptureEngine's Vulkan layer loads its hook there to apply the profile. The layer looked for that hook next to its own copy under `%LOCALAPPDATA%\CaptureEngine\vulkan_layers\`, which only holds the layer files, so the load failed (`error=126`) every time, while the game process had already stepped aside for the helper. Nothing applied the overrides, with no message outside the layer log. CaptureEngine now records its install folder beside the staged layer at every start and the layer loads the hook from there. If the hook still cannot be loaded, the layer says which overrides will not apply and hands them back to the game process instead of leaving them unowned.

- **Recording never started in Portal RTX and other RTX Remix games (injected Vulkan capture):** the recording stayed in its preparation phase and was discarded when stopped. In these games the game process only hands its frames to a separate helper process (`NvRemixBridge.exe`), which draws them with Vulkan, and CaptureEngine's Vulkan layer captures them there. The recorder only accepted frames from the game process itself, so it threw away every frame the helper sent. It now also accepts frames from that helper, but only when the helper is the game's own child process and CaptureEngine's Vulkan layer registered it as the game's renderer. The mouse cursor in the recording is placed using the game's window, which the helper does not have. The media log now reports `Admitting split-renderer frames` (or `Refusing split-renderer frames` with the reason) when the helper's frames arrive.

- **Overlay showed a far too low, lagging FPS and frame-time graph, then no latency at all, after the game switched to composed presentation (seen in DOOM Eternal on Vulkan, going from native 4K to a 1440p mode):** at that resolution NVIDIA's Vulkan driver stops flipping the game's frames onto the screen itself and hands them to Windows to compose instead. From then on CaptureEngine's display timing saw no flips of the game's own. It kept every unflipped frame for 10 to 15 seconds and later matched unrelated screen updates whose internal number happened to be the same to those old frames. In the reported session every frame the overlay was given had supposedly taken 9 to 12 seconds to reach the screen. The overlay drew about 29 fps for a game running at 140, and its graph kept flipping between display and presentation timing. A frame now only counts as displayed if the screen update comes within one second of it, and frames nobody displayed are dropped after that second. Composed frames are now timed by Windows' compositor instead: a frame counts as displayed with the first compositor screen update made after the game finished it. The frame-time graph therefore keeps measuring what reaches the screen, and games without Reflex show "Latency est." again instead of "PC Latency -". The sensor log reports the switch and names the compositor process (`now expire without a flip completion` / `Flip completions resumed`). The health line counts `expired=` and `staleRejected=` frames and has a new `composed(...)` section.

- **No video after restarting CaptureEngine while a D3D11 game on DXVK kept running (injected Vulkan capture):** once the game had switched to the recorder's own textures, a restarted CaptureEngine was handed those old textures, which only the previous recorder could open, plus a sync object that was no longer signaled. The game now rebuilds its own capture textures for the new CaptureEngine instead. The same stale textures were also reused after the game recreated its display at the same size between recordings, and a busy moment during the handover could skip it entirely. Both are fixed.

- **Recording could show one still image for its whole length in D3D11 games running on DXVK (injected Vulkan capture):** when the game was already running before recording started, CaptureEngine switched to its faster direct-texture path shortly after the start, but kept waiting on a sync object that nothing ever signals. Every frame was then held back as not finished yet. The Vulkan layer now hands over its own sync object together with the textures.

- **Recording froze a few seconds after changing the resolution (injected Vulkan capture, seen in DOOM Eternal switching 4K to 1440p):** the rebuilt display got a new sync object for its frames, but CaptureEngine's Vulkan layer announced it in a place the recorder only reads for a different capture mode. The recorder kept checking the old, retired sync object, so the new frames looked finished until their count passed where the old one stopped; from then on every frame was held back and the video showed one still image until the recording ended. The layer now announces the new sync object exactly where the recorder reads it.

- **A crashing game froze for about a minute before it closed (games with the Steam overlay, seen in The Talos Principle Reawakened):** CaptureEngine re-reads the version information of certain loaded DLLs whenever a DLL loads, and did so by reopening the file through a system call the Steam overlay intercepts and locks. When the game's own crash reporter started writing its crash file (which loads a DLL and pauses every other thread of the game), CaptureEngine could be paused while holding Steam's lock, and the crash reporter then waited on that lock for every module it listed: 50 seconds of a frozen game in the reported session. CaptureEngine now reads that information from the DLL already in memory, without touching the file or the intercepted call.

- **CaptureEngine's dump of an Unreal Engine fatal error was either huge or too thin (Unreal Engine titles with an overlay loaded):** Unreal raises one specific error just before it shuts down on a fatal error, and CaptureEngine treated it as a harmless warning. Its dump first pulled in the whole game's global data (158 MB, an 18-second pause in The Talos Principle Reawakened), and then only thread call stacks (533 KB), which could say neither who held a lock the game hung on nor what the stacks pointed to. The dump now records call stacks, open handles with lock owners, the memory the stacks refer to and the memory layout, without the global data, and the crash log names the error as Unreal's fatal-error path.

- **DirectX 12 games closed at startup when their window was shown only after the display was set up (seen in The Talos Principle Reawakened in its "windowed" native-resolution mode, with or without the Steam overlay):** CaptureEngine deliberately ignores displays created for hidden windows, because programs create such helper displays that never appear. It therefore also forgot which GPU queue owned the game's real display when the game created it before showing its window. The first overlay frame was then sent on a different queue of the game's, which DirectX does not allow, so it shut down the graphics device and the game quit without a CaptureEngine crash dump. CaptureEngine now remembers what it skipped and catches up on the display's first frame once the window is visible, so the overlay goes out on the display's own queue. The log reports `Parked create-time queue ownership` at creation and `First visible Present of hidden-window swapchain` when it catches up. A new `No swapchain queue captured` line flags any other route that leaves the display's queue unknown.

- **Changing the resolution closed DirectX 12 games that have the Steam overlay (seen in The Talos Principle Reawakened, with or without frame generation):** the Steam overlay keeps a hold on each of the game's display images and lets go of them only in its own handling of the game's resize. It installs that handling by patching the start of DirectX's resize function, and it skips a function that another program has already patched there. CaptureEngine had put its own resize handling at exactly that spot (and in earlier builds, in the display's function table). Steam therefore never saw the resize and kept its holds, DirectX refused the new resolution, and the game quit. CaptureEngine now hooks further inside the resize function, as it already did for presenting frames, and leaves the start of the function to Steam. Steam releases its holds first, and CaptureEngine still runs right after it. A new diagnostic counts who takes and returns holds on the display images after every DirectX 12 resize (`BackBufferRefTrace:` lines). The log also names who owns each of the display's functions (`slot owners`) after the first resizes and at any refused one.

- **Recording never started in games with FSR frame generation drawn through FSR's own presentation step (injected DirectX 12 capture, seen in The Talos Principle Reawakened):** the recording stayed in its preparation phase and was discarded when stopped. To keep its cost off AMD's frame-generation threads, CaptureEngine stopped counting the game's GPU submissions on that route, but it still used that count to tell real frames from generated ones, so every frame looked generated and none was ever recorded. It now takes the real/generated decision from FSR itself, which reports it for every frame just before presenting it.

- **Recording could keep showing old frames after a game rebuilt its display (injected capture, mainly DirectX 12; also Vulkan resolution changes and DirectX 8-11/OpenGL display resets):** when a game recreated its swapchain (alt-tab in exclusive fullscreen, resolution change, switching frame generation), CaptureEngine replaced its shared capture textures, and Windows can give the new ones the same internal numbers the old ones had. The recorder identified textures only by those numbers, so it could keep reading the old, no longer updated textures. Each set of capture textures now carries its own generation number: the recorder reopens everything when it changes and skips the few frames that were captured just before the switch.

- **Recording froze on a still image after alt-tabbing out of a game and back (injected capture, seen in DOOM Eternal on Vulkan):** while the game was in the background it stopped drawing, and CaptureEngine kept its very last frame back as a safety reserve instead of recording it. When the game came back it rebuilt its display, which has to wait until CaptureEngine hands back every frame it still holds, so the game side waited for CaptureEngine and CaptureEngine waited for a newer frame that never came. The video then showed the same picture until the recording ended, while the audio kept going. A frame whose GPU copy is already finished is no longer held back when it is the only one left, so recording resumes on the game's first frame after the switch. This applies to every injected graphics API, not only Vulkan.

- **A Vulkan game started at the same moment as CaptureEngine could run without the overlay:** at every start CaptureEngine briefly removed its own Vulkan layer registration and added it back a few milliseconds later, because it mistook the 64-bit and 32-bit entries in the shared per-user registry key for leftovers of each other. A Vulkan game that initialized in that gap never loaded the layer and could not get the overlay or be recorded through it until it was restarted. The registration now stays in place the whole time.

- **"Recording saved - video degraded" shown when only audio was affected:** every degraded recording or stream was reported as video degraded, even when the only problem was audio (for example audio the recording could not keep up with, an unplugged microphone, or a crashed audio worker). The message now names what was affected: "audio degraded", "video degraded" or "audio and video degraded", in the in-game overlay and on the desktop alike. The recording's manifest file records it as `recording_degraded=`.

- **Recording reported as degraded when Windows repeated a piece of system audio:** when system sound resumed after a quiet period, the Windows audio engine sometimes handed over the same 10 ms of audio twice (flagged as a glitch). CaptureEngine correctly kept only one copy but counted the dropped repeat as audio lost to an overloaded pipeline, so the overlay showed "Recording saved - video degraded" for a recording with no missing audio or video. Only audio the recording really could not keep up with counts as lost now; dropped repeats are logged separately (`dedup=` in the stop summary).

- **10 ms of system audio lost when sound resumed after a quiet period:** when the output device had been silent for a while (for example between games), some audio drivers stamped the first packets of the returning sound with a time far in the past. CaptureEngine replaced each of those with the moment it read them, but it reads several packets at once, so they landed on top of each other and all but one were thrown away. The recording was then reported as degraded. Such packets now stay back to back, and nothing is discarded.

- **Game audio could waver in pitch on loading screens and static scenes (app audio capture, screen capture):** the catch-up that pulls game audio back toward the video briefly sped it up by up to 0.5%, several times a second, because its target followed the measured video delay, which jumps around while the screen barely changes. In one 4-minute recording it switched on and off 715 times. It now follows the delay's peak over the last several seconds, so it only runs for a real, lasting backlog.

- **Game audio ran ahead of the video when the game started after the recording (app audio capture):** a game whose audio appeared only after recording start (for example launched mid-recording, or restarted) joined its track without the delay that keeps audio in step with the delayed video. Its sound then played early by that delay for the rest of the recording (about 0.3 s in the reported desktop-duplication session). CaptureEngine then kept slowing that audio down by the maximum allowed amount (0.05%) trying to close the gap. A late game now joins at its correct position, with the same delay as every other track.

- **The recording thread ran without its high scheduling priority:** CaptureEngine registered its encoder thread for high-priority multimedia scheduling and undid the registration immediately, while the log still said it was enabled. Under heavy CPU load (for example a game loading or compiling shaders) the thread could fall behind, and the recording dropped frames to catch up, which is visible as a stutter. The registration now lasts the whole recording.

- **An audio speed correction stayed active after a game went quiet:** when an app's audio stopped (for example after the game closed), the last speed correction stayed set and applied to its first audio if it came back, and the stop summary reported it as maxed out. It is now cleared when the app goes silent.

- **Audio and video drifted apart in long CFR recordings (worse at high frame rates):** CaptureEngine picked each recorded frame on a real-time schedule that ran slightly faster than the file's frame timestamps, because the frame interval was rounded down to whole timer ticks. Video therefore fell behind the audio by about 14 ms per recorded hour at 60 or 120 fps, 23 ms at 144 fps, 58 ms at 240 fps and 100 ms at 360 fps. With capture sync active, the drift also caused an occasional repeated frame (about every 4 minutes at 240 fps). The schedule now places every frame at its exact time, for WGC, desktop duplication and injected capture alike.

- **A short click when a track's audio came back after silence (e.g. a game muting itself on alt-tab):** the fade-in at the resume point only lasted one video frame's worth of audio and then jumped to full volume, on top of the source's own fade-in. The fade now runs its full length across frames, and is skipped when the source already fades itself in. The recording-start fade could stop early the same way when the first audio chunk was short; it now runs its full length too.

- **The last fraction of a millisecond of a 44.1 kHz or 96 kHz audio track was silent:** the sample-rate converter's final samples were never written, so each such track ended on a tiny silent gap instead of the recorded audio. They are written now.

- **Audio crossfades after a trim in VFR recordings started too abruptly:** the crossfade began at 60% of the new audio instead of at the previous sample, and a backlog trim crossfaded the wrong spot while leaving the actual cut hard. Both now start exactly where the audio left off.

- **Possible crash in games that unload AMD's FSR library (e.g. GTA V Enhanced after every FSR session):** CaptureEngine could put its FSR breakpoint back at the address where the unloaded library used to be. Whatever the system loaded there next would then have been corrupted. It was never seen crashing, but GTA hit this situation at every start. CaptureEngine now forgets that address when the library unloads, and checks that the address still belongs to FSR before every change.

- **GTA V Enhanced: FSR frame generation cleanup never ran when the game closed FSR:** GTA loads AMD's FSR library fresh for every FSR session and creates frame generation right away, through function lookups CaptureEngine cannot redirect. CaptureEngine therefore never saw FSR frame generation being created and treated every FSR object the game closed as unrelated, so the cleanup that releases the overlay from FSR never ran; recent GTA fixes only worked around what it left behind. CaptureEngine now catches the creation as soon as the library loads, and recognizes any FSR object it still missed from the game's first FSR call on it.

- **Overlay disappeared for good in The Talos Principle Reawakened's menu after switching FSR frame generation on, off and then to DLSS frame generation:** while FSR frame generation was on, CaptureEngine drew its overlay through FSR's own presentation step, so at the switch to DLSS it wrongly concluded the overlay had not been visible and skipped preparing it for the new DLSS swapchain. Without that preparation nothing proved the new swapchain safe to draw on while the menu kept DLSS frame generation idle. CaptureEngine now counts the overlay as visible on any route it last drew on.

- **Overlay stayed hidden in GTA V Enhanced's menu after switching from FSR frame generation to all frame generation off:** in the menu GTA sets up FSR frame generation but never switches it on, so CaptureEngine kept holding its overlay back and waited for FSR to start. CaptureEngine normally stops waiting when the game closes FSR, but it had missed GTA creating FSR's frame-generation contexts, so it did not recognize them when they were closed. When the game then went back to its normal display, the overlay stayed off until the game was closed. CaptureEngine now stops waiting as soon as the game creates its normal display again in the same window.

- **Overlay stayed hidden in GTA V Enhanced's menu after toggling DLSS frame generation (after an earlier FSR frame generation session):** CaptureEngine kept a recovery guard from the old FSR-to-DLSS switch active after the game had already returned to its normal display, because that return happened shortly after frame generation was on. When DLSS frame generation was then switched on again in the menu, the game created a new DLSS display that stays idle while the menu is open, and the old guard kept the overlay switched off on it until the game was closed. The guard now ends as soon as the game's normal display or the new DLSS display is confirmed, so the overlay stays visible. The overlay on the normal display also no longer takes the slower copy path the guard forced.

- **GTA V Enhanced crashed with `ERR_GFX_STATE` when switching from FSR frame generation to DLSS frame generation:** with DLSS frame generation not yet running, CaptureEngine judged the new DLSS swapchain as left over because the game kept rendering on its own GPU queue. It then drew the overlay into that swapchain from the game's queue, which does not own those buffers, and Windows removed the GPU device. CaptureEngine now checks which queue the presented swapchain belongs to and leaves a live DLSS swapchain alone.

- **Overlay disappeared after switching from FSR frame generation to DLSS frame generation (DirectX 12):** on the new DLSS swapchain CaptureEngine never marked its own overlay GPU work as finished, so after 16 frames the overlay treated every buffer as busy and stopped drawing. It now marks that work as finished after every present, as it does on any other swapchain, and the overlay keeps drawing. Only AMD's own FSR presentation queue is still left untouched.

- **Overlay briefly missing after switching from FSR frame generation to DLSS frame generation:** during DLSS frame generation's first frames the overlay only reached its generated frames, not the real ones, until CaptureEngine's regular DLSS overlay route took over, and that takeover waited for the game to stop presenting through its old path. Switching again in that window left a real frame without the overlay on screen for up to a second. When the game explicitly enables DLSS frame generation after FSR on a proven safe route, the overlay is now drawn into every output from the first frame on.

- **DirectX 12 games dropped to 1 FPS for about 10 seconds after switching from FSR frame generation to DLSS frame generation (e.g. GTA V Enhanced):** CaptureEngine's overlay work on the new DLSS swapchain was never marked as finished until DLSS frame generation actually started (fixed separately above), and the overlay waited up to one second on every frame for that work before drawing again. The overlay never waits there anymore: while that work is still pending it skips drawing for that frame (as it already did after the wait), so the game keeps its full frame rate and the overlay comes back as soon as the queue catches up.

- **The DX12 frame generation switch test app could not switch from FSR FG back to DLSS FG after the first DLSS session:** it asked Streamline to accept its device a second time after rebuilding its renderer, which Streamline refuses by design, and then treated DLSS as unavailable for the rest of the run. It now keeps using the device Streamline already accepted. It also no longer tags the back buffers of a swapchain Streamline does not present: DLSS frame generation kept the tagged native or FSR swapchain alive, so switching DLSS FG -> OFF -> DLSS FG (or FSR FG -> DLSS FG after an earlier DLSS session) failed to create the new swapchain and the app stopped.

- **DirectDraw / DirectX 7 games closed with their own error box when rebuilding their display (e.g. Gothic II after loading a save):** CaptureEngine still held on to the game's old screen surfaces and 3D device, so the game could not create new ones. CaptureEngine now lets go of them before the game rebuilds its display.

- **No crash dump when a game shows its own error box and then quits:** a game that reports a fatal error in a message box and exits normally afterwards now gets a crash dump, and the log records the message box text.

- **DirectX 7 and DirectX 8 games lost texture settings whenever they restored a state block (even with no filtering override configured):** after a game applied a saved state block, CaptureEngine wrote its own older copy of the texture settings back over it. With no override configured that copy was stale (the startup defaults, or whatever an earlier state block had set), so textures could switch to the wrong wrapping or filtering in state-block-heavy games. With no override CaptureEngine now writes nothing after a state block; with forced filtering it remembers what each state block restores (including blocks the game records), keeps the game's own values, and still forces the configured filtering.

- **A selected microphone or output device that was unplugged was silently replaced by the Windows default:** the recording then captured a different device (for example a webcam microphone) and was reported as saved. The track now stays on the selected device: it holds silence while the device is missing, switches back as soon as the device is plugged in again, and the recording completes as saved (degraded).

- **Audio lost to an overloaded audio pipeline was reported as a clean save:** captured audio the recording could not keep up with (logged as `starve=` in the stop summary) never reached the file, and a crashed or failed-to-start audio worker left every track silent, yet the recording still said saved. Both now complete as saved (degraded). A source that was simply quiet is not affected.

- **Overlay missing in DirectX games with two overlays active (e.g. Steam plus RTSS) when only part of CaptureEngine's present hook could be installed:** if the hook for the game's `Present` call failed while the one for `Present1` succeeded, CaptureEngine treated presentation as covered, never retried, and saw none of the game's frames. Coverage is now judged per call: the missing hook is retried on the next swapchain event without touching the part that works, and CaptureEngine's own swapchain view stays on while `Present` is uncovered.

- **Removing a hotkey from `config.ini` did not disable it until restart:** a blanked or deleted overlay, screenshot, audio-only or benchmark hotkey kept its previous binding after a live settings reload. Every reload now applies the file as written.

- **A settings reload during a locked `config.ini` published default settings and never retried:** if the file could not be read at that moment (an editor, sync tool or virus scanner holding it), games and the recording process switched to defaults and CaptureEngine considered the change applied. A reload is now used only when the whole file was readable and did not change while it was read; otherwise the current settings stay and the reload is retried.

- **Vulkan games could freeze for good after one failed overlay submission:** a failed overlay GPU submission left one of the overlay's fences in a state nothing would ever signal, and a later present could wait on it forever. A failed submission now re-arms its fence (or retires that slot for good), and the wait for a busy slot is bounded; in that case the overlay skips one frame instead of holding the game.

- **The logging process could outlive CaptureEngine after a crash:** if CaptureEngine was ended hard, its logging process kept running and competed with the next CaptureEngine's logger for the games' log buffers. It now exits when CaptureEngine does.

- **DirectX 9 games lost texture settings whenever they restored a state block (with anisotropic filtering or mip-map overrides active):** after a game applied a saved state block, CaptureEngine re-applied the filter override from the texture settings the game had used *before* that block, undoing the block's address modes, filters and LOD bias on every apply (wrong texture wrapping or blurriness in state-block-heavy games). With no override configured, the first state block after startup could reset every texture sampler to the Direct3D defaults. CaptureEngine now remembers what each state block restores (including blocks the game records), keeps the game's own values, and still forces the configured filtering.

- **Forced anisotropic filtering stopped working in DirectX 9 games once another overlay re-hooked the device:** a second overlay that took over the texture-sampler functions left CaptureEngine's filter override and its view of the game's texture settings dead for the rest of the session. When such a takeover persists, CaptureEngine now hooks the Direct3D 9 implementation underneath the other overlay (once, without touching the other overlay's hook), so filtering keeps working and both tools stay active.

- **Settings with Japanese, Chinese or Korean characters were misread on Japanese, Chinese or Korean Windows:** on those systems Windows' own settings reader garbled UTF-8 text in `config.ini` before CaptureEngine saw it, so paths such as a Japanese recordings folder or a profile named after a Japanese game executable did not work. UTF-8 configs are now read directly from the file.

- **The first section of a `config.ini` saved as "UTF-8 with BOM" was ignored:** the byte-order mark hid the first section header from Windows' settings reader, so its settings silently stayed at their defaults. The first section is read now.

- **Crash dumps, fallback logs, debug switches and add-on detection failed below folders with non-Latin characters:** with CaptureEngine or the game in a folder the Windows language setting cannot express, crash dumps written before the session folder was known went to a mangled path, the external crash-dump helper was never found, and the DirectX 12 debug flag files, fallback log folders, DXVK/ReShade/Special K/OptiScaler detection, the Streamline version check and the check for a game's own Streamline all came up empty. These lookups now use Unicode paths (or the folder's short 8.3 name where an older interface needs one).

- **A recording lost everything before an HDR switch:** turning HDR on or off during a recording (the Windows HDR toggle, or a game's own HDR setting with injected capture) made the encoder re-open the recording file and overwrite what had already been recorded. The recording now ends at the switch instead, keeps everything recorded so far, and completes as saved (degraded).

- **Cropped, stretched or frozen video after a resolution change during a recording:** when the recorded window or game changed size mid-recording (window resized, resolution changed, fullscreen toggled), the new frames went through a converter built for the old size. They are now scaled into the recording's size with the aspect ratio preserved and black borders, and the recorded cursor stays on the right spot.

- **OpenGL games rendered incorrectly once the overlay was shown (missing depth, wrong transparency, wrong textures):** the overlay's OpenGL 3+ path switched off depth testing and face culling and changed the blend mode and active texture unit without restoring them, and left its own vertex buffer bound. Games that set this state once, or keep their own copy of it, rendered wrongly from the first overlay frame on. Every piece of state the overlay touches is restored now; the older OpenGL path also restores the game's vertex array pointers (they could point into freed overlay memory), and the overlay's font upload no longer reads from a pixel buffer the game left bound.

- **System audio went silent after switching the Windows output device:** with the default setting (record the default output), switching the default output during a recording (the volume flyout, or a headset that becomes the default while the speakers stay connected) kept recording the old, now silent device for the rest of the recording. Recording now moves to the new default output (or default microphone) right away.

- **Silent microphone or system-audio track without any warning:** a device that was missing, busy or blocked by the Windows microphone privacy setting when the recording started was dropped for the whole recording, and the recording was still reported as saved. The track now picks the device up as soon as it becomes available (for example when a headset is plugged in), and a recording with such a gap, or with audio lost to encoder faults, completes as saved (degraded).

- **A recording kept running without video after a GPU driver reset:** when the video encoder or its GPU device failed for good, every frame failed and the recording went on as audio over no video, reported as saved. After 5 seconds without a single encoded frame the recording now ends, keeps everything encoded before, and completes as saved (degraded).

- **Game exit stalled and wrote a 50 MB crash dump for a normal quit:** a game that quits with exit code -1 (seen with Strange Brigade quitting through Steam) was treated as a crash, holding the exit for about 2 seconds. Small negative exit codes are ordinary exits now; real crashes are still dumped.

- **DirectX 12 games could hang for good after alt-tabbing out (windowed):** a wait for CaptureEngine's own overlay GPU work before presenting fell back to waiting forever after 2 seconds, even when that work could only finish after the game's present. The wait is bounded now; the overlay just waits for that work before it draws again.

- **Short stall during frame generation swapchain changes:** swapchain teardown polled for up to 100 ms on a counter that could not change at that point. The wait is gone.

- **DirectX 11 overlay garbled or missing in some games:** a geometry or tessellation shader the game left bound ran on the overlay's triangles. The overlay now disables those shader stages for its own draw and restores them, and it restores every viewport the game had bound, not just the first.

- **Settings with non-English characters were misread:** a `config.ini` saved as UTF-8 (the Windows Notepad default) turned characters such as umlauts in paths, window titles or process names into garbage, so recordings could go to a differently named folder and profiles never matched. UTF-8 configs are read correctly now; characters the Windows language setting cannot represent are logged.

- **Settings briefly fell back to defaults while `config.ini` was being saved:** a reload could read the file while an editor was still writing it, and for about a second the games and the recording process ran on defaults (profiles, injection targets and overrides dropped and re-applied). A change is now applied only once the file has stopped changing, and an empty or missing file is never applied.

- **Installations in a folder with non-Latin characters ran on default settings:** `config.ini` and the logs were looked up through a path the Windows language setting could not express, both in CaptureEngine and in the game. The folder's short (8.3) name is used when needed, and a warning is logged when the volume has none. This also works with the Windows "UTF-8 for worldwide language support" option, where the lookup previously came back empty.

- **Rare audio crash at recording start:** the audio timeline was rebuilt at recording start while the audio worker could still be reading it.

- **Overlay disappeared after switching from FSR frame generation to DLSS frame generation (e.g. The Talos Principle Reawakened):** when the switch was made in a menu, DLSS frame generation created its new swapchain on its own GPU queue but did not start generating frames yet. CaptureEngine waited for the game's rendering to move onto that queue before setting the overlay up again, which never happens, so the overlay stayed gone until the game closed. The overlay is now set up on the new swapchain right away, and the second wait path for the same condition recognizes the handoff too, so the menu-switch case cannot recur through it.

- **Long recordings were deleted when finalizing failed:** if writing the file's final index failed (a full disk at the end, or any earlier transient write error, which FFmpeg reports again at the end), the whole recording was removed. A video recording with committed packets that fails to finalize is now kept; its index may be incomplete, so seeking can be slower until it is remuxed. Audio-only recordings follow the same rule.

- **Stutters and stalls in games that handle their own exceptions (Unity/Mono, Java, .NET, LuaJIT titles, emulators):** CaptureEngine's in-game crash handler treated every first-chance access violation or runtime exception as a crash and wrote a dump, stalling the game for up to 5 seconds, using up the one crash dump, and then appending to `crash.log` on every following exception. Such exceptions are now only recorded. A dump is written, with the recorded faulting context, only when the process actually dies of one.

- **Recording could stop when settings changed during a recording:** one config-reload acknowledgement that took longer than 1 s tore down the channel to the recording process, which then stopped the live recording. A first late reply to a reload or ping is now discarded without dropping the channel; the recording process also acknowledges reloads before doing the work.

- **Rare crash when settings changed while recording:** a config reload replaced settings that the recording threads were still reading. Reloads during a recording are now applied when the next recording starts.

- **Rare game crash with FidelityFX frame generation when two threads configured it at once:** a second thread hitting CaptureEngine's `ffxConfigure` breakpoint while the first had just disarmed it was left unhandled and could end the game; it now simply continues. A breakpoint that could not be removed now fails visibly instead of hanging the thread.

- **Injection failed for installations in folders with non-Latin characters:** the hook DLL path was passed through the system ANSI code page, which turns characters such as Cyrillic or Japanese into `?`, so no game could be injected. Paths are now passed as Unicode.

- **Steam overlay recovery could write into the wrong memory:** CaptureEngine's recovery for a Steam overlay callback that is not yet initialized could act on crashes of unrelated threads, and fell back to a fixed Steam memory offset that current Steam builds no longer use. It now acts only on the thread it guards and only on the proven callback slot, and is registered once instead of on every frame.

- **Black screen in Vulkan games with sharpening enabled (e.g. DOOM Eternal):** when a game destroyed its swapchain and created a new one, CaptureEngine's sharpen pass kept drawing through views of the destroyed images, and the GPU driver reported a lost device on the next frame. The sharpen pass is now released before the swapchain is destroyed, and the semaphores a pending present may still wait on are kept until afterwards.

- **Black screen in Vulkan games that present from a compute queue with sharpening enabled (e.g. DOOM Eternal with "present from compute"):** the sharpen pass kept submitting graphics work to the game's compute-only present queue, which the GPU driver answered with a lost device. On such queues sharpening now runs as a compute shader on the game's own present queue; where the game's swapchain or GPU does not allow that, sharpening is skipped with a logged reason instead of breaking the game.

- **Sharpening changes had no effect in running Vulkan games:** a `sharpen` setting changed while a Vulkan game was running was ignored until the game restarted. The setting now applies on the next frame, as it already did for D3D11 and D3D12.

- **Delayed keystrokes in other applications while a hotkey fired:** the global hotkey keyboard hook, which every keystroke on the desktop waits for, wrote a log line (with a disk flush under a process-wide lock) inside its callback. A slow flush, typically right when a recording starts, held keyboard input for every application. The hook thread now only counts. The controller does the logging.

- **Keyboard input could wait on busy game threads:** the hotkey hook thread now runs at time-critical priority, so a game's high-priority render threads can no longer keep it from answering while all cores are busy.

- **Silent loss of the hotkey keyboard hook:** Windows removes a keyboard hook without notice after repeated timeouts, which left hotkeys dead in games that suppress normal hotkeys (e.g. DOOM Eternal). A late answer is now detected, logged (`[Hotkey] Keyboard hook answered late`), and the hook is re-armed immediately; a removal Windows had already made is logged and repaired.

- **Keyboard input froze during a CaptureEngine crash dump:** writing the controller's crash dump suspends its threads, including the keyboard hook's, so every keystroke on the desktop waited on the hook timeout until the dump finished. The hook is now removed before the dump starts.

- **Recordings with hours of content could still be deleted at stop:** a cancellation arriving after video was already written (or a single HDR metadata packet failing to normalize) removed the whole file. A recording with written video frames is now always kept; only recordings without a single written video frame are removed.

- **A full disk produced a recording with missing frames that was still reported as saved:** when the disk filled up or writes failed mid-recording, frames were dropped for the rest of the session (logged at most ten times) and the completion message still said saved. The recording now stops at the first lost write, keeps everything written so far, and completes as saved (degraded). A memory shortage while queueing encoded frames is counted the same way instead of dropping frames silently.

- **Stopping a recording could hang forever on a stuck disk or dead network share:** writes to local recording files were unbounded, so a hung write wedged the stop path and the recording was never finalized. Local outputs now have a write timeout (30 s): a write still blocked past it is cancelled, which turns it into a reportable error and lets the stop finalize the file.

- **A recording could be reported as cleanly saved while its finalization was still unfinished:** when stopping gave up waiting for a slow finalize, the completion was decided before the final index write and frame-continuity check had run, so a failure there never reached it. Such a stop now completes as saved (degraded).

- **Game crash at startup when a launcher spawns the game as a child process:** the injected parent freed the DLL path buffer in the child while the child's loader could still be reading it (a cross-process crash), and every outcome was logged as "Injected" even when the load failed. The buffer is now retained until the child's load finishes, the path is Unicode end to end, and the real result is reported.

- **Early child injection silently skipped for games launched with a command line and arguments (the common launcher shape):** the whitelist check compared the tail of the whole command line (e.g. `game.exe" -dx12`) against the executable name and never matched. It now resolves the program a launch actually starts.

- **Wrapper DLL, crash dumps, hook byte recovery, and child injection failed for installations in non-Latin folders:** the hook derived its own directory with the system ANSI code page, so characters such as Cyrillic or Japanese became `?` after loading. These consumers now derive the directory as Unicode; the per-app `config.ini` reader is still ANSI at its file API and remains affected.

- **Rare startup crash in 32-bit games from an out-of-range hook jump:** jump displacement was computed by a truncating cast, so a hook DLL loaded more than 2 GB away from the hooked function could receive a wrapped-around jump target. Displacements are now computed and range-verified explicitly and the install fails cleanly instead of writing a bad jump.

- **Game freeze at startup while installing hooks next to other overlays (Steam, RTSS):** the hook installer wrote log lines while every other thread of the game was suspended and could deadlock against a suspended thread holding the log lock. Failure reports are now emitted after all threads resume.

- **Steam overlay recovery logged a stale fixed memory offset as its callback slot:** current Steam builds moved it, so the diagnostic line named a random address. The read is gone; the recovery itself already acted only on proven slots.

- **Small hitch when switching from DLSS frame generation to FSR frame generation:** every such switch could stall the game for up to 200 ms draining GPU work even though the overlay state was deliberately kept alive. The keep-alive exceptions now cover the drain, teardown, and cooldown steps uniformly instead of being listed per step.

- **Frame generation status could stay wrong for the rest of the session:** a game re-enabling DLSS frame generation through the status query alone (no explicit enable call) stayed suppressed, leaving the overlay without frame generation status and the frame limiter at base rate against generated frames. Sustained real generation now clears the suppression, and the log states when suppression is active.

- **Rare crash risk when switching frame generation modes:** a deferred overlay GPU-signal path touched the overlay's fence outside its lifetime lock and could race an overlay rebuild. It is now serialized with rebuilds and pins the fence while signaling, and logs the fence identity for future diagnosis.

- **Game crash with NVIDIA Smooth Motion on DX12 (device removed 0x887A002B):** when Smooth Motion's private output chain appeared without its recorded GPU queue, the overlay draw was routed to an arbitrary queue and could take the device and the game down. The draw is now skipped there with a logged reason.

- **Recording kept filming the wrong screen after the game exited (window capture):** when the captured window closed mid-recording, capture retargeted to the foreground monitor or primary and recorded whatever the user was doing next. The retarget now lands on the same display the window was on (pinned at start) or stops the recording and keeps what was captured.

- **Recording ran to its end as a frozen picture when the capture source died:** a failed capture replacement whose rollback also failed left a frozen frame plus live audio with no visible error, and when the captured window itself had closed, the rollback restarted capture of that dead window, which can start and then deliver no frames. The recording now never rolls back onto a closed window; it stops through the normal path and completes as saved (degraded).

- **Screenshots could use the wrong HDR brightness on multi-monitor systems:** tone-map calibration read the primary monitor's SDR white level instead of the display the captured content lives on, which differs per monitor ("SDR content brightness"). The captured display's own level is used now, with the same 203-nit fallback.

- **Up to 2 seconds of wrong-color frames after toggling HDR during capture:** the format recheck waited for its periodic 2-second timer even when delivered frames visibly contradicted the capture's HDR contract. The recheck now fires immediately on the contradicting frame.

- **Misspelled settings silently changed behavior:** an unknown `capture_method` became `auto` with no warning, and `auto` normally means injected capture — one wrong character in `capture_method=wgc` quietly enabled injection. Unknown capture methods, hotkeys, and limiter modes now log which key was invalid and what replaced it, once per typo.

- **`crash.log` leaked the Windows account name:** the crash trace log is now privacy-masked like every other log, and the dump paths it names are collapsed to drive + file name, so it is safe to share in support requests.

- **UE5 `ensure()` errors could freeze the game repeatedly and flood the session with dump files:** every ensure wrote its own dump in-process (a multi-second stall with Steam or Social Club overlays loaded) with no limit. Assert dumps now go through the external dump helper when another overlay is present and stop after three per run.

- **Foreign breakpoint traffic could stall the game and cost the real crash its dump:** an `int3` from anti-cheat or another hooking tool (handled by that tool) each cost a full in-game dump stall, and the first one also used up the process's single crash dump, so a real crash afterwards got none. Breakpoints are now recorded like every other first-chance fault and dumped only if the process actually dies of one (through the unhandled-exception path, the termination that follows it, or the Windows error-reporting dump CaptureEngine adopts).

- **Rare capture statistics corruption during a capture stats reset:** the reset updated pool timing state without the lock the capture producers use.

- **Stack overflow with a co-resident overlay in DX8/DX9/OpenGL games (e.g. Steam overlay):** a foreign injector hooking below CaptureEngine re-issued presents through CaptureEngine's hooked entry until the stack overflowed (32,768 recursion levels in 2 ms in Gothic II). Present detours now answer a nested presentation with the real implementation past the foreign entry patch (once per present) instead of calling back into the cycle, and return without presenting, with a caller-module log, when no bypass can be built.

- **Game hang after the D3D7 overlay font-atlas upload (e.g. Gothic II):** the atlas lock was the one DirectDraw lock CaptureEngine took without DDLOCK_NOSYSLOCK, taking the Win16 lock inside the game's Flip; it now behaves like every other CaptureEngine lock and falls back to the CPU composite if rejected.

- **Overlay and freeze watchdog dead after one failed DirectDraw Unlock:** a failed Unlock (or an unbalanced application Lock/Unlock pair) permanently deferred DirectScanout presentations and the freeze-watchdog heartbeat while the game ran on. Unlock attempts now always resolve the surface's lock tracking, with a failed Unlock treated as a conservative "surface changed". Games holding several rectangle locks at once are tracked per lock, so the overlay is not composited while another rectangle is still being written.

- **Vulkan capture survives single-queue and async-present GPUs:** the sharpen and compute-present overlay submits raced game submissions on the game's own queue without the serialization lock every other CaptureEngine submit takes — the prime suspect for the recurring QueueSubmit/device-lost black-window failures (DOOM Eternal "present from compute"). All queue submissions now hold that lock.

- **Vulkan overlay/capture/sharpen can no longer be locked out of a game for the whole session:** a running CaptureEngine host completely masked the persisted Vulkan layer target list at layer negotiation (decided once per process), so a profile edit mid-session, a CaptureEngine/game start-order race, or a non-ASCII exe name silently removed the layer for the rest of the run. Either signal now admits (worst case: a dormant stale entry), and executable names are matched in Unicode end to end against both whitelists.

- **Vulkan implicit layer no longer maps the full layer into every Vulkan process from the fallback install path:** when layer staging falls back to the install directory, the stale manifest naming the full layer could be registered, bringing back the 1.5 MB layer (and its imports) in Explorer, browsers and anti-cheat-protected games. The negotiation-gate manifest is now generated in that path too.

- **Sharpen no longer stalls the present thread when two swapchains are live (Vulkan):** the per-device sharpen state rebuilt its whole pipeline — including up to 3x1 s fence waits — on every present of a second swapchain (auxiliary windows/tool surfaces). The first live swapchain keeps the filter, other chains pass through untouched until it is destroyed, and swapchains under 320x180 never trigger the filter.

- **FPS limiter no longer flips to async-present routing for a whole session off one stale worker submit:** the submit-thread heuristic remembered a single background-thread submit forever and permanently moved the limiter boundary and overlay route. It now requires a mismatch within the same 2-second recency window the acquire route uses.

- **Audio stays in place when the encoder rejects a frame:** a mid-track `avcodec_send_frame` failure froze the audio PTS counter, placing every later frame one frame early (~21 ms AAC, up to ~86 ms PCM) for the rest of the track, and back-pressure (`EAGAIN`) dropped the frame entirely — sends are now retried after draining, and a truly failed frame becomes an explicit silence hole at its exact position, never a re-placed track.

- **No more compressed audio after encoder faults:** a consumed chunk the encoder could not take (resampler/FIFO failure) was re-requested and refilled with newer samples, silently compressing the track while every length check stayed green — consumed ranges are never re-filled now; lost tails are placed as explicit silence holes at their exact timeline positions. Audio trimmed on purpose at the recording end is never counted as lost, and a hole on the final chunk stops at the recording end.

- **Audio encoder FIFO never truncates recorded audio:** the old five-second overflow ceiling was dead code with a stale "drop newest" policy; a consumed batch now enters in full (the FIFO grows to fit) or is refused whole and placed as an explicit hole, with honest capacity diagnostics.

- **Race-free audio timeline cursors:** the audio worker read the pull thread's sample cursors (write-cursor pinning, gap suppression, diagnostics) as plain integers; they are now snapshotted under a dedicated leaf lock, preventing erroneous timeline trims under load.

- **Possible game crash when an exception hit a Windows loader worker thread while the Steam overlay hook was active (games with the Steam overlay):** the exception handler that recovers from Steam's null callbacks runs first for every exception on every thread and read per-thread state that loader worker threads do not have, so it faulted inside itself until the stack ran out. It now checks a thread-id list first and only touches per-thread state on the thread that armed it.


### Removed

- **Limiter helper process:** the separate limiter process had not paced anything since frame pacing moved into the game process, but it still ran a highest-priority thread pinned to CPU core 1 with a spin-wait, which could delay other threads on that core, including input processing of unrelated applications. Its request wait could also spin a core at full load. It is gone. Capture-synced recording no longer waits for it or fails with "limiter readiness failure". The FPS limiter itself is unchanged.

- **In-game window procedure hook:** the injected runtime no longer replaces the game window's message handler. It forwarded every window message (including every high-rate mouse input message) through a lock without using any of them, and made unloading riskier alongside other overlays.

  the startup loader deadlock when Special K, ReShade, and OptiScaler load together (Special K now loads last, peer
  threads are suspended around tool loads, and loads run on the loader work queue).
- Fixed the pseudo-overlay font and circle scale to track the anchor monitor's DPI instead of the
  DPI-awareness-dependent window DPI, so text no longer resizes when the foreground app's DPI awareness changes.
- Fixed a DX12 startup crash in which the third-party-overlay Present-hook deferral was never made real: the
  deferred temp-swapchain Present hook now waits for the game's own D3D12 device and installs inside the same
  startup window, resolving the intermittent Steam-overlay recursion and the CaptureEngine access violation.
- Fixed FSR heuristic FG: an authoritative `ffxConfigure` OFF now vetoes the heuristic, preventing it from
  composing into AMD's UI resource after frame generation was explicitly disabled.
- Stopped re-attempting console-registry CVars whose layout CaptureEngine cannot drive, avoiding repeated failed
  writes and scan retries.
- Fixed frame timing under native FSR FG by ticking from the FFX present callback and submitting the overlay on the
  queue the FG runtime actually flushes.
- Fixed DLSS FG integration: the overlay no longer uses a dedicated overlay queue for NVIDIA DLSS FG, late-inject
  overlay submits route to the swapchain-owning queue, the FG multiplier is reported from MultiFrameCount, the
  Streamline multiplier stays latched across CreateFeature, and already-loaded DLSS-G/Reflex exports resolve at late
  injection.
- Fixed CodeQL-flagged format-argument and multiplication-overflow defects in overlay and device code.
- Fixed GCC compilation of the FFX hook header by ordering the `template` keyword before `inline`.
