  -> DLSS FG (epoch confirms ~15k submits on the live DLSS-G proxy queue `00000237F829ABE0`) -> menu OFF -> DLSS FG

  releasing stale swapchain queue …`) nulled `g_SwapchainQueue` although the make-before-break keep-alive kept

  no queue left: `SelectPostSLBootstrapSubmitPath` returned `kReject` and every resumed frame logged `refusing SL

  the ON-side stale-FSR-clear evaluation, so the resumed submit returns to the proven selected-scQueue original-ECL
  path. The OFF-side release and non-FG recovery classification stay unchanged. See guardrails.md (warm-resume proxy

- GTA `installed/captureengine/logs/20260623_060436` (2026-06-23) proved the revived no-callback FSR FG **game-ECL bundle CRASHES GTA** (it only "worked" because the test app never stressed it). `crash.log`: `0xC0000005 READ from 0x0` inside `nvwgf2umx.dll` (NVIDIA UMD), faulting stack `nvwgf2umx!… → D3D12Core!CCommandQueue::ExecuteCommandListsImpl → capture_hook_x64!… (CE's ECL detour forwarding [gameCLs, overlayCL]) → sl_interposer → GTA5_Enhanced`. `hook_debug.log` proved the CE substitute texture worked (`Created CE substitute UI texture 3840x2160`, overlay appended frames 1→18) then crashed ~18 frames in, ~0.2 s after the FFX takeover (mid-startup churn: EOS swapchain create + Streamline quiesce + FFX takeover). Device constant `…3956D20` the whole session — NOT a device mismatch. **Root cause:** the bundle reused its 3-slot allocator rotation with NO GPU fence — it "rode the game's fence", but the game's fence does not gate CE's allocator reuse. During GTA's takeover churn the GPU fell >3 frames behind, so CE reset an allocator whose appended command list was still executing → corrupted command list → driver null-deref inside `ExecuteCommandLists`. The bundle's "append to the game's ECL, no separate submit" design fundamentally cannot fence its own allocators. **Fix:** drive the overlay through the fenced **CE-owned-queue composite** `DX12_CompositeOverlayOntoFFXUiResource` (own `g_FFXUiCompositeQueue` + fence + per-slot allocator fence wait + CPU-wait before Present) via new `DX12_CompositeOverlayOntoCachedFFXUiResource()`, called from `DetourPresent`'s `kSkipBundleCovers` arm. The bundle (`RecordBundleOverlayForGameECL`/`TryAppendNoCallbackBundleOverlay`/`EnsureFFXUiCompositeBundleResources`) and the dead `DX12_ShouldCompositeOverlayOntoFFXUiResource` gate were removed; the composite gained the substitute transparent-clear + degenerate guard. Durable lesson: **never reuse a command allocator without a fence you control** — "ride the game's fence" is not a synchronization primitive for CE's own allocators, and a slower test app can hide a multi-frame-behind GPU that a real game (mid-startup, with EOS+Streamline+FFX churn) will expose. - GTA `installed/captureengine/logs/gtanooverlay` (2026-06-21) proved the no-callback FSR FG overlay path was structurally dead, not merely mis-gated. The overlay rendered ~4500 backbuffer frames, then `Overlay frame #` froze exactly at the native FFX takeover (`FG EVENT kind=native-fsr-configure-on runtime=FSR_FG active=1`) while `DetourPresent` heartbeats kept advancing — so the present hook was alive but `ProcessFrame` was being skipped. The intended replacement, the ECL UI-texture bundle, fired **0** times (`UI-bundle overlay appended` count = 0). Root cause: the bundle's GPU resources (`g_FFXUiCompositeList`/`RtvHeap`/allocators + FFX overlay adapter) were created only inside `DX12_CompositeOverlayOntoFFXUiResource`, which is dead (`DX12_ShouldCompositeOverlayOntoFFXUiResource()` hard-returns false and nothing calls it), so `RecordBundleOverlayForGameECL` always hit its null-resource guard and returned null. With `DX12_IsFFXUiResourceCachedForBundle()` true (a UI texture WAS cached during the brief pre-VEH-disarm window), `DetourPresent` took the near-passthrough skip and never drew — the overlay was skipped in Present AND never bundled = invisible the whole FG session. The matched `dx12_fg_switch_test.exe` capture `installed/captureengine/logs/fgswitchtestapp` showed the bundle fired 0 times there too; it only "worked" because that app toggles FG off, so the overlay was visible during FG-off phases via the normal backbuffer path. Fix: live `EnsureFFXUiCompositeBundleResources` (creates exactly the bundle-needed resources, no separate-ECL queue/fence), relaxed list+RTV-heap readiness guard, and a `ChooseNoCallbackFSRFGOverlayRoute(cached, firing)` gate so `DetourPresent` falls back to the minimal backbuffer draw whenever the bundle is not actually firing (never blank). Durable lesson: a silent null-return in the overlay submit path can hide total invisibility for an entire session — bundle skip/fire and the cached UI-resource pointer are now logged, and the "skip the backbuffer draw" decision is conditional on the bundle actually firing.

The callback-on-normal-route expectation was later relaxed in build `0.1.2554` so that `safePostFSRBootstrapPath` alone is sufficient (explicit `SetOptions` is no longer required), preventing deadlocks when the bootstrap topology is safe but SetOptions has not yet been observed.

## Current Practical Guidance
- Any FG fix should be reasoned through as a state-transition problem, not as a one-off title quirk.
- When you need a strict injected baseline, use `[Overlay] observer_only=true`; do not treat `enabled=false` alone as equivalent.
- After the strict passive baseline is clean, use `[Overlay] observer_only=true` plus `[Overlay] observer_policy_only=true` to reintroduce only the Streamline startup-policy family without re-enabling PostSL or special startup Present routing.
- If that remains stable, use `[Overlay] observer_only=true`, `[Overlay] observer_policy_only=true`, and `[Overlay] observer_startup_present_only=true` to reintroduce only the remaining non-Streamline startup-Present probe pieces while PostSL callback install/use and rendering still stay passive.
- If that staged seam still freezes on `0.1.2269` or newer, the next suspect is no longer any special Streamline Present routing path, because observer mode now keeps both the promoted and synthetic Streamline-originated startup Present families passive again.
- With `20260414_232934` now stable, the remaining gap has shifted back to active mode: observer probing shows GTA's reproduced crash requires special Streamline Present routing during startup, while the passive startup-policy-only path is stable. Re-check the active pre-armed PostSL plus special Streamline Present routing family next.
- With `20260415_002110` now analyzed, the next active validation target is narrower still: confirm whether removing both special startup Present seams from active mode is enough to stop the crash while preserving the startup-policy/window machinery and later wrapper-progress-backed PostSL activation path.
- If a change touches queue ownership, runtime classification, startup bypass, post-FSR recovery, or metrics publication, assume both Talos-style and GTA-style regressions are possible until proven otherwise.
- Preserve generic signals such as runtime mode, queue provenance, swapchain ownership, and stack evidence. Do not replace those with per-title conditions.
- If a change would make the correct path depend on the executable name, stop and justify that carefully before proceeding.

- Talos `installed/captureengine/logs/20260423_044543` on build `0.1.2551` exposed a new overlay disappearance seam after a long FSR/DLSS FG mode-switching sequence. After FSR turned off, then DLSS turned off, `ShouldDeferOverlayInitUntilCommandQueueSettlesAfterRecentStreamlineTeardown` locked the overlay out for ~600 frames because both `scQueue` and `lastWorkingQ` were null. `lastWorkingQ` had been cleared during the earlier FSR→DLSS ON transition (`ShouldInvalidatePostSLLastWorkingQueueOnFreshPostFSRStreamlineHandoff`) and was never repopulated because PostSL never activated during the subsequent DLSS epoch (`safeBootstrap=0`). The deferral policy skipped the `commandQueueMatchesPrimaryGameQueue` escape hatch when `hasSwapchainQueue` was false, so the perfectly valid primary game queue could not satisfy the recovery condition. Build `0.1.2552` evaluates that escape hatch even without a swapchain queue, restoring overlay visibility promptly after Streamline teardown.
- The same `20260423_044543` session also crashed with exception `0x00008000` inside `sl_dlss_g` (Streamline DLSS FG) on the present thread, called via `sl_interposer`. This is a Streamline internal threading/mutex exception (`0x00008000` is a user-mode software exception raised by `sl_dlss_g`), distinct from the older `std::_Throw_Cpp_error` or `dxgi!CDXGISwapChain::Present+0x5` breakpoint-corruption families. CE's VEH catches it and returns `EXCEPTION_CONTINUE_SEARCH`, but no SEH handler catches it and the game terminates. The rapid ON/OFF toggling (FSR→DLSS ON, OFF, ON, OFF within ~40 seconds) stresses Streamline's fragile multi-device initialization/teardown. The overlay-deferral fix may mitigate this indirectly by restoring normal GPU work promptly instead of leaving the game in a deferral loop for hundreds of frames, but there is no obvious non-invasive CE-side suppression for the exception without risking Reflex or other Streamline Present-hook features.
