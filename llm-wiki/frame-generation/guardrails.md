## Scope
This page records current guardrails and tested transition families for no-FG, DLSS FG, and FSR FG switching. The goal is generic support across games, not a pile of title-specific hacks.

## Project Guardrails
- We must be careful not to break DLSS FG and FSR FG in GTA again when fixing any FG issue in Talos.
- Talos and GTA are validation families, not excuses for game-specific runtime hacks.
- Switching FG must work gracefully in both Talos and GTA validation scenarios, in all directions and combinations, without crashes, without lost overlay rendering, and with the correct visible FG status.
- Fixes must stay generic so DLSS FG and FSR FG support scales across multiple games instead of accumulating title-specific branches.
- The pseudo-overlay is not an injected-overlay replacement for FG. It must not be used to paper over DLSS FG or FSR FG injected-overlay failures.

The 2026-07-02 proxy-Present driver moved that UI work before AMD's critical section, with presenter-thread fallback only when the proxy hook was not live. Its old bundle (`RecordBundleOverlayForGameECL`/`TryAppendNoCallbackBundleOverlay`/`EnsureFFXUiCompositeBundleResources`) was correctly removed: it appended to arbitrary game ECLs with unsynchronized allocator/upload reuse and caused the `nvwgf2umx`/`ffxQuery` crash family. Do not restore that mechanism. The old absolute "UI queue only" invariant is superseded by the current 2026-08-14 final-batch route above: the new path targets only a twice-stable final presenter batch, joins the existing ECL call rather than adding one, and proves reuse/lifetime with an inline writeback marker rather than a queue `Signal`. The FFX UI route remains the make-before-break fallback.
- `DetourPresent` (`hook/common/dxgi_shared.cpp`) chooses the no-callback FSR FG overlay route via `ChooseNoCallbackFSRFGOverlayRoute(runtimeOwns, liveQueueIsOrigGame, fsrFGDisabledSuspendPending, uiResourceCached, bundleOverlayActivelyFiring)`. **REVISED 2026-07-03 (session 20260703_210021):** while AMD OWNS the swapchain (runtime-owned, live queue != origGame) the route is ALWAYS `kSkipBundleCovers` — the backbuffer submit is NEVER used there, whether AMD is interpolating OR suspended. The old `runtimeOwns && !fsrFGDisabledSuspendPending` relaxation that sent a suspension to the backbuffer is GONE: the backbuffer submit on AMD's runtime-owned swapchain doesn't just crash during active interpolation — during a SUSPENSION its GPU-completion fence never signals (AMD stops flushing its runtime queue while suspended) so `DetourPresent` stalls ~1s EVERY present (app → ~1 fps). `fsrFGDisabledSuspendPending` no longer gates the route. `kSkipBundleCovers` → bundle composite on CE's own fenced queue (prework drives on the game thread; DetourPresent passthrough while the proxy hook is live, composite-only fallback otherwise); `kMinimalBackbuffer` is reached ONLY when the game owns its OWN native swapchain (`liveQueueIsOrigGame`, stale-latch recovery) or AMD does not own the swapchain (non-runtime-owned escape hatch, `bundleOverlayActivelyFiring` still consulted). If AMD does not composite the UI resource during a suspension the overlay is at worst blank — never a crash, never a stall.
- **RETAINED NO-CALLBACK SUSPENSION VISIBILITY RULE (2026-07-02, session 20260702_142655 — test app overlay blank for the whole FSR suspension):** during a retained no-callback FSR suspension the "inactive runtime-owned swapchain init queue-settle" defer must NOT apply (`ShouldDeferInactiveRuntimeOwnedSwapchainOverlayInit(..., retainedNoCallbackFSRSuspension)`): AMD keeps the FI swapchain+queue latched while the app renders on origGame, so cmdQ==scQ can never settle — the defer stranded overlay init (and the coverage gate was blind to it). The suspension-approved render path is the backbuffer on the runtime-owned swapchain queue (`kUseRuntimeOwnedSwapchainQueue` routing). Both queue-settle defer sites now attribute `[OVERLAY COVERAGE]` gates, and `[OVERLAY DOUBLE-DRAW]` flags two different overlay routes rendering in the same present window.
- **NO-CALLBACK FSR SUSPENSION RIDES THE BUNDLE, NEVER THE (STALLING) BACKBUFFER (2026-07-03, TWO sessions on the same `dx12_fg_switch_test.exe` suspend edge):** the overlay-route decisions (`ChooseNoCallbackFSRFGOverlayRoute` at present time AND `ShouldSkipSeparateOverlayGpuWorkForRuntimeOwnedFrameGeneration` at the init/dedicated-queue gate) must AGREE, and while AMD owns the swapchain that agreement is: overlay rides the UI-resource composition BUNDLE (CE's own fenced queue), CE submits ZERO backbuffer/separate work on AMD's runtime queue — active OR suspended. Two failed iterations proved why:
  - **20260703_204119 (blank):** the skip decision fed the raw cached-UI-texture latch `DX12_IsFFXUiResourceCachedForBundle()` (a pointer, set once, never cleared on suspend) as "bundle covers" → `skip=true` deferred overlay init the whole suspension, while the router had been sending the suspend to `kMinimalBackbuffer` — net "nobody draws" = blank.
  - **20260703_210021 (perf death):** the "fix" that made the suspend actually take the backbuffer (`DX12_ProcessFrameMinimal`) collapsed the app to **~1 fps** — `DescFree GPU-completion wait timed out (guard=1 completed=0)` + `DetourPresent TOTAL SLOW ~999ms` EVERY present (40+ times). AMD stops flushing its runtime queue while suspended, so the overlay's GPU-completion fence never signals and CE waits the full ~1s timeout per frame. Dump: game/present thread parked in `WaitForSingleObjectEx` inside CE's wrapped-present path, called from `amd_fidelityfx_framegeneration_dx12` Present. This **DISPROVED** the "suspension backbuffer is safe (AMD not interpolating)" assumption (session 20260623_054929): safe-from-crash ≠ non-stalling.
  - **ROUTING RESOLUTION:** `ChooseNoCallbackFSRFGOverlayRoute` drops the `&& !fsrFGDisabledSuspendPending` gate → `runtimeOwns` (active OR suspended) always returns `kSkipBundleCovers`; the skip decision matches (`bundleCovers = ffxUiResourceCompositionActive && !liveSwapchainQueueIsOriginalGameQueue`, no suspend gate). `kMinimalBackbuffer`/`skip=false` is reachable ONLY at a stale latch (game recreated its own native swapchain, `liveQueueIsOrigGame` — backbuffer on the game's own actively-flushed queue is safe) or non-runtime-owned. So CE submits ZERO work on AMD's runtime queue in either active or suspended runtime-owned states.
  - **VISIBILITY RESOLUTION (session 20260703_212441 proved AMD does NOT composite the UI resource in passthrough — the overlay was drawn onto the UI texture every frame yet blank):** during the suspension the proxy-present prework draws the overlay DIRECTLY onto the game-facing FI-proxy's CURRENT backbuffer (`DX12_CompositeOverlayOntoSuspendBackbuffer`, `GetCurrentBackBufferIndex`+`GetBuffer`, `PRESENT→RT→PRESENT`, blend on top, no clear) instead of the (ignored) UI texture — but STILL on CE's own dedicated composite queue `g_FFXUiCompositeQueue` (untracked by AMD, CPU-waited before Present), NEVER AMD's runtime/game queue (that submit is the ~1fps stall). The UI-texture composite is kept EXACTLY as-is for active FG (GTA path, byte-for-byte untouched); the backbuffer function is a separate, isolated, gracefully-skipping function. STRICTLY GATED to `DX12_IsNativeFSRFGSuspendedDisablePending()` in the prework, so GTA's active FSR FG (0 suspensions, session 20260703_213508) never reaches it. Diagnostic: `FSR-suspend overlay drawn onto PRESENTED BACKBUFFER via CE queue ...`; prework log gains `route=suspend-backbuffer|ui-resource`. Units: `NativeFSRNoCallbackSuspendRidesBundleNeverStallingBackbuffer`, `SuspendBackbufferOverlayUsesCEQueueGatedToSuspension` (wiring + CE-queue-only invariant), revised `NoCallbackFSRFGOverlayRouteNeverSubmitsBackbufferWhenRuntimeOwnsSwapchain`. **OPEN — needs on-hardware validation:** (a) test app overlay now visible + full-speed during suspend; (b) GTA/Talos still crash-free (the backbuffer function only runs if a real game ever suspends FSR FG — GTA didn't, but if it does, `GetBuffer`-on-proxy + the `PRESENT`-state barrier assumption are the unproven parts, guarded to skip-not-crash).
- **RETAINED-SWAPCHAIN LEAK BOUNDARY (2026-07-02, session 20260702_092933 — GTA crash on FSR→DLSS APPLY):** the retained Streamline startup-activation swapchain is an AddRef'd COM reference; while CE pins it, DXGI refuses a replacement swapchain on the same HWND (E_ACCESSDENIED) and a runtime-managed create failure is FATAL (GTA null-derefs the missing swapchain). Rules: (1) startup-transport retains (bypass / overlayless-handoff present paths) STOP at PostSL confirmation (`ShouldRetainStreamlineStartupActivationSwapchainFromStartupTransport` — the slot is never consulted after confirmation, so later retains are pure leaks; the single release fires AT confirmation); (2) the post-FSR Streamline runtime swapchain create releases the retained chain BEFORE forwarding (make-before-break, INLINE defer block); (3) E_ACCESSDENIED is NEVER blindly passed through — runtime-managed/third-party creates get the minimal CE unpin (release retained chain, no overlay teardown/GPU flush) + retry, escalating to the full overlay cleanup only if the HWND stays pinned (`ChooseCreateSwapchainAccessDeniedRecovery`). Regression tests in `tests/test_dxgi_shared.cpp` (retain gate, recovery choice, source invariants).
- **FOREIGN-ENTRY-CHAIN RETRY BOUNDARY (2026-08-13, sessions 20260813_200741 / 20260813_211734 — dx12_fg_switch_test via Steam overlay + RTSS exits cleanly after E_ACCESSDENIED, no dump):** the deep CreateSwapChainForHwnd hook forwards through its below-the-chain trampoline, which performs the genuine DXGI create WITHOUT entering the foreign overlay entry chain. A foreign overlay whose CreateSwapChainForHwnd entry/vtable handler holds the old swapchain (and with it the HWND association DXGI checks) until a replacement create arrives through that handler then never gets to release it, so every trampoline retry stays E_ACCESSDENIED even after CE's own overlay/RTV/retained-chain cleanup (the app's native fallback create fails identically and the app stops its main loop). Session 20260813_211734 proved the residual pin precisely: the post-destruction pin probe showed 3 FOREIGN refs on the old OFF-phase chain (wrapper "real refs=8" = CE base + 4 promoted + 3 foreign; the route probe shows the entry holding original bytes with RTSS's vtable-slot handler as the immediate caller), so the pin is RTSS/Steam per-swapchain bookkeeping, not CE. After CE's cleanup the recovery retries ONCE through the live entry chain (`ShouldRetryAccessDeniedCreateThroughLiveEntryChain` policy; nested below-the-chain calls pass straight through under `s_forwardingAccessDeniedCreateThroughEntryChain`), so the foreign handlers can release the old swapchain before the genuine create runs. Excluded: third-party-overlay callers (an overlay's own internal create must not re-enter its own entry handler), shutdown, and ReShade-style proxy factories (saved-slot vtable guard, sessions 20260813_004853/004923 — the call is only legal on the system DXGI factory vtable). Diagnostics: `DeepHook: route diagnostics` (immediate caller module + live entry bytes), bracketed `DeepHook: E_ACCESSDENIED pin diagnostics` (pre-cleanup / post-cleanup / post-entry-retry guarded refcount probes), and the wrapper `post-destruction real refcount` probe. Regression tests: `AccessDeniedRetryThroughLiveEntryChainRequiresForeignChainAndSafeCaller` (`tests/test_dxgi_shared_part8.cpp`), `AccessDeniedExhaustionWritesDiagnosticDumpAndBracketedPinProbes` (`tests/test_dxgi_shared_access_denied_dump.cpp`).
- **E_ACCESSDENIED-EXHAUSTION DUMP BOUNDARY (2026-08-13, sessions 20260813_211734 / 20260813_220022):** a failed runtime-managed swapchain create is fatal to the game, yet the failure exits CLEANLY (exit code 0, no exception), so `ShouldCapturePreTerminationDump` (which skips exit code 0) never fires and the session keeps no dump. Every exhausted recovery arm (deep + inline) must therefore write a session-local diagnostic minidump itself: `CaptureCreateSwapchainAccessDeniedExhaustedDump` (implemented in `hook/main_fatal_dump.cpp`) writes once per process (hint `swapchain_access_denied_exhausted.dmp`, synthetic exception code 0xE000EACC). **The dump must go through the EXTERNAL helper first** (`TryCapturePreTerminationDumpWithExternalHelper` -> `captureengine.exe --dump-helper`) with only a minimal in-process MiniDumpNormal-class fallback: session 20260813_220022 ran the in-process quick-assert capture on the render thread for ~36 s (114 MB) and visibly froze the game until the FreezeWatchdog fired (cdb stack: `DeepHookCreateSwapChainForHwnd -> CaptureCreateSwapchainAccessDeniedExhaustedDump -> WriteSupplementalCrashDump -> HookedMiniDumpWriteDump -> dbgcore!MiniDumpWriteDump`). The test app mirrors this on its own fatal path: `WriteFatalSwitchDump` with a light MiniDumpNormal+ThreadInfo+UnloadedModules type (never DataSegs/IndirectlyReferencedMemory) plus a nonzero 0xE000EACC process exit code instead of a clean 0.
- **SWAPCHAIN-RECREATION PIN BOUNDARY (2026-08-14, sessions 20260813_222058 / 20260813_234123):** dxgi refuses `CreateSwapChainForHwnd` with 0x80070005 while ANY chain for the HWND is alive, even when the create uses a different factory (proven with a standalone dxgi probe). After the game and CE release everything, residual references remain (foreign per-chain bookkeeping plus one internal ref) and they do not drain within any acceptable retry window, so retry-waiting is not a fix and must not be added as one. The switch app therefore keeps the FSR swapchain/context alive across OFF<->FSR (real-FSR3-game lifecycle: FG off = passthrough Present through the FFX proxy, re-entry = `ffxConfigure` only); the OFF branch in `dx12_fg_switch_render_switch.cpp` keeps the FFX chain and never recreates a native chain. - **DEADLOCK BOUNDARY (2026-07-02, session 20260701_213656 — permanent GTA freeze on the FIRST FSR-FG frame):** CE must NEVER call `ffxConfigure` (RegisterUiResource or anything else) from AMD's presenter thread — i.e. never from `DetourPresent`/real-swapchain present paths during runtime-owned no-callback FSR FG. CE's re-assert from the presenter thread closed the cycle. ## Streamline API generation (1.x vs 2.x) - an ABI precondition, not a detail

- **`slSetTag` and `slEvaluateFeature` exist in both Streamline generations with different signatures, so CE must establish the generation before hooking either.** `hook/common/streamline_api_generation.h` classifies the interposer from generation-exclusive exports (1.x: `slSetFeatureConstants`, `slGetFeatureSettings`, `slSetFeatureEnabled`, `slIsFeatureEnabled`, `slGetFeatureConfiguration`; 2.x: `slSetTagForFrame`, `slGetNewFrameToken`, `slGetFeatureRequirements`, `slSetD3DDevice`, `slGetFeatureFunction`, `slIsFeatureLoaded`). The two ABI-sensitive exports may never classify anything, because they are present in both. Both marker sets, or neither, is `Unknown` and installs nothing ABI-sensitive - the generation-independent hooks (`sl.common!slGetPluginFunction`, the DLSS-G/Reflex feature exports) are unaffected either way. The gate covers the inline hooks, the IAT patches **and** the GetProcAddress-time dynamic routes, which is why those two moved out of `RegisterDynamicHooksOnce` into `RegisterAbiSensitiveDynamicHooksOnce`.
  - The 2.x hook on a 1.x interposer is not a mis-parse, it is memory corruption: 1.x passes the command buffer in RCX, CE's 2.x prototype reads RCX as `uint32_t feature`, and forwarding hands Streamline the truncated 32-bit half back as its command buffer. The Witcher 3 (sl.interposer 1.5.6, session `20260820_221409`) died on `sl.common+0x2379D` dereferencing `0x11C5F6F0`, the low half of a live `ID3D12GraphicsCommandList`. The 1.x `slSetTag` hook was the same bug one arming away - it walks `tags[i]` out of what 1.x passes as a small `BufferType` enum.
- **1.x keeps the official-UI overlay route, on 1.x terms.** `hook/apis/streamline_hook_v1.cpp` forwards both exports verbatim and returns `bool` (1.x returns in AL; a 32-bit zero written where the caller reads one byte is a silent behavior change). 1.x `slSetTag` carries no command buffer, so the UI record is deferred to the next `slEvaluateFeature`, which supplies one and still precedes the present DLSS-G consumes. 1.x also has no `slSetD3DDevice`, so the first evaluate whose command buffer answers as an `ID3D12GraphicsCommandList` is what proves the D3D12 route and arms the same `BeginPreactivationStandby(2)` the 2.x path arms.
- **The 1.x `sl::Resource` layout is proven per resource, never assumed.** 48 bytes committed and readable, `type == eResourceTypeTex2d`, `native` non-null and pointer-aligned behind a readable vtable whose first slot is executable, `state` a subset of the defined `D3D12_RESOURCE_STATES` bits, then a real `QueryInterface` to `ID3D12Resource` with a `TEXTURE2D` desc. A mislaid offset yields "no record"; it can never produce a barrier from a garbage before-state. `eBufferTypeUIColorAndAlpha` is 23 in sl.common 1.5.6's own name table, the same value as 2.x.
- **Both 1.x hooks are hot-path code and cost two atomic loads when the bootstrap is dormant.** `dx12_streamline_ui_overlay::IsFrameTagTrackingActive()` (the atomic `OnFrameTag` reads first) plus a pending-tag flag gate every probe, `QueryInterface` and held reference. The remembered texture is adopted from the `QueryInterface` that proved it - never released and re-taken, which would be a window for the game to free it underneath CE - and is dropped by the very next evaluate whether or not it was used.
- **`streamline_dll_path` cannot upgrade a title across generations and refuses to try.** A 1.x game imports the five 1.x-only exports; a 2.x interposer exports none of them, so the loader fails the import and the process dies before its first frame. `StreamlineOverrideGenerationMatches` compares the replacement file's `VS_FIXEDFILEINFO` major against the loaded interposer's - the one property the whole sl.* set shares, plugins included - and refuses a mismatch on both redirect routes, naming the generation-independent alternative in the log. The NGX runtimes (`dlss_sr_dll_path`, `dlss_fg_dll_path`) are the upgrade path that does work on a 1.x title. Unknown on either side keeps the historical behavior rather than breaking a working setup on an unreadable version resource.
- **A 2.x runtime can be hosted inside a 1.x process, because 2.x binds its plugins by path and not by base name.** Measured 2026-08-21 by a standalone probe (`sl_coexist_probe.cpp`, modes `sl1only` / `sl2only` / `coexist`), which is the feasibility gate for any in-process generation bridge. With The Witcher 3's `sl.interposer` 1.5.6 and its `sl.common` / `sl.dlss` / `sl.dlss_g` / `sl.reflex` already resident, loading Talos Reawakened's 2.11.1 interposer by full path and calling `slInit` with `Preferences::pathsToPlugins` pointing at that folder returns `eOk`, maps a **second** `sl.common.dll` at a distinct base address, and resolves every 2.x plugin from the 2.x folder; `slIsFeatureSupported` answers `eOk` for both `kFeatureDLSS` and `kFeatureDLSS_G`, and `slShutdown` returns `eOk`. Throughout, `GetModuleHandleW(L"sl.common.dll")` still returns the **1.x** image - so the base-name collision that would have killed the idea does not decide plugin binding. The duplicate-instance guard in `graphics_runtime_module_policy.h` must therefore be exempted narrowly for a cross-generation pair; two instances of the *same* generation is still the crash it was written for (`20260816_045933`).
  - Two measured facts constrain any bridge built on this. SL1's `VS_FIXEDFILEINFO` reads `1.0.0.0` where its StringFileInfo reads `1.5.6.0`, so `DllFileMajorVersion()` is sound for *generation* gating but cannot pin a specific 1.5.x minor - that needs the string table. And under the default `PreferenceFlags` (`eAllowOTA | eLoadDownloadedPlugins`) the 2.x interposer also discovers OTA plugins under `C:\ProgramData\NVIDIA\NGX\models\sl_*_0\versions\...` and resolves duplicates by version (`Removing plugin with name: sl.common superseded by plugin sl.common`). The staged 2.11.1 set won that arbitration in this run, but a bridge that claims a pinned runtime should clear those flags rather than let an OTA update choose which plugin it actually runs.
- **`streamline_upgrade` bridges a 1.x game onto a 2.x runtime, and it is deliberately NOT the substitution path.** `hook/apis/streamline_bridge_policy.h` (policy, unit-tested) plus `hook/apis/streamline_bridge.{h,cpp}` (runtime) load the `streamline_dll_path` folder's 2.x interposer by full path as a SECOND, CE-owned runtime, initialise it with `pathsToPlugins` pinned to that folder, and repoint the game's `sl.interposer` import slots at CE thunks. The game's own 1.x runtime stays loaded and untouched; nothing on disk is renamed or patched, because the imports were resolved before CE existed and are rewritten in memory instead. Default off - it is more invasive than the path overrides and carries the same anti-cheat warning.
  - **The duplicate-instance guard needed no exemption, contrary to the original plan.** `WouldRedirectDuplicateLoadedModule` governs *redirecting the game's own loads*, and the bridge never asks for a redirect. What the bridge does need is the opposite: while it is active, `StreamlineOverrideRedirectAllowed` stands the whole sl.* substitution down. Both mechanisms want the same configured folder for opposite purposes, and letting both act would rewrite the game's 1.x plugin loads into the 2.x folder - the version mixing those guards exist to prevent.
  - **Activation is all-or-nothing and decided once, before anything is touched.** It requires the opt-in, a configured path, a genuine V1-process/V2-runtime pairing, and that the game has not already driven its own Streamline (`sl.common.dll` resident is the late-signal: 1.x loads its plugins from inside `slInit`). The module is then re-checked by its *export surface*, not just its file version, before CE binds to it. Any refusal leaves the process exactly as it was, because a half-bridged process - some calls translated, a device created through one generation and driven through the other - is worse than either end state.
  - **The `sl::Preferences` mirror in `streamline_bridge.cpp` was measured, not read.** The hook DLL has no path to the vendored SDK headers (`get_fg_sdk_include_flags` is wired for the FG test apps only), so the struct is mirrored by hand - a claim about somebody else's ABI. Comparing it against the real 2.11.1 header found the `BaseStructure` header **inverted**: `next` leads at offset 0 and `structType` follows at 8, the opposite of how the declaration reads. Size and every payload field were already correct, so this would have initialised the runtime with a garbage struct type and version and failed nowhere near its cause. Now verified at 18/18 offsets, size and GUID (scratchpad `sl_prefs_layout.cpp`). Re-measure whenever the pinned SDK version moves.
- **Where the 1.x ground truth comes from, and how far each source can be trusted.** There is no public Streamline 1.5.6 header: the upstream repo's 1.x tags stop at **v1.1.1**, so the hand-off assumption that 1.5.6 layouts come straight from public headers is wrong. Three sources, in decreasing authority for this title:
  - **W3's own `sl.interposer` / `sl.common` 1.5.6 binaries** - authoritative for anything version-specific. The feature-name table (DLSS 0, NRD 1, NIS 2, Reflex 3, Debug 4, DLSS_G 5, Common UINT_MAX) and the 38-entry buffer-type table (0..37) come from here, and only from here.
  - **OptiScaler's vendored `external/streamline1/sl1*.h`** - a real SL1 header set used against shipping SL1 titles. Its `Constants` is field-identical to v1.1.1's, which is what makes the 1.x `Constants` layout trustworthy across the 1.x line. Its `Resource` (`type/native/memory/view/state/ext`) independently confirms the offsets CE already encodes in `streamline_api_generation.h` (type 0, native 8, state 32, size 48). But it predates DLSS-G: its `Feature` enum has no `eFeatureDebug` or `eFeatureDLSS_G`, and its buffer-type list stops at 33 with index 23 still spelled `eBufferTypeUIHint` (1.5.6 renamed that same slot to `UIColorAndAlpha`, which is why 23 survives into 2.x). Use it for the stable core; never for the feature enum.
  - **The 2.11.1 headers vendored under `build/fg_sdk_include/streamline/include`** - authoritative for the 2.x side.
- **Feature values are not identity across the generations; buffer types are.** From sl.common 1.5.6's own name tables against the vendored 2.11.1 headers in `build/fg_sdk_include/streamline/include` (provisioned by `tools/build/build_fg_sdk.py`): `BufferType` matches 1:1 through index 25, which covers every value 1.x can emit, `UIColorAndAlpha` 23 included. `Feature` does not - `DLSS` / `NIS` / `Reflex` hold at 0 / 2 / 3 and `Common` stays `UINT_MAX`, but 1.x `eFeatureDLSS_G` is **5** where 2.x `kFeatureDLSS_G` is **1000**, 1.x `eFeatureNRD` 1 is 2.x `kFeatureNRD_INVALID`, and 1.x `eFeatureDebug` 4 collides with 2.x `kFeaturePCL` 4. Any translation must remap the feature enum and must never pass 4 or 5 through untranslated.
