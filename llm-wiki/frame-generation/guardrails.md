## Scope
This page records current guardrails and tested transition families for no-FG, DLSS FG, and FSR FG switching. The goal is generic support across games, not a pile of title-specific hacks.

## Project Guardrails
- We must be careful not to break DLSS FG and FSR FG in GTA again when fixing any FG issue in Talos.
- Talos and GTA are validation families, not excuses for game-specific runtime hacks.
- Switching FG must work gracefully in both Talos and GTA validation scenarios, in all directions and combinations, without crashes, without lost overlay rendering, and with the correct visible FG status.
- Fixes must stay generic so DLSS FG and FSR FG support scales across multiple games instead of accumulating title-specific branches.
- The pseudo-overlay is not an injected-overlay replacement for FG. It must not be used to paper over DLSS FG or FSR FG injected-overlay failures.

## Facts
- The tree now has a shared FG session/planner layer in `hook/common/fg_session_state.{h,cpp}` that captures the current mixed DX12/Streamline/FFX FG state, computes a concrete `FGActionPlan`, and emits structured transition/session logs. It is currently used as the common authority for diagnostics and publication, while some low-level queue/route/transport execution still remains in the older DX12/DXGI code paths.
- `hook/common/dx12_fg_transition_model.cpp` is now a compatibility adapter over that planner-backed session snapshot instead of a separate competing reducer. Existing transition/replay tests still validate the same public transition contract, but the underlying snapshot now comes from the shared FG session layer.
- The planner currently sees explicit hook events from DX12, Streamline, FFX, and top-level Present observation for at least: authoritative Streamline startup handoff, authoritative FFX takeover, native-FSR configure on/off, PostSL callback install/remove, PostSL activation complete, PostSL first confirmed render, swapchain invalidation, Streamline runtime updates, and top-level Present observation.
- Intercepted `slGetFeatureFunction` lookups for DLSSG feature functions should return CE's stable wrapper when a callable original/trampoline exists, even when inline patching reports ready. This keeps cached game/app feature pointers observable across Streamline export reload/repair during mixed-FG switches; direct import and inline hooks still cover direct callers.
- Fresh `sl.*.dll` module-load notifications must not proactively call Streamline feature-function lookup. `installed/captureengine/logs/20260601_152148` crashed inside Streamline during `slInit` after CE's load-notification path re-entered plugin/feature lookup while Streamline was still mutating plugin state. Module-load inspection may use direct exports/IAT readiness, but DLSSG/Reflex feature lookup is deferred to normal runtime calls. Healthy logs include `Deferred proactive feature-function lookup during module load`.
- A post-FSR DLSS handoff with safe bootstrap proof is stronger than generic startup evidence. It may bypass the repeated-callback PostSL activation countdown and reactivation warmup so the overlay does not visibly blank during the short FSR->DLSS interval. Pure-DLSS cold startup still keeps the warmup.
- Pure-DLSS startup can be proven either by explicit `slDLSSGSetOptions(ON)` or by official active state from `slDLSSGGetState` (`updateActive=1` / CE `g_StreamlineFGRunning=1`). The latter is still stronger than mere Streamline DLL presence and is enough to invoke normal-route PostSL callbacks and bypass the startup callback deferral; logs should show `activeDLSSSignal=1`.
- Pure `DLSS FG -> off` menu suspend/resume with no FSR history, no FSR API active, no runtime-owned native-FSR present path, a healthy device, and a live overlay/sync/swapchain queue can rebuild immediately after the safe drain. Do not spend the generic 60-frame FG handoff cooldown blanking the overlay in that case. Mixed/post-FSR paths keep the stricter cooldown because their queue/swapchain teardown proof is different.
- Current trace-replay tests explicitly cover:
  - Talos-style `off -> DLSS -> off -> FSR`
  - GTA-style `FSR -> DLSS` without a clean `off`
  - GTA-style DLSS suspension and resume during loading
  - startup coexistence using startup bypass first and normal routing after settle
- Current overlay status tests explicitly cover visible label switching between `FSR FG` and `DLSS FG`, plus clearing back to `FG` when frame generation turns off.
- Talos `installed/captureengine/logs/20260423_215138` / `20260423_220858` and GTA `installed/captureengine/logs/20260424_020300` showed that generic FG switching correctness also depends on CE actually observing the last Streamline feature-call edge. When Streamline export inline patching fails or a title uses newer feature entrypoints, CE still needs generic direct-import / dynamic-lookup interception for `slDLSSGSetOptions`, `slDLSSGGetState`, current Reflex `slReflexSetOptions`, and legacy `slReflexSetConstants`, and that fallback has to be armed on the actual owner module of the failing export rather than only on the core Streamline DLLs. Otherwise CE can miss either the menu-side `DLSS FG -> off` edge that clears the overlay label or the Reflex `frameLimitUs` traffic needed to diagnose stale half-rate caps after DLSS FG is disabled.
- Talos `installed/captureengine/logs/20260425_002642` on build `0.1.2584` sharpened that rule: the game turned DLSS FG off in the 2D menu, but CE only saw steady active `slDLSSGGetState` and never saw an explicit OFF edge before the user noticed the stale label. Feature-hook discovery now covers every loaded `sl.*.dll`, not just `sl.interposer.dll` / `sl.common.dll`, and direct-import fallback retries are idempotent so late-loaded/menu-side imports can be patched without corrupting the original target.
- Talos `installed/captureengine/logs/20260425_173428` on build `0.1.2587` sharpened the 2D-menu `FSR FG -> DLSS FG` path. A fresh authoritative Streamline handoff created a new runtime-owned swapchain queue and CE detected DLSS FG through active `slDLSSGGetState`, but PostSL remained dormant because `safeBootstrap=0` while no SL wrapper queue appeared in the menu. The current guard now marks that fresh handoff as pending immediately to suppress false queue-change `FSR_FG` relabels, and accepts a runtime-owned Streamline swapchain queue as safe post-FSR bootstrap evidence when it is the live command queue and its ECL submit path is already tracked.
- GTA `installed/captureengine/logs/20260425_000339` showed that a pure-DLSS enable can still produce transient `slDLSSGGetState` OFF jitter after PostSL has already confirmed and submitted more than the short frame 9-12 stale-OFF stabilization window. The current guard now keeps only GetState OFF deferred until the 30-frame PostSL warmup proof threshold; explicit `slDLSSGSetOptions(OFF)` uses the older shorter guard so user/requested disables are not broadened by the GetState-only protection.
- Explicit native-FSR off via `ffxConfigure(frameGenerationEnabled=0)` is now treated as stronger evidence than queue-change/ECL heuristics during runtime-owned teardown. That prevents `FSR_FG -> off` from immediately re-latching heuristic `FSR_FG` on the lingering runtime-owned queue and leaving the overlay status stale. GTA `installed/captureengine/logs/20260519_144449` sharpened the endpoint: if FSR has explicitly configured OFF and a later swapchain queue proof returns to `origGame` while no authoritative FSR runtime is active, CE must end the runtime-owned native-FG teardown instead of preserving ownership solely because the stale native-FG present path latch is still true.
- FFX present-callback bridge installation is only for enabled native-FSR frame-generation configures that actually provide a real app/default present callback to wrap. Disabled `ffxConfigure(frameGenerationEnabled=0)` packets can repeat rapidly during teardown; they should be treated as OFF evidence and diagnostic breadcrumbs, not as a reason to reinstall CE's callback bridge. Existing bridge state may remain available for any final already-in-flight runtime callback until context destroy. GTA `installed/captureengine/logs/20260519_191243` sharpened the startup re-enable variant: a fresh runtime-owned native-FSR takeover can send an initial disabled startup-arming configure before the real enabled configure. CE preserves the authoritative FSR-arming state for that packet, but still forwards the disabled configure unmodified and waits for an enabled configure before installing the CE callback bridge. GTA `installed/captureengine/logs/20260602_161000_gtafreezestartwithfsrfg` sharpened the no-callback variant: if enabled native FSR supplies `presentCallback=null`, CE must preserve AMD's internal no-callback composition path instead of synthesizing its own FFX present callback and taking over current-to-output composition. Expected diagnostics include `Native FSR disabled startup-arming configure forwarded without CE present-callback bridge`, `Native FSR disabled configure used for startup arming`, `Native FSR enabled with no app present callback`, and `Native FSR present routing configured ... internalNoCallback=1`.
- Official AMD FFX startup swapchain creation before direct enabled FFX API proof is a protected pass-through. GTA `installed/captureengine/logs/20260520_012459` showed process exit `0xC0000409` immediately after `amd_fidelityfx_dx12.dll` created a runtime-owned swapchain behind EOS, before any `ffxConfigure` line. CE latches native-FSR startup arming and FSR history there, treats the protected pending state as runtime-owned for a first disabled startup-arming `ffxConfigure`, and returns from the create-swapchain hook before Present-hook refresh, queue-ownership mutation, FFX hook retry/export inspection, deferred probes, capture, or separate overlay GPU work. Live Streamline/PostSL overlay state is the exception only in the negative direction: it is quiesced immediately so stale DLSS callbacks cannot submit after AMD begins takeover. A staged Direct queue from the protected create-swapchain call is deferred takeover data only; it must not be used for pre-enable overlay-only ECL submission. GTA freeze dump `installed/captureengine/logs/20260525_195848_gtafreeze/GTA5_Enhanced.exe_FREEZE_2026-05-25_20-28-52_360.dmp` disproved the progress-only escape hatch, and GTA freeze dump `installed/captureengine/logs/20260602_153554/GTA5_Enhanced.exe_FREEZE_2026-06-02_15-38-18_231.dmp` disproved pre-enable overlay-only rendering on the staged FFX queue: both can wedge AMD FSR presenter/interpolation and/or render threads in `amd_fidelityfx_dx12!ffxQuery`. Sustained ProcessFrame/ECL progress and staged-queue availability are diagnostic only now; expected diagnostics include `Protected official FFX startup pending - keeping ProcessFrame tracking-only`, `Protected official FFX startup suppressing separate overlay GPU work`, `Preserving overlay backend across protected official FFX startup swapchain change`, and `Protected official FFX startup has sustained frame progress but remains quiesced`. Old `... keeping ProcessFrame overlay-only`, `... using staged runtime queue for overlay-only rendering`, protected-startup cooldown bypass, or sustained-progress finalization breadcrumbs are regressions.

- The 2-second timeout enforcement (build 0.1.3409) and the overlay completion fence (build 0.1.3410) both **failed** — the AMD FSR FG runtime rejects ANY unexpected `ExecuteCommandLists` on the shared device, regardless of fencing or timing. The root cause is not about GPU work completion (inconsistent backbuffer) but about the AMD driver actively monitoring the queue and removing the device when unexpected ECLs appear.

- The current official AMD FFX bridge path has two safe interception layers. Official AMD modules still skip standard inline JMP export hooks, but use IAT and dynamic `GetProcAddress` routing for `ffxCreateContext`, `ffxConfigure`, and `ffxDestroyContext`; `FFXHook::RegisterDynamicHooks()` must run before process-wide `GetProcAddress` interception is enabled so an early native-FSR preload cannot cache original unwrapped FFX entrypoints. Build `0.1.3610` adds a narrow guarded re-arming int3/VEH fallback for official DX12 `ffxConfigure` because some SDK dispatch-table or intra-module calls bypass both dynamic lookups and caller IAT thunks. Expected diagnostics include `FFX Hook: Registered module-filtered dynamic hooks for FFX exports`, `FFX Hook: Using IAT/dynamic hooks for protected official FFX module ... guarded ffxConfigure VEH fallback enabled`, `FFX Hook: Armed VEH breakpoint for ...!ffxConfigure`, `GetProcAddress: Intercepted FFX API ffxConfigure` when the dynamic route is used, `FFX Hook: Installed DX12 overlay present-callback bridge for context=...`, and `DX12: FFX present callback rendered overlay on runtime-owned FSR path`.

- The FFX present-callback overlay backend should be allowed when official/direct FFX evidence exists and a real callback bridge is active, even if `HookHasRuntimeOwnedNativeFGPresentPath()` is still false. `ShouldBridgeOverlayViaFFXPresentCallback(...)` trusts any of: runtime-owned native-FG path, authoritative FSR API-active state, direct FFX confirmation, or an FSR runtime mode. This matters for the local `dx12_fsr_fg_test.exe` path, where the callback bridge can be installed and active before the older native-FG-present-path latch is set. While native FSR owns presentation through an active CE callback bridge, separate normal `ProcessFrame` overlay work should remain suppressed. The exception is official native FSR with no app present callback: AMD's runtime keeps its internal composition path, CE should not expect FFX callback progress, and normal DX12 overlay work is allowed on the runtime-owned swapchain queue. Healthy no-callback diagnostics are `Native FSR uses AMD internal no-callback composition; allowing normal overlay rendering`; callback-bridge sessions should still show `DX12: FFX present callback rendered overlay on runtime-owned FSR path`. After a protected official-FFX startup reaches enabled `ffxConfigure`, `FSR FG active but scQueue=null, SKIPPING overlay` is now suspicious unless a prior `Protected official FFX startup could not stage runtime queue` explains why no Direct queue was available.

- `dx12_fg_switch_test.exe` is now the local mixed-runtime stress test for real-world FG mode switching. It starts with all FG off, automatically switches OFF -> FSR -> DLSS -> FSR, and supports live keys `1` off, `2` DLSS, and `3` FSR without restarting the process. Default auto timings are intentionally asymmetric now: FSR starts after 3 seconds, DLSS starts after 12 seconds, and the return to FSR waits until 30 seconds so DLSS-G has enough time to initialize and report generated frames. Config keys/CLI overrides are `auto_fsr_start_seconds` / `--auto-fsr-start`, `auto_dlss_start_seconds` / `--auto-dlss-start`, and `auto_return_fsr_seconds` / `--auto-return-fsr`. FSR sessions now default to `fsr_present_callback_toggle_stress=1`: each FSR entry starts with `presentCallback=null` / AMD internal no-callback routing, then alternates into the app-callback route every `fsr_present_callback_toggle_interval_seconds` seconds (`--fsr-present-callback-interval`, default 6). The on-screen test-app status appends `INT` during the internal no-callback route, and logs `presentCallbackRoute=amd-internal` or `presentCallbackRoute=app-callback`. It writes `[FG-DIAG] Switching FG mode` / `Mode now` lines so a single app log can prove transition order, official SDK result codes, cleanup behavior, callback routing, and resolved auto timings.

- Leaving active FSR FG at runtime is not just an API flag change in the test apps. A disabled but still FSR-owned swapchain can stop advancing the frame-latency waitable, and normal overlay submissions on a disabled/inactive FSR-owned swapchain can still remove the D3D12 device with `0x887A002B`. The test-app runtime OFF path therefore destroys the FSR context and recreates a native swapchain; cleanup does not recreate a native swapchain because the process is exiting. CE must continue treating FSR-owned presentation as callback-only until ownership is actually gone **for callback-bridge sessions**; the internal no-callback composition route is the explicit exception (see the suspension invariant below) because it has no bridge that could render the overlay.
- **A game-created swapchain after explicit native-FSR OFF/destroy ends the runtime-owned teardown (2026-06-11, `installed/captureengine/logs/20260611_191950`).** Runtime ownership was classified as `pQueue != origGame`, so a game that recreates its swapchain on a FRESH queue after leaving FSR FG stayed misclassified as runtime-owned forever: the FSR_FG->Off transition armed the 60-frame draw cooldown ("preserving FSR queue ownership until a stronger off signal appears"), the swapchain change armed the 90-frame recent-FG reinit cooldown, and stale heuristics could re-latch FSR_FG on the plain game queue. Current invariant: a swapchain created by a caller that is neither an FG runtime, an FFX stack, nor a third-party overlay, while explicit native-FSR OFF or contexts-destroyed evidence is pending, IS the stronger off signal (`ShouldEndRuntimeOwnedNativeFGTeardownOnGameSwapchainCreation`): CE ends ownership, clears the no-callback latch/heuristics/arming state at the create hook, records the recovery queue, exempts the FSR_FG->Off transition cooldown (`IsGameSwapchainRecoveryToggleAfterNativeFSROff`), and reinits the overlay immediately on the recovery swapchain change (`ShouldReinitOverlayImmediatelyAfterGameSwapchainRecoveryFromNativeFSROff`). Same session also proved two robustness facts: the test app's generation-1 raw FFX export pointers can bypass the `ffxDestroyContext` dynamic hook entirely (only `ffxConfigure` has the VEH fallback), and swapchain pointer reuse can defeat `g_LastSwapChain` change detection (destroyed AMD swapchain and the new game swapchain shared the same heap address), so the recovery edge must not depend on either signal alone. Expected diagnostics: `Game-created swapchain after explicit native FSR OFF/destroy — ending runtime-owned native-FG teardown`, `gameSwapchainRecoveryToggle=1` in the no-cooldown transition log, `Swapchain change is game-created swapchain recovery after explicit native FSR OFF/destroy — immediate overlay reinit`. **Follow-up (2026-06-12, `installed/captureengine/logs/20260612_000936`)**: ending ownership alone made the overlay disappear FOREVER, because the accidental keep-alives (runtimeOwns latch, heuristic FSR) were what had kept ProcessFrame alive: frame classification still counted ECLs against the game's RETIRED original queue, so every present on the recovered swapchain classified as zero-ECL/interpolated and `ShouldSkipProcessFrameForZeroECLPresent` starved ProcessFrame. Current invariant: the recovery edge also RE-BASELINES `g_OriginalGameQueue` to the game-created recovery queue (pointer-guarded; Talos-style same-queue recreates no-op), so classification/routing/future FG-cycle proofs anchor on the queue that actually presents, and `ShouldSkipProcessFrameForZeroECLPresent` has a recovery-queue escape as defense-in-depth (presents on the game-created recovery swapchain are real game frames by construction). Expected diagnostic: `Re-baselined original game queue to game-created recovery queue`.
- **No-callback native-FSR suspension must keep the normal overlay route alive (2026-06-11, `installed/captureengine/logs/20260611_142923`).** A disabled `ffxConfigure` with no bridge and no app callback while the runtime-owned swapchain is still the live present path is a suspension, not a teardown: `g_NativeFSRInternalNoCallbackComposition` is retained (`ShouldRetainNativeFSRInternalNoCallbackCompositionForDisabledConfigure`), separate overlay GPU work stays allowed, and `DecideSwapchainOverlayRouting` keeps the FSR swapchain queue (`nativeFSRInternalNoCallbackCompositionLive` parameter) instead of the post-FSR original-queue recovery (which would be a cross-queue mismatch against the still-live FSR backbuffers). The latch is force-cleared on contexts destroyed, explicit teardown end via origGame swapchain return, Streamline FG comeback, and shutdown. FSR_FG<->Off mode toggles skip the 60-frame draw cooldown only when the overlay backend already renders on the exact runtime-owned swapchain queue (`IsLiveNoCallbackNativeFSRSuspensionToggle`); and the swapchain change right after a finalized enabled-configure FFX takeover reinits the overlay immediately instead of blanking through the 90-frame cooldown (`ShouldReinitOverlayImmediatelyAfterNoCallbackFFXTakeoverSwapchainChange`). All bypasses require enabled-`ffxConfigure` proof, so pre-enable protected startup and app-callback/bridge sessions keep all existing cooldowns. Expected diagnostics: `Native FSR suspension retains internal no-callback composition route`, `retainedNoCallbackSuspension=1`, `liveNoCallbackNativeFSRSuspensionToggle=1`, `Swapchain change is finalized no-callback official FFX takeover — immediate overlay reinit`, `Cleared retained native FSR internal no-callback composition route`. Unit coverage: `tests/test_dxgi_shared.cpp` (`SuspendedNoCallbackNativeFSRKeepsFSRSwapchainQueueRouting`, `LiveNoCallbackNativeFSRSuspensionToggle*`, `NativeFSRNoCallbackCompositionRetainedAcrossSuspension`, `FinalizedNoCallbackFFXTakeoverReinitsOverlayImmediately`).
- **[OVERLAY COVERAGE] is the FG-transition blank regression gate (2026-06-13).** Every processed present (top-level `DX12_ProcessFrameExternal` plus SL-routed `PostSLOverlayRenderGated` invocations) is accounted covered/uncovered from the draw-counter delta of all overlay routes; zero-ECL interpolated frames and SL-owned transport presents inherit coverage from the previous covered present. Streak-end logs report `missed/longestStreak/gate/route`; transition edges and shutdown log summaries. Validation criterion: no uncovered streak > 1-2 presents during the scripted transition matrix; `gate=` attributes any regression to the responsible skip site.
- **FG-detection heuristic evidence is reset at every transition/recovery edge (2026-06-13, session `logs/20260612_215439`).** `RequestFGDetectionHeuristicReset()` resets both the queue-change heuristic AND the ECL-count-pattern counters. Stale interp counts from a finished FG phase re-latched phantom `FSR_FG` on the fresh post-FSR-off swapchain and the resulting double label flip armed two 60-frame draw cooldowns (61-present blank on a healthy overlay). Defense-in-depth: `IsHeuristicOnlyRuntimeModeFlip` — a mode flip with `sl_signal 0->0`, no runtime ownership, no authoritative FSR, and the overlay backend live on the current queue is a label change, not a transport change, and must not arm the draw cooldown. `IsLiveNoCallbackNativeFSRSuspensionToggle` accepts `kStreamlineNoFG` as the non-FSR side (with SL DLLs merely loaded the classifier never reports `kOff`); the hard proof requirements (enabled-configure no-callback latch, runtime ownership, backend bound to the exact live scQueue) are unchanged.
- **DX12 overlay backends are device-scoped and stay WARM across FG transitions (2026-06-13).** `CustomOverlay::DX12Backend` stores but never uses its bound queue; the DescFree backend fetches the backbuffer per frame. Warm reuse is device+format scoped (`CanReuseWarmDX12OverlayBackend`); FG transitions rebuild only swapchain/queue-bound state (RTVs via `CleanupRTVs`, allocators/fence via `InitOverlaySync`) after the existing GPU drains. The x64 DescFree backend survives `CleanupRTVs` and is rebuilt only on device/RTV-format change (`EnsureDescFreeBackendForDeviceAndFormat`), x86 Texture2D selection, or shutdown. The x86 Texture2D adapter keeps its original swapchain-scoped teardown.
- **Pure-DLSS engage is no-blank only under the explicit-enable proof (2026-06-13).** `HasExplicitEnablePureDLSSColdStartProof` (explicit per-comeback `slDLSSGSetOptions(ON)` provenance + retained startup-activation swapchain + installed PostSL callback) bypasses the 8-callback pure-DLSS countdown and the 15-callback cold-start warmup. GetState-only enables keep both protections — that is the historical GTA startup-churn/hang family. GTA/Talos validation gates this proof; rollback is dropping the proof from the two bypass sites.
- **CE must never pin a swapchain that blocks the game's swapchain recreation (2026-06-13, session `logs/20260613_032326`).** The retained Streamline startup-activation swapchain is an AddRef'd reference; while CE holds it, `CreateSwapChainForHwnd` on the same HWND fails `E_ACCESSDENIED` (the app exits cleanly with "Fatal switch failure: no swapchain after OFF request" — no dump, because nothing faulted). The churn-suppression OFF path releases the retention too (a quick re-ON re-retains per startup-route present), and both `CreateSwapChainForHwnd` E_ACCESSDENIED recovery paths release it before retrying. Source-invariant test: `RetainedStartupActivationSwapchainReleasedOnChurnOffAndAccessDeniedRecovery`.
- **Make-before-break PostSL keep-alive across explicit Streamline FG OFF (2026-06-13).** A CONFIRMED PostSL path stays armed-and-rendering across the `slDLSSGSetOptions(off)` edge (`g_PostSLExplicitOffKeepAlive`) — the proxy keeps presenting through menus/suspension and tearing PostSL down at the edge is what blanked those presents. Never while an FSR/native-FG takeover is in play (the quiesce invariant wins; any authoritative `SetPostSLCallbackInstalled(false)` clears the latch). Retirement is event-driven: a real normal-route draw (render route flips to `kNormal` only on an actual normal submit), Streamline unload, swapchain invalidation/resize. - **Streamline module unload/reload generations must invalidate CE hook state (2026-06-12, crash `installed/captureengine/logs/20260612_003407`).** Games can fully unload and reload the whole Streamline stack when toggling DLSS FG off/on (the switch app does; real games unloading SL on FG-off would too). CE's Streamline hook bookkeeping was per-function-name and process-global: `g_Original_*` trampolines, `g_*Target` addresses, `g_*Hooked` flags, and the interposer/common install/IAT masks survived the unload. On reload the new `sl.common.dll` landed INSIDE the previous generation's `sl.interposer.dll` address range, so the call-time `IsSavedStreamlineOriginalCallable` owner check (which only verifies "belongs to a loaded module") passed and the stale trampoline jumped mid-instruction into the wrong module — AV write inside `sl.common` on the game thread during the next DLSS enter. Current invariants: (1) the loader DLL-unload notification dispatches every `sl.*` unload to `StreamlineHook::OnModuleUnloaded`, which invalidates each hook slot whose target/original lies in the departing image (original cleared first so detours fail safe via the existing null-callable paths) and clears the per-module install/IAT masks so the next load of the same name re-hooks the fresh instance; (2) load-time self-heal: a core-module load whose mask claims "installed" but whose stored core targets do not belong to the arriving instance treats the mask as a stale generation, clears core slots that belong to no live core instance, and re-hooks (covers missing unload notifications). Expected diagnostics: `Streamline Hook: Invalidated <fn> hook slot for unloaded sl.*`, `Module sl.* unloaded ... invalidated N stale hook slot(s)`, `reloaded at ... installed-module mask refers to a previous unloaded generation`. Open hardening item: the FFX guarded `ffxConfigure` VEH breakpoint stores a raw target address; an FFX module unload/reload at a DIFFERENT base could re-arm 0xCC into re-mapped foreign memory — needs the same unload invalidation if a crash ever lands there.

- Build `0.1.2771` adds a **DllMain startup guard** for the Present hook chain. The true root cause of the persistent Talos DLSS FG crash (0xC0000005 RIP=0) was **Present hook interference during SL's DllMain**, not earlier theories about CE wrapping DXGI factories. CE installs Present hooks via **vtable patching** on the D3D12 swapchain (because Steam overlay already has an inline E9 JMP on dxgi!Present, CE uses the vtable hook path). The D3D12 swapchain vtable is **shared by ALL swapchain objects from the same D3D12 factory**, so swapchains created by SL during its DllMain have vtable[8] pointing to CE's DetourPresent. When SL's DllMain calls Present, the call goes through CE's DetourPresent → original dxgi!Present → Steam's inline E9 JMP on dxgi!Present → `gameoverlayrenderer64!OverlayHookD3D3` → crash with RAX=0 (Steam's TLS uninitialized on the SL loader thread). Build `0.1.2771` removes the `runtimeMode != kDLSSFG` condition (now always bypass when SL is loaded and FG not running), adds early bypass in `DetourPresent`/`DetourPresent1` for SL module callers during DllMain, and adds a last-resort bypass fallback in `CallOriginalPresent`.
