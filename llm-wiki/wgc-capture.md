## Current Summary

Windows Graphics Capture remains the default non-injected capture path. Same-device WGC capture is now the preferred low-overhead default (`wgc_same_device_capture=true`); the dedicated capture D3D11 device remains a supported fallback/diagnostic path when same-device initialization is disabled or fails. Split-device WGC still uses keyed mutex synchronization on shared texture-pool slots.

WGC CFR now aims for smooth output with lower steady-state pressure on the game: it asks the Windows compositor for a modest producer cadence (`ceil(output_fps * 1.25)`) through `MinUpdateInterval`, switches the producer back to max-rate only while recovering from source starvation or an underfilled delay reservoir, and restores the cap after sustained fresh input. This producer cadence is separate from the local copy throttle: CFR recording keeps local WGC copy throttling disabled so the scheduler can still consume every delivered source frame, preserve reservoir fill, and make its own drop/repeat decisions. Explicit 10-bit capture is quality-mandatory: when `Video.bit_depth=10`, WGC must stay on a high-precision input path (`R10G10B10A2` first, FP16 as the only fallback) and fail loudly if no high-precision frame-pool path is available. BGRA8 throughput fallback is allowed only for 8-bit or automatic SDR paths.

Native WGC cursor capture remains enabled by default; disabling cursor capture is a workaround, not the current fix. When cursor capture is requested, CE asks `IGraphicsCaptureSession4` for dirty-region metadata in `ReportOnly` mode. That mode must not crop or hide frame content. If the runtime reports a cursor-only dirty region that overlaps the current or previous cursor rect, CE suppresses only redundant cursor-only updates that arrive sooner than the active producer cadence after the last delivered source frame. It must not drop all cursor-only movement, and it must not drop cursor updates once they are needed to represent the producer-cadence stream. Logs to watch are `Dirty-region metadata enabled (mode=ReportOnly)`, `Producer cadence target active`, `[WGC Perf] ... Throttle=<producer fps>`, and `DropCursor`.

When a 10-bpc SDR WGC source cannot create an `R10G10B10A2` frame pool (WGC's `Direct3D11CaptureFramePool` uses `D3D11_RESOURCE_MISC_SHARED_NTHANDLE` internally; R10+SHARED_NT fails on some GPU/drivers), the fallback logic first tries progressively fewer pool buffers (down to the minimum of 3) before concluding that R10 truly cannot work on this system. Only then does it fall back to `R16G16B16A16_FLOAT`. The FP16→R10 shader conversion is lossless for 10-bit content (FP16 mantissa exactly represents all R10 values). The VRAM cost is 2x per source surface (63.3MB vs 31.6MB at 4K), which is why the budget was raised to 3000MB. That FP16 source must still convert to `bit_depth=8` output entirely on the GPU: prefer native D3D11 VideoProcessor FP16 input when the driver accepts it, otherwise blit through the fullscreen shader to `R10G10B10A2_UNORM` using a typed `R16G16B16A16_FLOAT` SRV and SDR linear-to-sRGB encoding before VP conversion to NV12. Shader SRVs must not use typeless DXGI formats. For explicit 10-bit output, the final VP/encoder surface remains P010 and compatibility fallbacks must not introduce BGRA8/NV12 intermediates.

WGC CFR startup A/V sync now uses one shared start anchor by construction. Capture performs the existing pre-live cadence/encoder settling delay first, flushes pre-anchor warmup material, arms a one-frame startup barrier, then waits for usable post-delay WGC material at or after that barrier. Before live handoff, it drains the pending WGC queue and buffered WGC frames. With no active render-domain delay, it selects the freshest valid post-barrier frame rather than accepting the first stale candidate. With an active render-domain delay, the measured render-loopback delay is treated as a required video-content reservoir: startup selects the candidate closest to `latestCandidateSelectionQpc - requestedDelayQpc`, keeps newer candidates buffered for the first live ticks, and may wait briefly before live output for roughly the measured delay plus two frames if the reserve span/low-water count is not yet sufficient. If the adaptive smoothness buffer is armed, a bounded startup-only smoothness extra delay is added to the same media/audio anchor as the render-loopback delay; later source deficits become normal CFR repeats, not live audio-anchor shifts. If the wait budget expires or the span is insufficient, it logs the failure reason and falls back to the safest available candidate; a timeout with no span growth is logged as `source_startup_underfeed`, while a timeout with partial usable span can preserve newer post-barrier frames for the first live ticks instead of collapsing to a one-frame reserve. During live WGC CFR, the reservoir low-water frame count is derived from `ceil(requestedDelayQpc / frameIntervalQpc)` and the target adds one extra frame. If the reservoir drops below low-water, WGC can temporarily return to max-rate capture recovery, then restore the conservative overcapture cap after the reservoir recovers. Active-delay selection first prefers strict candidates. If those leave only an older fallback while a slightly too-new frame is inside the hard residual limit, the selector evaluates timestamp damage plus repeat-cluster pressure: a bounded relaxed candidate may be chosen to avoid extending a visible repeat streak, but candidates beyond the hard residual limit are rejected and counted as sync-risk rejections. After any index-changing step such as low-source clamping or reserve-preservation fallback, the final selected frame is revalidated against both the smoothed selection timestamp and raw WGC timestamp; if either timestamp is too new beyond the hard late-residual cap, CE repeats/classifies instead of encoding that frame and increments `delayPostSelectionRejectedSync`. Mediaengine selects the accepted video timestamp as the shared audio/video anchor; when automatic render-domain delay is active, the first audio anchor is the accepted video QPC plus the resolved render-loopback delay plus any selected startup smoothness extra delay. First stream packets should start at PTS zero, and the accepted frame should be either the requested delayed-reserve candidate or the freshest safe fallback. The startup barrier log includes freshness and reserve diagnostics such as `freshened`, `bufferedExamined`, `queueExamined`, `discardedOlder`, `discardedBeforeBarrier`, `startupReserveFrames`, `startupReserveSpanUs`, `startupDelayTargetUs`, `startupSelectedByDelayReserve`, `startupReserveReason`, `keptReserveFrames`, `startupReserveWaitedUs`, `startupReserveSpanGrowthUs`, `startupReserveWaitFreshened`, `startupSelectedDelayUs`, `startupFallback`, and `startupPartialReserveFallback`. `[AVSyncApply] wgc_schedule_anchor` may report a nonzero startup `scheduleOffsetUs`, but that value is diagnostic only (`selectionOffsetUs=0`); steady WGC source selection must not subtract it on top of the requested content delay.

WGC retained copy-pool textures are ownership-protected. Every retained WGC texture carries `poolSlot`, `poolGeneration`, and a move-only `WgcPoolSlotLease` through `WGCCapturedFrame`, direct callbacks, `QueuedFrame`, startup candidates, the live frame queue, buffered WGC frames, and `g_LastFrame`. `CopyFrameToPool` may copy only into an unleased slot. If all slots are leased, CE drops the incoming WGC frame as `wgc_pool_saturated_safe_drop` instead of overwriting queued, selected, or currently encoding content. The lease is released when a queued/cached frame is dropped or after `MediaEngine_ProcessFrameD3D11` returns, relying on the current media-engine contract that WGC input is copied/converted into media-engine owned D3D11 frame storage before return. If media-engine ownership becomes asynchronous, the lease must extend to the corresponding GPU completion fence. Pool generations prevent stale leases from a recreated pool from affecting new slot counters.

The WGC smoothness surface budget covers WGC source frame-pool buffers and CE copy-pool slots separately. Source frame-pool buffers are reserved first when budget permits (default 8, minimum 3 under tight budgets), then copy-pool slots reserve render-loopback sync-delay frames plus safety/in-flight/free slots, then extra smoothness frames. The retained reservoir stores WGC source frames, not output CFR slots, so desired retained frames are sized with 125% source-rate headroom (`GetWgcSmoothnessBudgetFps`): at 120 fps output and 300 ms smoothness, the storage target is 45 retained source frames instead of 36 output ticks. This is storage capacity only: startup smoothness delay is still clamped to the configured millisecond target (`GetWgcStartupSmoothnessTargetDelayQpc`), so 120 fps / 300 ms remains a 36-output-tick delay target and cannot inflate the audio/video anchor to 375 ms. The cadence-event and final `[WGC CFR SMOOTHNESS BUFFER]` diagnostics must pass the same `outputFps/maxSmoothnessMs` clamp; otherwise logs report an impossible 375 ms target while runtime correctly used 300 ms. At 4K FP16 source + R10 retained copy with the default 3000 MB budget, the expected shape is 12 WGC source buffers plus 64 copy-pool slots, retaining the full 45-frame source reservoir with `capLimited=0`. At 2048 MB and 250 ms, the split-budget optimizer may trade source buffers for retained copy slots (about 7 source buffers + 50 copy slots) to reach the 38-frame source target. Extra smoothness is reduced first when `wgc_smoothness_buffer_vram_budget_mb` caps the total large WGC surfaces. Unknown/zero startup source-rate windows and sustained source-below-CFR windows must not arm the full extra reservoir; logs should distinguish source/delivery coverage holes from encoder, mux, pool, and audio causes.

When the adaptive smoothness reservoir is armed, WGC startup reserve waiting must budget for the full requested smoothness reservoir, not just the render-loopback content delay. The startup wait budget is now at least `contentDelay + smoothnessTarget + 4 frames` when smoothness startup is attempted; without smoothness it remains the older `contentDelay + 2 frames` shape. If startup still cannot fill the reservoir, logs and analyzer triage should expose `smoothDelayDeficit`, `startupDelayDeficit`, and `wgc_startup_smoothness_underfilled` instead of making audio look suspect when exported track sync is clean.

Live WGC copy-pool pressure trims only surplus buffered reservoir frames. If current free copy slots fall to the reserved-free threshold while the live WGC buffer is deeper than the active delay target, CE drops newest surplus buffered frames down to the active delay target and releases their pool leases. This does not change CFR PTS, audio anchors, track lengths, or default VRAM budget; it protects fresh WGC copies without collapsing the delay reservoir that smoothness depends on. Diagnostics include `poolFreeNow`, `poolPressureTrim`, and the existing pool/free-min evidence.

With `wgc_active_delay_uniform_cadence=true`, the nearest-target playout layer owns source-above-target surplus such as 144 Hz WGC input into 120 fps CFR output. The 2026-06-29 desktop run `installed/captureengine/logs/20260629_220408` showed enough WGC input for most one-second windows but still produced visible repeats because ingress soft/credit pressure pre-dropped frames before the uniform playout could choose the smooth 144-to-120 cadence. The current rule is: if the recent WGC input min windows are at or above the CFR target, WGC ingress accepts frames under soft reserve or decimation-credit pressure and reports them as `uniform_playout_soft_reserve` / `uniform_playout_credit`; a truly full copy pool (`freeCopySlots==0`) still drops before copy. This does not increase the copy-pool/VRAM budget and does not move audio timing; it only prevents avoidable no-frame slots that later become CFR repeats. Watch `[WGC Perf] Ingress` `accPlaySoft`/`accPlayCredit` and final `ingressPlaySoft`/`ingressPlayCredit` together with hard pool saturation, `delayPaceCapTrim`, and `sourceRepeatLowerBound` when judging a 140/144 fps source recorded to 120 fps CFR.

WGC active-delay smoothness attribution estimates the source-limited CFR repeat lower bound from output ticks and unique WGC source frames, then compares it with actual repeats. Source-limited sync-delay holds count toward the lower bound even when a hard-safe candidate exists, because a stalled/underfed WGC source can still force a repeat without CE policy being at fault. `sourceRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, `excessRepeatClusters`, and `excessRepeatClusterMax` answer whether a run is near the best achievable CFR cadence for the flawed input or whether CE added avoidable repeat damage. Important nuance: a stable 140/144 Hz source into 120 fps CFR should be consumed as surplus source drops with zero repeats; repeats are not caused by FPS mismatch alone. Repeats become necessary when a CFR output slot has no sync-safe fresh source frame, for example because source FPS falls below target, frame times spike, WGC/DWM delivery is gappy/batched, or the only candidate is too new for A/V-safe selection. The final `[WGC CFR SOURCE COVERAGE]` line makes this explicit with `coverage`, `reason`, `bestEffort`, `sourceRepeatLowerBound`, `syncSourceRepeatLowerBound`, `deliveryRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, and clean encoder/mux/pool/selection booleans; `wgc_source_coverage_best_effort` is a non-fault analyzer verdict meaning CE matched the source/delivery lower bound and did not add avoidable repeat damage. The `[WGC CFR SUMMARY]` `longest=<ms>` / `longestDup=<ticks>` fields are EPISODE-scoped (longest below-target *episode* wall duration, and dup ticks *within* it) — they OVERSTATE a visible freeze because the source still delivers new frames during the episode (e.g. real run `20260630_202659`: `longest=4110ms longestDup=292`, but during that 4.1s episode ~201 unique frames still arrived ≈49fps, not a static freeze). The true visible-freeze metric is `longestContiguousDup=<ticks> (<ms>)`: the longest CONTIGUOUS held-frame run, tracked session-wide (`CaptureSessionSummary.longestContiguousDupTicks`) so it survives the per-window `[Cadence Health]` `DupStreak` reset and is not split/undercounted across a logging-window boundary. For `20260630_202659` the worst contiguous hold was ~115 frames (~0.96s), not 4.1s, matching the user observing no multi-second freeze; `ShortfallMax=0.0ms` confirmed CFR output timing never stalled. The analyzer surfaces this as `worst_contiguous_freeze=<f>/<ms>` and relabels the episode fields `longest_episode`/`episode_dups` so triage no longer reads a below-target episode as a freeze. Analyzer triage now parses WGC duplicate percentage, longest duplicate run, longest contiguous freeze, and worst input/delivered FPS from `[WGC CFR SUMMARY]`; a run with bounded residuals, `delaySoftLateAccepted=0`, no soft-safe missed candidate, and zero lower-bound excess is classified as `wgc_source_limited_smoothness_ceiling` rather than `wgc_audio_late_risk`. `delayPostSelectionRescuedSync` means a final too-new selection was rescued to a safe candidate before encode; `delayPostSelectionRejectedSync` remains strict until fresh runs show zero. Active-delay max-rate recovery is reserved for a healthy but underfilled delay reservoir; true source underfeed is classified instead of being chased with aggressive capture recovery. Unstable-FPS windows are split into healthy, recoverable-underfill, hard source stall, and post-stall recovery classes. Healthy/recoverable/post-stall active-delay candidate scoring uses a soft late target derived from the frame interval and clamped to about 5-7 ms. The hard 10 ms cap is only a safety boundary: a hard-safe frame above the soft target is not a quality-safe choice in those windows. When no soft-safe frame exists, WGC should repeat and log the hold as `delaySyncProtectedRepeats` / hard-only source limitation instead of encoding near-cap visual content that can make audio feel late. True source-limited or hard-stall windows retain the hard cap and are attributed honestly instead of forcing extra repeats to chase an impossible delay.

WGC CFR audio continuity policy separates visual overload recovery from audio integrity. The live scheduler owns the video PTS and the audio sample target. WGC source-frame selection normally targets the scheduled tick, but if visual shortfall exceeds the bounded live window (`250 ms` or `32` frames, whichever is tighter), the live scheduler rebases old owed ticks as covered visual hold/drop debt and source-selection clamps toward the live-window floor. Live scheduler rebase is deliberately incremental: `kWgcMaxLiveSchedulerRebaseTicksPerLoop` caps each loop to one CFR tick so recovery cannot create multi-frame PTS holes that look like stutter.

When the source is healthy but the encoder is sustainably behind target, WGC enters an encoder-limited smoothness path instead of treating the backlog like source starvation. The classifier splits true source-under-target evidence from CE/encoder delivery pressure: encoder recovery-limited state should imply encoder-limited smoothness unless the source is genuinely below target, and a mode-mismatch warning is strict policy evidence. That mode keeps CFR timestamps and audio sample targets exact, but bounds live visual debt to roughly `50 ms` or `3` target frames, coalesces skipped old visual slots as `encoder_limited_source_drop` events, and drops stale buffered history more aggressively after a near-live frame has been selected. Source-starved behavior stays separate: genuine missing source frames are still represented as repeats/holds and attributed as source-limited evidence. In both modes WGC rejects frames that are too far in the future for the effective target, never emits selected source timestamps backward, and does not burst-encode fresh WGC frames to spend historical shortfall. Audio remains real samples or real encoded silence from sample 0 to the final CFR endpoint; it is not shortened, trimmed, or pitch-corrected to hide WGC/encoder debt. At stop, WGC generic CFR drain is disabled: post-stop frames and pending buffered WGC frames are discarded rather than encoded into a frozen visual tail.

The audio side has one extra guardrail under WGC overload: CFR source-clock compensation must not spend normal buffer-level deficit as clock drift. Healthy WGC CFR runs should stop with `[STOP AUDIO DETAIL] ... ratePpm=+0.00 compDelta=0 sat=0`; saturated `ratePpm` while packet durations and source clocks are otherwise exact is content-drift evidence, not an acceptable pitch correction.

Shared CFR audio/timeline rules for both WGC and injected capture live in `cfr-capture-sync.md`. In particular, CFR timer-rebase debt is not disposable: deleting scheduled ticks can make visual content jump ahead while continuous audio appears to lag, even when final packet durations are equal.

Diagnostics now keep timing concepts separate. CFR frame spacing (`8.33 ms` at 120 fps, for example) is the video frame interval, not the audio/video offset. A/V sync evidence comes from the shared startup anchor, stream first PTS values, per-track audio-vs-video `Drift` / `DriftAdj`, stop-time sample counts, and final mux duration delta. WGC visual-frame selection bias is published separately from generic output-schedule bias so audio logs can report `WgcFrameLead`, `WgcFrameLag`, and `WgcSelBias` without conflating selected content timing with encoder-thread wake timing. The realized active-delay metric (`recordWgcDelayRealization` → `realizedDelay*`/`delayResidual*`) is measured against the GRID playout reference (`scheduledSampleQpc − frame.timestamp`, the slot's ideal wall time == the audio anchor reference), **not** wall-clock `selectionNow` (iter-5 fix). Measuring against `selectionNow` folded encoder-thread late-wake jitter (a perpetually-late cadence thread under 100% GPU / network-drive mux I/O woke 27-88 ms late in `20260626_050554`) into a content-delay metric, inflating `realizedDelayMax` to ~108 ms and falsely tripping `wgc_active_delay_realized_delay_unstable` even though the content placed in each PTS slot was grid-correct. Encoder-thread wake jitter is reported separately as `SchedSel`/`SelMax`.

### Split-Budget Optimization (2026-06-30)

The WGC smoothness budget computation for FP16 source pool (8bpp) + R10 retained copy (4bpp) uses "best retention" candidate selection. The algorithm iterates source buffer counts and picks the split that maximizes retained extra frames under the VRAM budget. With the later source-rate-headroom sizing, 4K 120fps FP16+R10 at 2048 MB / 250 ms selects about 7 source buffers + 50 copy pool slots (retained=38 full source-frame target). With the default 3000 MB / 300 ms budget it selects 12 source buffers + 64 copy pool slots (retained=45 full source-frame target).

### Active Delay Residual Tolerance (2026-06-30)

`kWgcActiveDelayResidualTolerancePermille` raised from 600 to 900 (60%→90% of frame interval). At 120fps output, this widens the acceptance window from 5ms to 7.5ms. With a ~140fps source (7.14ms spacing), 5ms rejected ~30% of surplus frames as "too new" even during massive surplus (400+ fps). At 7.5ms, most frames within one source interval are accepted, reducing unnecessary repeats from 20-30% to ~5-10%. The relaxed candidate path (`delayRelaxed`) remains at 0 because the strict path now covers the range that previously needed relaxed scoring.

### Pool Headroom Slots (2026-06-30)

Added `kWgcSmoothnessBufferPoolHeadroomSlots=8` (8 extra copy pool slots beyond the reservoir requirement). With the 3000MB budget, the previous 41 copy slots were often 37+ leased simultaneously at 100% GPU load, with only 4 free. The 8 extra slots give 49 total, leaving 12+ free at peak, reducing `overwritePrevented` from ~1887/sec to near zero. Cost: 8 × 31.6MB = 253MB, total ~2310MB out of 3000MB budget.

### Timer Rebase Threshold (2026-06-30)

`GetCfrTimerRebaseThresholdTicks` for screen grab (WGC with smoothness buffer) reduced from 10000 ticks (83 seconds at 120fps) to 18 ticks (150ms), matching `kCfrShortfallForceCatchupThresholdTicks`. Previously the screen-grab threshold was effectively infinite, so WGC's encoder-timer drift never triggered a cadence rebase. The current default 4K FP16+R10 smoothness budget provides 64 copy-pool slots and 45 retained source frames, giving frame continuity during rebase when WGC delivery is healthy enough to fill the reservoir. Inject capture path (no smoothness buffer) is unaffected — it still uses the 10000-tick threshold implicitly (inject uses `activeScreenGrab=true` → `GetWgcCatchupTicksThisLoop` path, not the timer rebase path).

### CFR Source Coverage Limits

At ~140fps source -> 120fps CFR output, repeats are not the theoretical minimum by themselves. A regular source above the output rate should mostly produce source drops, because each 120 fps output slot can choose a suitable unique source frame and discard surplus. Repeats are the CFR coverage-limit signal: they appear when an output slot has no sync-safe fresh source frame, which can happen with source frame-time spikes, brief source FPS below target, WGC/DWM callback or delivery gaps, or safety rejection of too-new candidates. Under 100% GPU load, WGC is more exposed than inject because the DWM/WGC frame-pool delivery layer can batch or gap frames even when the game presents reasonably smoothly. The inject capture path (no DWM intermediary) is less exposed to that WGC delivery layer, but any CFR path can repeat under actual source coverage holes.

Do not treat D3D12 COPY queues or HAGS as a proven WGC fix. Current WGC receives `Direct3D11CaptureFrame` / `ID3D11Texture2D` surfaces and the bad `sbwgc` run showed CE copy/convert/encode health was OK while WGC callback/source gaps dominated. A D3D12 COPY queue may be worth a proof-first DX12 inject experiment, but WGC would first need share/import feasibility proof and evidence that CE copy work, not upstream delivery, is the limiter. See `performance-priority.md`.

## Config Flags

- `[General] wgc_skip_split_device_flush=false`: when true, split-device WGC skips the producer-side `ID3D11DeviceContext::Flush()` after `CopyResource`. Keyed mutex acquire/release remains unchanged. Treat this as a GPU-bound performance experiment until runtime validation proves it does not corrupt frames or underfeed the encoder.
- `[General] wgc_same_device_capture=true`: preferred low-overhead WGC path. When false, WGC creates a dedicated capture D3D11 device and uses the split-device keyed-mutex texture-pool path. A live option change requests WGC retarget/reset so the device choice is reinitialized. Treat dedicated mode as a diagnostic/fallback path, not the normal smoothness target.
- `[General] wgc_smoothness_buffer_enabled=true`: enables the bounded WGC startup smoothness reservoir when CFR, active render-domain delay, source-rate, and VRAM-budget gates allow it.
- `[General] wgc_smoothness_buffer_max_ms=300`: maximum requested extra WGC smoothness delay. The selected startup extra delay is applied to both audio and video anchors; it is not adjusted live after the first encoded frame.
- `[General] wgc_smoothness_buffer_vram_budget_mb=3000` (was 2048): budget for WGC source frame-pool buffers plus CE copy-pool retained surfaces. Raised to 3000MB to eliminate cap-limited smoothness buffer under the FP16+R10 pipeline at 4K 120fps. At 3000MB the FP16 split budget gives 12 source buffers + 64 copy pool slots, achieving the full 45-frame retained source reservoir for 120 fps / 300 ms with `capLimited=0`. The startup smoothness delay remains capped by `wgc_smoothness_buffer_max_ms`; the extra source-frame budget is not an audio-anchor delay increase.
- `[General] wgc_prefer_compact_10bit_pool=true` (default true): when R10 WGC frame pool is unavailable and 10-bit capture is requested, try BGRA8 as the source pool format before falling back to FP16. Halves VRAM per source surface (31.6MB vs 63.3MB at 4K). The retained copy format stays R10 via shader conversion, and encoding stays 10-bit P010. FP16 preserves full 10-bit input precision; BGRA8→R10 upscales from 8-bit (2 LSB zeroed).
- `[General] wgc_smoothness_floor_ms=auto` (default `auto`): WGC-only baseline jitter-buffer FLOOR. The active-delay smoothness machinery (nearest-target playout, uniform cadence, reservoir) was previously hard-gated behind an active audio-latency content delay (`avContentDelayActive`); with no audio latency (video-only capture, or a low-confidence `[AVSyncAuto]` probe) WGC ran near-live and was maximally exposed to bursty DWM→frame-pool delivery under GPU load. The floor engages that same machinery even when `avContentDelayQpc==0`. `auto` derives the depth from measured pre-live WGC delivery jitter (`callbackGap`/`sourceJitter`, `DeriveWgcSmoothnessFloorDelayQpc`), clamped to `[~2 frames, min(wgc_smoothness_buffer_max_ms, buildable reservoir)]`; an explicit value (ms) overrides; `0` disables the floor and reproduces prior behavior exactly. **No-op in the healthy with-audio path**: there `smoothnessTargetDelayQpc` already targets the full reservoir, so the conditional `avContentDelayActive ? reservoirTarget : min(floor, reservoirTarget)` leaves it unchanged. **Sync-neutral by construction**: the audio anchor delay stays `= avContentDelayQpc` (true latency `L`, mediaengine `GetWgcStartupAudioAnchorQpc(firstVideoQpc, renderDelayQpc)` uses `L` only; the floor `S` is realized purely as older startup video + later live-start absorbed by `scheduleOffset`), so audio is byte-exact and the floor cannot move the anchor or reintroduce ghost-image judder. Resolved once at the startup barrier and held fixed for the session (no live anchor retiming). Enabling the floor also enables the smoothness copy-pool budget allocation in `StartWgcRecordingCapture` (`hasWgcContentDelayBudget || wgcSmoothnessFloorBudgetDesired`); inject capture is unaffected. Diagnostics: one-time `[AVSyncApply] wgc_smoothness_floor`, per-window `[WGC CFR JITTER BUDGET]`, and end-of-session `[WGC CFR SMOOTHNESS FLOOR]`.
- `[General] wgc_active_delay_uniform_cadence=true` (default true): when an A/V content delay is active, WGC selects video frames with a **fixed-latency jitter-buffer playout** (`DecideWgcNearestPlayout` + `ShouldDropWgcFrontForNearerPlayout`, `media_main.cpp`'s `useInjectParityDelayPacing` block) instead of the legacy grid-rate timestamp-target reservoir (`tryPopBufferedWgcFrameForTarget`, used when the flag is false). **The core problem this solves:** WGC frame *delivery* (DWM→capture frame pool) is bursty/gappy under a GPU-bound VRR borderless source **even when the game itself presents perfectly smoothly** — real session `20260625_180512` (build 0.1.4277, Strange Brigade 4K WGC, 30ms loopback delay, fast p1, GPU~100%): the in-game present hook shows max present interval **10.5ms** across recording-sec 20-50 (game smooth), yet WGC delivery dipped to 24-110fps with 170-200ms callback gaps. The earlier oldest-first Bresenham pacer (`DecideWgcActiveDelayPace`, now retired from production but kept as a tested building block) amplified that delivery jitter into harsh stutter: a count-based depth cap **bulk-dropped** a whole delivered burst in one tick and then the buffer ran dry across the following delivery lull, so a ~115fps source manufactured **~20 dups AND ~14 drops in the same second** (simultaneous drop+dup churn, observed `tickDup`/`dropObs` per second); and oldest-first emission **rubber-banded** the realized content delay 0..243ms vs the 30ms target. The setpoint depth-cap (iter-3, `20260625_135221`) bounded the *steady* VRR-above-output inflation but did not fix the delivery-jitter churn or the rubber-band. **The nearest-target playout** treats the buffer as a fixed-latency jitter buffer: each output tick selects the buffered frame nearest the grid playout target (`computeDelayedWgcSelectionTargetQpc` = `gridTick − contentDelay`, **unclamped** so low-source/recovery does not collapse the delay; iter-5 fix: this target now routes through `GetWgcActiveDelaySelectionTargetQpc`, which keeps subtracting the content delay through **latched WGC live-recovery** on the uniform path — `computeWgcSelectionTargetForTick` previously dropped the delay via a raw `!wgcLiveRecoveryModeActive` gate, so once a below-output VRR source latched live-recovery the realized delay collapsed to ~0 and stayed there for the rest of the recording: real session `20260626_050554`), drops frames the audio timeline has already passed (older than target when a closer not-too-new successor exists, `playoutLeadToleranceQpc = GetWgcActiveDelayResidualToleranceQpc`), emits the slot frame once it has aged in, otherwise holds (an evenly distributed source-limited / delivery-gap repeat) leaving newer frames as future reserve. If that hold would repeat the previous frame but the front buffered frame is still within the existing hard active-delay residual limit and scores better than repeating, the uniform path now uses the same `ScoreWgcActiveDelayRepeatRescueCandidate` policy as the legacy reservoir path and logs `[WGC CFR] Uniform playout rescued repeat with sync-safe frame`; this avoids an unnecessary repeat without changing CFR PTS, audio timing, or VRAM usage. This consumes unique frames at the SOURCE rate **by construction** — no over-drain and no clustered "too new" holds like the old grid-rate reservoir (which force-advanced one unique frame per OUTPUT tick) — so the realized delay is **pinned near `contentDelay` regardless of delivery burstiness** (A/V sync preserved, track lengths/PTS unchanged) and the unavoidable repeats are even. After a true delivery gap it resumes at the correct delay by **dropping the audio-passed backlog** (logged as `[WGC CFR] active-delay playout catch-up: dropped N audio-passed frame(s) ... NOT a game render hitch`) rather than replaying it as a rubber-band; the in-gap freeze stays a clean freeze. Delivery jitter *within* the ~30ms content-delay budget is fully absorbed (smooth); jitter *beyond* the budget still forces even holds (unavoidable with a 30ms playout budget — a deeper adaptive A/V buffer is a possible future option). Set false to A/B against the legacy timestamp-target reservoir. The inject path is structurally immune to this family: it already selects nearest-to-delayed-grid (`SelectFrameClosestToGridIf` + `ComputeDelayedContentGridStartQpc`) over an abundant per-present (non-batched) stream.
- `[Video] bit_depth=10`: explicit 10-bit capture is non-negotiable. WGC can use `R10G10B10A2` or FP16 internally, and the encoder output remains 10-bit. It must not silently fall back to BGRA8.
- `[Video] bit_depth=8` with a high-precision WGC source: final output is NV12, but the source-side fallback stays high precision until the final RGB/YUV conversion. FP16 SDR fallback uses typed FP16 SRVs plus gamma encoding before RGB10A2/NV12 compatibility conversion; no CPU readback/upload path is allowed.

## Locking Model

WGC callback processing now uses a separate processing mutex so WinRT frame draining and GPU copy/COM work remain serialized without holding the pull-mode frame queue mutex. `frameMutex_` is held only while moving completed `WGCCapturedFrame` objects into `pendingFrames_`. Direct callback/VFR mode remains serialized through the existing callback drain path plus the processing mutex.

The callback thread performs one-time QoS setup through MMCSS and disables thread power throttling when available. This is diagnostic and scheduling support only; correctness must not depend on timing sleeps or polling delays.

## Encoder Pressure Policy

The encoder D3D11 device no longer raises GPU thread priority merely because a capture is 10-bit. If `gpu_priority` is explicitly configured, that value is still applied. With the default neutral priority, the encoder raises to `+1` only after sustained encode time reaches 75% of the frame budget, then restores neutral after sustained recovery below 50%. This keeps the game and capture from competing unnecessarily when encode is already healthy.

`[Performance] gpu_scheduling_priority` is a separate OBS-style D3DKMT process GPU scheduling class for the media process. It is opt-in (`off` by default) and logs set status, readback verification (`verified=1` when current class matches the request), and elevation state. It may help WGC only when CE-owned D3D11 copy/convert/encode work is being scheduled too late; it cannot directly prioritize the DWM/WGC producer that delivers frames to CE.
