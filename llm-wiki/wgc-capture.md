## Current Summary

### Monitor target selection and privacy boundary (2026-07-21)

Monitor-scope WGC and DXGI Duplication capture exactly one physical display. `[Capture] monitor` accepts `auto`, `primary`, `window`, `cursor`, or `id:<stable-id>`; the same key (or `Capture.monitor`) may override a named profile. `auto` resolves the known target application's window first, then an eligible foreground application window, then the Windows primary display. Thus global explicit DXGI capture no longer ignores an available source window and blindly records primary. `window` requires a valid matched target, while `cursor` is sampled once at recording start. `CaptureEngine.exe --list-monitors` enumerates active displays and prints a copyable DisplayConfig monitor-device-path ID, friendly name, GDI device, bounds, primary state, adapter LUID, and source/target IDs. If DisplayConfig identity is unavailable, the command labels its `gdi:` fallback as topology-unstable.

Resolution is centralized before backend initialization and logs selector, reason, context, stable ID, device/friendly names, bounds, primary state, adapter, and source/target identity. An explicit selector that is missing or cannot initialize fails closed: routing does not select primary, another monitor, or a window on another display. A DXGI initialization/start failure may use WGC only for the already resolved same monitor. Runtime reset pins the resolved stable identity, so hotplug/re-enumeration can reacquire the same physical display but cannot drift to whatever display later becomes primary or contains the cursor. `auto` also becomes identity-pinned after recording starts. Multi-monitor stitching/composition remains a separate unimplemented feature rather than an implicit virtual-desktop capture mode.

### HDR desktop color contract (2026-07-19)

Windows HDR being enabled makes monitor-scope WGC/DXGI capture HDR even when the desktop application or game is SDR. DWM maps that SDR content into its HDR desktop composition, and Desktop Duplication/WGC exposes the result as linear FP16 scRGB: Rec.709 primaries, extended range, and `1.0 = 80 nits`. The encoder must therefore preserve the scRGB interpretation rather than treating `R16G16B16A16_FLOAT` as already encoded RGB10/PQ.

HDR/SDR classification is source-scoped, not guessed from pixel brightness. A monitor capture sees only DWM's final composite; once SDR and HDR surfaces have been mapped into that FP16 scene-referred image, pixels carry no reliable provenance with which CE could separate SDR applications from native HDR content. Therefore `color_space=auto` encodes an HDR-mode monitor capture as HDR even when every visible application happens to be SDR. Explicit `color_space=bt709` instead requests the implemented whole-frame HDR-to-SDR tone map. Pre-DWM inject capture is different: its swapchain/surface color contract can classify the game itself independently of the display mode, so an injected SDR game remains an SDR recording and a native HDR game becomes HDR.

Session `20260719_170645` proved the old failure. The output probe reported HDR color space 12, DXGI delivered authoritative `R16G16B16A16_FLOAT`, and AV1/P010 metadata was BT.2020/PQ. NVIDIA rejected the native FP16 VP input view with `0x80070057`; the compatibility path then quantized linear scRGB to `R10G10B10A2` unchanged and labeled that UNORM texture as linear G10 input for a driver-owned transfer/primary conversion. The resulting bitstream was structurally valid but its pixels were severely green/magenta and complementary-color corrupted. Correct stream tags could not repair already-corrupt pixels.

Build `0.1.5108` proved that the first correction was incomplete. Follow-up session `20260719_181518` logged the new scRGB-to-PQ transform, NVIDIA successfully accepted the normalized RGB10 input view, and ColorSpace1 reported the exact `12 -> 13` PQ/Rec.2020 contract, but the decoded desktop remained severely green. The remaining corruption was therefore inside the driver-owned RGB10/PQ-to-P010 video-processor conversion; treating that matrix/subsampling step as reliable was the false assumption. Correct RGB10 pixels and correct stream tags were insufficient while the VP still produced the encoded YUV planes.

HDR now bypasses VideoProcessor color conversion completely. FP16 is still normalized on the GPU as linear scRGB/Rec.709 (`1.0 = 80 nits`) -> linear Rec.2020 -> ST 2084 PQ -> RGB10, after cursor composition and before quantization. Two cached plane-specific D3D11.3 render-target views then write the encoder-owned P010 surface directly: the luma shader applies the BT.2020 non-constant-luminance matrix and limited 10-bit `64..940` mapping, while the half-resolution chroma shader averages the corresponding four output samples and writes `64..960` Cb/Cr around neutral `512`. Each code is stored as `code << 6`, including zero low bits. Optional scaling stays GPU-side with bilinear sampling and configured luma sharpening. No CPU readback/upload, wait, extra synchronization, driver color conversion, or legacy HDR BGRA staging surface remains in production.

Color conversion is budgeted by source/output contract. Ordinary SDR stays on the fixed-function VideoProcessor path. Forced HDR-to-SDR performs the expensive transfer/tone/gamut work exactly once per source pixel in one fullscreen RGB10 pass, then lets fixed-function hardware perform scaling and RGB-to-YUV. HDR output performs scRGB-to-PQ once, then reuses that RGB10 result for lightweight luma and chroma plane passes; it deliberately does not repeat PQ conversion in each plane shader. The fixed tone curve avoids per-frame histogram/exposure work and its associated extra textures, readbacks, synchronization, cost, and temporal pumping. Rec.2020-to-Rec.709 out-of-gamut colors are compressed toward the equal-luminance neutral axis, preserving luminance and hue direction instead of independently clipping channels. All render targets, views, shaders, samplers, and constant buffers are cached across frames; logs publish pass count, intermediate format, driver-transfer use, and CPU-wait status. `[PERF]`, `[PERF SUMMARY]`, and `[Framegrab PERF]` conversion fields measure CPU wall/submission time around asynchronous D3D11 work, not GPU timestamp duration, and now say `timing=cpu-wall-or-submit`. They prove that the encoder thread does not block, but an A/B of the same GPU-bound scene remains authoritative for game-FPS cost.

HDR output still fails closed for explicit 8-bit output, runtime shader failure, or unavailable P010 plane RTVs; it never falls back to the known-corrupt VP path. `ID3D11VideoContext1` is no longer an HDR requirement because it has no role in the direct-plane contract. Explicit `color_space=bt709` is not HDR output: it forces a whole-frame GPU tone map from FP16 scRGB or packed PQ/Rec.2020 into gamma-encoded Rec.709 before the SDR VP matrix/subsampling step, then writes BT.709 codec/frame metadata and honors the configured SDR range. `color_space=auto` follows the source; HDR `bt2020` preserves HDR. The tone-map luminance knee places the configured Windows SDR white at 80% linear output and preserves highlight separation in the remaining headroom. MediaEngine resolves the captured monitor through DisplayConfig, queries `DISPLAYCONFIG_SDR_WHITE_LEVEL`, and applies `(raw / 1000) * 80 nits`; a logged 203-nit fallback is used only if the query fails. Unsupported HDR texture contracts fail closed rather than being relabeled. Logs identify both transforms and distinguish `sourceHdr` from `outputHdr`.

Presented backbuffer alpha is not content coverage. Injected games can leave R10 alpha at zero while CE's overlay writes nonzero alpha; preserving it in the forced-SDR RGB10 intermediate allowed the VideoProcessor to discard the game and retain only the overlay in session `20260719_214733`. Every fullscreen RGB preparation now writes opaque alpha after color conversion, and the forced-SDR activation log states `frameAlpha=opaque`. Actual D3D11 readback covers both zero-alpha FP16 paper white and zero-alpha packed PQ overlay green; the latter remains colored at the expected SDR level. Direct native-HDR P010 plane shaders already ignore source alpha and are unchanged.

`VideoFormatPolicyTest` locks format/bit-depth selection and scRGB/PQ tone-map routing. `VideoEncoderSourceTest` compiles all four runtime shader profiles, checks direct-P010-before-VP ordering, and runs actual D3D11 hardware render/readbacks: configured SDR paper white must map to the expected RGB10 headroom code with opaque output, correctly encoded packed-PQ overlay green must retain its chroma and opaque output, and pure PQ/Rec.2020 red must produce exact P010 codes `Y=294`, `Cb=387`, `Cr=960` with zero low six bits. Build `0.1.5114` was then exercised on the live 3840x2160 HDR desktop at 120 fps: native DXGI and WGC files decoded with correct color and BT.2020/PQ/P010 metadata, while explicit `bt709` DXGI and WGC files decoded with correct color and BT.709/P010 metadata. Exact analysis found contiguous CFR packets, decoder-clean video, zero overload/repeat/skip in the representative forced-SDR runs, and three sample-exact audio tracks. DXGI CPU submission timing was about 0.14-0.15 ms for native HDR and 0.21-0.27 ms for forced SDR; WGC forced-SDR submission was about 0.03-0.05 ms. These are not GPU timestamp measurements. Injected SDR/HDR game capture remains a user-run manual validation boundary.

### Transactional CFR startup and delayed-debt pruning (2026-07-14)

WGC and DXGI Duplication share the screen-grab CFR scheduler and therefore share this startup contract. After the post-delay barrier supplies authoritative dimensions/format, captureengine asks mediaengine to prepare the D3D11 device, codec, and mux header without encoding frame zero. Frames arriving during that work remain available to reservoir selection. The selected generation-numbered `CfrTimelineStartContract` is immutable; newer selected-reserve and queued frames survive live handoff, and the contract is committed only after the first successful encode. If the successful frame differs from the originally selected candidate, the contract is rebased to that frame while preserving its integer content/render/smoothness delays. Encoder initialization duration is logged as prewarm time and commit lateness, not folded into permanent playout delay.

Live stale-history pruning subtracts the active content delay before applying its bounded-live or encoder-limited excess-debt allowance. A delayed target is consequently never classified as stale merely because its intentional reservoir exceeds 250 ms. The supplied desktop failure had healthy WGC delivery but almost every CFR slot repeated because a deferred first encode inflated the active delay while the old wall-relative 250 ms floor deleted every candidate before it reached that target. Diagnostics now expose prewarm success/duration, selected and committed contract generations, raw/selection timestamp offset, retained reserve depth, active delay on debt drops, and contract commit lateness. Inject remains on its separate causal GPU-native path and does not acquire a historical texture reservoir or D3D11 screen-grab prewarm.

### Contention prewarm and video memory (2026-07-12)

The fixed `wgc_smoothness_buffer_vram_budget_mb=3000` default remains deliberate. At 3840x2160/120 with FP16 WGC input and retained R10, policy targets eight FP16 source buffers plus sixty-four R10 retained slots when the cap permits; it does not shrink against physical-VRAM percentages or current OS headroom. Explicit `0` disables optional reservoir allocation, and explicit 10-bit/HDR never falls back to BGRA8.

Once WGC format/dimensions are authoritative, retained-copy shaders/state and the pool are built before callback registration and `StartCapture`. Duplication prewarms from its output hint; a differing first acquired texture rebuilds before publication. Full configured counts are attempted first. Only allocation-exhaustion HRESULTs reduce source buffers or optional retained depth; unsupported format, access, and device-removal failures do not. Mandatory sync, safety, and reserved-free capacity is preserved, and every attempt/final millisecond reduction is logged.

`IDXGIAdapter3::QueryVideoMemoryInfo` logs budget, process usage, reservation, available reservation, estimated pool, and over-budget observations before/after allocation and once per second. OS budget movement alone never resizes a live pool. Diagnostic `wgc_video_memory_reservation=mandatory|full` clamps reservation to the reported amount, verifies readback, and resets it on teardown; shipped/default mode is `off` pending controlled A/B evidence.

### Lifecycle, retarget, and handoff invariants (2026-07-11)

WGC callbacks never queue an unguarded raw `this`. Each capture instance owns a callback epoch; frame/closed callbacks acquire a lease before touching instance state, shutdown closes the epoch and drains existing leases, and late callbacks become no-ops. Capture publication uses atomically loaded `shared_ptr` ownership plus an exclusive lifecycle gate, so a callback/encoder read pins the object while retarget, stop, or destruction waits. Retarget is transactional: the replacement is fully initialized before publication, and failure restores/restarts the prior source rather than leaving capture unavailable. Source epochs are assigned by the producer and travel with each queued frame; the encoder discards retired epochs and resets repeat/cursor state only when the active WGC lineage actually changes.

Auto inject fallback is a two-phase handoff. Inject remains authoritative while standby WGC/DXGI starts; the switch occurs only after the replacement has delivered first-frame proof. The standby source keeps its publication epoch at commit, so the proven frame and the last successful inject repeat remain usable across the boundary instead of creating a CFR hole. Failure or readiness timeout stops only standby capture and keeps inject alive. The fallback target must resolve to the requested process window/monitor (or a process-matching foreground window); an unresolved source is left unarmed and never silently becomes primary-monitor capture.

The duplication acquire thread parks on a condition variable while reset/unusable instead of polling. Thread creation failures unwind cleanly, callback exceptions are contained, MMCSS registration is always balanced, and capture-running state is cleared on every exit. WGC pool recreation is transactional and includes HDR/VFR options; start/stop/reset paths are exception-safe and never destroy a capture object while its callbacks can still run.

Windows Graphics Capture remains the default non-injected capture path. Same-device WGC capture is the preferred low-overhead default (`wgc_same_device_capture=true`); the dedicated capture D3D11 device remains a supported fallback/diagnostic path when same-device initialization is disabled or fails. DXGI Desktop Duplication always owns a dedicated same-adapter D3D11 device/context, regardless of the WGC setting, so duplication acquisition/canonicalization cannot serialize the encoder immediate context. Split-device screen capture uses an explicit keyed-mutex handoff: capture acquires producer key 0 and publishes key 1; the media encoder acquires key 1 and returns key 0. Inject retains its independent key-0/fence contract.

The split-device key lifecycle also covers frames that are not encoded. If CFR selection discards a published retained frame, releasing its CPU lease cannot itself change the keyed mutex from consumer key 1 back to producer key 0. Once the slot lease is exclusively reacquired by the producer, it therefore tries key 0 first and then safely reclaims an abandoned key 1 before overwriting and republishing the canonical surface. `[WGC Perf] KMReclaim` counts this expected reclamation separately from a real `KMFail`; sustained `KMFail` or `poolSaturatedDrops` is still a fault. Cursor-aware CFR repeats perform a second source read after fresh conversion, so the repeat-source cache explicitly reacquires key 0, copies and flushes submission, then releases key 0. Copying that cache without mutex ownership produces the diagnostic signature seen in `20260711_200954`: valid fresh frames alternating with black repeated frames. The one-shot screenshot consumer has the same contract: it reads on the texture-owning device, acquires published key 1 before `CopyResource`/`Map`, and releases producer key 0. Omitting that acquisition produced a valid 353-byte but entirely black HDR AVIF even though D3D readback reported success. Expect `Cursor-aware repeat source cache synchronized at keyed mutex 0->0` for video and `Texture-owned D3D11 readback ... keyed_mutex=acquired` for a split-device screenshot, with no acquire/release failure.

DXGI Desktop Duplication is a supported frame-source backend behind the shared screen-grab engine. `DxgiDuplicationSource` acquires frame-on-change desktop textures on a dedicated MMCSS thread and feeds the same preflight, retained-copy pool, ingress, CFR, cursor-composition, and A/V-sync machinery as WGC. Pointer-only updates do not create video frames; `AccumulatedFrames>1` measures consumer lag; `ACCESS_LOST` requests a full retarget/reset. Duplication preserves the separate hardware cursor plane where Windows exposes it, while live pointer-state diagnostics suppress encoder cursor composition if Windows embeds the cursor in the desktop image. **Strict format/handoff policy (2026-07-11):** `DXGI_OUTDUPL_DESC.ModeDesc.Format` is only a display-mode hint; the first acquired texture is authoritative. Explicit `capture_method=dxgi_dup` with `bit_depth=10` offers R10 then FP16 for SDR (FP16 only for HDR), waits for and validates the first frame, rejects BGRA8 instead of upconverting it, and fails recording rather than silently switching to WGC. Raw duplication textures never reach the encoder: R10 is shader-canonicalized into a CE-owned shared R10 render-target/SRV surface, while FP16 SDR uses the existing FP16-to-retained-R10 shader path; both then convert to P010 without an 8-bit intermediate. Direct VP input is probed only on these CE-owned canonical surfaces, with canonical staging fallback if the driver rejects the view. Budgeting uses the proven first-texture format and `requiresSourceFramePool=false`. Logs distinguish backend, canonicalization, staging, keyed-mutex failures, and CPU-wall/submission timing; those CPU values are not GPU timestamp durations. Real-hardware 4K120 validation remains required for throughput and random-stutter proof.

Fresh configs define application targets with named `[Profile.*]` sections. `video_capture=wgc` generates a window-scoped WGC route; `video_capture=dxgi_dup` uses `monitor=auto` to select the matched window's monitor unless the profile supplies another selector. `process`, optional `window_title`, and `window_match=exact|contains|contains_or_class` feed the existing scored window selector, and the selected process profile is loaded before recording so its media overrides apply. The compatibility-only `wgc_window_detection` list is still parsed, but a canonical profile for the same process/window removes that legacy entry. WGC and DXGI profile candidates are scored together at recording start so a foreground/fullscreen/title match wins rather than backend declaration order.

For a confirmed application-profile screen-grab target, media publishes the selected window PID and CE capture-device adapter LUID through ABI 37's separate seqlocked screen-grab target snapshot. The sensor service uses it only while no hook-owned source exists, preserving CPU/GPU/VRAM attribution for `dll_injection=never` WGC/DXGI recordings. This does not set hook `sourcePid`, request injection, read target memory, or hide CE from anti-cheat software; identity uses Windows' documented limited-query API and the already selected window owner.

When auto WGC recording has no source PID and no matched configured profile/legacy window, CE prefers the foreground top-level fullscreen-like non-shell window before falling back to monitor capture. This is meant to keep borderless/FSO game captures on a window-scoped WGC item instead of a desktop/monitor item that is more likely to disturb DirectFlip/VRR and cursor-plane behavior. Configured targets do not block this fallback merely by existing; they block it only after a configured window actually matched and initialized. The selector rejects desktop shell windows, owned/tool windows, child windows, CE itself, and common shell host processes. Configured per-window detection scores all matching candidates instead of taking the first enumeration result, strongly preferring the foreground root, fullscreen-like windows, title/class matches, process matches, and large capture area. Logs to watch are `[Media] WGC window detection selected ...`, `[Media] Application profile selected WGC window capture ...`, `[Media] Application profile selected DXGI duplication ...`, `[Media] Auto mode: no source PID; foreground fullscreen WGC window capture selected ...`, or the fallback diagnostic `[Media] Auto mode: foreground WGC window candidate not used ... matchedConfiguredWindow=... configuredEntries=...`.

WGC window item creation now has explicit diagnostics and a best-effort `WindowId` path. Window capture first tries dynamically resolved `GetWindowIdFromWindow` plus `GraphicsCaptureItem::TryCreateFromWindowId`; if unavailable or rejected, it falls back to `IGraphicsCaptureItemInterop::CreateForWindow` and logs the method/HRESULT evidence. Monitor capture still uses the existing interop path. The recording log should include `[WGC] Capture item created: target=... method=WindowId|InteropWindow|InteropMonitor ...`, `[WGC] Capture session diagnostics: ... framePool=CreateFreeThreaded sourceBuffers=... borderless=... nativeCursorRequested=... producerTargetFps=... localThrottleFps=...`, `[WGC] Capture origin diagnostics: target=... originMode=... origin=(...) itemSize=...`, and `[Media] WGC recording target: target=window|monitor ... nativeWgcCursor=0 encoderCursor=...`. Window initialization failures no longer silently become monitor capture in detection/start paths; the fallback is explicit in logs. `CE_WGC_ITEM_SOURCE=interop` and `CE_WGC_BORDER_MODE=keep` are developer A/B diagnostics only, not user-facing `config.ini` requirements or default behavior.

WGC CFR always requests `MinUpdateInterval=0` (max producer rate) and keeps the local copy throttle disabled. A finite `MinUpdateInterval` is a minimum accepted-update gap, not a cadence resampler. For an ideal periodic source rate `S` and finite producer limit `P`, accepted delivery is approximately `S / ceil(S / P)`: 138 fps limited to 120 becomes about 69 fps, 144 limited to 120 becomes 72, and a 160 fps source limited to the old 150 fps headroom target becomes about 80. The exact phase makes the transition appear random across otherwise similar recordings. Worse, callback-derived source-rate telemetry is already downstream of this sampler, so feeding it back into the interval creates a self-confirming half-rate state. No finite target inferred from variable post-gate input is universally safe; the old 125% cap, source+5 adaptive retune, max-rate recovery switching, and cap-restore actuator are removed rather than retuned.

The timestamp-nearest CFR scheduler is the only source-frame resampler. It consumes every WGC callback, retains the bounded look-ahead history, chooses the closest monotonic source frame for each content timestamp, and discards surplus/stale history there. Startup and live classification telemetry remains, but it cannot alter producer cadence. Cached 250/500/1000 ms input/delivery rates age to zero when callbacks stop, so a loading-screen stall cannot leave stale healthy FPS in diagnostics. `[WGC CFR] Producer contract` must report `producerTargetFps=0`; WGC applies and reads back the WinRT interval; `WgcThr` and `Adj` must stay zero. A nonzero target or readback mismatch logs a contract error, is forced back to zero, and the analyzer reports `wgc_producer_rate_contract_fault`. DXGI Duplication has no `MinUpdateInterval` implementation but shares the zero-target screen-grab invariant; inject stays causal, GPU-native, and outside this controller. Explicit 10-bit capture is quality-mandatory: when `Video.bit_depth=10`, WGC must stay on a high-precision input path (`R10G10B10A2` first, FP16 as the only fallback) and fail loudly if no high-precision frame-pool path is available. BGRA8 throughput fallback is allowed only for 8-bit or automatic SDR paths.

WGC recording must preserve the user's live hardware cursor. `capture_cursor=true` still means the cursor appears in the recording, but the WGC session is configured with native cursor capture disabled (`IsCursorCaptureEnabled(false)`) so Windows can keep the game cursor in the hardware plane and avoid software-cursor/DirectFlip/VRR side effects. CE composites a cursor copy into encoded frames on the GPU in the media engine. Cursor state is sampled once in captureengine, carried with fresh frames through the EXE/DLL ABI, and retained in bounded timestamp-ordered histories. Every scheduled CFR output kind—fresh, fresh catch-up, and repeated—samples/publishes once at the scheduled QPC and selects from the same cursor timeline at the same target (`scheduledQpc - active WGC content delay` for screen grab; scheduled QPC for inject). A fresh frame must not bypass that resolver with its attached snapshot: doing so makes cursor motion jump at every fresh/repeat boundary and video prediction exposes the discontinuity as a one-frame gray ghost or sharp/blurry pulse. Pixel ownership remains authoritative after timeline selection, so a selected source texture with an embedded cursor suppresses composition even if the delayed timeline selected an older visible state. DXGI duplication publishes one coherent source-pointer observation from `DXGI_OUTDUPL_FRAME_INFO`: `PointerPosition.Position` is the cursor shape's top-left rather than its hotspot, is valid only while `Visible` is true, and belongs to `LastMouseUpdateTime`. Both GPU composition paths therefore ignore the bitmap hotspot only for this coordinate convention; generic WGC/inject snapshots retain hotspot semantics. Authoritative DXGI hidden or embedded updates clear handle-visibility fallback, and embedded/software-cursor state suppresses encoder composition. Mixing these coordinate conventions makes fresh and CFR-repeated frames alternate by the cursor hotspot and visibly jitter. Inject capture resolves the source process client rectangle and maps desktop coordinates through client-to-swap-chain scaling instead of assuming screen origin `(0,0)`.

Cursor resources are keyed by handle plus per-monitor requested dimensions. `GetSystemMetricsForDpi` supplies the monitor-DPI target, `CopyImage(..., LR_COPYFROMRESOURCE)` requests the nearest native Windows cursor resource before any point-filtered fallback, and larger accessibility/custom cursors are never downscaled. `DrawIconEx` renders each selected shape over opaque black and white once; their difference reconstructs one canonical straight-alpha BGRA bitmap regardless of whether the original Windows color bitmap stored premultiplied, straight, mask-only, or monochrome pixels. This prevents partial-alpha edges from being multiplied twice. Hotspots scale with rounded integer math; negative-monitor origins, client/swap-chain scaling, clipping, and out-of-order timeline selection have unit coverage.

The NV12/P010 path never supplies the cursor as a second video-processor stream. A separate cursor is point-sampled into the captured RGB surface first, so it and a Windows-embedded/software cursor both travel through the same single progressive RGB-to-YUV conversion. On the normal CE-owned WGC, DXGI, and inject surfaces, only the clipped cursor rectangle is copied to a small cached texture, drawn, consumed by the VP, and restored in immediate-context command order before keyed-mutex ownership returns; there is no full-frame copy, flush, readback, CPU/GPU wait, or game-process work. A cached full-frame GPU-copy fallback exists only for an unexpected non-render-target input. Cursor-resource/composition failures are rate-limited and fail open for video: that frame continues through conversion without the separate draw instead of being dropped or repeated. The direct-RGB encoder path uses the same bitmap/shader. SDR remains sRGB; FP16 scRGB converts the cursor to linear P709; HDR10 converts linear P709 cursor primaries to P2020 before PQ encoding. Target RTVs are cached per surface to avoid per-frame view creation. The one VP main stream is progressive with driver automatic processing disabled, so desktop/UI capture does not inherit optional denoise, de-ringing, stabilization, or other temporal video heuristics; explicit scaling and configured edge enhancement remain separate.

Runtime shader compilation must not unload `d3dcompiler_47.dll` while any returned code/error blob remains alive, because the blob's `Release` implementation resides in that module. The compiler module guard is declared before all compiler-created COM guards so reverse destruction releases every blob before unloading the module on success or failure. Inline shaders also avoid HLSL reserved words such as `linear` as identifiers; violating either rule can turn a fail-open cursor-resource error into a media-process crash.

The previous `IGraphicsCaptureSession4::DirtyRegionMode(ReportOnly)` cursor-only suppression path remains removed because the `20260701_092742` run showed DirectFlip/VRR loss while dirty-region metadata and native WGC cursor capture were active. Logs to watch include the rate-limited `[Cursor] CFR timeline ... output=fresh|fresh-catchup|repeat ... source=... selected=... coord=hotspot|shape-top-left`, `[Cursor] Point RGB precomposition before VP active ... smallRestore=1`, `[VideoProcessor] Deterministic single-stream processing: progressive=1 auto=0`, the native-cursor-disabled messages, `DropCursor=0`, and absence of `Dirty-region metadata enabled` or the compatibility-only `RGB precomposition fallback uses a full-frame GPU copy`.

R10 (`R10G10B10A2`) WGC frame pools are rejected by the WinRT capture layer itself with `E_INVALIDARG`; one R10 attempt remains for future Windows versions, then WGC uses FP16. The FP16 source pool is staging-only and its callback converts FP16 to retained R10 on the GPU; FP16 exactly represents all R10 values, so explicit 10-bit capture keeps a true >8-bit chain through P010 encode. The canonical option is `wgc_allow_lossy_bgra8_pool=false`. Setting it true may select a lower-VRAM BGRA8 staging pool only for non-explicit/auto bit-depth operation; `bit_depth=10` and HDR always gate that branch out, and DXGI duplication never consults it. `wgc_prefer_compact_10bit_pool` is a deprecated alias used only when the canonical key is absent; the canonical key wins if both exist. The prior claim that the old option set false was not a true 10-bit chain was incorrect: observed FP16 source → R10 retained → P010 encode contains no lossy 8-bit intermediate. Typed SRVs and all conversion remain GPU-side.

WGC CFR startup A/V sync now uses one shared start contract by construction. Capture performs the existing pre-live cadence/encoder settling delay first, flushes pre-anchor warmup material, arms a one-frame startup barrier, then waits for usable post-delay WGC material at or after that barrier. Before live handoff, it drains the pending WGC queue and buffered WGC frames. With no active render-domain delay, it selects the freshest valid post-barrier frame rather than accepting the first stale candidate. With an active render-domain delay, the measured render-loopback delay is treated as a required video-content reservoir: startup selects the candidate closest to `latestCandidateSelectionQpc - requestedDelayQpc`, keeps newer candidates buffered for the first live ticks, and may wait briefly before live output for roughly the measured delay plus two frames if the reserve span/low-water count is not yet sufficient. If the adaptive smoothness buffer is armed, its bounded startup-only extra delay becomes the contract's video playout reserve while the audio anchor remains the accepted video QPC plus only the resolved render-loopback delay; later source deficits become normal CFR repeats, not live audio-anchor shifts. If the wait budget expires or the span is insufficient, it logs the failure reason and falls back to the safest available candidate; a timeout with no span growth is logged as `source_startup_underfeed`, while a timeout with partial usable span can preserve newer post-barrier frames for the first live ticks instead of collapsing to a one-frame reserve. When the reserve is underfed via that partial-span fallback (`startupPartialReserveFallback`) AND the source is delivering at/above the CFR target, `ResolveWgcStartupSmoothnessActiveDelayQpc` caps the locked smoothness extra read-delay DOWN to the measured jitter floor (`wgcSmoothnessFloorDelayQpc`) rather than letting the non-deterministic startup buffer pile-up become the permanent active delay. Source-rate proof accepts either the existing minimum-window rate or the cadence of at least three actual startup reserve candidates whose mean interval is no slower than the CFR interval. The candidate proof avoids pre-live settling gaps polluting the minimum windows and making identical startup candidates produce different permanent delay decisions; the cap log reports `minWindowProof`, `candidateProof`, candidate count, and span. No-span underfeed and genuinely below-target cadence remain uncapped. Rationale: the pile-up depth is timing-dependent, and because the active read delay equals the forward-reservoir span, a too-deep accidental lock leaves the read target older than the source can sustainably keep buffered, so the oldest buffered frame is chronically "too new" and repeats cluster into multi-frame freezes for the whole session (startup-timing-dependent judder; two runs under identical conditions randomly land smooth or juddery, e.g. locked 187ms vs 252ms on the same Fortnite build). A shallower lock only adds fresh-frame headroom (which the repeat-rescue needs to advance instead of holding); the cap never increases a shallow pile-up, is sync-neutral (the extra delay is absorbed by the live-start schedule offset while audio stays anchored to `avContentDelay`), and is skipped when the source runs BELOW the CFR target so the deep reservoir is preserved for genuine sub-target-lull absorption. The cap logs `[EncoderThread] WGC startup underfed active-delay capped to measured jitter floor`. During live WGC CFR, the reservoir low-water frame count is derived from `ceil(requestedDelayQpc / frameIntervalQpc)` and the target adds one extra frame. Producer capture remains max-rate while low-water changes selection/repeat attribution only. Active-delay selection first prefers strict candidates. If those leave only an older fallback while a slightly too-new frame is inside the hard residual limit, the selector evaluates timestamp damage plus repeat-cluster pressure: a bounded relaxed candidate may be chosen to avoid extending a visible repeat streak, but candidates beyond the hard residual limit are rejected and counted as sync-risk rejections. After any index-changing step such as low-source clamping or reserve-preservation fallback, the final selected frame is revalidated against both the smoothed selection timestamp and raw WGC timestamp; if either timestamp is too new beyond the hard late-residual cap, CE repeats/classifies instead of encoding that frame and increments `delayPostSelectionRejectedSync`. Mediaengine commits the accepted raw video timestamp as the video origin; the first audio anchor is that origin plus only the resolved render-loopback delay, while the smoothness reserve advances the live playout QPC. First stream packets should start at PTS zero, and the accepted frame should be either the requested delayed-reserve candidate or the freshest safe fallback. The startup barrier log includes freshness and reserve diagnostics such as `freshened`, `bufferedExamined`, `queueExamined`, `discardedOlder`, `discardedBeforeBarrier`, `startupReserveFrames`, `startupReserveSpanUs`, `startupDelayTargetUs`, `startupSelectedByDelayReserve`, `startupReserveReason`, `keptReserveFrames`, `startupReserveWaitedUs`, `startupReserveSpanGrowthUs`, `startupReserveWaitFreshened`, `startupSelectedDelayUs`, `startupFallback`, and `startupPartialReserveFallback`. `[AVSyncApply] wgc_cfr_start_contract` reports the committed generation, schedule offset, and raw-versus-selection offset; steady WGC source selection must not subtract that schedule offset on top of the requested content delay.

Current terminology clarification: “drains the pending WGC queue and buffered frames” above means transfers them into the ordered startup candidate set; it does not flush the newer selected reserve at live handoff. The current contract keeps `audioAnchorQpc = videoOriginQpc + renderLoopbackLatency` and `liveQpc = audioAnchorQpc + smoothnessReserve`; smoothness reserve therefore delays video playout but is not added to the audio anchor. `[AVSyncApply] wgc_cfr_start_contract` now reports the committed generation and the raw-versus-selection timestamp offset instead of assuming `selectionOffsetUs=0`.

WGC retained copy-pool textures are ownership-protected. Every retained WGC texture carries `poolSlot`, `poolGeneration`, and a move-only `WgcPoolSlotLease` through `WGCCapturedFrame`, direct callbacks, `QueuedFrame`, startup candidates, the live frame queue, buffered WGC frames, and `g_LastFrame`. `CopyFrameToPool` may copy only into an unleased slot. If all slots are leased, CE drops the incoming WGC frame as `wgc_pool_saturated_safe_drop` instead of overwriting queued, selected, or currently encoding content. The lease is released when a queued/cached frame is dropped or after `MediaEngine_ProcessFrameD3D11` returns, relying on the current media-engine contract that WGC input is copied/converted into media-engine owned D3D11 frame storage before return. If media-engine ownership becomes asynchronous, the lease must extend to the corresponding GPU completion fence. Pool generations prevent stale leases from a recreated pool from affecting new slot counters.

The WGC smoothness surface budget covers WGC source frame-pool buffers and CE copy-pool slots separately. Source frame-pool buffers are reserved first when budget permits (default 8, minimum 3 under tight budgets), then copy-pool slots reserve render-loopback sync-delay frames plus safety/in-flight/free slots, then extra smoothness frames. The retained reservoir stores WGC source frames, not output CFR slots, so desired retained frames are sized with 125% source-rate headroom (`GetWgcSmoothnessBudgetFps`): at 120 fps output and 300 ms smoothness, the storage target is 45 retained source frames instead of 36 output ticks. This is storage capacity only: startup smoothness delay is still clamped to the configured millisecond target (`GetWgcStartupSmoothnessTargetDelayQpc`), so 120 fps / 300 ms remains a 36-output-tick delay target and cannot inflate the audio/video anchor to 375 ms. The cadence-event and final `[WGC CFR SMOOTHNESS BUFFER]` diagnostics must pass the same `outputFps/maxSmoothnessMs` clamp; otherwise logs report an impossible 375 ms target while runtime correctly used 300 ms. At 4K FP16 source + R10 retained copy with the default 3000 MB budget, the expected shape is 12 WGC source buffers plus 64 copy-pool slots, retaining the full 45-frame source reservoir with `capLimited=0`. At 2048 MB and 250 ms, the split-budget optimizer may trade source buffers for retained copy slots (about 7 source buffers + 50 copy slots) to reach the 38-frame source target. Extra smoothness is reduced first when `wgc_smoothness_buffer_vram_budget_mb` caps the total large WGC surfaces. Unknown/zero startup source-rate windows and sustained source-below-CFR windows must not arm the full extra reservoir; logs should distinguish source/delivery coverage holes from encoder, mux, pool, and audio causes.

When the adaptive smoothness reservoir is armed, WGC startup reserve waiting must budget for the full requested smoothness reservoir, not just the render-loopback content delay. The startup wait budget is now at least `contentDelay + smoothnessTarget + 4 frames` when smoothness startup is attempted; without smoothness it remains the older `contentDelay + 2 frames` shape. If startup still cannot fill the reservoir, logs and analyzer triage should expose `smoothDelayDeficit`, `startupDelayDeficit`, and `wgc_startup_smoothness_underfilled` instead of making audio look suspect when exported track sync is clean.

Live WGC copy-pool pressure trims only surplus buffered reservoir frames. If current free copy slots fall to the reserved-free threshold while the live WGC buffer is deeper than the active delay target, CE drops newest surplus buffered frames down to the active delay target and releases their pool leases. This does not change CFR PTS, audio anchors, track lengths, or default VRAM budget; it protects fresh WGC copies without collapsing the delay reservoir that smoothness depends on. Diagnostics include `poolFreeNow`, `poolPressureTrim`, and the existing pool/free-min evidence.

With `wgc_active_delay_uniform_cadence=true`, the nearest-target playout layer owns source-above-target surplus such as 144 Hz WGC input into 120 fps CFR output. The 2026-06-29 desktop run `installed/captureengine/logs/20260629_220408` showed enough WGC input for most one-second windows but still produced visible repeats because ingress soft/credit pressure pre-dropped frames before the uniform playout could choose the smooth 144-to-120 cadence. The current rule is: if the recent WGC input min windows are at or above the CFR target, WGC ingress accepts frames under soft reserve or decimation-credit pressure and reports them as `uniform_playout_soft_reserve` / `uniform_playout_credit`; a truly full copy pool (`freeCopySlots==0`) still drops before copy. This does not increase the copy-pool/VRAM budget and does not move audio timing; it only prevents avoidable no-frame slots that later become CFR repeats. Watch `[WGC Perf] Ingress` `accPlaySoft`/`accPlayCredit` and final `ingressPlaySoft`/`ingressPlayCredit` together with hard pool saturation, `delayPaceCapTrim`, and `sourceRepeatLowerBound` when judging a 140/144 fps source recorded to 120 fps CFR.

WGC active-delay smoothness attribution estimates the source-limited CFR repeat lower bound from output ticks and unique WGC source frames, then compares it with actual repeats. Source-limited sync-delay holds count toward the lower bound even when a hard-safe candidate exists, because a stalled/underfed WGC source can still force a repeat without CE policy being at fault. `sourceRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, `excessRepeatClusters`, and `excessRepeatClusterMax` answer whether a run is near the best achievable CFR cadence for the flawed input or whether CE added avoidable repeat damage. Important nuance: a stable 140/144 Hz source into 120 fps CFR should be consumed as surplus source drops with zero repeats; repeats are not caused by FPS mismatch alone. Repeats become necessary when a CFR output slot has no sync-safe fresh source frame, for example because source FPS falls below target, frame times spike, WGC/DWM delivery is gappy/batched, or the only candidate is too new for A/V-safe selection. The final `[WGC CFR SOURCE COVERAGE]` line makes this explicit with `coverage`, `reason`, `bestEffort`, `sourceRepeatLowerBound`, `syncSourceRepeatLowerBound`, `deliveryRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, and clean encoder/mux/pool/selection booleans; `wgc_source_coverage_best_effort` is a non-fault analyzer verdict meaning CE matched the source/delivery lower bound and did not add avoidable repeat damage. The `[WGC CFR SUMMARY]` `longest=<ms>` / `longestDup=<ticks>` fields are EPISODE-scoped (longest below-target *episode* wall duration, and dup ticks *within* it) — they OVERSTATE a visible freeze because the source still delivers new frames during the episode (e.g. real run `20260630_202659`: `longest=4110ms longestDup=292`, but during that 4.1s episode ~201 unique frames still arrived ≈49fps, not a static freeze). The true visible-freeze metric is `longestContiguousDup=<ticks> (<ms>)`: the longest CONTIGUOUS held-frame run, tracked session-wide (`CaptureSessionSummary.longestContiguousDupTicks`) so it survives the per-window `[Cadence Health]` `DupStreak` reset and is not split/undercounted across a logging-window boundary. For `20260630_202659` the worst contiguous hold was ~115 frames (~0.96s), not 4.1s, matching the user observing no multi-second freeze; `ShortfallMax=0.0ms` confirmed CFR output timing never stalled. The analyzer surfaces this as `worst_contiguous_freeze=<f>/<ms>` and relabels the episode fields `longest_episode`/`episode_dups` so triage no longer reads a below-target episode as a freeze. Analyzer triage now parses WGC duplicate percentage, longest duplicate run, longest contiguous freeze, and worst input/delivered FPS from `[WGC CFR SUMMARY]`; a run with bounded residuals, `delaySoftLateAccepted=0`, no soft-safe missed candidate, and zero lower-bound excess is classified as `wgc_source_limited_smoothness_ceiling` rather than `wgc_audio_late_risk`. `delayPostSelectionRescuedSync` means a final too-new selection was rescued to a safe candidate before encode; `delayPostSelectionRejectedSync` remains strict until fresh runs show zero. Active-delay max-rate recovery is reserved for a healthy but underfilled delay reservoir; true source underfeed is classified instead of being chased with aggressive capture recovery. Unstable-FPS windows are split into healthy, recoverable-underfill, hard source stall, and post-stall recovery classes. Healthy/recoverable/post-stall active-delay candidate scoring uses a soft late target derived from the frame interval and clamped to about 5-7 ms. The hard 10 ms cap is only a safety boundary: a hard-safe frame above the soft target is not a quality-safe choice in those windows. When no soft-safe frame exists, WGC should repeat and log the hold as `delaySyncProtectedRepeats` / hard-only source limitation instead of encoding near-cap visual content that can make audio feel late. True source-limited or hard-stall windows retain the hard cap and are attributed honestly instead of forcing extra repeats to chase an impossible delay.

WGC CFR audio continuity policy separates visual overload recovery from audio integrity. The live scheduler owns the immutable video PTS grid and audio sample target. WGC source-frame selection normally targets the scheduled tick; if visual shortfall exceeds the bounded live window (`250 ms` or `32` frames, whichever is tighter), obsolete source snapshots may be pruned and selection clamps toward the live-window floor. The scheduler never advances the output grid without submitting a packet. Temporary encoder debt is recovered through bounded faster-than-real-time tick processing and cached repeats, not PTS holes.

When the source is healthy but the encoder is sustainably behind target, WGC enters an encoder-limited smoothness path instead of treating the backlog like source starvation. The classifier splits true source-under-target evidence from CE/encoder delivery pressure: encoder recovery-limited state should imply encoder-limited smoothness unless the source is genuinely below target, and a mode-mismatch warning is strict policy evidence. That mode keeps CFR timestamps and audio sample targets exact, but bounds live visual debt to roughly `50 ms` or `3` target frames, coalesces skipped old visual slots as `encoder_limited_source_drop` events, and drops stale buffered history more aggressively after a near-live frame has been selected. Source-starved behavior stays separate: genuine missing source frames are still represented as repeats/holds and attributed as source-limited evidence. In both modes WGC rejects frames that are too far in the future for the effective target, never emits selected source timestamps backward, and does not burst-encode fresh WGC frames to spend historical shortfall. Audio remains real samples or real encoded silence from sample 0 to the final CFR endpoint; it is not shortened, trimmed, or pitch-corrected to hide WGC/encoder debt. At stop, WGC generic CFR drain is disabled: post-stop frames and pending buffered WGC frames are discarded rather than encoded into a frozen visual tail.

The audio side has one extra guardrail under WGC overload: CFR source-clock compensation must not spend normal buffer-level deficit as clock drift. Healthy WGC CFR runs should stop with `[STOP AUDIO DETAIL] ... ratePpm=+0.00 compDelta=0 sat=0`; saturated `ratePpm` while packet durations and source clocks are otherwise exact is content-drift evidence, not an acceptable pitch correction.

Shared CFR audio/timeline rules for both WGC and injected capture live in `cfr-capture-sync.md`. In particular, CFR timer-rebase debt is not disposable: deleting scheduled ticks can make visual content jump ahead while continuous audio appears to lag, even when final packet durations are equal.

Diagnostics now keep timing concepts separate. CFR frame spacing (`8.33 ms` at 120 fps, for example) is the video frame interval, not the audio/video offset. A/V sync evidence comes from the shared startup anchor, stream first PTS values, per-track audio-vs-video `Drift` / `DriftAdj`, stop-time sample counts, and final mux duration delta. WGC visual-frame selection bias is published separately from generic output-schedule bias so audio logs can report `WgcFrameLead`, `WgcFrameLag`, and `WgcSelBias` without conflating selected content timing with encoder-thread wake timing. The realized active-delay metric (`recordWgcDelayRealization` → `realizedDelay*`/`delayResidual*`) is measured against the GRID playout reference (`scheduledSampleQpc − frame.timestamp`, the slot's ideal wall time == the audio anchor reference), **not** wall-clock `selectionNow` (iter-5 fix). Measuring against `selectionNow` folded encoder-thread late-wake jitter (a perpetually-late cadence thread under 100% GPU / network-drive mux I/O woke 27-88 ms late in `20260626_050554`) into a content-delay metric, inflating `realizedDelayMax` to ~108 ms and falsely tripping `wgc_active_delay_realized_delay_unstable` even though the content placed in each PTS slot was grid-correct. Encoder-thread wake jitter is reported separately as `SchedSel`/`SelMax`.

### Split-Budget Optimization (2026-06-30)

The WGC smoothness budget computation for FP16 source pool (8bpp) + R10 retained copy (4bpp) uses "best retention" candidate selection. The algorithm iterates source buffer counts and picks the split that maximizes retained extra frames under the VRAM budget. With the later source-rate-headroom sizing, 4K 120fps FP16+R10 at 2048 MB / 250 ms selects about 7 source buffers + 50 copy pool slots (retained=38 full source-frame target). With the default 3000 MB / 300 ms budget it selects 12 source buffers + 64 copy pool slots (retained=45 full source-frame target).

### Active Delay Residual Tolerance (2026-06-30)

`kWgcActiveDelayResidualTolerancePermille` raised from 600 to 900 (60%→90% of frame interval). At 120fps output, this widens the acceptance window from 5ms to 7.5ms. With a ~140fps source (7.14ms spacing), 5ms rejected ~30% of surplus frames as "too new" even during massive surplus (400+ fps). At 7.5ms, most frames within one source interval are accepted, reducing unnecessary repeats from 20-30% to ~5-10%. The relaxed candidate path (`delayRelaxed`) remains at 0 because the strict path now covers the range that previously needed relaxed scoring.

### Pool Headroom Slots (2026-06-30)

Added `kWgcSmoothnessBufferPoolHeadroomSlots=8` (8 extra copy pool slots beyond the reservoir requirement). With the 3000MB budget, the previous 41 copy slots were often 37+ leased simultaneously at 100% GPU load, with only 4 free. The 8 extra slots give 49 total, leaving 12+ free at peak, reducing `overwritePrevented` from ~1887/sec to near zero. Cost: 8 × 31.6MB = 253MB, total ~2310MB out of 3000MB budget.

### Timer Rebase Threshold (2026-06-30)

`GetCfrTimerRebaseThresholdTicks` for screen grab (WGC with smoothness buffer) reduced from 10000 ticks (83 seconds at 120fps) to 18 ticks (150ms), matching `kCfrShortfallForceCatchupThresholdTicks`. Previously the screen-grab threshold was effectively infinite, so WGC's encoder-timer drift never triggered a cadence rebase. The current default 4K FP16+R10 smoothness budget provides 64 copy-pool slots and 45 retained source frames, giving frame continuity during rebase when WGC delivery is healthy enough to fill the reservoir. Inject capture path (no smoothness buffer) is unaffected — it still uses the 10000-tick threshold implicitly (inject uses `activeScreenGrab=true` → `GetWgcCatchupTicksThisLoop` path, not the timer rebase path).

### Uniform Playout Anti-Freeze Floor (2026-07-01)

The uniform active-delay playout target (`computeDelayedWgcSelectionTargetQpc` = `gridTick − contentDelay`) is grid-anchored and intentionally **unclamped toward live** so low-source/recovery does not collapse the realized delay. But the CFR encoder grid can fall behind wall-clock and be unable to repay the deficit under sustained encoder overload: the grid→wall resync (`media_main.cpp`, `liveTicksOutput % 60 == 0`) is gated on `outputShortfallTicks < 2`, and the per-loop live rebase is capped (`GetWgcLiveSchedulerRebaseTicksThisLoopForMode`, 1–4 ticks). When the grid drifts far enough that the grid-anchored target sits **below the entire reserve** — even the OLDEST buffered frame is "too new for the slot" — `DecideWgcNearestPlayout` holds every tick: the last frame repeats forever while fresh frames pile up and drop as stale. **Observed as a multi-second hard video freeze** (build 0.1.4402, `sbfreeze` log, Strange Brigade 4K120 WGC window capture, av1_nvenc: `[WGC CFR SUMMARY] Live=3091 Dup=2604 (84.2%) DupReason(src=17 timer=2587) longestContiguousDup=2510 (20916ms)` — a 20.9 s frozen run with only the composited cursor moving; `Encode=9.55ms` > 8.33 ms budget confirms the initial 4K120 encoder bottleneck that seeded the grid drift).

**Invariant / fix:** `ApplyWgcUniformPlayoutAntiFreezeFloor(playoutTargetQpc, oldestBufferedSlotQpc, targetIntervalTicks)` (in `capture_pipeline_policy.h`, applied in `media_main.cpp`'s `useInjectParityDelayPacing` block). When (and only when) even the oldest reserve frame is too-new for the slot (`IsWgcFrameTooNewForCfrSlot`, `kWgcCfrSelectionMaxLeadTicks`=3), it raises the slot target to `oldest − GetWgcActiveDelayResidualToleranceQpc` so the oldest (deepest / max-delay) frame ages in and playout resumes at the SOURCE rate. Emitting the OLDEST frame (not a near-live one) keeps video BEHIND the co-timed audio at the reservoir delay, so the A/V content offset is preserved and never inverts. Only VIDEO source selection changes; the CFR video PTS grid and audio timeline/anchor are untouched. **Strict no-op in healthy cadence**: the oldest reserve frame is normally OLDER than the slot (it sits well below the too-new boundary — ~41 ms below vs ~17 ms max delivery jitter — so bursty delivery cannot toggle the floor). Diagnostics: `[WGC CFR] Uniform playout anti-freeze floor engaged: ...` (throttled) and `AntiFreezeFloor=N` in `[WGC CFR SUMMARY]`; non-zero ⇒ encoder-overload grid drift. Tests: `WgcUniformPlayout{FreezesUnderGridDriftWithoutAntiFreezeFloor,AntiFreezeFloorResumesPlayoutBehindAudio,AntiFreezeFloorRaisesOnlyWhenReserveIsTooNew}`.

### CFR Source Coverage Limits

At ~140fps source -> 120fps CFR output, repeats are not the theoretical minimum by themselves. A regular source above the output rate should mostly produce source drops, because each 120 fps output slot can choose a suitable unique source frame and discard surplus. Repeats are the CFR coverage-limit signal: they appear when an output slot has no sync-safe fresh source frame, which can happen with source frame-time spikes, brief source FPS below target, WGC/DWM callback or delivery gaps, or safety rejection of too-new candidates. Under 100% GPU load, WGC is more exposed than inject because the DWM/WGC frame-pool delivery layer can batch or gap frames even when the game presents reasonably smoothly. The inject capture path (no DWM intermediary) is less exposed to that WGC delivery layer, but any CFR path can repeat under actual source coverage holes.

Do not treat D3D12 COPY queues or HAGS as a proven WGC fix. Current WGC receives `Direct3D11CaptureFrame` / `ID3D11Texture2D` surfaces and the bad `sbwgc` run showed CE copy/convert/encode health was OK while WGC callback/source gaps dominated. A D3D12 COPY queue may be worth a proof-first DX12 inject experiment, but WGC would first need share/import feasibility proof and evidence that CE copy work, not upstream delivery, is the limiter. See `performance-priority.md`.

## Config Flags

- `[Diagnostics] wgc_skip_split_device_flush=false`: when true, split-device WGC skips the producer-side `ID3D11DeviceContext::Flush()` after `CopyResource`. Keyed mutex acquire/release remains unchanged. Treat this as a GPU-bound performance experiment until runtime validation proves it does not corrupt frames or underfeed the encoder.
- `[WGC] wgc_same_device_capture=true`: preferred low-overhead WGC path. When false, WGC creates a dedicated capture D3D11 device and uses the split-device keyed-mutex texture-pool path. A live option change requests WGC retarget/reset so the device choice is reinitialized. Treat dedicated mode as a diagnostic/fallback path, not the normal smoothness target.
- `[WGC] wgc_smoothness_buffer_enabled=true`: enables the bounded WGC startup smoothness reservoir when CFR, active render-domain delay, source-rate, and VRAM-budget gates allow it.
- `[WGC] wgc_smoothness_buffer_max_ms=300`: maximum requested extra WGC smoothness delay. The selected startup extra delay is applied to both audio and video anchors; it is not adjusted live after the first encoded frame.
- `[WGC] wgc_smoothness_buffer_vram_budget_mb=3000` (was 2048): budget for WGC source frame-pool buffers plus CE copy-pool retained surfaces. Raised to 3000MB to eliminate cap-limited smoothness buffer under the FP16+R10 pipeline at 4K 120fps. At 3000MB the FP16 split budget gives 12 source buffers + 64 copy pool slots, achieving the full 45-frame retained source reservoir for 120 fps / 300 ms with `capLimited=0`. The startup smoothness delay remains capped by `wgc_smoothness_buffer_max_ms`; the extra source-frame budget is not an audio-anchor delay increase.
- `[WGC] wgc_allow_lossy_bgra8_pool=false` (default false): preserve >8-bit WGC source precision with an FP16 staging pool when WinRT rejects R10. `true` permits a lower-VRAM but lossy BGRA8 staging pool only for non-explicit/auto bit-depth capture. Explicit `bit_depth=10` and HDR never permit the BGRA8 branch. `wgc_prefer_compact_10bit_pool` is a deprecated fallback alias only when the canonical key is absent.
- `[WGC] wgc_smoothness_floor_ms=auto` (default `auto`): WGC-only baseline jitter-buffer FLOOR. The active-delay smoothness machinery (nearest-target playout, uniform cadence, reservoir) was previously hard-gated behind an active audio-latency content delay (`avContentDelayActive`); with no audio latency (video-only capture, or a low-confidence `[AVSyncAuto]` probe) WGC ran near-live and was maximally exposed to bursty DWM→frame-pool delivery under GPU load. The floor engages that same machinery even when `avContentDelayQpc==0`. `auto` derives the depth from measured pre-live WGC delivery jitter (`callbackGap`/`sourceJitter`, `DeriveWgcSmoothnessFloorDelayQpc`), clamped to `[~2 frames, min(wgc_smoothness_buffer_max_ms, buildable reservoir)]`; an explicit value (ms) overrides; `0` disables the floor and reproduces prior behavior exactly. **No-op in the healthy with-audio path**: there `smoothnessTargetDelayQpc` already targets the full reservoir, so the conditional `avContentDelayActive ? reservoirTarget : min(floor, reservoirTarget)` leaves it unchanged. **Sync-neutral by construction**: the audio anchor delay stays `= avContentDelayQpc` (true latency `L`, mediaengine `GetWgcStartupAudioAnchorQpc(firstVideoQpc, renderDelayQpc)` uses `L` only; the floor `S` is realized purely as older startup video + later live-start absorbed by `scheduleOffset`), so audio is byte-exact and the floor cannot move the anchor or reintroduce ghost-image judder. Resolved once at the startup barrier and held fixed for the session (no live anchor retiming). Enabling the floor also enables the smoothness copy-pool budget allocation in `StartWgcRecordingCapture` (`hasWgcContentDelayBudget || wgcSmoothnessFloorBudgetDesired`); inject capture is unaffected. Diagnostics: one-time `[AVSyncApply] wgc_smoothness_floor`, per-window `[WGC CFR JITTER BUDGET]`, and end-of-session `[WGC CFR SMOOTHNESS FLOOR]`.
- `[WGC] wgc_active_delay_uniform_cadence=true` (default true): when an A/V content delay is active, WGC selects video frames with a **fixed-latency jitter-buffer playout** (`DecideWgcNearestPlayout` + `ShouldDropWgcFrontForNearerPlayout`, `media_main.cpp`'s `useInjectParityDelayPacing` block) instead of the legacy grid-rate timestamp-target reservoir (`tryPopBufferedWgcFrameForTarget`, used when the flag is false). **The core problem this solves:** WGC frame *delivery* (DWM→capture frame pool) is bursty/gappy under a GPU-bound VRR borderless source **even when the game itself presents perfectly smoothly** — real session `20260625_180512` (build 0.1.4277, Strange Brigade 4K WGC, 30ms loopback delay, fast p1, GPU~100%): the in-game present hook shows max present interval **10.5ms** across recording-sec 20-50 (game smooth), yet WGC delivery dipped to 24-110fps with 170-200ms callback gaps. ## Locking Model

WGC callback processing now uses a separate processing mutex so WinRT frame draining and GPU copy/COM work remain serialized without holding the pull-mode frame queue mutex. `frameMutex_` is held only while moving completed `WGCCapturedFrame` objects into `pendingFrames_`. Direct callback/VFR mode remains serialized through the existing callback drain path plus the processing mutex.

The callback thread performs one-time QoS setup through MMCSS and disables thread power throttling when available. This is diagnostic and scheduling support only; correctness must not depend on timing sleeps or polling delays.

## Encoder Pressure Policy

The encoder D3D11 device no longer raises GPU thread priority merely because a capture is 10-bit. If `gpu_priority` is explicitly configured, that value is still applied. With the default neutral priority, the encoder raises to `+1` only after sustained encode time reaches 75% of the frame budget, then restores neutral after sustained recovery below 50%. This keeps the game and capture from competing unnecessarily when encode is already healthy.

`[Performance] gpu_scheduling_priority` is a separate D3DKMT process GPU scheduling class for the media process. Its default is `auto`: confirmed HAGS-on resolves to HIGH and HAGS-off/unavailable resolves to ABOVE_NORMAL against the actual capture adapter; explicit values, including `off` and diagnostic `realtime`, remain authoritative. Set/readback, adapter, driver, Windows build, WDDM caps, and elevation evidence are logged. It may help WGC only when CE-owned D3D11 copy/convert/encode work is being scheduled too late; it cannot directly prioritize the DWM/WGC producer that delivers frames to CE.
