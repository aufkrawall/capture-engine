## Current Summary

Windows Graphics Capture remains the default non-injected capture path. The current implementation keeps the dedicated capture D3D11 device as the default for split-device WGC, with keyed mutex synchronization on shared texture-pool slots.

WGC CFR now aims for smooth output with lower steady-state pressure on the game: it starts capture at a modest over-target cadence (`ceil(output_fps * 1.25)`), switches to max-rate only while recovering from source starvation, and restores the cap after sustained fresh input. Explicit 10-bit capture is quality-mandatory: when `Video.bit_depth=10`, WGC must stay on a high-precision input path (`R10G10B10A2` first, FP16 as the only fallback) and fail loudly if no high-precision frame-pool path is available. BGRA8 throughput fallback is allowed only for 8-bit or automatic SDR paths.

When a 10-bpc SDR WGC source cannot create an `R10G10B10A2` frame pool, it may fall back to `R16G16B16A16_FLOAT`. That FP16 source must still convert to `bit_depth=8` output entirely on the GPU: prefer native D3D11 VideoProcessor FP16 input when the driver accepts it, otherwise blit through the fullscreen shader to `R10G10B10A2_UNORM` using a typed `R16G16B16A16_FLOAT` SRV and SDR linear-to-sRGB encoding before VP conversion to NV12. Shader SRVs must not use typeless DXGI formats. For explicit 10-bit output, the final VP/encoder surface remains P010 and compatibility fallbacks must not introduce BGRA8/NV12 intermediates.

WGC CFR startup A/V sync now uses one shared start anchor by construction. Capture performs the existing pre-live cadence/encoder settling delay first, flushes pre-anchor warmup material, arms a one-frame startup barrier, then waits for usable post-delay WGC material at or after that barrier. Before live handoff, it drains the pending WGC queue and buffered WGC frames. With no active render-domain delay, it selects the freshest valid post-barrier frame rather than accepting the first stale candidate. With an active render-domain delay, the measured render-loopback delay is treated as a required video-content reservoir: startup selects the candidate closest to `latestCandidateSelectionQpc - requestedDelayQpc`, keeps newer candidates buffered for the first live ticks, and may wait briefly before live output for roughly the measured delay plus two frames if the reserve span/low-water count is not yet sufficient. If the wait budget expires or the span is insufficient, it logs the failure reason and falls back to the safest available candidate; a timeout with no span growth is logged as `source_startup_underfeed`, while a timeout with partial usable span can preserve newer post-barrier frames for the first live ticks instead of collapsing to a one-frame reserve. During live WGC CFR, the reservoir low-water frame count is derived from `ceil(requestedDelayQpc / frameIntervalQpc)` and the target adds one extra frame. If the reservoir drops below low-water, WGC can temporarily return to max-rate capture recovery, then restore the conservative overcapture cap after the reservoir recovers. Active-delay selection first prefers strict candidates. If those leave only an older fallback while a slightly too-new frame is inside the hard residual limit, the selector evaluates timestamp damage plus repeat-cluster pressure: a bounded relaxed candidate may be chosen to avoid extending a visible repeat streak, but candidates beyond the hard residual limit are rejected and counted as sync-risk rejections. After any index-changing step such as low-source clamping or reserve-preservation fallback, the final selected frame is revalidated against both the smoothed selection timestamp and raw WGC timestamp; if either timestamp is too new beyond the hard late-residual cap, CE repeats/classifies instead of encoding that frame and increments `delayPostSelectionRejectedSync`. Mediaengine selects the accepted video timestamp as the shared audio/video anchor; when automatic render-domain delay is active, the first audio anchor is the accepted video QPC plus the resolved render-loopback delay. First stream packets should start at PTS zero, and the accepted frame should be either the requested delayed-reserve candidate or the freshest safe fallback. The startup barrier log includes freshness and reserve diagnostics such as `freshened`, `bufferedExamined`, `queueExamined`, `discardedOlder`, `discardedBeforeBarrier`, `startupReserveFrames`, `startupReserveSpanUs`, `startupDelayTargetUs`, `startupSelectedByDelayReserve`, `startupReserveReason`, `keptReserveFrames`, `startupReserveWaitedUs`, `startupReserveSpanGrowthUs`, `startupReserveWaitFreshened`, `startupSelectedDelayUs`, `startupFallback`, and `startupPartialReserveFallback`. `[AVSyncApply] wgc_schedule_anchor` may report a nonzero startup `scheduleOffsetUs`, but that value is diagnostic only (`selectionOffsetUs=0`); steady WGC source selection must not subtract it on top of the requested content delay.

WGC active-delay smoothness attribution estimates the source-limited CFR repeat lower bound from output ticks and unique WGC source frames, then compares it with actual repeats. Source-limited sync-delay holds count toward the lower bound even when a hard-safe candidate exists, because a stalled/underfed WGC source can still force a repeat without CE policy being at fault. `sourceRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, `excessRepeatClusters`, and `excessRepeatClusterMax` answer whether a run is near the best achievable CFR cadence for the flawed input or whether CE added avoidable repeat damage. `delayPostSelectionRescuedSync` means a final too-new selection was rescued to a safe candidate before encode; `delayPostSelectionRejectedSync` remains strict until fresh runs show zero. Active-delay max-rate recovery is now reserved for a healthy but underfilled delay reservoir; true source underfeed is classified instead of being chased with aggressive capture recovery.

WGC CFR audio continuity policy separates visual overload recovery from audio integrity. The live scheduler owns the video PTS and the audio sample target. WGC source-frame selection normally targets the scheduled tick, but if visual shortfall exceeds the bounded live window (`250 ms` or `32` frames, whichever is tighter), the live scheduler rebases old owed ticks as covered visual hold/drop debt and source-selection clamps toward the live-window floor. Live scheduler rebase is deliberately incremental: `kWgcMaxLiveSchedulerRebaseTicksPerLoop` caps each loop to one CFR tick so recovery cannot create multi-frame PTS holes that look like stutter.

When the source is healthy but the encoder is sustainably behind target, WGC enters an encoder-limited smoothness path instead of treating the backlog like source starvation. The classifier splits true source-under-target evidence from CE/encoder delivery pressure: encoder recovery-limited state should imply encoder-limited smoothness unless the source is genuinely below target, and a mode-mismatch warning is strict policy evidence. That mode keeps CFR timestamps and audio sample targets exact, but bounds live visual debt to roughly `50 ms` or `3` target frames, coalesces skipped old visual slots as `encoder_limited_source_drop` events, and drops stale buffered history more aggressively after a near-live frame has been selected. Source-starved behavior stays separate: genuine missing source frames are still represented as repeats/holds and attributed as source-limited evidence. In both modes WGC rejects frames that are too far in the future for the effective target, never emits selected source timestamps backward, and does not burst-encode fresh WGC frames to spend historical shortfall. Audio remains real samples or real encoded silence from sample 0 to the final CFR endpoint; it is not shortened, trimmed, or pitch-corrected to hide WGC/encoder debt. At stop, WGC generic CFR drain is disabled: post-stop frames and pending buffered WGC frames are discarded rather than encoded into a frozen visual tail.

The audio side has one extra guardrail under WGC overload: CFR source-clock compensation must not spend normal buffer-level deficit as clock drift. Healthy WGC CFR runs should stop with `[STOP AUDIO DETAIL] ... ratePpm=+0.00 compDelta=0 sat=0`; saturated `ratePpm` while packet durations and source clocks are otherwise exact is content-drift evidence, not an acceptable pitch correction.

Shared CFR audio/timeline rules for both WGC and injected capture live in `cfr-capture-sync.md`. In particular, CFR timer-rebase debt is not disposable: deleting scheduled ticks can make visual content jump ahead while continuous audio appears to lag, even when final packet durations are equal.

Diagnostics now keep timing concepts separate. CFR frame spacing (`8.33 ms` at 120 fps, for example) is the video frame interval, not the audio/video offset. A/V sync evidence comes from the shared startup anchor, stream first PTS values, per-track audio-vs-video `Drift` / `DriftAdj`, stop-time sample counts, and final mux duration delta. WGC visual-frame selection bias is published separately from generic output-schedule bias so audio logs can report `WgcFrameLead`, `WgcFrameLag`, and `WgcSelBias` without conflating selected content timing with encoder-thread wake timing.

## Config Flags

- `[General] wgc_skip_split_device_flush=false`: when true, split-device WGC skips the producer-side `ID3D11DeviceContext::Flush()` after `CopyResource`. Keyed mutex acquire/release remains unchanged. Treat this as a GPU-bound performance experiment until runtime validation proves it does not corrupt frames or underfeed the encoder.
- `[General] wgc_same_device_capture=false`: when true, WGC attempts to reuse the encoder D3D11 device/context instead of creating a dedicated capture device. A live option change requests WGC retarget/reset so the device choice is reinitialized. Keep false by default until load testing proves it helps.
- `[Video] bit_depth=10`: explicit 10-bit capture is non-negotiable. WGC can use `R10G10B10A2` or FP16 internally, and the encoder output remains 10-bit. It must not silently fall back to BGRA8.
- `[Video] bit_depth=8` with a high-precision WGC source: final output is NV12, but the source-side fallback stays high precision until the final RGB/YUV conversion. FP16 SDR fallback uses typed FP16 SRVs plus gamma encoding before RGB10A2/NV12 compatibility conversion; no CPU readback/upload path is allowed.

## Telemetry

`[WGC Perf]` includes split-device diagnostics and callback resilience data in addition to source cadence, queue, drop, selection, copy, encode, and fence data:

- `DropPool`: texture-pool copy failures or saturation.
- `Copy`: last WGC copy duration in microseconds.
- `SlotAge` / `FastSlot`: most recent texture-pool slot rewrite interval and count of rewrites under 5 ms.
- `KMFail`: keyed-mutex acquire/release failure deltas.
- `Flush`: performed/skipped split-device flush deltas.
- `Dedicated`: whether the current WGC device path is the dedicated capture-device path.
- `CbGap`, `CbProc`, `CbDrainMax`: callback gap, callback processing time, and maximum drained frames per callback.
- `Target`: adaptive WGC capture target. `0` means max-rate recovery; positive values are capped overcapture.
- `SchedSelAvg` / `SchedSelBias`: output schedule timing error, i.e. whether the encoder/cadence thread woke early or late versus the CFR grid.
- `WgcSelAvg` / `WgcSelBias`: selected WGC content timestamp error versus the intended CFR selection target. Positive signed bias means selected visual content is newer than the target; negative means older.
- `WGC CFR visual timeline debt drop`: WGC visual debt exceeded the live window. Treat this as a sync warning to inspect; it must not trigger audio trimming, pitch recovery, or fresh-frame fast-forward into old CFR slots.
- `WGC CFR live scheduler rebase`: live scheduler skipped old WGC visual ticks after the live-window debt bound was exceeded. Normal WGC debt recovery permits only one skipped tick per loop; encoder-limited mode may skip a few old visual ticks per loop inside the tighter near-live window while preserving the CFR/audio timeline. Larger chunks outside that mode indicate a stale build or regression that can create visible cadence holes. Inspect the total count and mode for smoothness impact under overload.
- `WGC CFR stale visual debt drop`: buffered visual history older than the active live window was discarded. In encoder-limited mode this window is intentionally near-live so stale backlog does not create delayed wobble.
- `WGC CFR encoder-limited source drop`: an encoder-pressure-only visual backlog was coalesced instead of selecting stale content for old CFR slots. This should appear only when source input is healthy and encoder/video capacity pressure is present.
- `WGC CFR selected source backtrack blocked`: a stale source timestamp would have moved selected visual content backward under pressure. This is strict regression evidence; normal encoder-limited recovery should hold/repeat monotonically or drop stale source history.
- `[WGC CFR] encoder-limited mode mismatch`: recovery state says encoder-limited but smoothness mode was not active while the source was not genuinely starved. Treat as an overload policy fault.
- `[WGC CFR CADENCE EVENT]`: compact per-window cadence attribution with mode, source/target/live timing, content phase error, repeat/drop/rebase reason counts, sync-delay source/policy/source-recovery hold counts, delay residual avg/max/p95/late-max and rolling-window residuals, raw WGC residuals, raw-minus-predicted residual spread, bounded relaxed selections, relaxed decision/rejection counters, post-selection sync-risk rejections, repeat-cluster pressure, buffer state, encoder EMA, and overload flags.
- `[WGC CFR SMOOTHNESS SUMMARY]`: end-of-session smoothness rollup with phase error, shortfall, stale drops, too-new repeats, live rebases, encoder-limited drop counts, sync-delay source/policy hold counts, startup reserve fields, requested/effective A/V delay evidence (`avDelay`, `startupDelay`, `scheduleOffset`, `effectiveDelay`), delay reservoir low-water/target/tick counts, realized delay min/avg/max, residual signed/absolute average, residual max/p95, late/early residual maxima, raw residual avg/p95/late/early maxima, raw-minus-predicted avg/max, bounded relaxed-selection counts, relaxed selection reasons (`delayResidualRelaxedBetter`, `delayResidualRelaxedCluster`), relaxed rejection reasons (`delayResidualRelaxedRejectedSync`, `delayResidualRelaxedRejectedHeadroom`, `delayResidualRelaxedRejectedCost`), post-selection rescue/rejection counts (`delayPostSelectionRescuedSync`, `delayPostSelectionRejectedSync`), repeat-cluster pressure (`delayRepeatClusterPressure`, `delayRepeatClusterMax`), source-recovery attribution (`delaySourceRecoveryHolds`, `delaySourceRecoveryTicks`), source-limited lower-bound fields (`sourceRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, `excessRepeatClusters`, `excessRepeatClusterMax`, `smoothnessNotMaximal`), and `mixedPolicyFault`.
- `WGC CFR stop drain using held pre-stop frame`: stale-build/failure signature. Current WGC exact-stop policy should not use generic stop drain.
- `WGC CFR stop drain discarded frozen-tail debt`: superseded older policy. Treat this as a stale-build warning if it appears in new validation.
- `WGC CFR post-stop frame drop`: a WGC frame timestamped after the stop QPC was discarded. This is endpoint protection when discarded; it must not extend the file.
- `WGC CFR slot repeat: buffered frame is too new for scheduled slot`: recovery path when the WGC buffer only contains future visual content for the effective selection target. It is expected only briefly or while the requested render-domain delay reserve is being maintained. New logs split sync-delay holds into `syncSourceLimited`/`syncDelaySourceHold` versus `syncDelayPolicyHold`; repeated policy holds, requested/startup/effective mismatch, or realized-delay residual over the strict target are CE faults, while small source-limited reserve pressure with bounded residual is a minor warning. Inspect `LiveClamp`, `WgcSelBias`, `BufNow`, reservoir low-water ticks, residual max/p95, and recent input/delivery FPS.
- `CFR Catchup applied using fresh frame`: for WGC shortfall this is a validation failure signature. WGC fresh catch-up budget is zero; old CFR slots must not be filled with newer WGC content.

Large early residual outliers during source-starved WGC are not an audio-late fault when requested/startup/effective match and late residual remains bounded. `wgc_sync_delay_reserve_pressure` is a minor source-limited warning. `wgc_sync_delay_policy_fault` remains a visual/sync fault for healthy-source policy holds, visible residual/phase damage, or mixed source/policy pressure where policy holds are at least 120 and reach at least 25% of active-delay holds or exceed source-limited holds. Strict log validation should catch stale startup handoff, unbounded live rebase chunks, repeated healthy-source policy too-new slot holds, realized-delay residual, raw/predicted timestamp-domain mismatch, encoder-limited phase sawtooth, and excess repeat clusters as separate failure families.

Use these with existing `FreshMiss`, `BufAvg`, `BufMin`, `NoFresh`, `NoReserve`, `EncQ`, `Encode`, and encoder overload flags to separate encoder-limited visual drops, mux backpressure, and WGC source starvation. Shared memory publishes WGC capture health flags; the overlay encoder-overload warning is suppressed while WGC is source-limited or scheduler-limited instead of showing a misleading hard-encoder warning. ## Locking Model

WGC callback processing now uses a separate processing mutex so WinRT frame draining and GPU copy/COM work remain serialized without holding the pull-mode frame queue mutex. `frameMutex_` is held only while moving completed `WGCCapturedFrame` objects into `pendingFrames_`. Direct callback/VFR mode remains serialized through the existing callback drain path plus the processing mutex.

The callback thread performs one-time QoS setup through MMCSS and disables thread power throttling when available. This is diagnostic and scheduling support only; correctness must not depend on timing sleeps or polling delays.

## Encoder Pressure Policy

The encoder D3D11 device no longer raises GPU thread priority merely because a capture is 10-bit. If `gpu_priority` is explicitly configured, that value is still applied. With the default neutral priority, the encoder raises to `+1` only after sustained encode time reaches 75% of the frame budget, then restores neutral after sustained recovery below 50%. This keeps the game and capture from competing unnecessarily when encode is already healthy.
