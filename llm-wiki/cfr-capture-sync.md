## Summary

### Frame ownership and failure recovery (2026-07-11)

An inject `FrameSlot` is not acknowledged when it is merely copied into the media queue. Its move-only ring lease remains attached through buffering/defer and is completed only after the synchronous media-engine copy succeeds or the frame is deliberately discarded. Completion clears the physical slot but advances shared `readIndex` only across the longest contiguous completed prefix, so out-of-order encoder selection cannot release an older slot. Every inject producer checks all still-valid ring metadata before writing a texture and drops the new frame if every transport texture is outstanding. This prevents queued frames from silently aliasing newer pixels. D3D12 resource generations likewise remain published until all referencing frames are retired.

Fresh-frame state is transactional. The candidate becomes `g_LastFrame` and updates source/cursor lineage only after a successful non-deferred encode. If a scheduled CFR fresh encode fails, CE repeats the prior successful media-engine cache at the same scheduled QPC when available; the failed candidate is released and its metadata never becomes authoritative. If both fresh encode and repeat fail, the tick is reported as a real miss. WGC source-epoch changes explicitly clear every repeat-cache layer, while an inject-to-WGC standby commit keeps the already-published WGC epoch and preserves the prior inject repeat until replacement pixels have actually encoded.

Post-mux probing runs synchronously on the writer/finalizer owner with an FFmpeg interrupt deadline and bounded packet scan. It no longer launches a nested thread that could outlive the media-engine DLL or force unsafe detach/late join behavior.

CFR duration metadata cannot prove that every scheduled tick became a packet: the sparse DXGI failure capture declared about 6.19 seconds at 120 fps but contained only 170 video packets, with PTS gaps up to 48 ticks. Finalization now logs expected/emitted/missing CFR coverage from successfully written video packets after encoder flush, and `tools/analyze_capture_av.py` independently scans file packet PTS, fails any missing tick or gap above 1.01 nominal ticks, and handles reordered codec PTS by sorting before gap analysis. `cfr_packet_coverage_fault` is a strict visual/sync event. The default/codec A/V matrix now includes `dxgi_dup`, `wgc`, and `inject`; the codec finalization pass covers AAC, ALAC, FLAC, Opus, and PCM for every backend.

All CFR capture paths share the same invariant: the CFR media clock is authoritative, and audio follows that timeline without live trims, source drops, wall-clock catch-up, or audible pitch recovery. This applies to WGC and injected shared-memory capture when `Video.useVFR=false`. A very small source-clock drift correction lane is allowed only after startup has settled and the CFR timeline is healthy; current code caps it at `0.05%`, far below the user-accepted `1-2%` inaudible upper bound, and it must not be used to recover video/encoder debt.

Packet-level duration equality is necessary but not sufficient for real sync or visual smoothness. If the encoder thread discards accrued CFR timer debt during a stall, the visual timeline can jump forward while audio remains continuous. If WGC accepts stale visual debt for too long, video content can fall seconds behind live and then catch up too quickly. If WGC selects arbitrary fresh/current frames for old CFR PTS slots, video content jumps ahead of the audio timeline. If WGC refuses every usable frame because the scheduled source-selection target has itself fallen outside the bounded live window, the output becomes a repeat cluster even though good near-live frames are buffered. If WGC live scheduler rebase skips many CFR ticks at once, the file can have correct durations but obvious cadence holes. If WGC stop drain closes old debt with held frames, the file can look aligned structurally while the picture has already stopped and audio continues. Final video/audio packet durations may still match in all of those cases. Therefore WGC live overload is handled while the recording is still running: once WGC visual shortfall exceeds the bounded live window, the live scheduler rebases the current CFR tick toward live in one-tick increments and counts skipped old ticks as covered visual hold/drop debt instead of leaving them owed for stop. WGC source selection still clamps only after the live-window bound is breached, stale history is pruned, and WGC fresh catch-up for historical shortfall stays disabled. Inject CFR keeps its existing bounded candidate/repeat policy and must preserve tick order.

Fast zero-drift validation uses CE's own sample accounting as the strict oracle. Once an audio track has completed startup in CFR mode, the live track cursor must advance sample-exactly to the current CFR target on every pull/check; settled CFR pulls no longer keep a 5 ms quantum residual. Periodic `[A/V SYNC CHECK]` and `[A/V SYNC SUMMARY]` lines include `audio_vs_encoded_us`, `audio_vs_target_us`, `audio_vs_scheduled_us`, `residual_samples`, `residual_us`, `target_samples`, and `cursor_samples`. Any `[A/V ZERO DRIFT WARNING]` after startup is a strict audio timeline fault in both stimulus analysis and real-session triage. MKV content analysis still confirms decoded behavior within marker/analyzer precision, but zero drift itself is enforced from CE's target/cursor sample state. Short-run decoded offset slope is corroborating evidence: it fails only when the fitted slope exceeds the configured `ms/min` threshold and the matched offsets span more than the short-run excursion guard, so tiny 4-10 ms decode/interpolation wobble does not masquerade as long-run drift when CE residual is exactly zero.

Do not let CFR source-clock compensation chase ordinary buffer-level wobble. The source-clock correction lane exists for genuine long-run device clock drift only, not for normal pull-buffer deficit, encoder debt, or stop-drain shape. The current CFR Tier1 lane has a wide deadband of roughly 80 ms and still caps correction at `0.05%`; healthy synthetic runs should finish with `ratePpm=+0.00`, `compDelta=0`, and `sat=0` in `[STOP AUDIO DETAIL]`. A run can have exact packet/container durations while decoded markers drift if the compensation lane is saturated from a bogus buffer deficit, so `ratePpm=-500.00` or `ratePpm=+500.00` in a healthy CFR run is a bug signature even when final sample counts are exact.

WGC encoder-limited overload is now distinct from WGC source starvation. If source input is healthy but encoder/mux capacity pressure appears, WGC switches to an encoder-limited smoothness mode even if an earlier low-source/recovery state was originally triggered by delivery pressure. CFR timestamps and audio clocks remain exact, but visual source selection uses a near-live debt window of about `50 ms` / `3` output frames and coalesces old visual slots as explicit encoder-limited source drops. Genuine source starvation stays on the source-starved path and can still repeat planned/missing source frames. The intended overload behavior is honest CFR repeat/drop cadence around near-live content, not a large sawtooth where stale buffered frames are dragged forward and then fresh frames snap back. `wgcEncoderRecoveryLimitedCurrent` should imply encoder-limited smoothness unless the source is genuinely under target; a mode-mismatch warning means the policy split regressed.

WGC active render-domain sync is a content reservoir problem, not only a startup/effective configuration value. The audio probe resolves a render-to-loopback delay; WGC must realize that delay by selecting video content around `scheduledTickQpc - requestedDelayQpc`. A bounded WGC smoothness reservoir may add startup-only extra playout delay when longer-window source-rate evidence says the source can repay it and VRAM budget allows it. The retained reservoir stores source frames, so its frame count is sized with 125% headroom for 140/144 Hz source into 120 fps CFR, but the startup delay target remains clamped to the configured millisecond window; extra source-frame storage must not inflate the shared audio/video anchor. Cadence-event and final smoothness-buffer diagnostics must use the same millisecond clamp so the logs do not report a larger target than the runtime audio/video anchor used. That extra delay is part of the shared startup audio/video anchor; after the first encoded frame, CE must not move the media/audio anchor live to chase WGC source deficits. Later deficits become normal CFR repeats with source/budget attribution. Startup can wait briefly before live output to build the reservoir, live capture can temporarily raise WGC capture to max-rate when the reservoir is below low-water and the source is healthy, and the selector may use a bounded relaxed residual frame only when it is less damaging than repeating the previous frame. Long repeat streaks carry a small explicit policy cost, so WGC can spend bounded residual to avoid extending visible clusters, but the hard late-residual limit is unchanged. A stale strict fallback should not force a repeat when a bounded relaxed frame would reduce total damage. Uniform active-delay playout owns source-above-target surplus: for 140/144 Hz WGC input into 120 fps CFR output, ingress must not pre-drop frames merely because soft reserve or decimation credit says the buffer is high. A regular above-target source should become source drops, not repeats; repeats indicate CFR coverage holes where a slot lacked a sync-safe fresh source because of source spikes, below-target intervals, WGC/DWM delivery gaps, or too-new safety rejection. The playout layer drops audio-passed surplus in timestamp order (`delayPaceCapTrim`) while preserving the shared CFR/audio timeline; ingress still drops before copy only for true hard pool exhaustion. This boundary avoids manufacturing no-frame CFR slots from a healthy source without changing audio timing. Unstable-FPS windows are classified as healthy, recoverable-underfill, hard source stall, source-limited, or post-stall recovery using source/delivery FPS, fresh misses, reservoir depth, source starvation, and safe-candidate availability. Healthy/recoverable/post-stall windows use a softer late target around 5-7 ms; repeated near-cap choices are rejected even if they remain under the 10 ms hard cap. If no soft-safe frame exists, WGC should repeat and log a sync-protected/hard-only source limitation instead of encoding a hard-only near-cap frame that can make audio feel late. Source-limited and hard-stall windows retain the hard cap and are attributed instead of being chased. Candidate and final-selection checks must use both the smoothed/predicted WGC selection timestamp and the raw WGC timestamp; raw-late or post-adjust too-new selections are sync faults even if the smoothed residual looks bounded. The smoothness summary estimates a source-limited CFR repeat lower bound and separates `sourceRepeatLowerBound`, `syncSourceRepeatLowerBound`, `deliveryRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, and `excessRepeatClusters`, so a flawed input source can be judged against the best achievable CFR cadence instead of against zero repeats. `[WGC CFR SOURCE COVERAGE]` and analyzer verdict `wgc_source_coverage_best_effort` are non-fault diagnostics when repeats match the source/delivery lower bound and encoder/mux/pool/selection evidence is clean. Healthy-source active-delay recordings should keep realized-delay residual mean within about `5 ms`, max/p95 within about `10 ms`, `delayPostSelectionRejectedSync=0`, `syncDelayPolicyHolds=0`, and no sustained soft-late accepted pressure. Source-starved runs with bounded late residual, `delaySoftLateAccepted=0`, no soft-safe missed candidate, and repeats at the lower bound now report `wgc_source_limited_smoothness_ceiling` instead of `wgc_audio_late_risk`; this means CE protected sync and the remaining roughness follows the WGC/source input limit. Excess repeats, policy-added repeats, CE-amplified repeat clusters, mixed source/policy pressure, over-soft accepted content, pool lifetime faults, or safe-drop pressure beyond the budget are still visual/sync evidence to inspect. If the source cannot physically deliver enough frames, the logs should say source-limited with bounded residual and lower-bound repeat evidence rather than claiming a perfect healthy run.

The WGC startup smoothness wait budget must cover the full selected reservoir when that reservoir is armed: at least `contentDelay + smoothnessTarget + 4 frames`, while non-smoothness startup keeps the older `contentDelay + 2 frames` bound. Pool-pressure recovery must release only surplus buffered WGC frames beyond the active delay target; trimming below that target would trade one smoothness fault for another. These operations are video-reservoir management only and must not move the shared CFR/audio anchor, shorten audio, alter mux endpoints, or increase default VRAM requirements.

`dx12_av_sync_test.exe` is the deterministic content-level validation stimulus for this class of bugs. It renders event color changes, visual-marker v2 frame marker tiles, inverse/checksum/parity sentinels, a slow smooth-motion lane, and a faster one-second ruler lane while playing a synchronized WASAPI sine schedule. `--encoder-stress-scene` adds deterministic high-entropy animated tiles outside the reserved marker/motion/event regions so NVENC p5/p6/p7 work is meaningfully harder than flat bars. The stress-tile layout is row/column aligned: visible colored tiles should never include a clipped final row, and the manifest records tile size, bounds, row/column counts, and the central reserved event-sample region. Windowed mode defaults to borderless (`window_chrome=0`) so WGC captures the exact rendered client area instead of title-bar chrome; the manifest records requested/render dimensions, fullscreen/window-chrome/borderless state, marker geometry, motion-lane geometry/speeds, event sample region, source stalls, encoder-stress-scene state, and QPC anchors. Its manifest and `AVSYNC ...` logs provide the app-side truth; `tools/analyze_av_sync_stimulus.py` decodes the resulting MKV to recover video event colors, redundant frame markers, corrupt marker/checksum/parity evidence, planned source-stall repeat clusters, unplanned repeat/drop clusters, slow/fast motion stalls, motion expected-position errors, and audio frequency transitions per stream. For CFR MKV analysis, raw decoded video frames are timestamped from the declared stream frame rate when FFmpeg expands CFR playback, rather than mixing sparse packet `best_effort_timestamp_time` rows with the rawvideo frame stream. This is the preferred agentic check when packet-duration equality is not enough.

Synthetic source stalls are intentional app-side source gaps, not CE failures. Launch the app with `--source-stall <start_seconds>:<duration_ms>` such as `--source-stall 8.0:300`. During the stall the app keeps audio, QPC logging, stimulus time, and message pumping active, but suppresses `Present`. The final manifest rewrites `source_stalls[]` with requested and actual QPC/time ranges, suppressed present count, expected repeat span, and tolerance. The app log emits `AVSYNC SOURCE_STALL_BEGIN`, `AVSYNC SOURCE_STALL_END`, and summary counters. Analyzer classification rules are strict: a repeat cluster passes as `planned_source_stall` only when it overlaps the manifest stall window, stays within tolerance, and the surrounding audio/event sync remains correct; any repeat cluster outside those windows is `unplanned_repeat_cluster`.

Codec padding is handled below the same invariant. AAC and Opus may require padded codec frames internally, but the effective final sample count, packet duration, skip/trailing metadata, mux duration tags, and post-mux reopened-file probe follow the authoritative encoded video duration. Do not diagnose an AAC/Opus tail by packet frame size alone; inspect those signals together. Post-mux duration deltas at or below one audio sample or one mux timebase tick are informational rounding evidence; larger post-mux mismatches remain strict warnings.

Content-level audio sync also depends on startup policy. Each exported audio track has its own timeline cursor, and that cursor advances from sample 0 on the shared video anchor. System and mic sources are timeline-valid immediately and produce real encoded silence until packets arrive. App-audio sources are optional only while CE has no evidence that they are active. If process-loopback packets arrived while recording sync was pending, startup must wait for the first post-anchor packet and enough real buffered samples; otherwise the app track can encode one silent startup chunk and all decoded codecs appear inter-track shifted. Once an app source first appears, source timestamps decide which already-encoded silent range it overlaps or which future range it fills. No source may delay the whole track, force a 500 ms bootstrap, or trigger startup backlog trimming just because its first real packet was late or silent.

Started app-audio sources can still become sparse later, especially when the same process loopback source is routed into multiple pure/mixed tracks or when a source stops producing packets before the video endpoint. Once an app source has completed bootstrap, lack of buffered samples is treated as silence for that source instead of blocking the whole exported track, but final CFR stop has stricter handling: once stop finalization begins, CE marks the session as finalizing and waits/drains real process-loopback packets instead of letting a short live pull synthesize stop-time app-source silence. A process-loopback source whose first real packet appears after the recording has already advanced joins at the current track cursor (with only a small fade cushion when available), trims/discards stale first-packet backlog that maps behind the encoded cursor, and logs `Late app source live join` plus per-source `qjoin/qjoinKeep` stop counters. It must not backfill a multi-second synthetic gap into strict exported tracks. Final stop-time audio drain loops in bounded chunks until every exported track cursor reaches the selected video endpoint or a no-progress condition is logged; a single 500 ms force-drain chunk is not sufficient for long sparse-source gaps.

Mux finalization and post-mux validation are separate ownership phases. Trailer write, file close, and muxer cleanup must finish before optional reopened-file probing starts. The post-mux probe is deadline-bound/cancellable and logs `post_mux_probe_start`, `post_mux_probe_complete`, `post_mux_probe_timeout`, or `post_mux_probe_cancelled`; a probe timeout is validation evidence, not permission for the destructor to wait forever or for later captures to be blocked.

## Invariants

- Explicit CFR (`Video.useVFR=false`) disables the wall-clock audio anchor. Wall-clock chasing is a VFR/non-CFR tool, not a CFR sync tool.
- Every scheduled CFR video tick through the final assigned PTS must have exactly one emitted packet. Declared stream/container duration is not a substitute for packet coverage; missing ticks or multi-tick PTS gaps are strict failures.
- Settled CFR audio pulls are sample-exact to the current target. Quantum rounding is still allowed for non-CFR/settling paths, but a settled CFR track must not carry a nonzero target/cursor residual.
- Audio is not sped up, trimmed, or dropped during normal CFR overload recovery. Audio ring pressure and post-resample backlog are warnings; if samples actually overflow/drop/trim, the recording is a validation failure instead of an acceptable recovery path.
- Track startup is not real-sample-gated. A source that is timeline-valid but currently silent contributes zero samples; late packets are placed by source timestamp/QPC and cannot move the track cursor.
- Final audio may be drained/filled up to the final video CFR timeline, but audio packets must not start beyond the final video duration and final packets are clamped sample-exactly where possible.
- Enabled audio tracks, including inactive app tracks or tracks whose sources stay silent, should be encoded as real zero samples through the selected codec up to the video timeline. Sparse container gaps are not the compatibility contract.
- App-audio with pre-start process-loopback packets is not optional for bootstrap. It must not produce a leading silent chunk before its first post-start packet is stitched into the track.
- App-audio that already bootstrapped but later has no buffered samples contributes silence for the missing source range. It must not stall a mixed/exported track whose other sources and the CFR endpoint continue.
- App-audio that first becomes active after the exported track cursor has advanced joins live at that cursor, after trimming stale source-local backlog. Late join is allowed; late buffered content replay is not.
- Final mux stream duration metadata is written from the final encoded video duration for every stream. This prevents codec padding or muxer rounding from making an audio track appear longer than video after sample accounting has already matched it.
- Post-mux audio duration deltas at or below one sample / one mux timebase tick are logged as rounding evidence, not strict failures. A 1 microsecond delta in a reopened MKV probe is expected container/timebase rounding only when the packet/sample accounting is otherwise clean.
- Audio layout is per-track. Multichannel 5.1/7.1 tracks must preserve the resolved source layout when `downmix=false`; only `downmix=true` may force stereo.
- Inject CFR may use cached last-frame repeats to close already accrued CFR debt at stop, because the injected source has no separate post-stop frame-drain path.
- Live inject CFR should keep only a low-latency candidate reserve during steady-state: source-side overcapture is capped around `output_fps * 1.25`, live headroom returns to the low-latency cap after startup, and stale candidates are trimmed by age while preserving the minimum fence reserve.
- Inject CFR catch-up should use fresh queued frames when CFR debt is large, frame credit is available, and the encoder is not bottlenecked/actively too slow. Cached repeats are still correct for true source limitation, fence deferral, no credit, hard encoder/mux pressure, or stop drain.
- WGC CFR generic stop drain is disabled. Post-stop WGC frames and pending buffered WGC frames are discarded rather than encoded into a frozen tail. Any WGC stop-drain repeat or nonzero WGC drain duplicate summary is a validation failure/stale-build signature.
- WGC CFR visual source selection is bounded to about `250 ms` or `32` frames behind live, whichever is tighter. Stale buffered WGC history is dropped before selection.
- WGC CFR frame PTS and audio samples follow the live scheduler endpoint. Source-frame selection normally targets the scheduled tick; once live shortfall exceeds the bounded visual-debt window, the scheduler rebases old owed ticks as covered visual hold/drop debt in one-tick-per-loop increments and source-selection clamps toward the live-window floor. This avoids repeat clusters caused by stale slots rejecting usable buffered frames, while preventing stop from manufacturing old debt as a tail and preventing large visible PTS holes. Without active render-domain delay, a buffered WGC frame more than three output ticks newer than the effective selection target is skipped/held.
- WGC automatic render-domain sync may choose the first audio anchor from the accepted startup video frame plus the resolved render-loopback delay plus any selected startup smoothness extra delay. The startup schedule offset between that anchor and the encoder live-start QPC is diagnostic only; it must not be subtracted from steady-state WGC selection targets. Steady-state selection applies only the requested content delay, otherwise WGC can build a larger delay reserve through repeated frames and create visible judder while A/V sync appears fixed. The selected extra smoothness delay is not a live audio retiming loop; source deficits after startup are represented as CFR repeats.
- WGC retained copy-pool slots are single-owner resources. A slot with an outstanding WGC lease must not be overwritten while it is queued, buffered, cached as the last frame, selected for startup, or inside the media-engine copy. Exhausted copy pools must drop the incoming WGC frame with `wgc_pool_saturated_safe_drop` instead of reusing old/leased content. Pool generations must make stale releases harmless after a pool recreate.
- WGC copy-pool pressure trim may discard newest surplus buffered frames only down to the active delay target. It is a lease/free-slot protection mechanism, not an audio sync mechanism and not permission to shrink the smoothness reservoir below the requested target.
- WGC active-delay hard-safe is not the same as quality-safe. In healthy/recoverable/post-stall windows, a frame must be soft-safe (within the 5-7 ms target in both predicted and raw timestamp domains) to be preferred over a sync-protected repeat. The 10 ms hard cap exists to prevent invalid output, not to define the normal perceived-sync target.
- WGC encoder-limited mode is allowed only when the WGC source is healthy enough and encoder/mux capacity is the limiting factor. In that mode, visual debt is bounded to about `50 ms` or `3` target frames, stale buffered source frames are dropped aggressively, selected source timestamps must not move backward relative to the last emitted WGC source timestamp, and equal-source repeats under encoder pressure are explicit holds rather than stale-fresh-stale backtracking. Audio/sample accounting does not change.
- Source-starved WGC episodes must not be reclassified as encoder-limited smoothness. Missing source frames are source evidence; healthy source input plus encoder/mux pressure plus near-live source drops is encoder-limited evidence.
- WGC startup must not accept the first stale post-barrier frame if fresher WGC frames are already queued or buffered. With no active render-domain delay, the startup handoff drains pending WGC material and selects the freshest valid post-barrier frame before the shared A/V anchor is published.
- With active render-domain delay, WGC startup should use the available post-barrier reserve when it is sufficient: select the candidate closest to `latestCandidateSelectionQpc - requestedDelayQpc`, keep newer candidates buffered for the first live ticks, and wait briefly before live output for reservoir low-water when needed. If the wait budget expires or the candidate span is insufficient, fall back to the safest valid frame and log whether this was source startup underfeed, partial-span timeout, or another reserve failure; do not invent delay or feed startup schedule offset back into steady-state selection. During live active-delay selection, strict residual tolerance is tighter than generic CFR future-frame tolerance; a bounded relaxed selection is allowed only when it stays inside the hard residual limit and its target-distance/repeat-cluster cost is lower than extending a repeat. Rejections above the hard sync limit and repeat-cluster pressure must be counted in the WGC summary so future logs can distinguish source limitation from CE policy damage.
- After WGC active-delay selection, any later low-source clamp or reserve-preservation fallback must re-check the final frame against the same hard residual cap in both predicted and raw timestamp domains. If that final check fails, CE should repeat/classify rather than encoding the too-new frame, and the analyzer should report `wgc_active_delay_post_selection_reject` or `wgc_timestamp_domain_mismatch` as strict evidence.
- WGC source-limited repeats are acceptable only near the computed lower bound. Source-starved sync-delay holds can count as lower-bound repeats, but healthy-source or CE-policy repeats above the lower-bound thresholds should surface as `wgc_cfr_smoothness_not_maximal` instead of being hidden under source starvation.
- WGC smoothness FLOOR (`wgc_smoothness_floor_ms`, WGC-only) may engage the active-delay smoothness machinery even with no audio-latency content delay (video-only capture / low-confidence loopback probe), so WGC is not left on maximally-jitter-exposed near-live selection. The floor is **sync-neutral by construction** and this property is an invariant: the audio anchor delay stays `= avContentDelayQpc` (true latency `L`; the mediaengine derives the anchor from `GetWgcStartupAudioAnchorQpc(firstVideoQpc, renderDelayQpc=L)` and the smoothness/floor extra `S` is used only for logging). The floor `S` is realized purely as the selected startup video frame being `S` older with a correspondingly later live-start (`liveStart ≈ startupVideoQpc + (L+S)`, absorbed by `scheduleOffset`), so for every PTS tick the selected video content time equals the audio real-sound time independent of `S`. The floor is resolved once at the startup barrier (auto: from measured WGC delivery jitter; or explicit ms) and HELD FIXED for the session — it must never retime the media/audio anchor live, which is what would reintroduce the realized-delay-collapse / ghost-image-judder family. Floor delay flows only into the VIDEO effective delay (`getWgcEffectiveContentDelayQpc`) and reservoir sizing; CFR PTS grid, audio sample data, track lengths, stop/endpoint, and mux are unchanged. `wgc_smoothness_floor_ms=0` reproduces prior behavior bit-for-bit, and the floor is a no-op in the healthy with-audio path (the audio-latency reservoir target already dominates). Regression-locked by `CapturePipelinePolicyTest.WgcSmoothnessFloorIsSyncNeutralAcrossDelays` (the sync-neutrality property), `WgcSmoothnessFloorDerivationIsClampedAndMonotonic`, and `WgcSmoothnessDelayDesiredArmsForFloorWithoutAudioLatency`.

## Diagnostics

Use these signals together:

- `TimerRebase` / duplicate timer-rebase counts: nonzero values indicate live CFR rescheduling pressure. They must not represent discarded timeline debt in CFR captures.
- `CFR stop drain ... path=inject|WGC`: shows whether stop-time outstanding CFR ticks were closed.
- `[A/V START] Audio source reset ... timelineValid=...`: non-app sources should become valid at the shared anchor; app audio stays optional only until first packet evidence. If an app source saw sync-pending packets, subsequent bootstrap should wait rather than encode a leading silent head.
- `[PullAudio] Track ... bootstrap complete ... forced=0 trimmed=0`: any `forced=1` or nonzero `trimmed` indicates the old content-shortening startup path.
- `[PullAudio] App source gap silence ...`: a started app source has no buffered samples for the requested range and is intentionally contributing silence instead of blocking the exported track. This is expected for sparse app sources; repeated lines are still useful evidence when a mixed track sounds wrong.
- `[PullAudio] WARNING: Source underrun ... forceDrain=0`: live source underrun and strict audio evidence. The same line with `forceDrain=1` is stop-tail padding evidence; it is diagnostic only when decoded strict markers, inter-track spread, CE zero residuals, and final packet/post-mux durations are clean.
- `[AudioLoop] Late source cursor advance ...`: late source data is being stitched against the already-advanced source/track cursor rather than delaying the exported track.
- `[AudioLoop] Late app source live join ...`: a process-loopback source first became active after recording start and stale first-packet backlog was suppressed so the source joins the current track cursor.
- `[STOP AUDIO] Source ... qjoin=... qjoinKeep=... process=...`: late app-source join accounting, including how much stale queued gap was suppressed and how much fade cushion was preserved.
- `[STOP AUDIO TRACK] Track ... encoded=... expected=... realMixed=... fullSilence=... partialSilence=...`: per-exported-stream cursor and real/silence accounting.
- `[A/V SYNC SUMMARY] Track ... audio_vs_encoded_us=... audio_vs_target_us=... residual_samples=... target_samples=... cursor_samples=...`: live sample accounting. For strict CFR diagnosis, `residual_samples=0` is the hard requirement after startup; `audio_vs_encoded_us` is diagnostic because encoded packet duration can lag live scheduled duration under CFR.
- `[A/V ZERO DRIFT WARNING]`: settled CFR track cursor and CFR target sample disagree. Treat as a strict failure even when final packet/container durations still match.
- `[STOP AUDIO DETAIL] Source ... ratePpm=... compDelta=... sat=...`: source-clock compensation state at stop. For healthy CFR recordings this should stay effectively zero; saturated `ratePpm` with clean source clocks usually means compensation is chasing buffer level instead of real drift.
- `[StopAudio] forceDrain ... iterations=...`: stop-time force drain may run multiple bounded chunks. Warnings `forceDrain made no progress` or `forceDrain incomplete` are strict follow-up evidence for track-cursor failures.
- `[StopAudio] Source ... diff=+0 (+0.0 ms)`: sample-count equality to the selected final video timeline.
- `[VideoEncoder] Final packet timeline`: actual last written packet end per stream and packet-level delta.
- `[VideoEncoder] Final metadata durations`: container metadata duration after clamping.
- `[VideoEncoder] mux_closed ...`: trailer/file close and muxer cleanup completed; later probe problems should not imply the muxer is still owned.
- `[VideoEncoder] post_mux_probe_start/complete/timeout/cancelled ...`: reopened-file stream duration/end check after trailer write; this is the external duration authority when it completes, and a timeout is a bounded validation failure/diagnostic rather than a shutdown hang.
- `[VideoEncoder] Post-mux duration probe`: legacy/summary reopened-file stream duration/end check after trailer write.
- `[VideoEncoder] Post-mux audio duration rounding evidence`: reopened-file audio duration differs from the target only within the one-sample / one-timebase-tick rounding tolerance. This is informational; larger mismatches still log `WARNING: Post-mux audio duration mismatch`.
- `[VideoEncoder] Stop: WARNING writer_finalize_slow phase=...`: phase-aware stop diagnostic emitted once when trailer/final probe/cleanup is slow. It is diagnostic evidence, not by itself mux corruption.
- `[VideoEncoder] Stop: ERROR writer_finalize_timeout ...`: strict mux ownership failure unless the same session later has exact final packet/container/post-mux evidence and no sync-finalize fallback. The async writer still owns the FFmpeg context, so CE must not run a synchronous trailer write on the same context. Old logs that combine `Writer thread did not finish ... detaching` with `Sync Stop: Finalizing file...` indicate the double-finalize crash family.
- `[AudioEncoder] Using codec: requested=... resolved=... channels=... mask=...`: codec alias, resolved encoder, and track layout policy.
- `[AudioEncoder] Silence queue ...`, `Clamping final packet duration ...`, and `Added packet end-skip side data ...`: encoded silence and AAC/Opus padded-tail handling.
- `[AudioEncoder] Opus requires 48000 Hz ...`: expected adjustment when Opus was configured with another sample rate.
- `[Cadence Health]` inject fields: `InjectCatch=fresh/repeat`, `InjectAgeTrim`, `TickUnique`, `TickDup`, `Shortfall`, and `AgeAvg/AgeMax` distinguish healthy fresh catch-up from repeat clusters.
- `[Inject CFR SUMMARY]`: `FreshCatchup`, `RepeatCatchup`, `StaleTrim`, duplicate reasons, and source FPS show whether judder came from source/game FPS below target, fence deferral, or encoder pressure.
- `[Cadence Health]` WGC fields: `WgcSelBias`, `Shortfall`, `LeadExcess`, `Oldest`, `BufNow`, `LiveClamp`, and `AgeMax` expose visual debt, selected-content drift, and live-window source-selection clamping. Large values are a content-sync bug even when stream durations match.
- `[EncoderThread] CFR Catchup applied using fresh frame`: WGC fresh/current catch-up for old debt. With the current WGC policy this should be zero under strict validation, because fresh WGC catch-up budget is disabled.
- `[EncoderThread] WGC CFR slot repeat: buffered frame is too new for scheduled slot`: expected only for short gaps or while WGC is honestly building/holding the requested render-domain delay. Frequent events while `Shortfall` is near/above the live-window limit mean source selection may still be pinned too far behind live and should be investigated with `LiveClamp`, `WgcSelBias`, `BufNow`, reservoir low-water ticks, and the sync-delay hold attribution.
- `[EncoderThread] WGC CFR visual timeline debt drop`: WGC visual debt exceeded the live window. It logs current and maximum excess ticks as a warning to inspect, not permission to shorten audio or move future frames into old slots.
- `[EncoderThread] WGC CFR live scheduler rebase`: the live WGC scheduler skipped old visual ticks after the live-window debt bound was exceeded, so those ticks are not owed at stop. Current policy caps each event to one CFR tick; per-event chunks above one indicate a stale build/regression. The total count is still useful for smoothness impact under sustained overload.
- `[EncoderThread] WGC CFR stale visual debt drop`: buffered WGC frames older than the live-debt window were dropped instead of being encoded as delayed visual history.
- `[EncoderThread] WGC CFR encoder-limited source drop`: WGC source input is healthy but encoder/mux pressure forced coalescing old visual slots to stay near-live. This is the intended overload hardening path; excessive counts still mean visible overload impact.
- `[EncoderThread] WGC CFR slot repeat: buffered frame is too new for scheduled slot`: WGC intentionally repeated the prior frame instead of selecting future visual content for the delayed source-selection target. New builds log `allowedLead`, `avDelay`, `syncDelay`, `syncSourceLimited`, `lowSource`, `sourceStarved`, `encoderLimited`, recent input/delivery FPS, and `noFresh` so a real-game repeat can be attributed to sync-delay reserve pressure, true source starvation, or capacity recovery without sacrificing A/V sync. ## UPDATE 2026-06-17 — per-device-domain latency model + render→loopback auto-detect (fixes the per-source regression)

The 2026-06-16 fix delayed video by `max(per-source captureLatencyMs)` and equalized faster sources up to it. Modeling latency PER-SOURCE was wrong and regressed real use (session `20260617_010909`, Fortnite/WGC): the user set `[Audio] capture_latency_ms=46` but `[General]=0`, so app process-loopback inherited 0 while system loopback got 46; equalization then delayed the game's app-loopback by 46 ms even though it shares the SAME render endpoint. Latency is a per-DEVICE-DOMAIN property:

- **Domain 1 = default render endpoint:** system loopback (`[Audio]`/`[Audio.N]`) + ALL `[AppAudio.N]` process-loopback → ONE value (`[General] audio_capture_latency_ms`). They all capture the same endpoint.
- **Domain 2 = each mic/input:** its own value (`[General] mic_capture_latency_ms` or per-mic `capture_latency_ms`). Mics no longer inherit the render-endpoint value (`common/config.cpp` mic fallback fixed). This is the regression fix.

**Auto-detection (no hardcoded value — works automatically on any system):** `mediaengine/audio_latency_probe.{h,cpp}` renders a brief near-inaudible Hann marker to the default render endpoint and detects it in a loopback capture; latency = loopback marker-CENTER QPC − render-start marker-center QPC. It takes 5 independent shots and aggregates with `MedianWithConsistency` (≥3 within 8 ms) so a noisy reading cannot over/under-correct; no consensus → ok=false → NO correction applied and `[AVSyncAuto] confidence=low` is logged (graceful, never a guessed value). The resolved value is cached only in process memory, keyed by endpoint format and period metadata; CE must not create or update `audio_latency_cache.ini`, and legacy files are best-effort deleted at startup. The tradeoff is one near-inaudible probe per fresh CE process instead of persistent endpoint data on disk. The marker is low amplitude (`0.015`) and sample rates below 44.1 kHz are rejected as likely audible. `[General] audio_latency_autodetect` (default true); a manual `audio_capture_latency_ms > 0` is an OPTIONAL override that disables the probe. `captureengine/media_main.cpp` measures once before `MediaEngine_Init` (not while recording) and re-applies the resolved value to render-domain sources on every config (re)load via the mediaengine export `MediaEngine_MeasureRenderEndpointLatency`. The default config ships with NO latency values set; do not hardcode one.

**No visible product calibration:** the old WGC/window-flash calibration code (`av_sync_calibrator.*`, `audio_av_calibration`) was removed on 2026-06-18. The DX12 A/V stimulus app and matrix harness remain test/validation tools only; normal product startup must not spawn windows or flash video to calibrate.

**Delay-only reconciliation:** `ApplyCaptureLatencyCompensation` (`audio_time_utils.h`) no longer advances live audio at the packet-placement sites in `audio_capture.cpp`/`app_audio_capture.cpp` (advancing is absorbed by the CFR pipeline and double-counts with the video delay on devices that report a nonzero `GetStreamLatency`). ALL latency flows through the video content delay + equalization. `streamLatency`, device period, packet duration, buffer depth, WASAPI QPC, and device position stay telemetry/passive model inputs. `[AVSyncApply]` shows WGC `wgc-selection-bias` or inject `inject-buffer-reserve` with reserve frames and residual estimate; `[AVSyncAuto] stop_summary` records final confidence/reason. The A/V harness writes `audio_latency_autodetect=false` so its explicit latency stays authoritative.
