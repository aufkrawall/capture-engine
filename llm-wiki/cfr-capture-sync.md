## Inject contention invariants (2026-07-12)

Inject publishers release-publish metadata and signal a controller-PID-named auto-reset event only on an empty-to-nonempty metadata transition. Media drains every visible entry before waiting on frame-ready plus shutdown events, then rechecks after every wake. `FrameRingBuffer::ingestIndex` records metadata observation independently from `readIndex`, which remains the delayed contiguous texture-lease acknowledgement. This distinction is required: using lease acknowledgement for event coalescing can miss a refill wake while previously ingested textures are still queued. Event open/create failure uses a logged bounded shutdown wait, but correctness remains ring-index based.

Every explicit producer path requires both no outstanding media lease and completion of the prior producer GPU operation before reuse. DX12 scans all sixteen fence-tracked slots; native DX11 uses per-slot fences or `DONOTFLUSH` event queries; DX10 skips pending queries; Vulkan combines relay/timeline/fence completion with media leases. No Present path waits. All-busy means a safe source-frame drop and downstream CFR repeat. DXVK/implicit-only paths retain their documented synchronization contract. Shared ABI version 30 carries capture-lock, CPU-lease, GPU-busy, metadata-full, event-signal, and publication-to-ingest diagnostics.

Session triage distinguishes upstream screen-source starvation, proven DXGI Duplication consumer pressure, capture-GPU queue starvation, hardware-encoder starvation, and settled-live media-CPU starvation. WGC verdicts retain the `wgc_` prefix; DXGI Duplication sessions use `dxgi_dup_` verdict/context names instead of misleading WGC terminology. A nonzero DXGI `AccumulatedFrames`/`DupMissed` count without overload, pool exhaustion, or ingress pressure is `dxgi_dup_delivery_gap` context, not consumer starvation. A publication-to-ingest spike confined to the first two seconds around live activation is `inject_startup_publication_backlog` context, not starvation. External overlays are also context rather than faults. HAGS and memory-budget state are contextual evidence, never automatic causal verdicts.

## Summary

### Adaptive audio ingestion reservoir (2026-07-25)

The CFR audio consumer pulls to `videoTimeline - pullLatency`. `kDefaultSteadyAudioPullLatencyMs = 60 ms` is the ONLY margin between that cursor and the live capture edge, and its realized headroom is `reservoirMs - captureDeliveryLatencyMs` — typically 40-70 ms, not 60. That margin was fixed, and overrunning it was **unrecoverable**: the track exported silence for the missing range, `ResolveSourceTimelineWriteCursor` pinned the source write cursor forward to the exported cursor, and every later packet then placed behind it and was trimmed as timeline overlap. Because the exported cursor and the capture edge both advance at exactly wall rate, the deficit could never repay itself. The source stayed permanently silent while packet delivery remained perfectly healthy, and the file still had sample-exact track lengths, contiguous PTS, `maxPacketDelta=0`, and `residual_samples=0`.

The pull lookahead is now adaptive and closes that hole in two places:

- **Instant hold.** A started source whose ring is short but that has ingested a real packet within `kAudioIngestLiveSourceWindowMs` (400 ms) is LATE, not silent. `ShouldHoldCfrAudioPullForLateLiveSource` defers the pull and raises the reservoir by the shortfall plus a margin instead of exporting silence. The hold is bounded by the reservoir cap, excluded during `forceDrain`/stop finalization, during large-backlog catch-up, and for inactive/route-ended app sources, so it can never reintroduce the multi-app track freeze.
- **Steady-state controller.** `AudioLoop` publishes the worst per-packet ingest headroom (`packetStartSamples - encodedCursor`, measured before the write-cursor pin) through one atomic whose `INT64_MAX` sentinel also means "no observation". `ComputeAudioIngestReservoir` ratchets the extra lookahead up to `kAudioIngestMinHeadroomMs` (25 ms) of headroom plus margin, caps it at `kAudioIngestMaxExtraReservoirMs` (500 ms), holds it when a window has no placement evidence, and decays it by 5 ms per 2 s only while headroom is comfortably above the minimum.

**Deepening the reservoir is sync-neutral by construction and this property is an invariant:** it moves only WHEN samples are pulled (the pull target), never WHERE a sample lands on the timeline (the track cursor). Sample zero keeps PTS zero, every later sample keeps its position, track lengths and mux endpoints are unchanged, and no pitch/rate compensation is involved. The buffered-audio target (`baseTargetLatencySamples`) is derived from the same adaptive value so the drift/backlog compensation lane cannot fight a deepened reservoir. `ComputeAudioPullLatencyMs` clamps its startup cap to at least the base, because an adaptive base above 120 ms would otherwise make `std::clamp` undefined.

A deepened reservoir legitimately leaves the exported cursor leading the reduced pull target, so `[A/V ZERO DRIFT WARNING]` now allows a positive residual up to the accumulated extra lookahead. A cursor BEHIND the target, and any lead the reservoir cannot explain, stay strict.

Last resort only: if a live source is still fully overlap-trimmed for 1.5 s while the reservoir is already at its cap, `ShouldResyncStarvedLiveAudioSource` re-anchors that source's placement by the unrecoverable deficit. This costs that one source a single content skip so live audio resumes; track lengths, PTS, and every other source are untouched. It is logged as a WARNING and counted, and reaching it at all is a bug signature.

### Warm-up cancellation and output commit (2026-07-19)

The second recording hotkey is always accepted. `Idle -> Warmup -> Live` and `Warmup -> Cancelling` share one atomic phase transition, so a concurrent stop and first-live-frame decision have exactly one winner. A stop that wins before live disarms the encoder worker, discards queued/pre-anchor audio without flushing it into the mux, and asks `VideoEncoder` to cancel; a stop after live commits follows normal CFR drain and exact A/V finalization. The explicit `firstVideoFrameCommitted` state avoids treating a valid zero-valued timestamp as “no frame.”

Video prewarm may still open the device, codec, muxer, and header to preserve startup latency, but the staging reservation is created only at recording start and remains an identity-owned unpublished `.part` file. Final-extension publication is a same-directory atomic rename and requires no cancellation request, successful trailer and close, positive duration, and at least one successfully written video packet. Thus idle media initialization creates no file, and even a late race or unexpected empty-success path cannot expose a header-only MKV. Cancellation and publication decisions emit high-signal lifecycle/output reason logs; no sleep, debounce, or ignored input is part of correctness.

### Transactional timeline start and exact completion (2026-07-14)

WGC and DXGI Duplication CFR startup now use one integer/QPC `CfrTimelineStartContract`: `contentDelay = liveQpc - videoOriginQpc`, `smoothnessReserve = contentDelay - renderLoopbackLatency`, and `audioAnchorQpc = videoOriginQpc + renderLoopbackLatency`. Startup issues a generation-numbered reset, waits for every audio route and encoder to acknowledge it, prewarms video without committing frame zero, realizes the available reservoir, recalculates the entire contract when the reservoir is partial, selects the matching source frame, and commits every anchor only after the first successful encode. The D3D11 prepare path opens the deferred device/codec/mux state without incrementing the input-frame counter or assigning a CFR slot. Newer frames retained behind the selected frame survive the warmup-to-live handoff. Deferred initialization wall time is diagnostic commit lateness, never a new content delay. A failed/deferred candidate cannot advance audio, video, source, cursor, or reset generations independently.

WGC and DXGI request a 300 ms source-history reservoir with a one-second startup deadline. For each CFR content timestamp the selector chooses the monotonic source frame with the smallest absolute timestamp distance, while never moving source time backwards. A true source stall repeats the latest successful surface and discards obsolete history on recovery. Encoder overload also preserves every CFR slot by repeating the last successful surface while stale pending content is coalesced; audio remains on the unchanged CFR cursor. Inject remains GPU-native, causal, nonblocking, and copy-free apart from the existing encode handoff, but its normal shallow queue now uses the same nearest-timestamp principle for the smaller render-loopback content-delay target.

A repeated screen-grab tick means the base desktop texture did not advance; it does not require the separately composed cursor to freeze. The media-engine repeat cache retains the uncomposited RGB source and re-renders the cursor state chosen for each scheduled tick before conversion/encode. Final `cursorAwareRepeatRenders` telemetry counts successful repeat submissions that took this path. Consequently, high `duplicated` counts can coexist with smooth recorded pointer motion, while `input`/delivered-source cadence and the source-limited lower bound remain the correct evidence for stuttering base content. A repeat that cannot use the cursor-aware source cache remains separately diagnosable rather than being treated as proof that the producer delivered a new desktop image.

Inject CFR selection is keyed directly to `scheduledOutputQpc - avContentDelayQpc`; the measured input-rate EMA is telemetry only. The protected tail contains only physical GPU/fence reserve. Treating the content-delay frames as another unselectable tail hid all useful candidates at normal queue depth, while wall-age pruning deleted the intentional delayed frame; together those policies created repeated-frame/stale-trim churn even with a limiter-stable 120 Hz source. Startup now waits for `fenceReserve + contentDelayFrames + 1` frames, live pruning is relative to the last committed source timestamp, and only a hard count cap can discard an otherwise fresh delayed frame. A half-output-interval lead tolerance gives true nearest-neighbour resampling: matched source/output cadence adds no repeat, a lower or varying game rate receives evenly placed honest repeats, and an above-target rate is evenly decimated. Recovery catch-up uses the same target decision and encoder-health gate rather than source-rate credit. WGC/DXGI retain their wider compositor tolerance, but the successor is advanced to only when it is actually at least as close as the current frame; an exact/closer front can no longer be skipped merely because a later frame falls inside the broad tolerance.

Capture-sync cadence has both frequency and phase. The hook-local limiter therefore advances an overdue capture-sync deadline by whole rational-grid slots until it is at least half an interval ahead, instead of rebasing the next deadline to `now + interval`; general FPS limiting keeps the established now-relative recovery. This prevents a game hitch from permanently moving an otherwise exact 120 Hz source onto the CFR selector's half-frame boundary. A backend-neutral media phase lock independently observes inject timestamps or smoothed WGC/DXGI selection timestamps. After stable integer-multiple cadence and coherent phase evidence, it offsets only the source-selection target by at most half a source interval; it never rebases CFR PTS, the audio anchor, or output scheduling. Stable underfeed and capture-sync multipliers remain eligible. Genuinely varying cadence releases/fails to acquire the lock and uses the unchanged timestamp-nearest policy, so variable-FPS behavior does not inherit a forced fixed phase.

The stale-visual-debt window is measured beyond intentional playout delay: its oldest acceptable timestamp is `liveNow - contentDelay - debtAllowance`, not merely `liveNow - debtAllowance`. This distinction is mandatory whenever the selected WGC/DXGI reservoir is deeper than the 250 ms bounded-live allowance (or the 50 ms encoder-limited allowance). Pruning against wall time alone deletes every frame before it can age into the delayed content target and produces a permanent repeat freeze despite healthy source delivery.

Finalization derives every audio target from the final CFR frame count and extends video by only the minimum final repeats needed to reach the common CFR/audio integer lattice. Packet/container durations are diagnostic evidence, not the authority. The completed MKV/MKA is reopened and every audio stream is fully decoded to canonical float PCM; success requires `decodedSamples == targetSamples`, identical endpoints across tracks, valid first/last content markers, no packets/content past the endpoint, and clean decoder output. Matroska `timestamp_precision=1000` is required rather than silently falling back to millisecond timestamps.

### Frame ownership and failure recovery (2026-07-11)

An inject `FrameSlot` is not acknowledged when it is merely copied into the media queue. Its move-only ring lease remains attached through buffering/defer and is completed only after the synchronous media-engine copy succeeds or the frame is deliberately discarded. Completion clears the physical slot but advances shared `readIndex` only across the longest contiguous completed prefix, so out-of-order encoder selection cannot release an older slot. Every inject producer checks all still-valid ring metadata before writing a texture and drops the new frame if every transport texture is outstanding. This prevents queued frames from silently aliasing newer pixels. D3D12 resource generations likewise remain published until all referencing frames are retired.

Fresh-frame state is transactional. The candidate becomes `g_LastFrame` and updates source/cursor lineage only after a successful non-deferred encode. If a scheduled CFR fresh encode fails, CE repeats the prior successful media-engine cache at the same scheduled QPC when available; the failed candidate is released and its metadata never becomes authoritative. If both fresh encode and repeat fail, the tick is reported as a real miss. WGC source-epoch changes explicitly clear every repeat-cache layer, while an inject-to-WGC standby commit keeps the already-published WGC epoch and preserves the prior inject repeat until replacement pixels have actually encoded.

Post-mux probing runs synchronously on the writer/finalizer owner with an FFmpeg interrupt deadline and bounded packet scan. It no longer launches a nested thread that could outlive the media-engine DLL or force unsafe detach/late join behavior.

CFR duration metadata cannot prove that every scheduled tick became a packet: the sparse DXGI failure capture declared about 6.19 seconds at 120 fps but contained only 170 video packets, with PTS gaps up to 48 ticks. A later real DXGI run (`20260717_021603`) exposed the subtler form: 13,812 packets covered a 13,847-tick endpoint, with one 18-tick live hole and seventeen one-tick stop-drain holes while all audio tracks reached the advertised endpoint. The source selector correctly used wall-grid timestamps, but the encoder incorrectly converted those timestamps back into CFR PTS indices; late timer/stop slots therefore jumped over unwritten media ticks. Screen-grab source selection still uses its explicit wall timestamp, but every successful CFR encoder submission now assigns exactly `lastAssignedPts + 1`. Finalization logs expected/emitted/missing CFR coverage after encoder flush, and `tools/analysis/analyze_capture_av.py` independently scans file packet PTS, fails any missing tick or gap above 1.01 nominal ticks, and handles reordered codec PTS by sorting before gap analysis. Session completed-capture validation derives video duration/count from packets and decodes audio only; it must never invoke a full video-frame decode implicitly. `cfr_packet_coverage_fault` is a strict visual/sync event. The default/codec A/V matrix includes `dxgi_dup`, `wgc`, and `inject`; the codec finalization pass covers AAC, ALAC, FLAC, Opus, and PCM for every backend.

All CFR capture paths share the same invariant: the CFR media clock is authoritative, and audio follows that timeline without live trims, source drops, wall-clock catch-up, or audible pitch recovery. This applies to WGC and injected shared-memory capture when `Video.useVFR=false`. A very small source-clock drift correction lane is allowed only after startup has settled and the CFR timeline is healthy; current code caps it at `0.05%`, far below the user-accepted `1-2%` inaudible upper bound, and it must not be used to recover video/encoder debt.

Packet-level duration equality is necessary but not sufficient for real sync or visual smoothness. If the encoder thread discards accrued CFR timer debt during a stall, the visual timeline jumps while audio remains continuous. If WGC accepts stale visual debt for too long, content can fall seconds behind live and then catch up too quickly; selecting live pixels for an old PTS slot creates the opposite content jump. The emitted packet grid is therefore immutable for WGC, DXGI duplication, and inject: every successful CFR submission receives the next contiguous PTS, while source-history pruning and temporal selection remain independent. Normal overload recovery defaults to held/repeated output slots and must never independently move source selection toward current wall time or accelerate one audio route. A buffered historical frame may replace a hold only when both smoothed and raw source timestamps match that exact old content target, source lineage stays monotonic, the active delay reservoir remains intact, and measured fresh-frame encode cost proves recovery headroom; this changes only the slot's pixels, never its PTS or audio target. At stop, every CFR backend drains only the accrued contiguous prefix to the stop QPC when it has a queued/buffered frame or a valid media-engine repeat cache. Final validation requires the expected written packet count and maximum forward PTS gap no greater than 1.01 ticks; violations are logged as artifact failures instead of being hidden by desired-duration metadata. VFR has no CFR debt drain.

WGC and DXGI also prevent a small sustained capacity deficit from escaping retained history and degenerating into an all-static sync-protected hold. The shared screen-grab path separately measures end-to-end fresh and cached-repeat service. After at least eight valid samples of each, confirmed encoder/mux pressure, a healthy source, a covered candidate, and a valid repeat cache, it computes the fresh fraction that keeps weighted service at 95% of the CFR interval and distributes the required repeats with a credit accumulator. A natural source hold earns the next fresh credit; transient pressure-flag clearing does not disarm a still-measured overload mix. The policy is inactive when fresh service fits, repeats do not provide a meaningful saving, repeat service cannot fit the budget, or source health is not established. It leaves the candidate buffered and advances the CFR/audio grid normally, so the only effect is an evenly distributed loss of unique pixels that the requested encoder capacity cannot sustain. Inject does not use this policy.

Fast zero-drift validation uses CE's own sample accounting as the strict oracle. Once an audio track has completed startup in CFR mode, the live track cursor must advance sample-exactly to its current pull target on every pull/check; settled CFR pulls no longer keep a 5 ms quantum residual. The pull target intentionally trails the live capture edge by 60 ms so ordinary WASAPI/process-loopback delivery jitter and short encoder/CPU starvation do not become exported silence. This is an ingestion/encode scheduling reservoir, not a content or PTS offset: sample zero still has PTS zero, every subsequent sample retains its timeline position, and final force-drain closes the reservoir to the exact CFR endpoint. Periodic `[A/V SYNC CHECK]` and `[A/V SYNC SUMMARY]` lines include `audio_vs_encoded_us`, `audio_vs_target_us`, `audio_vs_scheduled_us`, `residual_samples`, `residual_us`, `target_samples`, and `cursor_samples`. Any `[A/V ZERO DRIFT WARNING]` after startup is a strict audio timeline fault in both stimulus analysis and real-session triage. MKV content analysis still confirms decoded behavior within marker/analyzer precision, but zero drift itself is enforced from CE's target/cursor sample state. Short-run decoded offset slope is corroborating evidence: it fails only when the fitted slope exceeds the configured `ms/min` threshold and the matched offsets span more than the short-run excursion guard, so tiny 4-10 ms decode/interpolation wobble does not masquerade as long-run drift when CE residual is exactly zero.

App-audio latency distributions are live-phase evidence. Stop-time forced drain intentionally observes remaining ring backlog while closing every track to the exact video endpoint, so those samples are counted separately as `stopDrainObservations/Avg/Max` and cannot trigger live `[AppLatency]` warnings or inflate the live stop summary. Live warning count alone is not a session fault when the current `[STOP AUDIO LATENCY]` distribution proves target-relative excess stayed below the elevated thresholds and reports zero queue overruns, underruns, trims, and catastrophic recovery; that shape is `app_audio_latency_within_slack` context. Elevated target-relative excess or concrete integrity evidence remains `audio_app_latency_elevated`, and legacy warning-only logs without a final distribution stay strict because they cannot prove the warning was benign. The analyzer also retains older stop compatibility: warnings occurring only after `[Media] Stopping recording...` become `app_audio_stop_drain_latency` context rather than a recording fault. This diagnostic separation changes no resampling, correction, mixing, or finalization behavior.

Do not let CFR source-clock compensation chase ordinary buffer-level wobble. The source-clock correction lane exists for genuine long-run device clock drift only, not for normal pull-buffer deficit, encoder debt, or stop-drain shape. Encoder pipeline/lookahead latency is downstream of capture: inject CFR therefore adds none of it to either the source-clock drift expectation or ring-buffer target and retains only the base 60 ms ingestion reservoir. WGC/DXGI keep their independently measured content/buffer lag targets; VFR/non-CFR keeps the historical pipeline-lag policy. The current CFR Tier1 lane has a wide deadband of roughly 80 ms and still caps correction at `0.05%`; healthy runs should finish with `ratePpm=+0.00`, `compDelta=0`, and `sat=0` in `[STOP AUDIO DETAIL]`. Inject session `20260717_015533` ended every otherwise healthy source at `ratePpm=-500.00` because roughly 250 ms of NVENC lookahead/pipeline latency was misclassified as missing source lead; DXGI session `20260717_021603` correctly ended every source at zero. A run can have exact packet/container durations while decoded markers drift if the compensation lane is saturated from a bogus buffer deficit, so `ratePpm=-500.00` or `ratePpm=+500.00` in a healthy CFR run is a bug signature even when final sample counts are exact.

Shared process-loopback capture does not imply shared route backlog. Each output route owns its ring, resampler, and track cursor, so drift compensation must use the route's own buffered lead; a delayed sibling route is diagnostic evidence, not a control input. Process-loopback exit also has an ordered end marker after all captured tail packets. Once each fanned route consumes that marker, the ended source becomes nonblocking timeline silence for live and final pulls until a later activation/epoch rejoins at the live cursor. These rules apply equally to WGC, DXGI duplication, and inject CFR because they protect the common audio timeline rather than any video backend.

WGC encoder-limited overload is now distinct from WGC source starvation. If source input is healthy but encoder/mux capacity pressure appears, WGC switches to an encoder-limited smoothness mode even if an earlier low-source/recovery state was originally triggered by delivery pressure. CFR timestamps and audio clocks remain exact; source pruning uses a near-live history window of about `50 ms` / `3` output frames, but it never consumes an output slot or moves the slot's selection target. Genuine source starvation stays on the source-starved path and can still repeat planned/missing source frames. The intended overload behavior is honest packet-backed CFR repeats plus obsolete source-snapshot drops, not a large sawtooth where stale buffered frames are dragged forward and then fresh frames snap back. `wgcEncoderRecoveryLimitedCurrent` should imply encoder-limited smoothness unless the source is genuinely under target; a mode-mismatch warning means the policy split regressed.

WGC/DXGI worker wake cadence and CFR output cadence are separate clocks. Once output shortfall reaches the ordinary catch-up threshold, `GetWgcCatchupTicksThisLoop` emits one additional recovery slot; at the severe threshold it may emit up to four slots total. The fallback is a cached/held repeat. When measured end-to-end fresh WGC/DXGI service cost (encode plus waits/copy overhead) is below 75% of the frame interval, neither active bottleneck gate is set, and the buffer exceeds its active-delay low-water reserve, a recovery slot may instead consume a monotonic historical frame whose smoothed timestamp is within half an interval and raw timestamp within one interval of that slot's immutable content target. This is not fresh-frame fast-forward: the submitted timeline is still `computeLiveTimelineElapsedUs(repeatScheduledQpc)`, audio is untouched, and missing/unsafe candidates fall back to held repeats. Four submissions at the 75% ceiling fit inside three CFR intervals, so the maximum four-tick burst repays one wall-clock slot rather than increasing debt. Extra slots advance `liveStartQpc + liveTicksOutput * targetInterval` but do not advance the normal wake deadline again, so recovery can converge instead of producing a two-output/two-tick-wait stalemate. Source selection, cursor sampling, delay realization, and media submission use that immutable per-output grid QPC even if a worker wake deadline was rebased after an expensive encode. `ClampWgcSelectionTargetToLiveQpc` deliberately does not move the requested source-content time toward wall clock; obsolete source frames may still be pruned.

Every live audio source naturally accumulates capture backlog while the CFR video timeline is behind wall time. `ShouldSuppressCfrPositiveDriftCorrectionDuringLiveShortfall` marks that state as timeline recovery, and process-loopback `ComputeCfrAppAudioBacklogDrainDecision` returns `timeline_recovery` with zero route-local compensation. App-only acceleration in this state would move app audio relative to system/microphone tracks and the video-content grid. The ordinary bounded app backlog drain remains available only for a genuinely route-local backlog on an otherwise healthy CFR timeline. Stop force-drain remains sample-exact to the selected endpoint and never turns retained post-target capture backlog into exported audio.

WGC active render-domain sync is a content reservoir problem, not only a startup/effective configuration value. The audio probe resolves a render-to-loopback delay; WGC must realize that delay by selecting video content around `scheduledTickQpc - requestedDelayQpc`. A bounded WGC smoothness reservoir may add startup-only extra playout delay when longer-window source-rate evidence says the source can repay it and VRAM budget allows it. The retained reservoir stores source frames, so its frame count is sized with 125% headroom for 140/144 Hz source into 120 fps CFR, but the startup delay target remains clamped to the configured millisecond window; extra source-frame storage must not inflate the start contract. Cadence-event and final smoothness-buffer diagnostics must use the same millisecond clamp so the logs do not report a larger target than runtime used. That extra delay is part of the immutable startup contract's video playout reserve, not the audio anchor; after the first encoded frame, CE must not move either anchor live to chase WGC source deficits. Later deficits become normal CFR repeats with source/budget attribution. Startup can wait briefly before live output to build the reservoir, while live WGC capture remains at maximum producer rate (`MinUpdateInterval=0`) so the WinRT acceptance gate cannot alias a periodic above-output source into a half-rate callback stream. Producer-rate telemetry is diagnostic only; the selector performs all surplus-frame resampling and may use a bounded relaxed residual frame only when it is less damaging than repeating the previous frame. Long repeat streaks carry a small explicit policy cost, so WGC can spend bounded residual to avoid extending visible clusters, but the hard late-residual limit is unchanged. A stale strict fallback should not force a repeat when a bounded relaxed frame would reduce total damage. Uniform active-delay playout owns source-above-target surplus: for 140/144 Hz WGC input into 120 fps CFR output, ingress must not pre-drop frames merely because soft reserve or decimation credit says the buffer is high. A regular above-target source should become source drops, not repeats; repeats indicate CFR coverage holes where a slot lacked a sync-safe fresh source because of source spikes, below-target intervals, WGC/DWM delivery gaps, or too-new safety rejection. The playout layer drops audio-passed surplus in timestamp order (`delayPaceCapTrim`) while preserving the shared CFR/audio timeline; ingress still drops before copy only for true hard pool exhaustion. This boundary avoids manufacturing no-frame CFR slots from a healthy source without changing audio timing. Unstable-FPS windows are classified as healthy, recoverable-underfill, hard source stall, source-limited, or post-stall recovery using source/delivery FPS, fresh misses, reservoir depth, source starvation, and safe-candidate availability. Healthy/recoverable/post-stall windows use a softer late target around 5-7 ms; repeated near-cap choices are rejected even if they remain under the 10 ms hard cap. If no soft-safe frame exists, WGC should repeat and log a sync-protected/hard-only source limitation instead of encoding a hard-only near-cap frame that can make audio feel late. Source-limited and hard-stall windows retain the hard cap and are attributed instead of being chased. Candidate and final-selection checks must use both the smoothed/predicted WGC selection timestamp and the raw WGC timestamp; raw-late or post-adjust too-new selections are sync faults even if the smoothed residual looks bounded. The smoothness summary estimates a source-limited CFR repeat lower bound and separates `sourceRepeatLowerBound`, `syncSourceRepeatLowerBound`, `deliveryRepeatLowerBound`, `excessRepeats`, `policyAddedRepeats`, and `excessRepeatClusters`, so a flawed input source can be judged against the best achievable CFR cadence instead of against zero repeats. `[WGC CFR SOURCE COVERAGE]` and analyzer verdict `wgc_source_coverage_best_effort` are non-fault diagnostics when repeats match the source/delivery lower bound and encoder/mux/pool/selection evidence is clean. Healthy-source active-delay recordings should keep realized-delay residual mean within about `5 ms`, max/p95 within about `10 ms`, `delayPostSelectionRejectedSync=0`, `syncDelayPolicyHolds=0`, and no sustained soft-late accepted pressure. Source-starved runs with bounded late residual, `delaySoftLateAccepted=0`, no soft-safe missed candidate, and repeats at the lower bound now report `wgc_source_limited_smoothness_ceiling` instead of `wgc_audio_late_risk`; this means CE protected sync and the remaining roughness follows the WGC/source input limit. Excess repeats, policy-added repeats, CE-amplified repeat clusters, mixed source/policy pressure, over-soft accepted content, pool lifetime faults, or safe-drop pressure beyond the budget are still visual/sync evidence to inspect. If the source cannot physically deliver enough frames, the logs should say source-limited with bounded residual and lower-bound repeat evidence rather than claiming a perfect healthy run.

The WGC startup smoothness wait budget must cover the full selected reservoir when that reservoir is armed: at least `contentDelay + smoothnessTarget + 4 frames`, while non-smoothness startup keeps the older `contentDelay + 2 frames` bound. Pool-pressure recovery must release only surplus buffered WGC frames beyond the active delay target; trimming below that target would trade one smoothness fault for another. These operations are video-reservoir management only and must not move the shared CFR/audio anchor, shorten audio, alter mux endpoints, or increase default VRAM requirements.

`dx12_av_sync_test.exe` is the deterministic content-level validation stimulus for this class of bugs. It renders event color changes, visual-marker v2 frame marker tiles, inverse/checksum/parity sentinels, a slow smooth-motion lane, and a faster one-second ruler lane while playing a synchronized WASAPI sine schedule. `--encoder-stress-scene` adds deterministic high-entropy animated tiles outside the reserved marker/motion/event regions so NVENC p5/p6/p7 work is meaningfully harder than flat bars. The stress-tile layout is row/column aligned: visible colored tiles should never include a clipped final row, and the manifest records tile size, bounds, row/column counts, and the central reserved event-sample region. Windowed mode defaults to borderless (`window_chrome=0`) so WGC captures the exact rendered client area instead of title-bar chrome; the manifest records requested/render dimensions, fullscreen/window-chrome/borderless state, marker geometry, motion-lane geometry/speeds, event sample region, source stalls, encoder-stress-scene state, and QPC anchors. Its manifest and `AVSYNC ...` logs provide the app-side truth; `tools/analysis/analyze_av_sync_stimulus.py` decodes the resulting MKV to recover video event colors, redundant frame markers, corrupt marker/checksum/parity evidence, planned source-stall repeat clusters, unplanned repeat/drop clusters, slow/fast motion stalls, motion expected-position errors, and audio frequency transitions per stream. For CFR MKV analysis, raw decoded video frames are timestamped from the declared stream frame rate when FFmpeg expands CFR playback, rather than mixing sparse packet `best_effort_timestamp_time` rows with the rawvideo frame stream. This is the preferred agentic check when packet-duration equality is not enough.

Synthetic source stalls are intentional app-side source gaps, not CE failures. Launch the app with `--source-stall <start_seconds>:<duration_ms>` such as `--source-stall 8.0:300`. During the stall the app keeps audio, QPC logging, stimulus time, and message pumping active, but suppresses `Present`. The final manifest rewrites `source_stalls[]` with requested and actual QPC/time ranges, suppressed present count, expected repeat span, and tolerance. The app log emits `AVSYNC SOURCE_STALL_BEGIN`, `AVSYNC SOURCE_STALL_END`, and summary counters. Analyzer classification rules are strict: a repeat cluster passes as `planned_source_stall` only when it overlaps the manifest stall window, stays within tolerance, and the surrounding audio/event sync remains correct; any repeat cluster outside those windows is `unplanned_repeat_cluster`.

Codec padding is handled below the same invariant. AAC and Opus may submit padded codec frames internally, but negative priming PTS, start/end skip side data, `CodecDelay`, `SeekPreRoll`, and final `DiscardPadding` must describe the exact decoded interval. ALAC and FLAC submit exact short final blocks; PCM stays block aligned with zero priming. FLAC's EOF `AV_PKT_DATA_NEW_EXTRADATA` packet is an allowed zero-duration control packet and is counted separately; an unexplained durationless media packet is a protocol error. `DURATION` tags, codec-frame-sized tolerances, and priming-sized tolerances must never conceal a decoded-sample mismatch.

Content-level audio sync also depends on startup policy. Each exported audio track has its own timeline cursor, and that cursor advances from sample 0 on the shared video anchor. System and mic sources are timeline-valid immediately and produce real encoded silence until packets arrive. App-audio sources are optional only while CE has no evidence that they are active. If process-loopback packets arrived while recording sync was pending, startup must wait for the first post-anchor packet, the bounded real-sample cushion, and buffered timeline coverage through the first requested pull; otherwise the app track can consume slightly beyond available data and encode a short startup silence notch even though the next real packet is only one polling interval away. A genuinely packetless source still bootstraps as silence and an optional unstarted app source still cannot block the track. Once an app source first appears, source timestamps decide which already-encoded silent range it overlaps or which future range it fills. No source may delay the whole track, force a 500 ms bootstrap, or trigger startup backlog trimming just because its first real packet was late or silent.

Started app-audio sources can still become sparse later, especially when the same process loopback source is routed into multiple pure/mixed tracks or when a source stops producing packets before the video endpoint. Once an app source has completed bootstrap, lack of buffered samples is treated as silence for that source instead of blocking the whole exported track, but final CFR stop has stricter handling: once stop finalization begins, CE marks the session as finalizing and waits/drains real process-loopback packets instead of letting a short live pull synthesize stop-time app-source silence. A process-loopback source whose first real packet appears after the recording has already advanced joins at the current track cursor (with only a small fade cushion when available), trims/discards stale first-packet backlog that maps behind the encoded cursor, and logs `Late app source live join` plus per-source `qjoin/qjoinKeep` stop counters. It must not backfill a multi-second synthetic gap into strict exported tracks. Final stop-time audio drain loops in bounded chunks until every exported track cursor reaches the selected video endpoint or a no-progress condition is logged; a single 500 ms force-drain chunk is not sufficient for long sparse-source gaps.

Mux finalization and post-mux validation are separate ownership phases. Trailer write, file close, and muxer cleanup must finish before optional reopened-file probing starts. The post-mux probe is deadline-bound/cancellable and logs `post_mux_probe_start`, `post_mux_probe_complete`, `post_mux_probe_timeout`, or `post_mux_probe_cancelled`; a probe timeout is validation evidence, not permission for the destructor to wait forever or for later captures to be blocked.

## Invariants

- Explicit CFR (`Video.useVFR=false`) disables the wall-clock audio anchor. Wall-clock chasing is a VFR/non-CFR tool, not a CFR sync tool.
- Every scheduled CFR video tick through the final assigned PTS must have exactly one emitted packet. Declared stream/container duration is not a substitute for packet coverage; missing ticks or multi-tick PTS gaps are strict failures.
- Settled CFR audio pulls are sample-exact to the current pull target, which normally remains 60 ms behind the live scheduled edge. Quantum rounding is still allowed for non-CFR/settling paths, but a settled CFR track must not carry a nonzero pull-target/cursor residual; final drain must reach the full CFR endpoint exactly.
- Audio is not sped up, trimmed, or dropped during normal CFR overload recovery. Audio ring pressure and post-resample backlog are warnings; if samples actually overflow/drop/trim, the recording is a validation failure instead of an acceptable recovery path.
- The CFR audio ingestion reservoir is adaptive and self-recovering. A started source that is still delivering real packets but has an under-filled ring must hold the pull (and deepen the reservoir) rather than export silence, because exported silence pins the source write cursor ahead of the capture edge and every later packet is then destroyed as timeline overlap with no path back. Reservoir depth is scheduling state only: sample timeline positions, PTS, track lengths, mux endpoints, and playback rate never change with it. `starve=0` in `[STOP AUDIO INGEST]` is required for a clean recording; nonzero means captured audio was lost even though every duration still matches.
- Track startup uses only a bounded 25 ms real-sample proof, never an unbounded wait, but a started source with buffered content must also cover the first requested timeline range. A genuinely packetless timeline-valid source contributes zero samples instead.
- Final audio may be drained/filled up to the final video CFR timeline, but audio packets must not start beyond the final video duration and final packets are clamped sample-exactly where possible.
- Enabled audio tracks, including inactive app tracks or tracks whose sources stay silent, should be encoded as real zero samples through the selected codec up to the video timeline. Sparse container gaps are not the compatibility contract.
- App-audio with pre-start process-loopback packets is not optional for bootstrap. It must not produce a leading silent chunk before its first post-start packet is stitched into the track.
- App-audio that already bootstrapped but later has no buffered samples contributes silence only after the shared 60 ms ingestion reservoir has been exhausted. It must not stall a mixed/exported track whose other sources and the CFR endpoint continue. When a later packet arrives, packet stitching first advances to the already-exported per-source cursor, so a QPC gap adds only the unencoded remainder and late content cannot shift everything that follows.
- App-audio that first becomes active after the exported track cursor has advanced joins live at that cursor, after trimming stale source-local backlog. Late join is allowed; late buffered content replay is not.
- Final mux stream duration metadata is written from the final encoded video duration for every stream. This prevents codec padding or muxer rounding from making an audio track appear longer than video after sample accounting has already matched it.
- Post-mux audio duration deltas at or below one sample / one mux timebase tick are logged as rounding evidence, not strict failures. A 1 microsecond delta in a reopened MKV probe is expected container/timebase rounding only when the packet/sample accounting is otherwise clean.
- Audio layout is per-track. Multichannel 5.1/7.1 tracks must preserve the resolved source layout when `downmix=false`; only `downmix=true` may force stereo.
- Inject CFR may use cached last-frame repeats to close already accrued CFR debt at stop, because the injected source has no separate post-stop frame-drain path.
- Live inject CFR protects only the physical GPU/fence tail from selection. The requested A/V content delay is expressed in the timestamp target (`scheduledOutputQpc - contentDelayQpc`), not as another unselectable FIFO tail. The selector chooses the nearest fresh eligible source timestamp for each CFR slot, drops only monotonically superseded history, leaves too-new candidates buffered, and uses a hard count cap only as an emergency bound. Wall-age trimming must not delete intentionally delayed candidates.
- Capture-sync late recovery must preserve the rational limiter grid by skipping whole source slots; it must not use an arbitrary `now + interval` rebase. Media may phase-align the selection target only after stable cadence plus coherent phase confirmation. The adjustment is bounded to half a source interval, supports stable integer-multiple underfeed/multipliers, and must release or remain inactive for varying/incoherent cadence. It never changes CFR packet PTS, audio targets, or the requested content delay.
- Inject CFR catch-up enters a hysteretic recovery episode at 18 ticks of debt and stays armed until debt reaches one tick. Each normal wake may emit at most one extra tick, using the same timestamp-nearest target policy as the ordinary slot when a fresh candidate is available. The source-rate EMA is telemetry only and must never authorize or deny a live selection. The extra output advances the immutable output grid (`liveStartQpc + liveTicksOutput * targetInterval`) but does not advance the normal wake deadline a second time; otherwise a two-output recovery cycle is followed by a two-tick wait and cannot reduce debt. Capacity gating uses pure encode time plus full-cycle service time normalized by the number of output ticks, never the raw duration of a cycle that intentionally encoded twice. Authoritative encoder/mux bottleneck pressure still pauses recovery. Cached repeats remain correct for true source limitation, fence deferral, a too-new/missing timestamp candidate, hard encoder/mux pressure, or stop drain. WGC/DXGI keep their backend-specific scheduler and reservoir management, but their live selector shares the same actual-nearest timestamp comparison.
- CFR stop drain is backend-neutral and bounded by the captured stop QPC. It may use a queued/buffered pre-stop frame or the latest successful media-engine repeat cache to close only already-accrued ticks; post-stop source frames are discarded. Any packet beyond the stop target, missing accrued tick, or >1.01-tick PTS gap is a validation failure.
- WGC CFR visual source selection is bounded to about `250 ms` or `32` frames behind live, whichever is tighter. Stale buffered WGC history is dropped before selection.
- The live visual-debt bound is not a pre-live startup-reservoir bound. If an armed smoothness target exceeds the live window, pre-live WGC/DXGI pruning must preserve the retained-cap-bounded post-barrier history until the startup frame/contract is selected; otherwise the default 300 ms target can never outlive the 250 ms live window and every run falls into partial-span fallback. Once output is live, ordinary and encoder-limited pruning resume unchanged. This exception neither moves the immutable CFR grid nor changes the audio anchor.
- WGC/DXGI frame PTS and audio samples follow the immutable CFR endpoint. Source-frame selection targets the output slot's grid QPC and is never independently clamped toward current wall time or raised to the oldest retained frame; wall-clock frame age cannot prove content sync when the encoder grid is behind. Obsolete source history may be pruned, and overdue time is preferentially repaid with bounded cached/held repeats that do not postpone the next normal wake. Without active render-domain delay, a buffered screen frame more than three output ticks newer than the effective selection target is skipped/held.
- WGC automatic render-domain sync chooses the first audio anchor from the accepted startup video's raw QPC plus the resolved render-loopback delay. Any selected startup smoothness extra delay advances only the live playout QPC in the same immutable contract. The startup schedule offset between the audio anchor and encoder live-start QPC is diagnostic only; it must not be subtracted from steady-state WGC selection targets. Steady-state selection applies the contract's requested content delay, otherwise WGC can build a larger delay reserve through repeated frames and create visible judder while A/V sync appears fixed. The selected extra smoothness delay is not a live audio retiming loop; source deficits after startup are represented as CFR repeats.
- WGC retained copy-pool slots are single-owner resources. A slot with an outstanding WGC lease must not be overwritten while it is queued, buffered, cached as the last frame, selected for startup, or inside the media-engine copy. Exhausted copy pools must drop the incoming WGC frame with `wgc_pool_saturated_safe_drop` instead of reusing old/leased content. Pool generations must make stale releases harmless after a pool recreate.
- WGC copy-pool pressure trim may discard newest surplus buffered frames only down to the active delay target. It is a lease/free-slot protection mechanism, not an audio sync mechanism and not permission to shrink the smoothness reservoir below the requested target.
- WGC active-delay hard-safe is not the same as quality-safe. In healthy/recoverable/post-stall windows, a frame must be soft-safe (within the 5-7 ms target in both predicted and raw timestamp domains) to be preferred over a sync-protected repeat. The 10 ms hard cap exists to prevent invalid output, not to define the normal perceived-sync target.
- WGC encoder-limited mode is allowed only when the WGC source is healthy enough and encoder/mux capacity is the limiting factor. In that mode, visual debt is bounded to about `50 ms` or `3` target frames, stale buffered source frames are dropped aggressively, selected source timestamps must not move backward relative to the last emitted WGC source timestamp, and equal-source repeats under encoder pressure are explicit holds rather than stale-fresh-stale backtracking. Audio/sample accounting does not change.
- Source-starved WGC episodes must not be reclassified as encoder-limited smoothness. Missing source frames are source evidence; healthy source input plus encoder/mux pressure plus near-live source drops is encoder-limited evidence.
- WGC startup must not accept the first stale post-barrier frame if fresher WGC frames are already queued or buffered. With no active render-domain delay, the startup handoff drains pending WGC material and selects the freshest valid post-barrier frame before the shared A/V anchor is published.
- With active render-domain delay, WGC startup should use the available post-barrier reserve when it is sufficient: select the candidate closest to `latestCandidateSelectionQpc - requestedDelayQpc`, keep newer candidates buffered for the first live ticks, and wait briefly before live output for reservoir low-water when needed. If the wait budget expires or the candidate span is insufficient, fall back to the safest valid frame and log whether this was source startup underfeed, partial-span timeout, or another reserve failure; do not invent delay or feed startup schedule offset back into steady-state selection. During live active-delay selection, strict residual tolerance is tighter than generic CFR future-frame tolerance; a bounded relaxed selection is allowed only when it stays inside the hard residual limit and its target-distance/repeat-cluster cost is lower than extending a repeat. Rejections above the hard sync limit and repeat-cluster pressure must be counted in the WGC summary so future logs can distinguish source limitation from CE policy damage.
- After WGC active-delay selection, any later low-source clamp or reserve-preservation fallback must re-check the final frame against the same hard residual cap in both predicted and raw timestamp domains. If that final check fails, CE should repeat/classify rather than encoding the too-new frame, and the analyzer should report `wgc_active_delay_post_selection_reject` or `wgc_timestamp_domain_mismatch` as strict evidence.
- WGC source-limited repeats are acceptable only near the computed lower bound. Source-starved sync-delay holds can count as lower-bound repeats, but healthy-source or CE-policy repeats above the lower-bound thresholds should surface as `wgc_cfr_smoothness_not_maximal` instead of being hidden under source starvation.
- WGC smoothness FLOOR (`wgc_smoothness_floor_ms`, WGC-only) may engage the active-delay smoothness machinery even with no audio-latency content delay (video-only capture / low-confidence loopback probe), so WGC is not left on maximally-jitter-exposed near-live selection. The floor is **sync-neutral by construction** and this property is an invariant: the audio anchor delay stays `= avContentDelayQpc` (true latency `L`; the mediaengine derives the anchor from `GetWgcStartupAudioAnchorQpc(firstVideoQpc, renderDelayQpc=L)` and the smoothness/floor extra `S` is used only for logging). The floor `S` is realized purely as the selected startup video frame being `S` older with a correspondingly later live-start (`liveStart ≈ startupVideoQpc + (L+S)`, absorbed by `scheduleOffset`), so for every PTS tick the selected video content time equals the audio real-sound time independent of `S`. The floor is resolved once at the startup barrier (auto: from measured WGC delivery jitter; or explicit ms) and HELD FIXED for the session — it must never retime the media/audio anchor live, which is what would reintroduce the realized-delay-collapse / ghost-image-judder family. Floor delay flows only into the VIDEO effective delay (`getWgcEffectiveContentDelayQpc`) and reservoir sizing; CFR PTS grid, audio sample data, track lengths, stop/endpoint, and mux are unchanged. `wgc_smoothness_floor_ms=0` reproduces prior behavior bit-for-bit, and the floor is a no-op in the healthy with-audio path (the audio-latency reservoir target already dominates). Regression-locked by `CapturePipelinePolicyTest.WgcSmoothnessFloorIsSyncNeutralAcrossDelays` (the sync-neutrality property), `WgcSmoothnessFloorDerivationIsClampedAndMonotonic`, and `WgcSmoothnessDelayDesiredArmsForFloorWithoutAudioLatency`.

## Diagnostics

Use these signals together:

- `TimerRebase` / duplicate timer-rebase counts: nonzero values indicate live CFR rescheduling pressure. They must not represent discarded timeline debt in CFR captures.
- `CFR stop drain ... path=inject|WGC`: shows whether stop-time outstanding CFR ticks were closed.
- `[EncoderThread] CFR stop drain skipped before first live video frame`: the recording stopped before any video frame committed the output timeline. There is no CFR prefix to close; the encoder worker disarms the drain and proceeds to reserved-output cleanup instead of polling an already-shut-down empty queue.
- `[A/V START] Audio source reset ... timelineValid=...`: non-app sources should become valid at the shared anchor; app audio stays optional only until first packet evidence. If an app source saw sync-pending packets, subsequent bootstrap should wait rather than encode a leading silent head.
- `[PullAudio] Track ... bootstrap complete ... forced=0 trimmed=0`: any `forced=1` or nonzero `trimmed` indicates the old content-shortening startup path.
- `[PullAudio] Timeline source gap silence ... idle=<ms>`: a started source exhausted the ingestion reservoir and is intentionally contributing silence instead of blocking the exported track. `idle` is the time since that source last placed a real packet; a large value means a genuinely sparse source, while a small value with real packets, QPC overlap, or `Late source cursor advance` right after is consumer-overrun starvation evidence to inspect.
- `[PullAudio] Late live source hold ...`: the source was short but still delivering, so the pull was held and the reservoir deepened instead of exporting silence that would have destroyed the late audio. Informational recovery, not a fault.
- `[PullAudio] Ingest reservoir deepened|relaxed ... worstHeadroom=<ms> atCap=<0|1>`: adaptive pull-lookahead changes. `worstHeadroom` below zero means the consumer had already overrun the capture edge. `atCap=1` sustained is a real capacity problem; the reservoir cannot grow further and silence plus the last-resort re-anchor become reachable.
- `[AudioLoop] WARNING: source ingest starvation ...`: real captured audio is being discarded as timeline overlap because the exported cursor ran past the live capture edge. Strict; the recording is losing content even if every duration matches.
- `[AudioLoop] WARNING: unrecoverable ingest starvation - re-anchoring ...`: last-resort placement re-anchor after the reservoir saturated. Always a bug signature to investigate.
- `[STOP AUDIO INGEST] Source N: starve=... resync=.../... reservoirPeakMs=...`: per-source destroyed-sample total, last-resort re-anchor accounting, and the session's peak extra lookahead. `starve=0 resync=0/0` is required for a clean recording; a nonzero `reservoirPeakMs` alone is healthy adaptation.
- `[PullAudio] WARNING: Source underrun ... forceDrain=0`: live source underrun and strict audio evidence. The same line with `forceDrain=1` is stop-tail padding evidence; it is diagnostic only when decoded strict markers, inter-track spread, CE zero residuals, and final packet/post-mux durations are clean.
- `[AudioLoop] Late source cursor advance ...`: late source data is being stitched against the already-advanced source/track cursor rather than delaying the exported track.
- `[AudioLoop] Late app source live join ...`: a process-loopback source first became active after recording start and stale first-packet backlog was suppressed so the source joins the current track cursor.
- `[STOP AUDIO] Source ... qjoin=... qjoinKeep=... process=...`: late app-source join accounting, including how much stale queued gap was suppressed and how much fade cushion was preserved.
- `[STOP AUDIO TRACK] Track ... encoded=... expected=... realMixed=... fullSilence=... partialSilence=...`: per-exported-stream cursor and real/silence accounting.
- `[A/V SYNC SUMMARY] Track ... audio_vs_encoded_us=... audio_vs_target_us=... residual_samples=... target_samples=... cursor_samples=...`: live sample accounting. For strict CFR diagnosis, `residual_samples=0` is the hard requirement after startup; `audio_vs_encoded_us` is diagnostic because encoded packet duration can lag live scheduled duration under CFR.
- `[A/V ZERO DRIFT WARNING]`: settled CFR track cursor and CFR target sample disagree. Treat as a strict failure even when final packet/container durations still match.
- `[STOP AUDIO DETAIL] Source ... ratePpm=... compDelta=... sat=...`: source-clock compensation state at stop. For healthy CFR recordings this should stay effectively zero; saturated `ratePpm` with clean source clocks usually means compensation is chasing buffer level instead of real drift.
- `[StopAudio] forceDrain ... iterations=...`: stop-time force drain may run multiple bounded chunks. Warnings `forceDrain made no progress` or `forceDrain incomplete` are strict follow-up evidence for track-cursor failures.
- `[StopAudio] Source ... diff=+0 (+0.0 ms)`: sample-count equality to the selected final video timeline.
- `[VideoEncoder] Final packet timeline`: actual last written packet end per stream and packet-level delta. Audio pass/fail endpoints exclude terminal `AV_PKT_DATA_SKIP_SAMPLES` discard while retaining `rawAudioMaxEnd` for packet-topology diagnosis.
- `[VideoEncoder] Final metadata durations`: in-memory stream metadata sampled only after `av_write_trailer`; the log reports available/declared stream counts. Missing `AVStream::duration` fields are informational because some muxers do not populate them even after trailer. Packet timelines plus the bounded post-mux packet probe remain authoritative, and only complete metadata is compared against tolerance.
- `[VideoEncoder] mux_closed ...`: trailer/file close and muxer cleanup completed; later probe problems should not imply the muxer is still owned.
- `[VideoEncoder] post_mux_probe_start/complete/timeout/cancelled ...`: reopened-file stream duration/end check after trailer write; this is the external duration authority when it completes, and a timeout is a bounded validation failure/diagnostic rather than a shutdown hang.
- `[VideoEncoder] Post-mux duration probe`: reopened-file stream duration/end check after trailer write. Audio endpoints are decoded endpoints: Matroska packet coverage is reduced by codec-declared initial padding and terminal packet discard padding. Raw endpoints and padding evidence remain logged; an incomplete bounded tail scan cannot silently excuse a mismatch.
- `[VideoEncoder] Post-mux audio codec-padding applied`: informational proof that raw AAC/Opus packet coverage was translated to the externally decoded endpoint using explicit codec metadata.
- `[VideoEncoder] Post-mux audio duration rounding evidence`: reopened-file audio duration differs from the target only within the one-sample / one-timebase-tick rounding tolerance. This is informational; larger mismatches still log `WARNING: Post-mux audio duration mismatch`.
- `[VideoEncoder] Stop: WARNING writer_finalize_slow phase=...`: phase-aware stop diagnostic emitted once when trailer/final probe/cleanup is slow. It is diagnostic evidence, not by itself mux corruption.
- `[VideoEncoder] Stop: ERROR writer_finalize_timeout ...`: strict mux ownership failure unless the same session later has exact final packet/container/post-mux evidence and no sync-finalize fallback. The async writer still owns the FFmpeg context, so CE must not run a synchronous trailer write on the same context. Old logs that combine `Writer thread did not finish ... detaching` with `Sync Stop: Finalizing file...` indicate the double-finalize crash family.
- `[AudioEncoder] Using codec: requested=... resolved=... channels=... mask=...`: codec alias, resolved encoder, and track layout policy.
- `[AudioEncoder] Silence queue ...`, `Clamping final packet duration ...`, and `Added packet end-skip side data ...`: encoded silence and AAC/Opus padded-tail handling.
- `[AudioEncoder] Opus requires 48000 Hz ...`: expected adjustment when Opus was configured with another sample rate.
- `[Cadence Health]` inject fields plus `[Inject CFR QUALITY SUMMARY]`: `InjectCatch=fresh/repeat`, `TickUnique`, `TickDup`, `Shortfall`, `AgeAvg/AgeMax`, `TargetSelect`, `Superseded`, `TargetHold`, `HoldWithCandidate`, `BufferCapTrim`, and `TargetResidualMax` distinguish honest source-limited repeats from selector or buffer-policy churn. `InjectAgeTrim` is a legacy pre-target-playout metric and should remain zero in new sessions.
- `[Inject CFR] Recovery entered/progress/completed` and `[Inject CFR SUMMARY]`: start/best/current debt, episode duration, `Recovery=active/episodes`, `FreshCatchup`, `RepeatCatchup`, `StaleTrim`, duplicate reasons, pure encode time, normalized per-output service time, raw full-cycle time, and source FPS show whether debt converged, was paused for genuine encoder/mux pressure, or was caused by source/game FPS below target or fence deferral. A recovery that remains active long enough to emit the five-second warning is classified as `inject_cfr_recovery_stalled` by `tools/analysis/analyze_capture_av.py`; old summaries remain accepted.
- `FPS Limiter: Local timer stats ... phaseSkipped=N` reports whole capture-grid slots skipped after late Presents. `[CFR PhaseLock] path=screen_grab|inject` reports scheduler-path acquisition, stable rephase, or variable-source release; `[CFR PHASE LOCK SUMMARY] Backend=dxgi_dup|wgc|inject` records the actual final backend, offset, and transition counts. Legacy hard-coded phase-lock `backend=wgc` labels are not valid ordered backend-transition evidence. These are selection-phase diagnostics, not audio/CFR-grid corrections.
- Session present-gap triage uses the `source_frame_index` live span when available, excluding pre-live initialization and post-stop frozen metrics. Inject target-policy churn requires repeated hold-with-candidate/superseded pairs in consecutive per-window source-rate-matched, non-overloaded windows; a session-wide minimum distorted by one real hitch is not a valid stability test, and honest varying/under-target resampling is not classified as a policy fault.
- `[Cadence Health]` WGC fields: `WgcSelBias`, `Shortfall`, `LeadExcess`, `Oldest`, `BufNow`, `LiveClamp`, and `AgeMax` expose visual debt, selected-content drift, and live-window source-selection clamping. Large values are a content-sync bug even when stream durations match.
- `[EncoderThread] CFR Catchup applied using fresh frame`: legacy current-frame/old-PTS WGC catch-up and always a strict failure. Safe current recovery instead logs `[EncoderThread] WGC CFR grid-matched recovery frame` and requires a monotonic historical frame matched to that exact old selection target plus encoder-service/reservoir headroom.
- `[EncoderThread] WGC CFR repeat catch-up armed`: rate-limited proof that shortfall recovery will emit two to four packet-backed CFR slots on the immutable grid. `ticksThisLoop>1` is intentional under debt; an extra slot uses safe grid-matched history when available and otherwise holds the prior frame. It must not move the next normal wake deadline.
- `[WGC CFR] Uniform playout grid-debt sync hold`: every retained frame is substantially newer than the immutable audio-aligned content target. The old wall-age anti-freeze floor is gone; held-repeat catch-up must advance the grid until safe history becomes selectable. `GridDebtSyncHolds` and `GridDebtLeadMax` report the total and worst target/history gap.
- `[WGC CFR] Overload repeat pacer entered|exited` and `[WGC CFR OVERLOAD PACER]`: WGC/DXGI-only evidence that fresh and repeat service formed a feasible capacity mix. Logs include service EMAs/sample counts, budget, fresh fraction, decisions/emitted repeats, maximum paced repeat run, and explicit unchanged CFR/audio invariants. Paced repeats are separated from genuine no-source repeats.
- `[EncoderThread] WGC CFR slot repeat: buffered frame is too new for scheduled slot`: expected only for short gaps or while WGC is honestly building/holding the requested render-domain delay. Frequent events while `Shortfall` is near/above the live-window limit mean source selection may still be pinned too far behind live and should be investigated with `LiveClamp`, `WgcSelBias`, `BufNow`, reservoir low-water ticks, and the sync-delay hold attribution.
- `[EncoderThread] WGC CFR visual timeline debt drop`: WGC visual debt exceeded the live window. It logs current and maximum excess ticks as a warning to inspect, not permission to shorten audio or move future frames into old slots.
- `[EncoderThread] WGC CFR live scheduler rebase`: legacy output-grid skipping. Current `GetWgcLiveSchedulerRebaseTicksThisLoopForMode` returns zero because advancing coverage without a packet punches CFR PTS holes; any occurrence in a current build is a regression.
- `[EncoderThread] WGC CFR stale visual debt drop`: buffered WGC frames older than the live-debt window were dropped instead of being encoded as delayed visual history.

## UPDATE 2026-06-17 — per-device-domain latency model + render→loopback auto-detect (fixes the per-source regression)

The 2026-06-16 fix delayed video by `max(per-source captureLatencyMs)` and equalized faster sources up to it. Modeling latency PER-SOURCE was wrong and regressed real use (session `20260617_010909`, Fortnite/WGC): the user set `[Audio] capture_latency_ms=46` but `[General]=0`, so app process-loopback inherited 0 while system loopback got 46; equalization then delayed the game's app-loopback by 46 ms even though it shares the SAME render endpoint. Latency is a per-DEVICE-DOMAIN property:

- **Domain 1 = default render endpoint:** system loopback (`[SystemAudio]`/`[SystemAudio.N]`) + ALL `[AppAudio.N]` process-loopback → ONE value (`[AudioSync] audio_capture_latency_ms`). They all capture the same endpoint.
- **Domain 2 = each mic/input:** its own value (`[General] mic_capture_latency_ms` or per-mic `capture_latency_ms`). Mics no longer inherit the render-endpoint value (`common/config.cpp` mic fallback fixed). This is the regression fix.

**Auto-detection (no hardcoded device value — works automatically on any system):** `mediaengine/audio_latency_probe.{h,cpp}` renders a brief near-inaudible Hann marker to the default render endpoint and detects it in a loopback capture; latency = loopback marker-CENTER QPC − render-start marker-center QPC. It takes 5 independent shots and aggregates with `MedianWithConsistency` (≥3 within 8 ms) so a noisy reading cannot over/under-correct; no consensus → ok=false → NO correction applied and `[AVSyncAuto] confidence=low` is logged (graceful, never a guessed value). The resolved value is cached only in process memory, keyed by endpoint format and period metadata; CE must not create or update `audio_latency_cache.ini`, and legacy files are best-effort deleted at startup. The tradeoff is one near-inaudible probe per fresh CE process instead of persistent endpoint data on disk. The marker is low amplitude (`0.015`) and sample rates below 44.1 kHz are rejected as likely audible. `[AudioSync] audio_latency_autodetect` defaults true; the fresh profile explicitly uses `audio_capture_latency_ms=0`, meaning auto, while a manual value greater than zero disables the probe. `captureengine/media_main.cpp` measures once before `MediaEngine_Init` (not while recording) and re-applies the resolved value to render-domain sources on every config (re)load via the mediaengine export `MediaEngine_MeasureRenderEndpointLatency`. Do not ship a device-specific nonzero latency.

**No visible product calibration:** the old WGC/window-flash calibration code (`av_sync_calibrator.*`, `audio_av_calibration`) was removed on 2026-06-18. The DX12 A/V stimulus app and matrix harness remain test/validation tools only; normal product startup must not spawn windows or flash video to calibrate.

**Delay-only reconciliation:** `ApplyCaptureLatencyCompensation` (`audio_time_utils.h`) no longer advances live audio at the packet-placement sites in `audio_capture.cpp`/`app_audio_capture.cpp` (advancing is absorbed by the CFR pipeline and double-counts with the video delay on devices that report a nonzero `GetStreamLatency`). ALL latency flows through the video content delay + equalization. `streamLatency`, device period, packet duration, buffer depth, WASAPI QPC, and device position stay telemetry/passive model inputs. `[AVSyncApply]` shows WGC `wgc-selection-bias` or inject `inject-buffer-reserve` with reserve frames and residual estimate; `[AVSyncAuto] stop_summary` records final confidence/reason. The A/V harness writes `audio_latency_autodetect=false` so its explicit latency stays authoritative.
