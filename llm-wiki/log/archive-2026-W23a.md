### 2026-06-07 - DX12 API call-trace diagnostic (committed) + RTSS-technique ground truth: freeze is qualitative, not workload size

- **New diagnostic (committed, gated, off by default)**: `Dx12TraceEnabled()` in `hook/apis/dx12_hook.cpp`, armed by env `CE_DX12_TRACE=1` or a `ce_dx12_trace` flag file next to the hook DLL. When on, CE logs caller-attributed (`DX12 TRACE: <api> orig=<module> | <details> | trail=<module-chain>`) D3D12 device/queue calls: `CreateCommandQueue`, `CreateCommittedResource`, `CreateDescriptorHeap`, `CreateSwapChain[ForHwnd]`, `ExecuteCommandLists`, `Signal`. The creation/Signal hooks are installed in `DX12_HookDeviceVTable`/`DX12_HookQueueVTable` ONLY when tracing is enabled (zero impact otherwise). Driver/orchestrator: `tools/dx12_call_trace.py` (`run --overlay|--observe`, `parse`, `setup`, `cleanup`). LIMITATION: CE submits its own overlay ECL/Signal via the raw unhooked function pointer (`realECL`), so CE's OWN overlay submissions are not captured — the trace sees the app's and any co-resident injected module's calls; use the resource/descriptor footprint (created on the present thread, attributed to the app) to infer CE's contribution, or compare `--overlay` vs `--observe`.
- **Ground truth on RTSS (via the trace, x86 `dx12_test`)**: RTSS renders its overlay via **D3D11On12** (`trail=...>d3d11on12.dll>d3d11.dll>RTSSHooks.dll`), submitting on the **app's** command queue (no own queue). In a steady-state sample it issued **more** `ExecuteCommandLists` than the app (52 vs 38) and **more** `Signal`s (64 vs 26), plus a large footprint (~24 CUSTOM-heap resources + two 1,000,000-descriptor shader-visible heaps). It never freezes on the 32-bit Alt+Tab mode switch.
- **CE baseline (`--overlay`)**: native D3D12 — UPLOAD-heap vertex/index frame-pool buffers (`81920`/`16384` B = `4096*20`/`8192*2`), a DEFAULT font texture, and RTV heaps onto the swapchain backbuffers; submits on the app's queue via `realECL`.
- **Decisive conclusion**: RTSS does MORE work with a FAR bigger footprint than CE and is robust, so the 32-bit freeze is **NOT** caused by the amount/footprint of CE's overlay work — it is **qualitative**. RTSS's robustness comes from handing backbuffer-wrapping + resource/residency/submission bookkeeping to the D3D11 runtime (D3D11On12). That technique is forbidden by project rule (`use native DX12`).
- **Decision (user)**: stay fully native D3D12 (it already works on 64-bit without freeze); keep debugging the specific native qualitative trigger (candidate: how CE manages backbuffer RTV/reference lifetime + resource state across the `ResizeBuffers`/mode switch vs what the D3D11 runtime does). Do NOT pursue D3D11On12 or a composited (DComp/separate-window) overlay (rejected).
- **Source anchors**: `hook/apis/dx12_hook.cpp` (`Dx12TraceEnabled`/`Dx12TraceLog` ~2438, detours `DetourTrace*`/`DetourCreateCommittedResource`, installs in `DX12_HookDeviceVTable`/`DX12_HookQueueVTable`), `tools/dx12_call_trace.py`.

### 2026-06-06 - Dedicated overlay queue for NON-FG (Alt+Tab kernel GPU-allocation freeze; no hide)

- **Context**: After loader stalls + DRED were eliminated, the x86 Alt+Tab repro `logs/20260606_150849` (build 0.1.3784) STILL froze (gap=2010ms → `DEVICE_HUNG`), but now with the present thread in a KERNEL GPU allocation inside the APP's own submission: `dx12_test!Render -> DetourExecuteCommandLists -> CCommandQueue::ExecuteCommandLists -> nvwgf2um -> D3D12Core CDevice::AllocateCB -> NtGdiDdDDICreateAllocation`. (Also clarified: the constant "IAT: Initializing D3D11 hooks" is CE's benign 1 s periodic hook re-scan, not a d3d11 reload.)
- **Root cause**: CE's overlay submits an EXTRA `ExecuteCommandLists` every frame on the **application's shared command queue**, ~doubling the driver's command-buffer consumption on that queue. That forces the app's OWN `ExecuteCommandLists` to allocate a new command buffer (kernel GPU allocation) which, during the iflip<->composited mode switch, blocks ~2 s (VidMm busy reconfiguring) and trips the 2 s TDR. The bare app / RTSS don't hit this because they don't add a second per-frame submission to that queue. This matches the wiki's v10 "hold never hung" result (holding removed the overlay submission). The overlay GPU path itself is already efficient (pooled allocators/lists + persistent upload ring, no per-frame resource creation) — the issue is purely the extra submission on the *shared* queue.
- **Fix (user-chosen, no hide)**: enable the **dedicated overlay command queue for non-FG plain DX12** (it was FG-only). `ce::overlay_compat::ShouldUseDedicatedDX12OverlayQueue` now returns true for non-FG too, EXCEPT during startup-overlay compat (`processNeedsDelay`) or when a startup-blocking third-party overlay (Social Club / EOS) is loaded — those stay single-queue because cross-queue swapchain-backbuffer state transitions caused `ERR_GFX_STATE` in GTA5 Enhanced. Streamline-FG / runtime-owned-FG are already excluded earlier by `ShouldUseDedicatedOverlayQueue` (cross-queue access is rejected under SL FG). This reuses the existing, FG-validated cross-queue machinery: dedicated queue creation (`InitOverlaySync`), pre-submit `WaitForGameQueueBeforeDedicatedOverlaySubmission` (game-queue signal + 16 ms-bounded CPU wait — well under the TDR), and present-completion `DX12_WaitForOverlayCompletion` on BOTH present paths (`ShouldWaitForOverlayCompletion` returns true when `usingDedicatedQueue`). Cross-queue backbuffer access is legal because PRESENT==COMMON (0): the app leaves the backbuffer in PRESENT, the overlay queue does COMMON->RENDER_TARGET->COMMON. Overlay draws every frame (no hide).
- **Why a dedicated queue is clean for non-FG** (answering the design question): no FG runtime owns the swapchain/queues, so the FG-era `ERR_GFX_STATE` cross-queue conflict does not apply; the only cost is a small per-frame cross-queue fence sync (currently 16 ms-bounded CPU waits — could be optimized to GPU-side `Queue->Wait` later if latency matters).
- **Validation**: build clean x64+x86; `python build.py --no-build --run-tests --skip-updates` = 919/919 (updated `OverlayCompatTest.DedicatedQueueSupportsFGAndPlainDX12`). **PENDING live x86 Alt+Tab repro** — expect `InitOverlaySync: Dedicated overlay queue created`, no `gap=NNNNms` spike, no `DEVICE_HUNG`, overlay visible throughout. ALSO re-validate Talos/GTA FG scenarios (GTA stays single-queue via the Social Club exclusion; FG path unchanged).
- **OPEN / risk**: broad change — ALL non-FG DX12 apps now use the dedicated queue. Watch for any cross-queue `ERR_GFX_STATE`/`DXGI_ERROR_ACCESS_DENIED` on other non-FG games (the known offenders are excluded). If a future freeze dump shows the present thread now stalling in the OVERLAY queue's own `ExecuteCommandLists` allocation, the dedicated queue didn't isolate enough and DComp would be the next step.

### 2026-06-06 - ROOT CAUSE: forced-on DRED auto-breadcrumbs caused the Alt+Tab freeze (per-Reset kernel GPU alloc); DRED now default-OFF

- **Context**: Repro `logs/20260606_145929` (build 0.1.3781, FREEZE dump) after all overlay detectors + IsSLInterposerLoaded were made loader-free. The loader stalls were GONE (no GetModuleHandle in the present-thread stack), but it STILL froze: gap=2646ms → `DEVICE_HUNG`.

Correct allocation is `samples * bytes_per_sample * channels` for total storage, with one plane pointer for packed formats and per-channel plane offsets only for planar formats.
  - AAC external overrun: final packet clamping used the codec-padded frame boundary as both the submission limit and visible packet end. AAC needs padded submission, but the packet duration exposed to mux/probe must clamp to the exact video-authoritative sample target and carry end-skip metadata for the padded tail.
  - Pure-silence tracks: the pending recording-start reset was applied only on the first real `EncodeSamples()` call. If a track produced no samples before stop, `Flush()` never learned the start time and therefore had no video duration target to encode silence toward.
  - Long silent tails: the old pre-fill path capped tail silence at 3 seconds. This was memory-safe but wrong for inactive tracks or long source gaps; silence must be chunked, not truncated.
- **Fix**: Audio finalization now keeps separate `targetSamples` (exact video duration) and `maxSamples` (codec submission limit). It feeds required silence through the normal FIFO/encoder path in frame-sized chunks until `maxSamples`, allocates packed/planar zero buffers correctly for all channel counts, applies pending start during flush while preserving the already-set end time, clamps final packet durations to `targetSamples`, and writes 10-byte `AV_PKT_DATA_SKIP_SAMPLES` side data (`end reason=padding silence`) for padded AAC/Opus tails. `VideoEncoder` now reopens the completed file after trailer write and logs `[VideoEncoder] Post-mux duration probe ...` as the external stream-duration authority.
- **Silence invariant**: enabled tracks are encoded as real zero samples through the selected codec when sources are silent/inactive; sparse container gaps are not the compatibility contract.
- **Regression coverage**: Added `AudioSyncUtilsTest.PackedSilenceBufferIncludesEveryChannel`, `FinalPacketDurationClampsToVideoSampleTarget`, `AudioEncoderTest.AacFlushClampsPaddedFinalPacketToVideoTarget`, `OpusFlushPadsPackedSilenceWithoutPacketsPastTarget`, and `SilenceFlushIsBoundedForEveryAudioCodec` (AAC/ALAC/FLAC/Opus/PCM pure-silence matrix with AAC/Opus skip metadata checks).
- **Verification**: Focused build/test passed 72/72 with `python build.py --skip-updates --run-tests --gtest-filter=AudioEncoderTest.*:AudioSyncUtilsTest.*:AudioResamplerTest.*:ConfigTest.AudioDerivedSourcesInheritQualityAndDownmix:ConfigTest.AppAudioCanOverrideInheritedDownmixAndQuality` (build 0.1.3735). Full test-only pass succeeded with `python build.py --no-build --run-tests --skip-updates` (894/894, metadata 0.1.3736). Required plain build passed with `python build.py --skip-updates` (build 0.1.3737).

### 2026-06-04 - x86 Alt+Tab DX12 DEVICE_HUNG = overlay UPLOAD-ring data race (DescFree per-slot fence, v12) — SUPERSEDED as the freeze root cause (see 2026-06-06)

> **SUPERSEDED (2026-06-06)**: the live freeze persisted after v12. A fresh manual dump (`logs/20260605_231633`) showed the Present thread stalled in the **Windows loader** (`GetModuleHandleA` for not-loaded overlay modules), not in `ExecuteCommandLists`. The v12 UPLOAD-ring per-slot fence is a legitimate GPU-safety hardening and is kept, but the actual x86 Alt+Tab freeze was the per-Present loader walk; see the 2026-06-06 entry. Treat the "SOLVED" claim below as "GPU race hardened", not "freeze fixed".

- **Root cause (proven, not guessed)**: The injected x86 `dx12_test.exe` froze with `DXGI_ERROR_DEVICE_HUNG (0x887A0006)` on Alt+Tab. DRED (`logs/20260604_011053`) showed the hung GPU work was CE's **own overlay command list** (`DRAWINDEXEDINSTANCED`, `completedOps=2/7`, INCOMPLETE) with **`pageFaultVA=0`** = pure execution hang, not a bad address. The manual freeze dump's render thread was blocked in `dx12_test!Render -> capture_hook_x86!DetourExecuteCommandLists -> D3D12Core!CCommandQueue::ExecuteCommandLists -> nvwgf2um (AllocateCB) -> win32u!NtGdiDdDDICreateAllocation` — a **kernel GPU allocation waiting on the wedged GPU**, exactly one ~1.9s stall (`heartbeat gap=1923ms`) that tripped the 2s TDR. Only the render thread was involved (no CE-worker contention). The test app uses **one** queue for both ECL and present (`g_CommandQueue`); CE submits the overlay on that same queue (no cross-queue issue).
- **The actual bug**: `DX12DescFreeBackend::Render` (in `hook/apis/dx12_hook.cpp`) round-robins `kPoolSize=4` persistently-mapped UPLOAD vertex/index buffers (`slot = frameIdx_ % kPoolSize`) and `memcpy`s new geometry into the slot **with no fence guarding GPU read completion** — fully decoupled from `g_State.fence`/`fenceValues`. While the GPU keeps up the slot is free by the time it's reused (4 frames later). During the iflip<->composited mode switch the GPU stops retiring for hundreds of ms while the CPU keeps drawing the overlay at ~140fps → within 4 frames the CPU **wraps and overwrites vb/ib data the GPU is still reading** → corrupted draw → GPU wedges → TDR. x64 (faster/shorter pause) and the bare app (no overlay) stay under the wrap; RTSS fences its own uploads. This is why it was x86/WoW64-only and why the debug layer (timing change) masked it.
- **Fix (v12, never hides the overlay)**: Per-slot GPU-completion fence on the DescFree UPLOAD ring. Each render site publishes `s_descFreeSlotFence = g_State.fence` and `s_descFreeSlotGuardValue` (= `currentFenceValue+1` non-FG, `0` for FG/PostSL paths which already sync via their own completion fence). `Render` waits (`WaitForSlotGpuComplete`) for the prior occupant's guard before reusing a slot, then records the new guard. Decisions extracted to `ce::dx12_overlay_policy::DecideOverlayUploadSlotGuardValue` / `ShouldWaitForOverlayUploadSlot` (unit-tested). The fence is the real sync; the wait has a 1000ms (< 2s TDR) liveness bound that logs on timeout (a separate FG-transition path can legitimately discard a pending signal). Result: overlay is drawn every frame (never hidden) and the CPU paces to the GPU only when genuinely ahead — like RTSS.
- **Invariant**: The DescFree overlay UPLOAD ring must never be reused before the GPU has finished the previous frame that used that slot. Guard keyed on the overlay fence (`g_State.fence`); disabled (0) only when FG advances a separate completion fence or there is no overlay fence.
- **Diagnostic signature (durable)**: x86 DX12 present thread stuck in `NtGdiDdDDICreateAllocation` inside `ExecuteCommandLists` + DRED INCOMPLETE overlay `DRAWINDEXEDINSTANCED` with `pageFaultVA=0` = GPU wedged by a corrupted overlay draw, not a real fault. Suspect UPLOAD/ring reuse without a fence.
- **Verification**: `python build.py --skip-updates` clean (x64+x86 `dx12_hook.cpp` recompiled); full suite `889/889` incl. new `DXGISharedTest.OverlayUploadSlotGuardDisabledForFGAndMissingFence`, `OverlayUploadSlotWaitsOnlyWhenGpuBehindActiveGuard`, `OverlayUploadRingGuardPreventsModeSwitchStomp` (the ring sim fails against the pre-fix unguarded path). Binary-string marker bumped to `policy=v12 ...`. **Pending: live 32-bit Alt+Tab-spam repro to confirm the freeze is gone.**
