### 2026-04-21 - Let half-armed pure-DLSS synthetic PostSL startup rebuild overlay state on a fresh runtime-owned Streamline handoff without waiting for full ProcessFrame dormancy, and suppress generic scene-gap cooldown on that same startup

- **Motivation**: GTA V Enhanced `installed/captureengine/logs/20260421_223723` on build `0.1.2520` no longer hit the older immediate-expiry crash or extra-epoch restart seams, but DLSS FG still behaved wrong with CE active: the game eventually reached `PostSL CONFIRMED rendering` and `Post-SL overlay SUBMIT #1..#9` on the fresh runtime-owned Streamline `scQueue=000002572E52D6D0`, yet that confirmation arrived much later than healthy Talos and GTA still fell back to `STREAMLINE_NO_FG` almost immediately afterward.

- **Comparison that narrowed the seam**:
  1. This GTA session is not the older `epoch=2` pure-DLSS family from `20260421_213224`. The fresh runtime-owned Streamline handoff on `scQueue=000002572E52D6D0` really does stay on the live comeback, and CE eventually confirms rendering and submits PostSL overlay work on that queue.
  2. The first remaining divergence is earlier than the final OFF edge. Right after `DX12: PostSL synthetic startup activation complete`, GTA spends many callback entries on `DX12: PostSL SKIP — state unavailable (epoch=1 call#=34... init=0 sync=0 list=... alloc=16)` and only later logs the normal overlay reinit on `queue=000002572E52D6D0` (`[Overlay] Initializing DX12 backend ...`, then `InitOverlaySync: SUCCESS ...`). Healthy Talos does not get stranded in that `state unavailable` slice on its corresponding pure-DLSS startup.
  3. The second divergence appears immediately after that delayed reinit. GTA logs `DX12: Scene transition detected (gap=3024ms) during FG — overlay cooldown 30 frames`, then only about 0.78s later reaches `DX12: Post-SL scene transition cooldown complete — resuming overlay`, `PostSL first ECL submit approaching`, and finally the first confirmed submit. Talos does not insert that extra scene-gap overlay cooldown into its matching startup family.
  4. Because those two delays consume most of the startup-protected distance, GTA then reaches `Dropping stale suppressed slDLSSGSetOptions(OFF) ... startup is already stably active` immediately after `Post-SL overlay SUBMIT #9`, followed 21ms later by `FG state transition ON->OFF via GetState`. The stale-OFF drop is still a watch-item, but the newly exposed CE-side delay seam is now separately actionable and generic.

- **Root cause refinement**:
  1. `PostSLOverlayRender()` only called the overlay-state rebuild helper when `ShouldBootstrapPostSLOverlayState(...)` returned true, and that helper still encoded `!processFrameRecentlySeen` as a hard prerequisite.
  2. On GTA `20260421_223723`, the fresh authoritative Streamline handoff happens while synthetic PostSL startup is already half-armed (`activationPending` / `activeButUnconfirmed`), so PostSL is the code path that most urgently needs to rebuild overlay state for the new runtime-owned `scQueue`. But because `ProcessFrame` is still active, the old guard kept PostSL from rebuilding that state, and the callback path stayed stuck on `state unavailable` until the normal overlay path eventually reinitialized later.
  3. Once the normal path finally did rebuild overlay state, the generic scene-gap heuristic still treated the same startup as a normal FG scene transition and injected a new 30-frame overlay cooldown, even though the startup was still half-armed and unconfirmed. That needlessly stretched the invisible startup window and consumed almost all of the remaining startup-protected slack before stale-OFF drop/settling logic kicked in.

- **Fix**:
  1. `hook/common/dx12_overlay_policy.h` now broadens `ShouldBootstrapPostSLOverlayState(...)` to accept the half-armed synthetic-startup family too: if Streamline FG is live, PostSL is active, overlay state is torn down, and startup is still pending/unconfirmed, PostSL may rebuild overlay state even while `ProcessFrame` is still active.
  2. The same header now adds `ShouldSuppressSceneTransitionCooldownDuringSyntheticPostSLStartup(...)`.
  3. `hook/apis/dx12_hook.cpp` now threads the half-armed startup state (`startupActivationPending`, `HookIsPostSLOverlayActiveButUnconfirmed()`, `HookIsPostSLOverlayConfirmedRendering()`) into the bootstrap helper call in `PostSLOverlayRender()`.
  4. The ProcessFrame scene-gap branch now checks the new suppression helper before arming `g_SceneTransitionCooldown`. When the startup is still half-armed, CE now logs `DX12: Suppressing scene transition cooldown during half-armed synthetic PostSL startup ...` instead of starting a new 30-frame overlay cooldown.
  5. `tests/test_dxgi_shared.cpp` now extends the existing bootstrap coverage and adds `PostSLBootstrapsOverlayStateDuringHalfArmedSyntheticStartupEvenIfProcessFrameIsRecent` plus `SceneTransitionCooldownIsSuppressedDuringHalfArmedSyntheticStartup`.

- **Why this is generic**: This is not a GTA-only carve-out and not just a workaround for one queue value. Any pure-DLSS startup can surface the same shape: synthetic startup is already half-armed, a fresh authoritative Streamline handoff moves rendering onto a runtime-owned `scQueue`, and PostSL is the path that must bootstrap/recover overlay state on that new swapchain before first confirmation. The generic invariants are: half-armed synthetic startup must be allowed to rebuild overlay state on the fresh handoff swapchain without waiting for full ProcessFrame dormancy, and unrelated scene-gap heuristics must not inject a second overlay cooldown into that same half-armed startup before first confirmation.

### 2026-04-21 - Keep swallowed stale `slDLSSGSetOptions(OFF)` churn from poisoning CE's own pure-DLSS runtime state, and preserve half-armed synthetic PostSL startup through the overlay-reinit cooldown path too

- **Motivation**: GTA V Enhanced `installed/captureengine/logs/20260421_213224` on build `0.1.2518` still showed wrong pure-DLSS behavior even after the earlier explicit-startup stale-OFF-at-expiry fix from `0.1.2518`. Healthy Talos comparison remained `installed/captureengine/logs/20260421_165756_talosnocrash_multipleswitching`.

- **Comparison that narrowed the seam**:
  1. This GTA session is not the old immediate-expiry crash family from `20260421_204230`. GTA really does survive long enough to reach `DX12: ECL hook detected startup transition window expiry ...`, `DX12: PostSL REACTIVATED (epoch=1 hadFSR=0)`, later `DX12: PostSL CONFIRMED rendering via re-entrant Present`, and `Post-SL overlay SUBMIT #1..#9` on `scQueue=0000024787447F80` with no `DEVICE_REMOVED`.
  2. Compared with healthy Talos, GTA still restarts the same startup once before first confirmation: after the fresh runtime-owned Streamline handoff to `scQueue=0000024787447F80`, GTA logs `DX12: FG transition cooldown complete — preserving half-armed synthetic PostSL startup state until confirmed render`, then later `DX12: PostSL REACTIVATED (epoch=2 hadFSR=0)`. Talos reaches `epoch=1`, warms up, confirms rendering, and never needs that second epoch on its corresponding pure-DLSS startup.
  3. The later OFF edge is also narrower than the old stale-replay seam. Right after GTA reaches `Post-SL overlay SUBMIT #9`, CE logs `Streamline Hook: Dropping stale suppressed slDLSSGSetOptions(OFF) after startup window expiry because Streamline DLSS startup is already stably active ...`, yet a few milliseconds later still logs `DX12: Streamline FG OFF ...` and `Streamline Hook: FG state transition ON->OFF via GetState`.
  4. That means the final OFF did not come from forwarding the stale suppressed OFF into Streamline at that point; CE had already dropped it. The remaining OFF therefore had to come from CE's own local runtime reduction/state machine observing stale OFF-shaped bookkeeping that no longer matched what Streamline itself had actually seen.

- **Root cause refinement**:
  1. `Hooked_slDLSSGSetOptions()` still always called `BuildViewportRuntimeUpdateFromRequestedOptions(...)` / `UpdateViewportRuntimeState(...)` after the original/suppressed call returned `kSlResultOk`, even when the call was a startup-protected stale `slDLSSGSetOptions(OFF)` that CE had intentionally swallowed and never forwarded to Streamline.
  2. That meant CE could intentionally keep Streamline running through startup-protected OFF churn at the hook boundary, yet still poison its own per-viewport/runtime reduction as if Streamline had really processed the OFF. The later shared reducer then had enough stale local OFF state to self-publish `runtime=STREAMLINE_NO_FG active=0` and tear PostSL down even though the stale OFF was dropped rather than forwarded.
  3. Separately, the pure-DLSS runtime-owned handoff still had a second lifecycle seam in DX12. The main FG cooldown path already preserved active-but-unconfirmed PostSL startup, but the parallel overlay-reinit cooldown path still force-cleared `g_PostSLOverlayActive` every frame while `overlayInit=false`. Once the same half-armed startup later re-woke through that branch, `PostSLOverlayRender()` saw a fresh lifecycle edge and re-entered `PostSL REACTIVATED (epoch=2 ...)` before first confirmation.

- **Fix**:
  1. `hook/common/streamline_runtime_policy.h` now adds `ShouldApplyViewportRuntimeUpdateFromSetOptions(...)`.
  2. `hook/apis/streamline_hook.cpp` now uses that helper so intentionally suppressed startup-protected stale `slDLSSGSetOptions(OFF)` churn no longer updates CE's local viewport/runtime state at all. New logs now say `Skipping local runtime-state reduction for suppressed slDLSSGSetOptions(OFF) because Streamline never observed that disable edge ...`.
  3. The same file also now applies the existing `ShouldDropSuppressedOffChurnForStartupProtectedStreamlineComeback(...)` rule to the early `Hooked_slDLSSGSetOptions()` flush path, not just the later `GetState` / periodic flush seams, so stale suppressed OFF handling stays consistent across all replay points.
  4. `hook/apis/dx12_hook.cpp` now preserves half-armed synthetic startup through the overlay-reinit cooldown path too. While `ShouldKeepSyntheticStartupStateUntilConfirmedRender(...)` is still true, the `!g_State.overlayInit` FG-cooldown branch no longer force-clears `g_PostSLOverlayActive` every frame, and its cooldown-complete wake-up now keeps `streamlineStartupHandoffPending` aligned with `ShouldKeepStreamlineStartupHandoffPendingWhileSyntheticStartupHalfArmed(...)` instead of unconditionally clearing it.
  5. `tests/test_streamline_runtime_policy.cpp` now adds `SuppressedSetOptionsOffDoesNotApplyLocalRuntimeUpdate`, and `tests/test_dxgi_shared.cpp` now adds `ReinitCooldownAlsoPreservesHalfArmedSyntheticStartupState`.

- **Why this is generic**: This is not a GTA-only carve-out and not just a fix for one queue address or one epoch counter. The generic invariants are: if CE intentionally swallows a stale startup-protected `slDLSSGSetOptions(OFF)`, CE must not still mutate its own live runtime state as if Streamline had seen that OFF; and once synthetic PostSL startup is already half-armed, any parallel reinit/cooldown bookkeeping path must preserve that same startup until first confirmation instead of restarting it into another reactivation epoch.

  6. `common/crash_handler.cpp` / `.h` now expose `WriteSupplementalCrashDump(...)`, which writes a CE-owned dump into the active session directory using CE's richer dump-attempt policy when an externally handled crash is still giving us a valid process handle.
  7. `hook/main.cpp` now calls that helper immediately after successfully mirroring an intercepted external dump, so the session keeps the original mirrored `external_<original>.dmp` and also gets a second CE-owned `crash_external_<original>.dmp` when the target process is still dumpable.
  8. `tests/test_streamline_runtime_policy.cpp` now adds focused coverage for the new pure-DLSS startup-protected stale-OFF family plus the shared wrapper helpers, and `tests/test_crash_dump_policy.cpp` now covers the new supplemental dump naming helper.

- **Motivation**: Talos `installed/captureengine/logs/20260421_182513_taloscrash_dlssfgtofsrfgcrash` on build `0.1.2510` crashed on `DLSS FG -> FSR FG` even though the older Talos comparison `installed/captureengine/logs/20260421_165756_talosnocrash_multipleswitching` on build `0.1.2507` stayed healthy through multiple mixed switches. No CE crash dump was captured, so the diagnosis had to come from the hook traces alone.

- **Comparison that narrowed the seam**:
  1. Both Talos sessions still reach a healthy initial DLSS epoch first, so the later failure is on the native-FSR takeover/callback family rather than on first DLSS startup.
  2. The crash session still reaches authoritative FFX takeover on `queue=0000028B4A3AC010`, clears stale Streamline/PostSL ownership, publishes native FSR `configure-on`, and installs the callback bridge for `context=0000028B4AD1A640` / `frameID=1908-1909`.
  3. The exact crash boundary is narrow: `DX12: FFX present callback composition contract (frameId=1908 premulAlpha=0)`, `[Overlay] Initializing DX12 backend (device=000002887B503CF0, queue=0000028B4A3AC010, fmt=24)`, `[Overlay] DX12 backend initialized successfully (dpiScale=1.50)`, then no later `DX12: FFX present callback initialized overlay adapter ...` or `rendered overlay on runtime-owned FSR path` line appears.
  4. The healthy comparison reaches the matching callback family and immediately continues into `DX12: FFX present callback initialized overlay adapter for runtime-owned FSR ...` and repeated callback render lines.

- **Root cause refinement**:
  1. The callback-side native-FSR HDR/setup path still depended on probing DXGI output state through raw non-AddRef'd swapchain globals from the callback thread after authoritative FFX takeover.
  2. Those raw pointers are acceptable as weak tracking/diagnostic evidence, but not as an authoritative COM-lifetime source for late callback-thread classification. Runtime-owned callback execution can legitimately outlive the last normal tracked swapchain object.
  3. The crash boundary fits that seam exactly: callback-backend `InitDX12` already succeeds, so the failure is later than basic backend bring-up but earlier than CE's own `initialized overlay adapter` log, which is exactly where callback-side HDR/swapchain probing still ran.

  3. `hook/apis/dx12_hook.h` / `hook/apis/dx12_hook.cpp` now add `DX12_TryCacheRuntimeOwnedCallbackHDRStateFromSwapchain(void* swapChain)`, which snapshots that same trusted HDR/color-space state from the live `ffxConfigure(... swapChain=...)` pointer while the runtime is still handing CE a current swapchain object.
  4. `hook/apis/ffx_hook.cpp` now calls that helper before replacing the runtime callback with CE's bridge, so the later callback thread no longer needs to rediscover HDR through weak global swapchain pointers.
  5. `hook/apis/dx12_hook.cpp` now lets `EnsureOverlayAdapterReadyForFFXPresentCallback(...)` resolve callback-side HDR strictly from cached trusted state and logs `using cached HDR state instead of probing weak swapchain COM state ...` when the callback path needs that fallback.
  6. `tests/test_dxgi_shared.cpp` now adds `DXGISharedTest.RuntimeOwnedCallbackHDRFallbackUsesCachedKnownState` alongside the existing HDR policy tests.

- **Why this is generic**: This is not a Talos-only workaround and not a special case for one queue or one frame id. Any runtime-owned native-FSR callback path can outlive the last normal tracked swapchain object. The generic invariant is: callback threads may consume cached trusted swapchain/HDR facts captured earlier from a live swapchain, but they must not require weak raw COM pointer lifetime for late callback-side classification.
