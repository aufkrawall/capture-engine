### 2026-07-03 - WGC smoothness Fix 4: Bounded phase error via source-rate selection-target clamping

- **Problem:** Bad session had WgcSelBias=7.3ms (vs good 3.7ms). Each frame was selected ~7.3ms older than ideal grid position — a persistent subtle offset through the entire recording, not just during transients.
- **Root cause:** When source delivers below output target (e.g., 105fps source → 120fps output), the CFR selection grid advances 8.33ms per tick but only ~1 new source frame arrives per 9.5ms. The grid outruns the source by ~1.17ms/tick, accumulating bias. Without any bound the bias grows to ~7ms+ before reactive duplicates reduce it.
- **Fix:** After computing `effectiveSelectionTargetQpc`, if low-source mode is active and the target has drifted >1 output interval ahead of the newest buffered frame, clamp it to `newestFrameQpc + targetIntervalTicks`. This keeps the selection target within one interval of the real source content, bounding WgcSelBias to ~8ms max. Does NOT touch the output PTS grid, audio timeline, or content delay reservoir — only the frame selection reference point is adjusted. `wgcBiasClampCount` reports how many clamps fired (available in `[WGC CFR SUMMARY]`). Bias decays when source catches up.
- **Source anchors:** `captureengine/media_main.cpp` (~5902-5914), `llm-wiki/wgc-capture.md`.
- **Validation:** Full build + all 1236 unit tests pass.

### 2026-07-03 - Hardware-cursor research + dup ground-truth 10-bit + fullscreen-game dup priority + R10 misdiagnosis correction

- **Research (user-driven, web-verified):** WGC capture sessions demote the live cursor from the hardware plane to DWM-composed (software) rendering — reported since March 2020 (microsoft/Windows.UI.Composition-Win32-Samples #51 by an OBS dev; #128 shows WGC can even make the cursor INVISIBLE in fullscreen games, explicitly not reproducible with DXGI dup/BitBlt), toggling `IsCursorCaptureEnabled` does not help, and Microsoft closed it without a fix → architectural, NOT a Windows-update regression. OBS Display Capture "Automatic" defaults to DXGI on normal desktops — which is exactly why the user's OBS monitor recording kept the hardware cursor while WGC (OBS and CE alike) lost it.
- **Dup 10-bit ground truth (fixes 20260702_194424):** the old init-time policy gate read `DXGI_OUTDUPL_DESC.ModeDesc.Format` (display-mode format, NOT the delivery — that session's `DuplicateOutput1` succeeded with an FP16/R10-only list while ModeDesc claimed BGRA8) and wrongly fell back to WGC, silently costing the hardware cursor. - **Fullscreen-game dup priority:** new `[General] auto_fullscreen_capture=dxgi_dup|wgc_window` (default dxgi_dup): auto-mode UNHOOKED fullscreen-like game targets (source-PID window, foreground candidate, hook-connected scan) capture the game's monitor via duplication (`primeDxgiDupForWindowMonitor`, policy `ShouldPreferDxgiDuplicationForFullscreenAutoTarget`) with WGC window capture as fallback; windowed targets and configured `wgc_window_detection` matches keep WGC window capture.

- **R10 misdiagnosis corrected:** WGC R10 frame pools fail with `E_INVALIDARG` at the WinRT API level (all buffer counts, any driver — WGC supports only the BGRA8/FP16 family); the "R10+SHARED_NTHANDLE driver quirk" wiki claim was wrong and the 8→3 retry ladder was dead weight → removed (single attempt kept for future Windows).
