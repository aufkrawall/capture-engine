### 2026-04-20 - Keep Streamline Present routing disabled for the full native-FSR runtime-owned ownership window so GTA cannot re-attach SL mid-handoff

- **Motivation**: GTA V Enhanced `installed/captureengine/logs/20260420_121020_gtacrash_dlssfgtofsrfgcrash` on build `0.1.2482` still froze on `DLSS_FG -> FSR_FG` even after the earlier authoritative-FFX queue-ownership fix from `0.1.2472/2473`. But the later mirrored dump `GTA5_Enhanced.exe_2026-04-20_12-12-59.dmp` still lands in GTA's own breakpoint/wait path a few hundred milliseconds later, so a mixed-runtime seam still survived after callback bring-up.

- **Talos comparison that narrowed the seam**:
  1. Talos `installed/captureengine/logs/20260420_120906_talosnocrash_dlssfgtofsrfgnocrash` on the same build also performs `DLSS_FG -> FSR_FG`, reaches native FSR immediately, and keeps rendering normally.
  2. Talos already differs on callback composition provenance: it has a real runtime/game callback (`originalPresent=resolvedPresent=00007FF7414BBDB0`) while GTA stays on the no-runtime-composition fallback path (`originalPresent=resolvedPresent=null`). But GTA now still survives far enough to render multiple callback frames on that fallback path, so missing runtime composition alone no longer explains the freeze.
  3. The decisive new divergence is Present-routing ownership during the runtime-owned FFX window. GTA logs `SL routing DISABLED ...` at authoritative FFX takeover, but later in the same runtime-owned teardown window it logs `SL routing ACTIVE: Present calls will go through oPresent=... SL FG chain will execute` again while native FSR is still only publishing explicit `enabled=0` teardown callbacks on `scQueue=000001D88F1C6A70`. CE only force-disables that routing again once native FSR is already actively rendering callback frames (`DetourPresent: SL routing was active while FSR FG is active — force-disabling ...`). Talos does not show that mid-window Streamline Present-routing re-activation on its FSR-owned path.

- **Root cause refinement**:
  1. `DXGIShared::DetectSLPresentHook()` and the top-level `Present` / `Present1` routing latches were only using `RuntimeModeUsesFSR(g_FGCompat.GetRuntimeMode())` as the suppression signal for Streamline Present routing.
  2. That was too narrow for native-FSR teardown. GTA's trace shows a long explicit `ffxConfigure(frameGenerationEnabled=0)` window where the FFX/native runtime still owns presentation on the runtime-owned swapchain, but the effective runtime label is temporarily `Off` because native FSR has not re-enabled yet.
  3. During that `runtime=Off but still runtime-owned FFX Present path` window, `DetectSLPresentHook()` could see Streamline's E9/FF25 Present hook and re-arm `s_slRoutingActive` even though CE had just disabled Streamline routing at authoritative FFX takeover. Once that mixed routing is live again, GTA later has to force-disable it only after native FSR is already actively rendering callback frames, which means the native-FSR path spent part of its ownership window with Streamline's Present-hook chain spuriously reattached.

- **Fix**:
  1. `hook/apis/dx12_hook.cpp` now exports `HookHasRuntimeOwnedNativeFGPresentPath()`. It returns true while the swapchain is still runtime-owned and either authoritative native FSR is active or CE is still inside the explicit native-FSR OFF teardown window (`g_ExplicitNativeFSROffPendingRuntimeOwnedTeardown`).
  2. `hook/common/dxgi_shared.h` now adds `ShouldKeepSLPresentRoutingDisabledForNativeFG(...)`, making the intended suppression rule explicit and testable: keep Streamline Present routing disabled when either the effective runtime mode already uses FSR or the native/runtime-owned FSR Present path still owns presentation during teardown.
  3. `hook/common/dxgi_shared.cpp` now uses that stronger predicate in all relevant seams: `DetectSLPresentHook()` no longer re-enables Streamline routing during the runtime-owned native-FSR teardown window; the top-level `Present` and `Present1` routing latches now force-disable Streamline routing on that stronger ownership signal too; and the diagnostics now log `runtimeOwnedNativeFG=%d` so future traces show whether CE intentionally kept the Streamline hook chain detached because the native FSR path still owned presentation.
  4. `tests/test_dxgi_shared.cpp` now adds `SLPresentRoutingStaysDisabledAcrossNativeFGTeardownAndActiveOwnership`, and `tests/test_stubs.cpp` now exports the new `HookHasRuntimeOwnedNativeFGPresentPath()` stub for the shared DXGI test binary.

- **Why this is generic**: This is not a GTA-only workaround and not a special case for the `originalPresent=null` callback family. The generic invariant is that once a native/runtime-owned FSR Present path owns the swapchain, Streamline's Present-hook chain must remain detached until that ownership truly ends. A temporary explicit `ffxConfigure(frameGenerationEnabled=0)` edge during runtime-owned teardown is not sufficient evidence that the Present path is back in a safe Streamline/non-FSR topology. Re-attaching Streamline routing in that window creates mixed-runtime Present ownership on a swapchain the native FSR runtime still owns.

### 2026-04-20 - Keep post-FSR DLSS startup-window OFF extension one-shot per churn burst and align planner queue reasoning with safe post-FSR swapchain ownership

- **Motivation**: GTA V Enhanced `installed/captureengine/logs/20260420_110604_gta_weirdfgbehavior` on build `0.1.2477` exposed a later no-crash-but-bad-state seam after the earlier native-FSR callback and explicit post-FSR comeback fixes. The first `FSR_FG -> DLSS_FG` comeback in that same session is structurally healthy: CE preserves the fresh Streamline `scQueue=000001960B1F2680`, reaches `PostSL CONFIRMED rendering via re-entrant Present`, submits two PostSL frames, then the user turns FG back off and non-FG overlay recovery later succeeds. The later `FSR_FG -> DLSS_FG` comeback is different. It never surfaces `OFF->ON via SetOptions`; it only logs `FG state transition OFF->ON via GetState`, but still already has stronger post-FSR recovery proof: preserved runtime-owned `scQueue=000001960AF2EDB0`, `realECL=00007FFE55F39470`, and planner snapshots that repeatedly show `safeBootstrap=1`. Even so, the session remains stuck for tens of seconds in `startupPhase=churnWindow` / `postSLPending=1` / `postSLConfirmed=0` while the log prints thousands of `Streamline Hook: Deferring OFF signal during startup transition window ... — extended startup window` lines. The user-visible symptom matches that state: GTA never really finishes enabling the later DLSS FG comeback correctly, and the subsequent `all FG off` path then has to recover after a failed/unconfirmed DLSS epoch.

- **Talos comparison that narrowed the seam**:
  1. Talos `installed/captureengine/logs/20260420_110500_talosnocrash_noissues` on the same build also performs mixed FSR/DLSS switching and keeps working normally.
  2. Talos still reaches the post-FSR DLSS family with the preserved `scQueue`, ECL-side startup progress, PostSL warm-up, confirmation, and sustained `Post-SL overlay SUBMIT` traffic.
  3. The GTA-only divergence in the new logs is not missing queue ownership proof or missing safe-bootstrap proof; it is that startup-window OFF deferral keeps re-extending its own protection window during the later `GetState`-only comeback instead of converging once per churn burst.

- **Root cause refinement**:
  1. The live runtime fix from the older `0.1.236x`/`0.2468` slices intended startup-window OFF extension to be bounded by a one-shot latch (`g_StartupWindowOffExtensionPending`), not to be level-triggered forever.
  2. Current code drift re-primed that latch on every later steady-state active runtime update in `ApplyCombinedStreamlineRuntimeState(...)` (`else if (signalUpdate.effectiveActive) { g_StartupWindowOffExtensionPending = true; }`).
  3. On the later GTA `GetState`-only post-FSR comeback, that means every active `GetState` plus the mirrored suppressed `SetOptions(OFF)` churn can immediately re-arm the extension latch again after the previous deferred OFF already spent it. The result is exactly what the trace shows: startup remains stuck in `churnWindow`, PostSL never leaves the half-armed startup family, and the session never converges onto the preserved runtime-owned `scQueue` path even though `safeBootstrap=1` is already true.
  4. The same trace also exposed a derived-doc/planner drift. `FG SNAPSHOT` already reported the stronger proof combination (`hadFSR=1`, `safeBootstrap=1`, preserved runtime-owned `scQueue`), but `FG PLAN` still kept selecting `queueRole=wrapperBootstrap reason=wrapper-bootstrap` only because explicit `SetOptions` provenance was absent. That no longer matched the stronger queue-selection story the live runtime intended to follow once startup stops thrashing.

- **Fix**:
  1. `hook/common/streamline_runtime_policy.h` now adds `ShouldPrimeStartupWindowOffExtensionLatch(...)`. The rule is explicit and testable: only a fresh OFF->ON activation edge primes the one-shot OFF-extension latch. Later steady-state active polls do not.
  2. `hook/apis/streamline_hook.cpp` now uses that helper in `ApplyCombinedStreamlineRuntimeState(...)` instead of re-priming the latch on every active update. Deferred OFF can still extend the startup window once for the current churn burst, but once that burst already spent its one extension CE now logs `extension already consumed for current churn burst` and does not silently keep startup alive forever.
  3. `hook/common/fg_session_state.cpp` now aligns planner queue reasoning with the stronger live recovery proof. If a post-FSR DLSS comeback already has `safeBootstrap=1` and a preserved runtime-owned `swapchainQueue`, the planner no longer selects `wrapper-bootstrap` just because explicit `SetOptions(ON)` provenance is absent; it falls through to the safer `swapchain-queue` reasoning instead.
  4. `tests/test_streamline_runtime_policy.cpp` now adds `StartupWindowOffExtensionLatchOnlyPrimesOnFreshActiveEdge`, and `tests/test_fg_session_state.cpp` now adds `PostFSRDLSSPrefersSwapchainQueueOverWrapperBootstrapOnceBootstrapIsSafe`.

- **Why this is generic**: This is not a GTA-only workaround and not a special carve-out for `GetState` comebacks. The generic invariant is that startup-window OFF extension is a bounded stabilization tool, not a perpetual keepalive. Once the current churn burst already spent its one extension, later steady-state active runtime polls must not silently re-prime that latch or CE can strand otherwise safe post-FSR recoveries in permanent startup churn. Separately, when diagnostics/planner state already knows a post-FSR comeback has both a preserved runtime-owned `scQueue` and a safe bootstrap topology, it should not keep labeling that state as `wrapper-bootstrap`; that hides the real stronger topology that live runtime debugging needs to see.

- **Fix**:

  3. `hook/common/dx12_overlay_policy.h` now extends `ShouldHookSwapchainQueueVTableForFrameGenerationRuntime(...)` with an `authoritativeFFXRuntimeQueue` input. FFX-owned native/runtime-owned queues now force `false` there even if stale Streamline authority is also present on that queue.
  4. `hook/apis/dx12_hook.cpp` now logs the mixed-authority override explicitly: `Authoritative FFX ownership overrides stale Streamline runtime queue authority ...` plus `Skipping vtable hook for FFX-owned runtime queue ... despite stale Streamline provenance ...`, so future GTA/Talos traces show when CE intentionally kept a native-FSR queue off the ECL detour path.
  5. `tests/test_dxgi_shared.cpp` now adds focused coverage for the two new invariants: authoritative FFX queue authority stays distinct from Streamline runtime authority, and FFX queue ownership overrides stale Streamline hookability on the same non-origGame queue.

- **Why this is generic**: This is not a GTA-only workaround and not an anti-Streamline special case. The generic invariant is that mixed-runtime create-swapchain evidence may temporarily contain provenance from multiple FG runtimes, but only the runtime that currently owns the queue may decide how timing-sensitive that queue is. Once FFX/native FSR already owns a runtime queue, stale Streamline evidence from the same mixed handoff must not keep that queue on CE's `ExecuteCommandLists` detour path; otherwise CE can reintroduce exactly the kind of timing interference on native FSR queues that the code comments already call out as able to stall `amd_fidelityfx_dx12!ffxQuery`.

Once the explicit post-FSR comeback is already the live effective DLSS signal, a previously buffered startup OFF is stale noise and should be discarded instead of replayed later.
  3. `hook/apis/streamline_hook.cpp` now uses those helpers in all delayed-OFF seams: combined runtime-signal reduction, the `GetState` expiry flush, the inline `SetOptions` expiry flush, and `FlushSuppressedSetOptionsOffIfNeeded()`.   4. `tests/test_streamline_runtime_policy.cpp` now adds focused coverage for: keeping OFF churn deferred while an explicit post-FSR comeback remains half-armed, dropping stale buffered OFF once that comeback is already the active effective signal, and the combined runtime-signal reducer preserving `effectiveActive=true` across the post-expiry half-armed explicit-post-FSR case.

- **Why this is generic**: This is not a GTA-only workaround. The generic invariant is that startup-window OFF churn is only trustworthy as a real inactive edge before a stronger recovery epoch has already taken ownership. Once CE has a newer explicit post-FSR `SetOptions(ON)` comeback and that comeback is still half-armed or already the live effective signal, replaying an older buffered OFF into that same epoch reintroduces a false local `FG OFF` transition and can destroy the recovered queue/bootstrap state that the comeback depends on.
