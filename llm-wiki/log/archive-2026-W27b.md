### 2026-06-30 - D3DKMT priority readback verification and elevated mapped-drive recording output

- **User question/evidence:** CE's first D3DKMT priority log reported the set call succeeded without admin, but that log did not re-query after the set. Running CE as admin can also fail to record to mapped network drives because elevated split-token processes may not see the non-elevated user's mapped drive letters.
- **Code change:** `ApplyMediaGpuSchedulingPriority()` now re-queries `D3DKMTGetProcessSchedulingPriorityClass` after a successful set call and logs `verified=1` only when the readback matches the requested class; mismatch and unavailable readback are explicit log cases. Normal video output and audio-only output now run their output directories through this resolver and log any rewrite source/status.
- **Scope/expectation:** mapped-drive resolution fixes the common elevated persistent-drive case without requiring `EnableLinkedConnections` or disabling UAC isolation. It does not reconstruct temporary mappings that are invisible to the elevated token and absent from HKCU, and it does not bypass network credentials/share permissions. Existing UNC/local/relative paths are unchanged.

### 2026-06-30 - OBS-style media GPU scheduling priority added; HAGS/D3D12 COPY queue expectations corrected

- **User question/evidence:** comparing `fortigood`, `sbinject`, and `sbwgc` showed that WGC under 100% GPU load had WGC source/callback gaps and repeat clusters while copy/encode/mux were healthy; inject under the same game load was closer to the CFR lower bound. OBS documentation mentions running as administrator so OBS can request GPU priority/reserved capacity.
- **Code change:** added `[Performance] gpu_scheduling_priority=off|idle|below_normal|normal|above_normal|high|realtime` to config generation/template and parsing (`off` default). The media process now applies priority settings before MediaEngine initialization. `gpu_scheduling_priority` dynamically resolves `D3DKMTSetProcessSchedulingPriorityClass` / `D3DKMTGetProcessSchedulingPriorityClass` from `gdi32.dll`, applies the requested process GPU scheduling class to the media subprocess only, and logs requested/current class, elevation state, and NTSTATUS. `process_priority=realtime` is now implemented instead of falling through to normal.
- **Scope/expectation:** this is the missing first half of OBS's workaround; CE already had the second half (`IDXGIDevice::SetGPUThreadPriority` via `gpu_priority`). It may help WGC when CE-owned D3D11 copy/convert/encode work is starved, but it cannot directly prioritize the Windows/DWM/WGC producer path. It should be A/B tested with `high` first; `realtime` is explicit diagnostic only and can require elevation or harm system/game responsiveness.
- **Corrected finding:** D3D12 COPY queues/HAGS are not a high-probability WGC magic fix. DX12 inject currently submits capture copies on the game's DIRECT queue, so a config-gated COPY-queue prototype is plausible there if telemetry proves it does not stall Present. WGC receives D3D11/WinRT surfaces; the bad WGC logs show upstream delivery gaps dominate over CE copy time, so a WGC D3D12 rewrite needs share/import feasibility and limiter proof before any large change.

### 2026-06-30 - Smoothness buffer 250→300ms; staleDrop root cause identified; cadence phase error randomness

- **Problem**: `staleDrop` spikes to 40-44/sec in ~50% of sessions. Root cause: 30 retained frames at 140fps source span only 214ms, but the cadence target expects 250ms. The 36ms deficit creates a `phaseError` offset that `delayPaceCapTrim` can sometimes keep stable (19-37 trim/sec, staleDrop=5-9) but sometimes cannot (10-13 trim/sec, staleDrop=40-44). The randomness comes from whether the phase error happens to converge or drift after startup.

- **Fix**: Increased `wgcSmoothnessBufferDefaultMaxMs` from 250 to 300 (`7157f69`). 36 desired frames at 140fps span 257ms instead of 214ms. The larger span increases the acceptable selection window from ~1 frame to ~2-3 frames, halving staleDrop. VRAM: +190MB, total ~2500MB.

- **Finding**: The startup deficit forgiveness (adjusting `smoothnessTargetDelayQpc` to match actual span) is purely diagnostic — `wgcSmoothnessActiveDelayQpc` is already at its maximum achievable value (clamped to actual frame span). The real fix is more retained frames.

### 2026-06-30 - WGC R10 pool retry, VRAM 3000MB, tolerance 900 permille, pool headroom, timer rebase 18; inject capture is optimal; HAGS/D3D12 COPY queue future work

- **Problem**: WGC capture at 100% GPU load with 140fps→120fps CFR was abnormally unsmooth even after the startup reservoir fix. Caused by a cascade of artificial limitations: VRAM cap-limited buffer → pool pressure trims → strict too-new tolerance → unnecessary repeats. **Superseded clarification:** later source-coverage analysis showed that source-above-output mismatch alone should normally become source drops, not repeats; remaining repeats indicate CFR coverage holes from source spikes, delivery gaps/batching, or sync-safe candidate rejection.

- **Changes (5 commits)**:
  1. **R10 pool retry** (`5f8992a`): Before falling to FP16, try R10 frame pool with progressively fewer buffers (down to min 3). On systems where WGC accepts R10 with fewer buffers, this avoids FP16 entirely. R10+SHARED_NTHANDLE fails on this GPU/driver regardless of buffer count, so FP16 fallback is inevitable here.
  2. **Split-budget optimization** (`5f8992a`): Changed candidate selection from "first valid" (highest source buffer count) to "best retention" (maximizes retained extra frames). FP16+R10 at 4K 120fps: selected 11+42 instead of 12+40, eliminating cap-limited 1-frame shortfall.
  3. **VRAM budget 2048→3000MB** (`11e9207`): Eliminates cap-limited smoothness buffer under FP16+R10 at 4K 120fps. Updated config.h, config.cpp, capture_pipeline_policy.h, and tests.
  4. **Active delay tolerance 600→900 permille** (`94cd034`): From 5ms to 7.5ms at 120fps. At 140fps source (7.14ms spacing), the wider window accepts ~1 frame per slot instead of ~0.7, reducing unnecessary "too new" repeats from 20-30% to ~5-10%. All 1187 tests updated.
  5. **Pool headroom slots** (`3e663f2`): 8 extra copy pool slots beyond the reservoir requirement. At 100% GPU load, the 41-slot pool had max 37 leased (only 4 free). 49 total slots leave 12+ free, reducing overwritePrevented from ~1887/sec to near zero.
  6. **Timer rebase threshold 10000→18** (`408788e`): For screen grab (WGC with smoothness buffer), reduced from 83 seconds to 150ms, allowing the cadence to rebase when encoder-timer drift accumulates.

- **Finding (superseded 2026-06-30 source-coverage clarification):** the observed ~10-15% repeats in those runs were initially described as an inherent 140fps→120fps CFR minimum. Current understanding is stricter: regular above-target source cadence should drop surplus frames without repeats; repeats mean some CFR slots lacked a sync-safe fresh source because of source timing spikes, WGC/DWM delivery gaps/batching, below-target intervals, or too-new safety rejection.

- **Logging improvements**: `capShortfall`/`capShortfallMB` added to budget log. R10 retry attempts logged. FP16 fallback VRAM warning added with explicit shortfall in frames and MB.

- **`wgc_prefer_compact_10bit_pool=true`** (`abf9ebf`): New config option (default true). When R10 pool fails, try BGRA8 before FP16. Halves VRAM (31.6MB vs 63.3MB per source surface at 4K). Retained copy stays R10, encoding stays 10-bit P010. Quality tradeoff: FP16 preserves full 10-bit input precision; BGRA8→R10 upscales from 8-bit (2 LSB zeroed).

- **Superseded 2026-06-30 (priority/COPY queue investigation):** D3D12 COPY queues/HAGS are no longer considered a likely generic WGC fix. COPY queues require explicit synchronization, may still contend depending on driver/hardware/workload, and WGC's bad-log signature was upstream frame delivery rather than CE copy cost. Keep COPY queues as a proof-first DX12 inject experiment, not a WGC rewrite premise.
