### 2026-06-03 - v10 hold rejected+insufficient; v11 pins overlay resources resident so the draw never stalls

- **v10 repro** (`installed/captureengine/logs/20260603_151656`): still froze. The log shows RAPID Alt+Tab (focus edges every ~0.5s); the 60-present transition hold EXPIRED mid-thrash (`Resuming … foreground=0`), CE resumed the direct draw, and DRED again showed CE's overlay `DRAWINDEXEDINSTANCED` pure-hung (`pageFaultVA=0`). So the hold both (a) hides the overlay — which the user firmly rejects ("must never disappear, not even temporarily") — and (b) can't reliably cover rapid toggling. v10 is abandoned.
- **Decisive user data**: the BARE app (no injection) NEVER freezes on extreme Alt+Tab spam, and app+RTSS NEVER freezes — only CE freezes. So CE's overlay GPU work is the specific cause; a single render+present per frame survives the mode switch fine.
- **Root-cause reasoning**: the bare app's per-frame GPU work is `ClearRenderTargetView` only — NO input resources, NO PSO. CE's overlay command list binds a PSO and READS input resources (font ByteAddressBuffer + vertex/index UPLOAD buffers). DRED shows a PURE hang on CE's DRAW (not a fault). Under the WDDM residency model, the iflip<->composited mode switch makes DWM allocate large composition surfaces and can trim the game process's residency budget; if CE's overlay resources get evicted, the DRAW stalls paging them back in → TDR. The app's input-less clears never stall. RTSS (a mature overlay) survives, consistent with it keeping its resources resident.
- **Fix (v11)**: pin ALL CE overlay GPU resources at `D3D12_RESIDENCY_PRIORITY_MAXIMUM` via `ID3D12Device1::SetResidencyPriority` (`TrySetMaxResidencyPriority` in `dx12_hook.cpp`): the DescFree backend's font ByteAddressBuffer, the vertex/index UPLOAD pools (+ on resize), the two PSOs, the command allocators + fence (`InitOverlaySync`), and the offscreen RT (`EnsureOffscreenRT`). With resources pinned, CE renders the overlay EVERY frame — focused, unfocused-visible, AND through the transition — and never hides (v10's transition hold is removed; the transition window is now telemetry-only and widens the DRED dump window). Marker `DX12 focus-loss sync policy=v11 max-residency-no-hold`; per-transition log `Focus-change mode switch active — overlay STILL RENDERING (residency-pinned, not held)`. The v8 not-presentable hold (occluded/iconic/zero) still applies.
- **Validation**: build x64+x86, 878 tests pass; `HookDllContainsLazyExecRegressionStrings` pins the v11 markers. DRED stays armed.
- **OPEN / stale-risk**: This is a strong hypothesis (it explains the bare-app-vs-CE contradiction) but UNVERIFIED — UPLOAD-heap resources are in system memory, so whether the WDDM trim actually evicts them on this GPU is unconfirmed (ample VRAM may mean no eviction at all, in which case residency is not the cause and the hang is e.g. PSO/pipeline-revalidation or RT-bind related). If v11 still hangs, the DRED breadcrumb + the fact that the bare app's clears survive narrows it to the PSO/full-pipeline-draw vs fixed-function-clear difference; next step is the D3D12 debug layer (available: `d3d12SDKLayers.dll` present) gated by an env flag to capture the exact validation/hazard, or a PIX capture of RTSS's command stream. The predicate `ShouldHoldD3D12OverlayBackbufferWorkDuringFocusTransition` is now used as telemetry, not a hold (name is legacy).
- **Source anchors**: `hook/apis/dx12_hook.cpp` (`TrySetMaxResidencyPriority` + calls in DescFree font/buffers/PSOs, `InitOverlaySync`, `EnsureOffscreenRT`; v11 hold removal in `ProcessFrame`; marker), `tests/test_crash_handler.cpp`, `installed/captureengine/logs/20260603_151656`.

The v8 not-presentable hold (occluded/iconic/zero-size) still applies first. FG / runtime-owned / dedicated-queue / Steam-deferred routes are excluded.
