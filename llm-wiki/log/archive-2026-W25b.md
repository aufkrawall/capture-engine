### 2026-06-17 - Per-device audio capture-latency model: mic-domain split, delay-only (drop GetStreamLatency advance), render→loopback auto-detect

- **Problem (regression):** session `installed/captureengine/logs/20260617_010909` (Fortnite, WGC) had game audio ~46 ms late. Latency was modeled PER-SOURCE: the user set `[Audio] capture_latency_ms=46` but `[General] audio_capture_latency_ms=0`, so the system loopback got 46 while every `[AppAudio.N]` process-loopback (the game) inherited `[General]`=0. The per-source A/V equalization then DELAYED the game's app-loopback by `max−0=46` ms, even though it shares the SAME render endpoint as the system loopback (same real latency). Net: game audio left ~46 ms late.
- **Root cause:** latency is a per-DEVICE-DOMAIN property, not per-source. Domain 1 = default render endpoint (system loopback + ALL app process-loopback) → ONE value. Domain 2 = each mic/input → its own. The config modeled it per-source and the mic also inherited the loopback fallback.
- **Part A — device-domain config (`common/config.{h,cpp}`):** mics no longer inherit `audioCaptureLatencyMs`; they fall back to new `[General] mic_capture_latency_ms` (default 0) or a per-mic `capture_latency_ms`. System `[Audio]`/`[Audio.N]` and all `[AppAudio.N]` still inherit the one render-endpoint value. Regression tests `ConfigTest.CaptureLatencyIsPerDeviceDomain` / `MicLatencyOverrideAndFallback`.
- **Part C — delay-only (`mediaengine/audio_capture.cpp`, `app_audio_capture.cpp`):** stopped advancing live audio by `GetStreamLatency` in `ApplyCaptureLatencyCompensation` at the packet-placement sites (packets now placed at the raw / period-center QPC). Advancing live audio never worked (the earlier samples do not exist; the CFR pipeline pads the deficit and the encoded cursor re-pins → absorbed) and double-counts with the video delay on devices that report a nonzero `GetStreamLatency`. ALL latency now flows through the video content delay + equalization (delay-only). `streamLatency` is kept as telemetry; `[AudioCapture]/[AppAudioCapture] Started` logs say "latency routed via video content delay, not audio advance". AVR unaffected (`GetStreamLatency`=0); needs validation on a device that reports it.
- **Part B — render→loopback auto-detect (`mediaengine/audio_latency_probe.{h,cpp}`):** the "no hardcoded value, works automatically on any system" piece. On a cache miss, render a brief near-inaudible Hann-windowed marker (≈ near-Nyquist/ultrasonic, low amplitude) to the default render endpoint and detect its center in a LOOPBACK capture of the same endpoint (loopback taps the DIGITAL render mix pre-DAC, so the marker is captured perfectly even if ultrasonic). latency = loopback marker-CENTER QPC − render presentation QPC of the marker center (aligning Hann CENTERS via `IAudioClock` cancels the envelope; a leading-edge detector would inject a systematic bias). **Robustness for fully-automatic trust:** takes `kProbeShots=5` independent shots and aggregates with `MedianWithConsistency` (need ≥3 within 8 ms) so a single noisy reading cannot over/under-correct; no consensus → ok=false. Superseded on 2026-06-18: the endpoint value is now process-memory only, so a fresh CE process may re-probe instead of using the old `audio_latency_cache.ini` disk file. Fail-safe: any error / implausible (`<0` or `>2000 ms`) / no consensus → no correction (NOT a guessed value). Pure DSP/cache/aggregation logic is header-only and unit-tested (`tests/test_audio_latency_probe.cpp`: marker synthesis, narrowband Goertzel center detection with a sustained-run discriminator that rejects noise/silence, end-to-end latency recovery, memory cache lookup/upsert, median/consistency).
- **Integration:** new mediaengine export `MediaEngine_MeasureRenderEndpointLatency` (+ loader plumbing). `captureengine/media_main.cpp` measures ONCE (in `ensureMediaEngineReady`, before Init, only when not recording) and re-applies the cached value to render-domain sources on every config (re)load (`ApplyAutoDetectedRenderLatencyToConfig`) so BOTH the encoder thread (video content delay) and the media engine (equalization) read the resolved value from the same config. `[General] audio_latency_autodetect` (default true) opts out; a manual `audio_capture_latency_ms > 0` is an OPTIONAL override that disables measurement. The A/V harness writes `audio_latency_autodetect=false` so its explicit latency is authoritative.
- **Default config is fully automatic — no hand-set values.** `installed/captureengine/config.ini` ships `[General] audio_capture_latency_ms=0` and `[Audio] capture_latency_ms=0` (auto). If the probe succeeds it applies the measured value uniformly to system + all app sources; if it can't get a consensus it applies nothing → all render sources 0 → equalization no-op → graceful degradation to the pre-existing minor "audio slightly late" baseline, NEVER the per-source regression and NEVER a guessed number. (Do NOT reintroduce a hardcoded `46`; an earlier draft did and was reverted — it disabled the probe and defeated the automatic goal.)
- **Detection design notes:** Goertzel window ≈ 5 ms (`sampleRate/200`) for narrowband rejection of loud out-of-band audio; confidence = peak ≥ median × `peakOverFloorMin` AND a contiguous run of ≥4 windows above half-peak (a real burst is sustained; a noise spike is isolated).

If the probe value is wrong vs the gate, FIX the measurement (IAudioClock render-center vs loopback-center mapping) — do not hardcode.
