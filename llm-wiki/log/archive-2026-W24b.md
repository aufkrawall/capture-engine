### 2026-06-11 - FIXED: dx11_test animated rectangle missing under inject/overlay

- **Symptom (user log `installed/captureengine/logs/20260611_160022`)**: with CaptureEngine inject + DX11 overlay, `dx11_test.exe` rendered the background color and CE overlay but not the app's animated rectangle. Without inject it rendered normally; other API test apps were not affected. No `.dmp` files were present. Logs showed the wrapper-created immediate context at `version=4`, CE overlay initialization/draws, and app shader metadata, but the app's rectangle is not a shader draw: `testapp/dx11_test.cpp` uses `ID3D11DeviceContext1::ClearView` on a sub-rect after full-screen clears.

The wrapper then advertised `ID3D11DeviceContext1` based on `m_Version >= 1`, so `g_Context.As(&g_Context1)` succeeded in the test app, but wrapper `ClearView()` had no real Context1 pointer and silently did nothing. Result: the background clears ran, the rectangle sub-rect clear disappeared, and CE overlay still drew on top.
- **Fix**: cache Context1/2/3/4 independently in `PromoteInterfaces()`, gate wrapper `QueryInterface(ID3D11DeviceContextN)` on the matching cached real pointer instead of only the highest version, and add a rate-limited `ClearView requested without real Context1` diagnostic for any impossible future no-forward case. This is a generic D3D11 wrapper correctness fix, not a test-app special case.
- **Regression/validation**: new source invariant test `D3D11ContextWrapperSourceTest.PromotesInheritedContextInterfacesIndependently`. `python build.py --skip-updates` passed (build `0.1.3856`); focused no-build test passed 1/1; full no-build unit suite passed 939/939.

### 2026-06-09 - FIXED: dx12_fg_switch_test device-hung (TDR) after suspending DLSS FG under vsync

- **SUPERSEDED by the 2026-06-10 entry above**: the sync-interval root-cause claim was confounded — that build also set Reflex `eOff` at the suspend edge, which is the actual wedge trigger (Reflex must stay on while the DLSS-G proxy presents). The sync-0-for-DLSS-mode policy itself is kept. The A/B in this entry was additionally invalidated by the stress-timer harness bug (suspend fired in the same frame token as the enable).
- **Symptom**: app froze a few seconds after the user manually suspended DLSS FG. Manual freeze dump + the app's own log showed `[FG-DIAG] Present ... mode=DLSS FG sync=1 ... hr=0x887a0005` (`DXGI_ERROR_DEVICE_REMOVED`) and Streamline `PFunPresentBefore failed ... GPU device instance was halted` (device HUNG / TDR), plus `getAllocator: Couldn't reset the allocator pacer ... m_fenceValueAfterLastSwitch=<suspend fence>`. The first dump (caught pre-TDR) showed the main thread spinning in `WaitForFenceValue` with the device still alive.
- **Root cause**: the Streamline/DLSS-G proxy swapchain must be presented uncapped (`SyncInterval=0`). Suspending DLSS FG only calls `slDLSSGSetOptions(eOff)`; it does NOT recreate a native swapchain, so the proxy stays in place. `ResolvePresentSyncInterval()` returned uncapped only for *active* DLSS (`g_DlssEnabled && !g_DlssSuspended`) and fell through to the app-configured vsync for the suspended path. With vsync on (config `vsync=1` and/or driver-forced vsync), suspended DLSS presented the proxy at `SyncInterval=1`, which stalls Streamline's present-pacer (stuck on the suspend's fence) and hangs the GPU device after a few hundred suspended frames.
- **Fix**: `ResolvePresentSyncInterval()` now returns `0` for the entire DLSS mode (active AND suspended) — `if (g_CurrentMode == FGMode::DLSS) return 0;`. Driver-forced vsync (NVCP) still paces the output, so the user's vsync is honored; this is how real DLSS-G games behave (request uncapped, let Reflex/driver pace). Native/FSR/OFF are real (non-proxy) swapchains and still honor app vsync.
- **Rejected hypothesis (important)**: an earlier guess that skipping `slReflexSleep` while suspended caused a PCL-pipeline stall was WRONG — un-gating it did NOT fix the freeze (the user reproduced it on that build). `slReflexSleep` is now called every frame anyway (the documented Streamline contract; harmless and correct), and Reflex *mode* is still set `eOff` when suspended (the "no Reflex cap when suspended" intent), but neither is the fix. The fix is purely the present sync interval.
- **A/B proof** (same harness: config `vsync=1`, new `--dlss-suspend-stress` suspend-and-hold, `--auto-return-fsr 9999`, 25 s): OLD suspended=`sync=1` → 619 frames, 180 pacing spikes, 2980 ms max stall (pathological; TDR is its non-deterministic worst case). FIX DLSS=`sync=0` → 6861 frames, 4 spikes, clean exit, zero `0x887a0005`. ~11x throughput, ~45x fewer spikes.
- **Why the first soak missed it**: a suspend/resume *cycle* resets Streamline's present-pacer on every switch, so the failure only appears when the app HOLDS the suspended state. Repro requires suspend-and-hold, not cycling. Also requires vsync requested (the default `vsync=0` config never hit it).
- **New regression/diagnostic infrastructure**: `--dlss-suspend-stress` / `[Stress] dlss_suspend_resume` (+ `--dlss-suspend-interval`) suspends DLSS FG once after the interval and HOLDS it (one-shot), reproducing this class of bug without manual keys (off by default). `WaitForFenceValue` now re-logs a stalled-fence warning periodically (every ~1 s, bounded) including `GetDeviceRemovedReason()`, mode, and suspend state — so a future stall is characterized as TDR vs live-device deadlock directly from the log.

- **Why this tests the leading theory**: if the iflip<->composited switch makes DWM grab VRAM, the recorder will show the local Budget dropping below CurrentUsage (OVER-BUDGET) right as the gap spikes → confirms residency eviction is what makes the app's own `ExecuteCommandLists` stall in the kernel GPU-VA re-residency map. If budget/usage stay flat through the stall → it's NOT residency (points to VA fragmentation or a dxgkrnl device-lock wait, and the next step would be the real GPUView capture).
- **Deliberately NON-perturbing**: does NOT arm DRED forced auto-breadcrumbs or GPU-based validation (both proven earlier to CAUSE this freeze). Residency queries + a ring buffer are cheap; zero work when the option is off.
- **How to run**: set `dx12_focus_analysis=true` in `installed/captureengine/config.ini`, restart the controller, launch 32-bit `dx12_test`, Alt+Tab to repro, read `DX12 ANALYSIS:` lines in `hook_debug.log`. Compare CE-overlay-on vs `observer_only=true` to isolate CE's residency contribution. (The separate `ce_dx12_trace` flag still adds the D3D12 call trace.)
- **Validation**: build clean x64+x86; 920/920 tests (new `ConfigTest.ParseDx12FocusAnalysisOption`).
